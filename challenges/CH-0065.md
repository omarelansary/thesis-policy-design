# Title: Topic A omits three stored vendor passages that state the append mechanism, and the gap sentence "no number ... in tokens" is false for tokens

**Grade: SERIOUS (the PARTLY verdict survives, but the stated gap is mis-located, and pilot 1 needs the documented exceptions).**

**Objection.**
1. **Omitted vendor texts already in the workspace.** (i) EXT-0059 (r3-anthropic-midconv): with the inline-tools beta a `tool_addition` block "can define a tool by value ... by appending a role: 'system' message. The tools array and every earlier message stay exactly as sent, so the prompt cache still hits and only the appended message is processed as new input." (ii) EXT-0066 (same source): a documented exception, "A conversation whose tools array has no non-deferred tool is accepted, but the first tool it defines by value changes the start of the rendered prompt, which costs one full cache miss on that request" and "A tool search tool counts as non-deferred." (iii) EXT-0010 (OpenAI tool search): "tool search is designed to preserve the model's cache. When new tools are discovered by the model, they are injected at the end of the context window." `05` and SUM-0005 cite only the Anthropic caching page (EXT-0093/0096) and EXT-0074. So the vendor mechanism is documented for **two providers, in more specific terms than `05` states**, including where it fails. What is absent is a third-party measurement, not a mechanism. `05`'s gap column ("No number for the extra cost ...") is right about numbers but its Known column understates what vendors say, and the web article's and Slite's "mutate the tool list mid-conversation -> blow away the cache" (SL:61-62) describes the pattern the vendor mechanisms were built to avoid, which should be said.
2. **A token figure exists.** `05` says no number "in tokens or dollars, for any provider" for appended definitions. Anthropic's blog text (EXT-0074 lines 69-71) gives "Only the Tool Search Tool loaded upfront (~500 tokens); Tools discovered on-demand as needed (3-5 relevant tools, ~3K tokens)". It is a vendor illustration of definition size, not a cache or bill number, so the gap is in cost/cache effects, not in token size. Tighten the sentence.
3. The 41-80% headline: Table 1 is "best-performing cache mode", but Table 2 shows GPT-5.2 System Prompt 81.4% > the 79.6% listed, and GPT-4o Full Context 47.8% > 45.9% (EXT-0104 lines 37-56 / EXT-0103 lines 121-126); the full mode-by-model range is 27.8% to 81.4% cost saving, with TTFT regressions (GPT-4o full context -8.8%, Gemini excluding tool results -2.9%) and the abstract's "13-31%" TTFT versus the paper's Section 4.1 "6% to 31%" (EXT-0103 lines 160-162). Minor, but `05` quotes the abstract range as the study's result.
4. Provider heterogeneity matters for the gap: Gemini 28-41% vs GPT-5.2 79-81% (EXT-0103 lines 171-173). A one-provider check does not carry to the others.

**Evidence.** EXT-0059 line 23; EXT-0066 lines 37-41; EXT-0010 line 33; EXT-0074 lines 69-71; EXT-0103/0104 as cited. I read each; I did not read the rest of `r3-anthropic-midconv` (753 lines) and could not check whether EXT-0059 is a lead-picked passage (its note says "lead-run AUTH-005 pivotal passage").

**What would resolve it.** Add the three passages to `05` Known column; rephrase the gap as "no independent measurement of billed cost or cache fields for appended definitions on any provider; the documented exceptions are untested"; correct the 41-80% presentation.
