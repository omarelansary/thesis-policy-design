# Title: P1's construct omits that the seed hit rate h is set by the history generator, and its requirements omit the tool-call record the seed rule needs

**Objection.**
1. *h is manufactured by the data.* P1 reports "the effect of seeding ... with the seed hit rate h" and `05` compares h with h* from D-02. h is the share of the seed set that later sessions call. In every candidate the history is human role-played (Momento), LLM-generated (ATRBench, MPT, VitaBench 2.0, DolphinBench) or composed from separate corpora (MPT: "users are composed from existing corpora", SUM-0072 C6). h is then a parameter of the generator, not an estimate for any deployment. ATRBench treats recurrence of a gold-consistent choice in the learning sessions as a *defect* (preference leakage; 19/100 rules fail it in the human audit, Table 9, `c03` L1210-1216), and the recurrence there concerns preference choices, not tool names (SUM-0073 C14). For P1 the same recurrence of tool use is the thing being measured, so a benchmark that audits it away and one that builds it in measure different things. I2 item 7 found no candidate with more than about 100 tools in which later sessions need earlier tools. H1 says "recurrence measured, not assumed", which reports the generator's recurrence but does not make it a property of real use. The register's closing rule ("a synthetic-only result is not reported as real-world evidence") is right but P1's *claim form* (a point value of h against h*) cannot be validated by any benchmark found.
2. *The seed rule needs tool-call records.* V5-R13 (rule-based tool record) derives seeds from what the user's earlier sessions called. ATRBench's memory is a frozen transcript snapshot (500 characters per turn) that "carries preferences, not tool names" (I2 item 3); Momento sessions hold messages, summaries and extracted facts, not necessarily call records; only MPT stores `api_call` fields (I2 item 4) and it has 13 functions. H1 should require that history contains executable tool-call records with names and arguments, or state that V5 must add them (a modification, s1.3).
3. *Route compatibility is the bottleneck and is not a card field.* ATRBench raises for model ids outside an eight-model map and calls the Responses API, not Chat Completions; its user simulator and classifier are GPT and its router is Gemini (I2 item 3; SUM-0073 C15 needs OPENAI_API_KEY and GEMINI_API_KEY outside oracle runs). The route serves open-weight models through `/v1/`. `05` names ATRBench the closest stored design; the card (T/D/E/S columns) does not show that it needs a provider-layer change and a replaced simulator.
4. *Effective sample = users.* Sessions are not independent within a user (R5 cites clustering of up to 3X for QA evals). ATRBench: 20 personas; VitaBench 2.0: 56 users; Momento: 161 tasks, one per user in the 16-row sample I2 read. The card lists 568 and 284 sessions, 771 subtasks and 6,961 sessions as if they were n.

**Evidence.** `17` s4 L84; `05` s2 P1; SUM-0072 C6; SUM-0073 C14, C15; inspector I2 items 1-4, 7; `17` s3 R5; SUM-0066 M21.
[F] the cited statements. [I] that h is generator-determined; for ATRBench I did not read the generator. [U] whether any benchmark's history includes call records beyond MPT.

**What would resolve it.** (a) Treat h as a swept parameter and report the break-even h* as a function of the bill terms, so the result is conditional on recurrence and says so. (b) Add to P1 H1: history contains named tool-call records, or V5 adds them with a stated method. (c) Add a "route fit" field (closed-model dependencies, endpoint type, code change) to every card. (d) Report clusters (users) beside sessions in every multi-session card.
