# Title: D-01 prices every discovery as an extra request with a history re-read, which is not how the adopted vendor search works, and biases the regime boundary against deferral

**Objection.** `regime_bill.py:12-13` and `:26-30` assume each discovery is "one extra request that re-reads the cached prefix and H = 5,000 history tokens". For the Anthropic tool search that V5 adopts, the search is a server tool: the assistant response contains `server_tool_use`, the search result, and the model's own `tool_use` of the discovered tool in one response; "The search runs on Anthropic's servers" and the API expands the `tool_reference` blocks. DPR-0006:19 itself says a server-tool loop is "billed within that request". If no extra request is made, the per-discovery cost is the search output (q x o) plus the appended definitions, not H*r plus a prefix re-read. [O, hand arithmetic] At d = 250, r = 0.1, T = 10, break-even n* becomes 11 / about 19 / 45 for D = 1 / 3 / 10 instead of the printed 12 / 22 / 57; at T = 3, D = 10 it becomes 56 instead of 74. The headline "from about 10 to 75 tools" is therefore biased high by up to about a quarter at large D. Whether server-side iterations bill a prefix re-read is not shown in the pages read [U], and for OpenAI tool search and client-side search an extra request is right. The model needs both branches and says which provider each applies to.

**Evidence.** `design/package-v5/calc/regime_bill.py:12-13, :26-30`; `design/package-v5/calc/regime_bill.stdout.txt:118-127`; `L/v5-anthropic-tool-search-20261022.md:601-652, :849`; `design/proposals/DPR-0006.md:19`. Hand arithmetic only; no code was run.

**What would resolve it.** Add a switch for in-response versus separate-request discovery; read the usage record of one search call (P0 or P5) to see whether input tokens are re-billed per iteration; print n* for both and state which branch the policy's provider uses.
