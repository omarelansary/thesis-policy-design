# Title: The memory studies are read as supporting "tool memory only"; Apple's own result points at specification memory, and neither Apple nor MemToolAgent is shown to beat full history on completion

**Grade: SERIOUS (05 section 2.2 supports a student choice with evidence that does not bear on it, and arguably favours the supervisor's other reading).**

**Objection.**
1. `05` section 1 row C: "Direction of two studies: abstracted or selective memory beats archiving full history." and section 2.2: the choice of "tool-memory only, not conversation memory" is "consistent with" them. Apple: selective memory completed 12/12, full history 8/12, and the paper says they are "indistinguishable on completion (p = 0.125) and separate on price" (arXiv 2607.09493 text lines 41-43); the enterprise set 23/24 vs 19/24 vs 17/24, "no pairwise difference reaches significance" (lines 56-59). So against full history the supported claim is **cost** (3.9K vs 7.7K input tokens, abstract lines 31-35), not success.
2. What was persisted in Apple's winning condition is four categories, and the only failure mode of the no-memory arm was a **formatting specification** (lines 28-31, 43-46: "a formatting specification is established once and then withheld"; "Every no-memory failure is a specification failure and nothing else"). That is task/contextual memory (the supervisor's M-b in `04` section 4), not tool memory; tool configuration is one of four bundled categories with no leave-one-out ablation (the authors list this absence, steward AP2:1052-1073). So Apple, if anything, supports memory of specifications, and is silent on tool-only memory. The 04 section 4 recommendation "adopt M-a ... treat M-b as a common term" is not helped by it.
3. PREFINE stores latent user preferences used to fill argument values (steward PF:25-31); it supports "abstract rather than archive", which is not tool memory either. SUM-0005 rates it NOT RELEVANT (C1 item 5), but `05` section 2.2 then counts it as one of "the two studies".
4. MemToolAgent is not cross-session in the sense of the thread's question: the memory is seeded from the same benchmark (one query per template, 10 queries per template, "This setup is used to show the advantages of using the memory", MTA:397-405), single run (MTA:525-526), and the authors credit memory partly with showing "the tool calling format" (MTA:557-560). `04` section 4 and `05` list it among studies that "persist ... past tool executions"; fine, but the 57.56 -> 85.06 (Table 1, MTA:447-483) is a by-construction overlap number and should not be read as evidence about tool memory in the sense of rediscovery cost.

**Evidence.** `evidence/literature-20261019/arxiv-2607.09493.txt` lines 28-61, 86-97; `arxiv-2606.07909.txt` lines 397-407, 441-488, 525-526, 550-564. Numbers verified. Not verified: PREFINE table values; Apple's appendix.

**What would resolve it.** Delete or reverse section 2.2 of `05`: say "no stored study isolates tool-only memory; the one with a clear winner (Apple) won through a specification". Keep the sentence on token cost (selective 3.9K vs 7.7K, one run per cell, authors' tasks).
