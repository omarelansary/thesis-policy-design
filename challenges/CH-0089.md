# Title: The proof-of-concept items are called "in dependency order" but P1 precedes what it depends on, V5-R09 omits P5, and two items sit near REQ-U21-03

**Objection.** (a) `05` section 1 is headed "in dependency order", yet P1 (memory-informed offering) runs before P3 (do models search uninstructed) and P5 (does D-01's bill hold, including whether deferred definitions stay out of the carried prefix, CH-0079). P1's K1 arm and h* both assume that models search and that deferral costs what D-01 says; if P3 fails, K1's "discoveries" are failures and h* is not the right threshold. (b) V5-R09 (`04` section 6) gives the order: cache fields, memory hit rate, offering accuracy, uninstructed recovery. P5 is absent from that order and last in `05`, although it checks the arithmetic that every regime statement and h* rest on and costs "a few requests". (c) REQ-U21-03 says not to re-test the well tested. P5 re-reads list-price arithmetic from usage records (cheap and defensible, but then it is part of P0, not a separate item at the end); P4 re-tests a published masking result on one provider, justified only if H stays in the default, which CH-0082 questions; P3's outcome is model-specific (the university API offers several models) and cannot establish that deferral "can be the default beyond R-small" for models not run. (d) `05` section 3 puts the decision on whether the staged form is satisfied (Q-J31) after the loop is designed; the loop's value depends on that answer.

**Evidence.** `05-poc-loop-and-e2e.md` section 1 (header, rows P1, P3, P4, P5), "Loop rule", section 3 Q-J31; `04-design.md` section 6 V5-R09; `requirements/REGISTER.md` REQ-U21-03, REQ-U21-06; `03-reuse-map.md:75`.

**What would resolve it.** Reorder as P0 (fields, discount, one search request read, a priced check of the arithmetic, i.e. merge P5 into it), then P3, then P1 and P2; add P5/P0 to V5-R09; say which items are dropped if H leaves the default; state per item which models it was run on and that conclusions hold for those only.
