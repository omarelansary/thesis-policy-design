# Title: Four hard requirements are either restrictions without a basis, properties of V5's own harness rather than of a candidate, or an undefined condition

**Objection.** s4 says a candidate failing a hard requirement "is rejected for that item". Requirements that reject (or appear to reject) candidates must be necessary safeguards. These are not, as written.
1. **P3 H1: "a gold set of needed tools per task, allowing equivalent alternatives (Tool-DE: one gold per query under-credits)".** The basis is ToolEX on the Tool-DE benchmark, a retrieval evaluation; s6 itself records it as "C (by extension only)" and SUM-0075 D12 says Tool-DE's independence from its builders is not shown and that the equivalents are an automatic annotation. P3 does not score retrieval ranking; it counts searches, correct calls, wrong-tool calls and answers without a tool per cell (`05`). "Wrong tool" needs a gold set, but the oracle and wrong-tool-visible cells control for equivalence by construction (the cell designer knows which tool is the target). Making equivalence a hard requirement rejects nearly every candidate on a point established only by extension from retrieval.
2. **P3 H3: "a chosen tool can be deferred or withheld without editing the tools array".** This is V5-R02 (never change the tools array in a session; supported on two models by `10` s7). It is a rule of V5's harness M0, which s4 says every option needs; every candidate satisfies it once M0 builds the request. As a per-candidate requirement it does not discriminate, and it suggests BFCL fails it (BFCL's FC mode extends the tool list at a later turn; inspector I2 item 5) when what fails is only the unmodified BFCL loop, which M0 replaces anyway.
3. **P1 H5: "a check that later tasks need the history (DolphinBench's with-and-without test)".** P1 asks whether seeding the *tools* used before changes the bill; that needs the same tools to recur (H1), not that the *task information* be unavailable without history. A task whose facts are in the prompt but whose tool needs recur is valid for P1 and fails H5; a task that needs remembered facts but not recurring tools passes H5 and is useless for P1. V5 can run its own with-and-without-seeding arm, which is the P1 contrast. H5 conflates the memory-benchmark construct with the tool-seeding construct. (The supervisor's scope: "memory in service of tool calls", per STATE.)
4. **P5 H4: "licence allows use".** Never defined. P5 reads definitions to count tokens; the uses that matter are read, run locally, publish aggregate numbers, and redistribute a subset, and the answer differs (no licence file means no grant to redistribute, not that reading and reporting aggregates are barred). The cards mark "no licence file" for Toolathlon, TheMCPCompany, ETAPP and "no release" for LiveMCP-101. Without a definition, H4 will reject by accident. Also H4 for P1 ("no simulator or judge that the route cannot serve, or one replaceable with re-validation") is non-discriminating for the same reason as point 2, because every closed-model simulator is replaceable.

**Evidence.** `17` s4 L82-84; s6 L147; SUM-0075 D12; `05` s2; `10` s7 L75-103; inspector I2 items 3, 5; SUM-0074 C37; STATE ("memory in service of tool calls").
[F] the quoted text. [I] that points 2 and 3 are conceptual, not empirical. [U] licence consequences (I give no legal reading).

**What would resolve it.** Move P3 H1 to a scored property (and keep the oracle cell as the control); move P3 H3 into the description of M0; reword P1 H5 as "recurrence of tool use across sessions is measured" (already H1) plus a V5-side with-and-without-seeding arm; define H4 by the uses the thesis needs, as a question to the human if necessary.
