# Title: Every session in D-01 is priced cold, so R-return is not a separate regime, and a shared prefix (V5-R06) contradicts the per-return write

**Objection.** `expose_all` and `deferral` charge W on the first request of every session; the tables headed "per warm session" are cold-start tables. The block "extra cost per return = P*(w - r)" (`regime_bill.py:48-52`) is the cold-minus-warm difference and must not be added to those tables (DPR-0006:44: "already counted in W and R, so it must not be added again"). `04` section 2 lists R-return as a fourth regime in which expose-all "pays P_all(w - r) per return (115,000 ...)", but it names no winner different from the table. More important, V5-R06 (and the M3 placement) is justified by users sharing one cached prefix; on a shared prefix, other users' requests inside the lifetime keep it warm, and a given user's gap is irrelevant. DPR-0006:44 says shared caches make sessions not independent. The cold price per return therefore holds only for a low-traffic deployment; the real variable is the request rate per prefix, which D-01 never uses. Also the K0 row of `04` section 4 ("pays the full prefix on every return") and DPR-0008 section 5 item 4 inherit this.

**Evidence.** `calc/regime_bill.py:21-24, :48-52`; `04-design.md` section 2 (R-return row), section 3 (S2/M3), V5-R06; `design/proposals/DPR-0006.md:44`; `calc/regime_bill.stdout.txt:111-116` (115,000 = 100,000 x 1.15, reproduces).

**What would resolve it.** Define the traffic assumption (requests per prefix per lifetime); price expose-all both ways (warm shared prefix: first request at r; cold: at W); restate R-return as a condition on that rate and the gap, and show whether memory's "cold prefix" benefit survives on a shared prefix.
