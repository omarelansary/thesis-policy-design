# Title: node D4 is not statistically coherent as written (multiplicity, selection bias, ties, confirmation, reuse of dev data, OUT2 reachability)

**Grade: SERIOUS.**

**Objection.** (design/package-v3/02-supervisor-decision-graph.md node D4 and section 6.)
1. **Multiplicity and adversarial selection.** D4 tests feasibility (lower confidence bound of the success difference to the reference not below `-delta`) for every arm in D3, then picks the lowest estimated token cost among the arms that pass. Cheaper arms are, on average, the more restrictive and so the more likely truly inferior; selecting the cheapest passing arm therefore selects preferentially among the false passes. With `K` arms each tested at level `alpha`, the chance that at least one truly inferior arm passes grows towards `K alpha` and is concentrated in the cheap ones. D3 lists at least six arm types, each "with and without the core", and D2 adds a core size from a dev sweep, so `K` is in the tens. No multiplicity control or step-down is specified.
2. **Winner's curse on tokens.** The chosen arm has the lowest estimated tokens among those passing, so its estimate is biased downward. Held-out confirmation is mentioned but its rule is not: sample size, the quantity confirmed (noninferiority only, or also the token saving), the action on failure (next-cheapest feasible arm? a new tournament?). Each re-draw is another forking path.
3. **Ties are measure-zero.** "Ties: fewer components" never fires with continuous token estimates. A token-equivalence margin (below which two arms count as tied) is needed and absent; so is a definition of "component" (is a core a component? a selector's index? a scope statement?).
4. **Dev data reused for four jobs.** Dev tasks are used for the core's `p_t q_t` (D2), the core cut by sweep (D2), selector and ranker calibration (R2, R5), and the D4 tournament. Reuse inflates agreement between selection and estimation. Only "split recorded" is stated.
5. **OUT2 cannot occur in the D1-yes branch.** The reference is expose-all, which is an arm; its difference to itself is zero, so it is always feasible. OUT2 ("none feasible, report what is missing") is reachable only where the reference is a substitute that is not an arm, i.e. where the claim is already weakest. The diagram presents it as a symmetric third outcome.
6. **Feasibility test unspecified at the margin.** "Lower bound" of what interval at what level; paired or unpaired difference (same tasks across arms: paired, clustered by task and, for multi-turn, by session); one-sided or two-sided; whether `delta` is absolute or relative. The errata (section 1) specifies `Y_a(w_hat) >= Y_ref(w_hat) - delta` with "intervals carried", which differs from D4's lower-bound rule, and neither says where `w_hat` (the stratum prevalence) enters D4. The strata and prevalence machinery of correction 1 is not used by G at all.
7. **A pre-registered rule with an undecided `delta` is a function, not a decision.** Fine for a template, but 02 section 6 presents D4 as "testable". What is testable is the procedure's *behaviour* (false-feasible rate, regret), which would need a synthetic study with known truth; none is specified.

**Evidence.** 02 node table row D4 and section 6; errata section 1 (feasible set); `package-v2/01` section 8 (F1); DPR-0002 section C list of arm types for K. I did not run any simulation.

**What would resolve it.** Specify the interval, pairing and level; add a multiplicity rule or restrict the number of arms before looking; give the confirmation rule and the fallback; add a token-equivalence margin and define "component"; separate dev splits for estimation, selection and confirmation; decide whether OUT2 belongs in the D1-yes branch. A simulation with known arm truths (not authorised to run) would give the false-feasible rate of the rule as written.
