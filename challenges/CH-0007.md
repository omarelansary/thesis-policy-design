# Title: the cascade cost/recall model (DPR-0002 section D) can only show a stage losing recall, and prices deciding as linear in tools read; it cannot say which way the answer goes

**Objection.**
1. **Recall enters only as a loss.** Section D: stage 1 earns its place only if `b_1 + a_1 n_0 < a_2 (n_0 - n_1)` "and ... `(1 - r_1) * V < saving`". The comparator is introduced with its own recall `r_J^0` (single stage on `n_0` candidates), but the inequality never uses it. The end-to-end recall effect of adding stage 1 is `r_1 * r_2(n_1) - r_2(n_0)`, where `r_2(.)` depends on how many candidates the later stage reads. If a decider is less accurate on a long list than on a short one, this term can be positive, which is the whole case for a cascade (a costly accurate stage working on a short list). The model as written cannot represent that case, so it is tilted against cascades on recall. I do not claim the sign is positive; I claim the model cannot return a sign. [S] that decider accuracy falls with list length: I did not read a source in the workspace that measures it for tool selectors (S4G names LongFuncEval as C4 prior art; not read).
   Measured instance in the governing record: Enrich-Retrieve-Rank on a 7,278-tool registry, Match@1 about 0.39 "explained as about 0.56 (gold in the top 15) times about 0.70 (reranker accuracy given presence)"; selection only, no task success (S4F-PA L15). There is no single-stage arm on the full registry in that source, so it neither supports nor refutes dominance; it shows the decomposition the model needs is measurable.
2. **Linear read cost, tools as the unit.** `D_cas = sum_j (b_j + a_j n_{j-1})` takes stages to read tools. The vendor-recommended staged design reads groups first: "we recommend using namespaces or MCP servers ... For a namespace or MCP server ... the model sees only the namespace or server name and description at the beginning ... aim to keep each namespace to fewer than 10 functions" (EXT-0010, read). DPR-0001's own S3 registers "server grouping". With a group-level first stage, stage-1 reading is over `g << n` items, and `a_1 n_0` is the wrong cost.
3. **Cache and feasibility are not linear.** An LLM decider reading a static catalogue can have the catalogue in a cached prefix, so its per-task cost is a function of the cache regime, and it has a hard feasibility limit at context size. Neither appears in `a_j`. This is the "cache interaction" the proposer asked about: it can move the break-even in either direction and the model has no term for it.
4. **Correlation.** The text says recall is `prod r_j` "only if stage errors are independent" and "if errors are positively correlated ... the compounding is smaller". The proposer regards positive correlation (the same hard-to-match tools missed at every stage) as the realistic case. Then dominance condition (iv) (recall loss compounds) is nearly empty, and the remaining conditions (i), (ii), (iii), (v) are all cost conditions. So the model does not supply a recall-based reason for a single stage.
Net: "the cascade argument is plausible, not supported" (section D) is accurate, but the model is presented as the reasoning for the single-stage conclusion, and it is two-sided uncertain.

**Evidence.** DPR-0002 section D (lines 52-61); `evidence/governing/stage-reports/S4F-PRIOR-ART-ASSESSMENT-20261015.md` L15; EXT-0010 (OpenAI tool-search guide, namespaces and MCP servers); DPR-0001 S3 and R6 ("Cost of deciding is not a single term"). Not checked: any source measuring decider accuracy against list length.

**What would resolve it.** Section D states the net-recall term `r_1 r_2(n_1) - r_2(n_0)`, allows stage 1 to read groups, names the cache regime as a determinant of `a_j`, and says that the model returns no sign without measured `r_2(.)`, `a_j` and correlation.
