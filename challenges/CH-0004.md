# Title: the signal register understates leakage: class R signals on the closest vehicle already carry gold-identity cues, and class D has unlisted leakage routes

**Objection.**
1. **S2 (catalogue metadata) is classed R "by construction" with the risk "stub schemas on the closest vehicle".** The governing record says more: distractors outside the reference trace carry `{"type":"object"}` stubs while same-server siblings can carry real schemas, and "schema richness can act as a cue for the right tool". On that vehicle, metadata richness is a proxy for membership in the reference trace, which is gold. Any policy component that reads schemas (a retrieval index over metadata, an LLM selector S11, a rule on description length) can exploit it without anyone using S12. The classification R is correct for deployment and wrong for that benchmark; the register should carry a per-vehicle column, or the DPR should state that S2 cannot be treated as clean on that vehicle.
2. **Runtime messages in the replay vehicle are a second reference-route channel.** The cache-miss message "shows working argument shapes for exposed tools" and both messages "steer argument choices toward the reference route in every arm" (S4G L26). That is S7 content derived from the reference trace: S7 is classed X/R with the risk "only informative about tools the model attempted", but its content is also reference-derived (P-like) on that vehicle. The draft's "Rules for later records" (S12 only in the scorer) does not catch this because the leak is inside the environment, not in the policy's inputs by design.
3. **S10 (class D) lists one leakage route (training on the evaluation tasks).** Unlisted: (a) tuning policy parameters (the unset `k`, `tau`, `m`, `G`) on the evaluation tasks, which is the same-data composition problem recorded for C6 (S4D addendum 2.3); (b) catalogue overlap between the offline-data catalogue and the test catalogue (same tool descriptions seen in both); (c) the selector model or embedder having been trained on the public benchmark (labelled [S]: I have no source in the workspace measuring this for any selector, and "none found" here means only that I looked in the governing copies and the ledger); (d) D3's "pre-measured regime facts from S10-like offline data" (section 4.2) are measured on some tasks with some model, and if those are the evaluation tasks the gate is tuned on the test set.
4. The draft's P definition inherits AUTH-004's "unless legitimate availability is demonstrated" but does not say what a demonstration would be (e.g. a deployment in which the signal exists at decision time). Without that, the escape clause is unfalsifiable.

**Evidence.**
- `evidence/governing/stage-reports/S4G-SELECTION-READY-BRIEF-20261015.md` L23 (stubs and "schema richness can act as a cue for the right tool"), L26 (both messages steer "toward the reference route in every arm"; they concern exposed tools), L21 (replay from single reference; unexposed tools rejected).
- `evidence/governing/candidate-questions/S4D-QUALITY-ADDENDUM-20261014.md` L19 (composing from steps that paid in the same data is selection on the outcome; symmetric tuning).
- DPR-0001 rows S2, S7, S10, S12, section 4.2 D3, "Rules for later records".
- STAGE3 claim ledger C3-16 (ToolRet labels only each source dataset's target tools; equivalent tools count as negatives): a label-side validity limit, not a runtime leak; mentioned only because gold-based scoring is a threat of the same family. Not checked in the original paper.

**What would resolve it.** The DPR adds (a) a vehicle-conditioned note on S2 and S7, (b) the extra D-leakage routes and a rule that policy parameters are fixed on data disjoint from the evaluation tasks, (c) a statement of what would count as demonstrated legitimate availability of a P-class signal.
