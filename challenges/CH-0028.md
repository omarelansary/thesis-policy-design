# Title: the single-step vs loop gap T* ignores that a changed tools array also invalidates the system prompt, and mixes r from one provider with w from another

**Grade: SERIOUS (it is the proposer's answer to the lead's "single-step vs agent-loop gap"; the conclusion "a loop with T > T* would favour the restriction even with a per-task varying surface" is overstated).**

**What I checked and found correct.** Sections 3.1 and the Toollery fit: the break-even form `rho*[1-(1-r)h_r] < 1-(1-r)h_f`, equal hit rates giving ratio `rho`, `h_r* ~ 0.22`, predicted ratio ~1.09 at `h_r = 0.144` (I reproduced `r ~ 0.0087-0.0089` independently from EXT-0062 before reading DPR-0005, and the break-even `r ~ 0.0105` for the natural-replay hit rates). The closed form for `T*` is correct for its stated assumption.

**Objection.**
1. **Non-tool prefix.** Section 3.2 prices a per-task varying surface as a write of the restricted *tool block* at turn 1 and reads thereafter. EXT-0058 states "The tools array sits even earlier in the hashed request prefix than the top-level system field, so editing it invalidates the prompt cache for the entire conversation." A per-task change of the tools array therefore also forces a rewrite of the system prompt (size `N_s`) every task, while the full-library arm keeps both warm. Redoing the algebra with `x = N_s/N_f`: restricted cheaper iff `(rho*N_f + N_s)*(w + r*(T-1)) < r*T*(N_f + N_s)`, i.e. `T* = (rho + x)*(w - r) / (r*(1 - rho))`. With the proposer's own values (`rho ~ 0.025`, `r ~ 0.0088`, `w = 1.25`) the added term is `x*141`; a system prompt of only 1% of the tool block moves `T*` from ~3.6 to ~5 turns, and at `x = 0.1` to ~17. With a vendor-page `r = 0.1` the added term is `x*11.8`. So the loop-gap threshold is much larger for realistic agent prompts, and the Toollery single-step null is not "below T*" by a small margin but possibly far below. This holds for a provider that orders tools before the system prompt (stated for the Claude API in EXT-0058; the Table 15 provider's ordering is [U]).
2. **Mixed providers.** `r ~ 0.009` is inferred from Table 15 (provider and model unknown); `w = 1.25` is the Anthropic page value (EXT-0021). The Table 15 cells are consistent with no write premium (Toollery natural: cost ratio 0.857 = 0.856 + 0.144*0.0087), i.e. `w ~ 1` there. The "about 3.6 turns" combines two providers' parameters and so describes neither.
3. **Direction of the claim.** The last sentence of 3.2 ("would favour the restriction even with a per-task varying surface") is therefore conditional on `T > T*` computed with a system prompt term; as written it invites the reading that loops rescue per-request restriction.

**Evidence.** DPR-0005 section 3.2; EXT-0058 l.27; EXT-0021 l.32 (multipliers); EXT-0062 (cells); my arithmetic above.

**What would resolve it.** Correct `T*` with the non-tool prefix term and a provider-ordering caveat; take `r` and `w` from the same provider or give both cases; soften the last sentence.

**Response (proposer).** [round 1 reply, verbatim excerpt] "CONCEDE: CH-0028 (your T* is right: T*=(rho+s)(w-r)/(r(1-rho)); w must come from the same provider as r; fixed in DPR-0005 3.2)." [rounds used: 1 of 2]
