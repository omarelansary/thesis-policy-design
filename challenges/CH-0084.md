# Title: Three requirements listed as met by V5-R are met only nominally (REQ-O14F-06, REQ-O02-06, REQ-O21-03)

**Objection.** (a) REQ-O14F-06 (staged graph, a tool filtered out may be added again). `04` section 3 says "a filtered tool comes back through D". For an S1-filtered tool this is false: S1 removes it from `tools`, and `04` section 5 itself says "D recovers only if the tool is declared". It is true only for tools M2 holds back. S1 and S2 are once-per-deployment configuration (V5-R03: "per deployment, not per request"), yet the Mermaid graph draws them as run-time boxes at "Session start or return"; the claim in section 1 point 4 of "two session-level stages plus on-demand discovery" is then M2 alone at run time. Q-J31 discloses part of this; section 3's sentence does not. (b) REQ-O02-06 (Executor is a baseline) is in DPR-0007's `requirements` list, but the Executor row of the `04` section 4 table is empty ("to be read from its own MCP surface before the arm is defined"); at most it is a placeholder. (c) REQ-O21-03 (memory: the relevant part injected first, more when asked) is listed; M1 "loads the user's Markdown memory", with no "relevant part first" or on-request path. DPR-0008 marks the same requirement "Meets in part"; V5 does not. I do not challenge the requirements, only the claim of meeting them.

**Evidence.** `04-design.md` section 1 point 4, section 3 (graph, and the paragraph beginning "How the requirements are met"), section 4 (Executor row), section 5 (S1 row, "D recovers only if the tool is declared"), V5-R03; DPR-0007 header `requirements`; `requirements/REGISTER.md` REQ-O14F-06, REQ-O02-06, REQ-O02-09, REQ-O21-03; `design/proposals/DPR-0008.md` section 3.

**What would resolve it.** Reword section 3 to: filtered by S1 = not recoverable in-session (a design cost of S1), held back by M2 = recoverable by D; mark REQ-O02-06 as "baseline arm, not yet defined"; either specify the memory read for REQ-O21-03 (what is injected first, how more is obtained) or mark it "met in part".
