# Title: graph G is a policy family plus an offline arm-selection protocol; node D4 is experimental arm selection and re-imports the N0 problem

**Grade: DECISIVE against the description of G as "a policy" with D1-D4 as decision nodes. It is not decisive against G as a documented procedure.**

**Objection.** (design/package-v3/02-supervisor-decision-graph.md sections 2-4, 6, 7.)
1. **Plain answer.** D1 to D4 are an evaluation and tuning protocol run by the operator on labelled dev tasks; R1 to R6 are a run-time mechanism whose content (which of R2, R2-level-2, R6 exist; whether a core exists) is *determined by D4's outcome*. As drawn, G is "run these arms on dev, deploy the cheapest feasible one". In machine-learning terms D4 is model selection over a small discrete hypothesis class (argmin of an empirical cost under an empirical constraint), i.e. hyperparameter tuning. It is a legitimate deployment *procedure*. It is not a *decision mechanism of the policy*, because it never maps a run-time observable to an action: it maps a dev experiment to a configuration, once per catalogue, model and provider.
2. **This contradicts the settled N0 position of RV-0003.** RV-0003 section 3 item 2 recorded: "(i) which arms are evaluated is evaluation design (outside the policy); (ii) whether to restrict at all is decided inside the policy by A1 ... no learned selection rule is proposed", and I accepted that split. G puts (i) back inside the policy as D4 and so moves from "a rule with named run-time inputs" to "a tournament". G's own text makes the move ("node D4 selects by a pre-registered dev comparison"; section 2).
3. **Is it a learned selection rule?** Only if the procedure is itself the object of study: inputs (catalogue size, window, provider, model, dev outcomes), output (arm), with its generalisation tested across settings. G contains no such test. With one catalogue, one model and one provider, the output is a single data point of selection; "the output is a function of size" (section 6) requires several sizes, each a separate full tournament. Without replicates nothing distinguishes G from "run all arms and report the best", and the claim "G is a testable conditional decision" reduces to "the arms are testable". To test the rule one needs held-out *settings* (e.g. leave-one-setting-out: apply D4 on dev of setting A to predict the best arm of setting B); that experiment is nowhere specified.
4. **The offline cost of D4 is outside the objective.** AUTH-006: "Include all decision/discovery overhead." The errata's estimand (section 0) counts decider calls and discovery per trajectory but not the cost of running D3 arms on dev tasks (including an expose-all arm at the full prompt size over complete trajectories). v2 amortised offline cost over `N_dep` (package-v2/01 section 8; CH-0025 conceded). v3 dropped it. If D4 is part of the policy, its token cost is part of the policy's cost; if it is not, it is evaluation design and G is not a policy node. The dilemma cannot be avoided by calling D4 "design time".
5. **D4 needs an outcome scorer at deployment.** "End-to-end success" on dev tasks needs a scorer; a deployment without labelled tasks and scorer cannot run D4 at all. G does not say what a deployment without one does.
6. **AUTH-006 does not settle this in G's favour.** The AUTH asks for "a testable conditional decision" when the evidence does not select a mechanism. That is satisfied if the *condition* is stated over observable facts (catalogue size relative to window, whether need statistics exist, measured initiation rate) with a stated rule; it is not obviously satisfied by "the condition is whatever a dev tournament shows".
7. **Does G answer the supervisor's three needs?** *Context*: D4's output depends on setting, not on the request; request-level dependence exists only if R2 is selected. *Staged narrowing*: the stage count is an output and "may be zero" (section 1); with the core skipped at large catalogue (the case G is said to serve) and R2 not selected, the realised configuration is search-only, i.e. vendor deferral without a hand core, with no narrowing stage before run time. *Reintroduction*: R4-R5 is the model's search, not a re-adding of something an earlier stage removed unless R2 is present. So "answers the three needs" holds conditionally on arms for which G itself says there is no evidence. Defining a stage as "present only if a stated reason holds" makes the requirement satisfiable by any design, including expose-all.

**Evidence.** 02 read in full; RV-0003 section 3 (items 1-2); package-v2/01 sections 5 and 8; AUTH-006 verbatim text (ops/AUTHORIZATIONS.md lines 359-373); REGISTER rows REQ-O14-08/09/12/13/15 (read: REQ-O14-12 is class "unclear", REQ-O14-15 "supervisor-example", "can go back" is permissive).

**What would resolve it.** Either (a) restate G as "a policy family (R1-R6) plus a documented selection procedure (D1-D4), the thesis claim being about the family's arms, not about the procedure", and drop "policy" for D-nodes; or (b) define D4 as a rule over observable conditions with a stated generalisation test across settings and count its tournament cost. Experiment for (b): apply D4 independently in at least two or three settings and compare its picks with each setting's best arm on a held-out set (needs a smoke execution; not authorised).

**Response (lead, round 2).** Accepts the relabel: G = run-time policy R1-R6 plus a deployment selection protocol D1-D4 (02 sections 1, 7); D4 is "experimental arm selection", not a run-time node and not a learned rule unless tested (E6); offline cost charged as `O_dev / N_dep`; scorer requirement stated; conditional satisfaction of the three needs stated (02 section 2). **Disagrees** only on removing D-nodes from the supervisor-facing graph (AUTH-006 asks for a testable conditional decision; D1-D2 are factual conditions).
