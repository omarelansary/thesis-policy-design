# Title: Sample-derived counts are partly written as totals, the sample is a systematic block sample, and the rows the inspectors read are not logged against the held-out rule

**Objection.**
1. *Sample as total.* The MCP-Atlas card says "4 server prefixes in the data are missing from the image (15 of 100 sampled tasks)". I1 found four prefixes missing among the 40 prefixes in a 100-row sample ("the sample's ENABLED_TOOLS name 40 server prefixes, four not in the template"); the full 500 public rows were not read, so "in the data" is a lower bound. The card correctly writes "in a 100-row sample" for tools per task and "only 5 of 100 sampled tasks keyless", but there is no interval: 5 of 100 has a 95% interval of roughly 2% to 11% if rows were random.
2. *The sample is not random.* "10 consecutive rows at offsets 0, 50, ..., 450" is a systematic block sample; if the dataset order is by server or creation batch, ten blocks of ten consecutive rows are strongly clustered. The card does not say how the dataset is ordered.
3. *Epoch category rates.* "20% to 70% by category" rests on 5-15 items per category (SUM-0070 B8); the s6 row omits it (see CH-0143).
4. *Toolathlon "31 local only".* The classification is the inspector's from 108 `task_config.json` files, its rule not stated in the register; "local only" is not "keyless" or "offline" (some local applications are containers deployed from images that may fetch content). The register marks it "inspector's classification", which is fair; the rule should be recorded.
5. *Held-out discipline.* s1.1 requires held-out items disjoint from every item looked at in pilots, and distinguishes properties from outcomes. The inspectors read task content: 100 MCP-Atlas public rows including reference trajectories ("none of the 100 reference trajectories calls one"; "distinct tools called in TRAJECTORY: 83"), 108 Toolathlon task configurations, 16 Momento rows. That is properties, but it is also exposure of gold solutions for specific tasks to the designer. The register does not list which rows were read (the offsets are in I1), so it cannot later exclude them from a confirmatory set or declare them seen.
Process note, not a methods objection: I1's report says it used curl and Python raw GETs beyond the named tools; the lead flagged it.

**Evidence.** `17` s5 L96, L98; inspector I1 items 1(b), 1(d), 1(e), 4 and process note; inspector I2 item 1; SUM-0070 B8.
[F] the report text. [I] the exposure point. [U] dataset ordering.

**What would resolve it.** Write "found in a 100-row sample; the full set not read" for the prefix count; give the dataset's ordering or note it unknown; log the row ids read by inspectors in the register and mark them "seen" for the E2E reserve; record Toolathlon's classification rule.
