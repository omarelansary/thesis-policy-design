# Title: The MCP-Atlas keyless arm relies on "recorded once and replayed" tool results and on a subset defined by called tools, neither of which is shown to work

**Objection.**
1. *Replay cannot cover arm-divergent calls.* s7 uses replay to meet "no live drift between paired arms" (E2E H5, P3 H5). A recorded result can only answer a call the recording run made with the same arguments. The arms differ in what they call (deferral adds search calls, picks different tools or arguments; s6 L176 says exactly this about scorer behaviour). A call outside the recording needs a live call (drift returns) or an error (the arm is penalised for the replay, not the policy). The sandbox's own cache covers identical successful calls to whitelisted servers only (I1 1e/1g). The register does not say how novel calls are answered, what share of calls are novel, or how arms are kept comparable; it is an untested design element carried in two rankings and the E2E arm.
2. *Keyless subset: called versus enabled.* s7 P3 #2 defines the subset as "tasks whose called tools are all keyless: 18 of 100 sampled"; only 5 of 100 have every enabled tool keyless (I1 1e). P3's cells and E2E declare the task's ENABLED_TOOLS or the union catalogue, so the model can call a keyed tool that the reference trajectory never used (the "wrong tool visible" cell is designed to invite this). With no keys the result is an error unrelated to the policy. The register does not say how keyed tools are removed or answered.
3. *Selection from gold.* The subset is selected using the reference trajectory, which s4 uses as gold. R6 (s3) says a subset's representativeness is reported on the properties that matter, not claimed. s7 gives "about 90 of 500 if the sample holds" from 100 consecutive-block rows (CH-0153 accepted) and no comparison of the keyless tasks with the 500 on enabled-tool count, domain mix, or trajectory length. Several keyless servers serve live web content (I1 1e).
4. *Scorer.* s7 P2 #2 and E2E #2 use the native judge, pinned and "checked per arm". The authors' v3 judge reads claims only (I1 1f; L276 of i13) and the judge-human agreement figure of 78% is from v1 (register L107); per-arm check needs human labels from the student, whose cost is not stated for an arm with about 90 tasks times arms times models.

**Evidence.** [F] I1 items 1e, 1f, 1g; register L176, L189, L201, L212; CH-0153. [I] that replay cannot answer novel calls (no source says how the sandbox handles a miss in a replay file; the cache routes are `/cache-stats` and `/cache-clear` only).

**What would resolve it.** State the replay mechanism and what happens on a miss; measure on the 100 stored rows (or the reference trajectories) the share of calls a deferral arm would make that the recording lacks, or label MCP-Atlas as a record-only precedent; define how keyed tools are handled; report the keyless subset's properties beside the full set's; state the human-labelling effort for the per-arm judge check.
