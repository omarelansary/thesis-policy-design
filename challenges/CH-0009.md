# Title: the comparators P2/P6/P7 leave their key component unset, P3 is misdescribed, P4 is infeasible exactly where a cascade is said to win, and no cascade is written out to be compared

**Objection.**
1. **Win conditions are tautological where the scorer is unset.** P2 "rank non-core tools by one scorer ... (scorer type unset)" and "Wins when the scorer's recall at `m` is high and `n` large"; P6 and P7 inherit this. Whether lexical, dense, hybrid or LLM scoring is chosen changes the result and the evidence is benchmark-dependent (ledger K1, C3-01: BM25 level with or above conventional dense baselines on ToolRet, the reverse in Re-Invoke). A comparator that does not fix its scorer is a straw man or a strong man at the evaluator's will. S4D quality addendum 2.3 requires "symmetric tuning" and a "strong baseline" for static restriction; DPR-0002 does not say the comparators get tuning effort equal to the policy's.
2. **P3 "System takes no relevance decision" is not what the cited doc says.** In the Anthropic tool-search guide the API "runs the search" with a regex or BM25 variant over names, descriptions and argument names, and returns up to 5 matches by default ("Claude can set a `limit`") (EXT-0007, "How tool search works", read; EXT-0009: "Both tool search variants (regex and bm25) search tool names, descriptions, argument names, and argument descriptions"). So P3 is a model-composed query, a lexical ranker and a result cap (a top-N, which REQ-O14-08 says is not a policy). Its recall is the ranker's, and P3 is itself a two-component pipeline. Calling it "no relevance decision" removes the component that determines its success.
3. **P4 is infeasible at the scale where a cascade is hypothesised to win.** P4 carries a name+description line for all `n` tools every turn (DPR-0002 says "Costs the cheap-grade list for all `n` tools every turn"), listed as viable at "moderate catalogue size". The proposer concedes (DPR-0003 Card B, C) that a cascade "may win at very large `n` ... a regime this thread has no data for". In that regime P0 and P4 are infeasible, so the "simpler comparators" reduce to P2 and P3, each with an unset or lexical ranker. The vendor-recommended answer to large `n` is group-level disclosure (EXT-0010), which is a hierarchical, staged design and has no comparator among P0-P8.
4. **No cascade is specified.** HYP-0002 is tested against "a cascade of more than one filtering stage"; no cascade is written out (what each stage reads, what decides, what the recall estimator is). Any multi-stage design, including a degenerate one, satisfies the falsifier's wording. The symmetric requirement to AUTH-004's "not a straw man" for the simpler policy is a stated best-case cascade, so the comparison is between two complete designs.

**Evidence.** DPR-0002 section C (P2, P3, P4, P6, P7), section B (F4), DPR-0003 Cards B and C; EXT-0007, EXT-0009, EXT-0010 (read); ledger K1 (L49) and C3-01 (L12); S4D quality addendum L19 (read); HYP-0002 falsifier.

**What would resolve it.** Fix a scorer family per comparator (and say which is the strong one, by what evidence, K1 being unresolved); correct P3; state P4's feasible range and add a group-level comparator; write one complete cascade as the steelman. Answerable now by editing; which wins needs an experiment.

**Response (proposer).** [verbatim, round-1 reply, 2026-10-16; rounds used: 1 of 2] "CH-0009 CONCEDE. Scorer rule added (strong, symmetrically tuned; type is a factor). P3 wording corrected: EXT-0009 says regex/bm25 over names, descriptions, argument names and descriptions. P4 infeasibility at large n stated. A complete two-level cascade comparator P4g is now written out (group-then-tool, DPR-0002 section C), and HYP-0002 is tested against it, not 'any multi-stage design'."

**Outcome.** items 1-3 resolved (DPR-0002 section C checked). Item 4 (a cascade written out): P4g is written but is the model-driven hierarchy, not a system-run cascade; carried to CH-0018.
