Abstract

Users often omit essential details in their requests to LLM-based agents, resulting in under-specified inputs for tool use.
This poses a fundamental challenge for tool-augmented agents, as API execution typically requires complete arguments, highlighting the need for personalized tool calling.
To study this problem, we present Multi-Session Personalized Tool Calling (MPT), a benchmark comprising 4,695 instances over 459 multi-session interaction histories that cover three challenges: Preference Recall, Induction, and Transfer.
We further propose PRefine, a test-time memory method that maintains the user’s latent preference as a textual hypothesis revised through a generate–verify–refine loop.
Across five LLMs, existing memory systems often fail to improve on full-history prompting; PRefine outperforms all baselines and alone surpasses it on Preference Transfer.
These results indicate that memory for personalized agents must abstract behavior into preferences, rather than simply archive it.

1 Introduction

LLM-based agents increasingly rely on external tools to perform complex tasks such as deep research (Xu and Peng, 2025) and computer use (Sager et al., 2026).
These tools, typically realized as parameterized functions, are invoked with arguments often missing from user requests; e.g.,
a query as simple as “Book a flight for my trip” specifies neither the origin, the destination, nor the price.

A direct solution to such underspecification is to ask the user clarifying questions about the missing arguments.
A more proactive agent, however, could infer them from user preferences with minimal intervention, akin to a recommender system—the core idea behind personalized tool calling (Moghe et al., 2024; Xu et al., 2025).

Figure 1: Example of latent preference modeling for personalized tool calling.
No prior session involves flights, so flight_class=‘‘Economy’’ cannot be retrieved from past calls.
Instead, the agent must model the user’s preference from its cross-function expressions (price_range, free_entry, car_type) and apply it to the unseen argument.

Prior work in this direction has largely assumed that user preferences are provided explicitly.
Standing-instruction and profile-based approaches (Moghe et al., 2024; Huang et al., 2025) inject curated preferences into the input, while retrieval- and memory-based agents (Lewis et al., 2020; Chhikara et al., 2025; LangChain AI, 2025; Xu et al., 2026) assume the target arguments have appeared earlier in the context.
In both cases, personalized tool calling reduces to a search problem.
More challenging benchmarks merely make the preference harder to locate or apply: it may be indirectly phrased, context-dependent, or later superseded (Zhao et al., 2025; Kim et al., 2025; Jiang et al., 2025a; Jiang et al., 2025b); the task nevertheless remains one of search.

In this work, we argue that user preferences are, in reality, latent, and thus should be inferred rather than retrieved (see Figure 1).
In other words, the cues are mostly implicit in the user’s past tool calls.
Consider a user who books a cheap restaurant, tours a free attraction, and rents a compact car, each choice triggering a distinct tool with no shared parameters.
To infer that this user favors affordable options, a preference never stated, the agent must generalize across these seemingly unrelated calls.

To evaluate this capability in LLM-based agents, we propose Multi-Session Personalized Tool Calling (MPT), a benchmark of 4,695 instances over 459 multi-session histories drawn from three corpora.
MPT comprises three scenarios that differ in how much evidence prior sessions provide for the target argument.
In (1) Preference Recall, the argument is hinted at multiple times, as in existing benchmarks, so direct reuse is sufficient; in (2) Preference Induction, a single explicit mention must be corroborated by cross-function evidence; and in (3) Preference Transfer, the preference must be applied to an argument absent from the history.

Alongside MPT, we introduce PRefine, a test-time memory method that maintains the estimate of the user’s preference as a textual hypothesis, revised across sessions through a generate–verify–refine loop.
A candidate hypothesis enters memory only after being verified against the accumulated behavioral record, yielding a memory that is an abstraction of user behavior rather than a raw log.

Across five LLMs and six methods, agents reliably recover explicit arguments but struggle with omitted preference-sensitive ones, and performance degrades from Recall through Induction to Transfer.
Retrieval- and organization-based memories (RAG, Mem0, LangMem) even fall below full-history prompting, indicating that surfacing past records is not enough unless the evidence is abstracted into a preference.
PRefine, in contrast, outperforms all baselines, and is the only method to exceed full-history prompting on Transfer without session context.
Its advantage also holds as competing and unrelated observations accumulate in history, a difficulty we quantify with a new evidence interference score: all methods degrade under high interference, but PRefine remains the best.
Ablations on PRefine further show that verification, not repeated refinement, drives these gains.

2 Related Work

Personalized Tool Calling

Existing tool-use benchmarks primarily evaluate planning, failure recovery, and chained execution in multi-turn settings (Wang et al., 2024; Lee et al., 2024; Yao et al., 2025; Patil et al., 2025; Chakraborty et al., 2025; Shim et al., 2025).
Personalized tool-calling studies further incorporate standing instructions, user profiles, or prior API calls to constrain tool arguments (Moghe et al., 2024; Xu et al., 2025).

However, these methods use explicit preference profiles or derive tool preferences from history, without evaluating whether implicit preferences can be inferred from cross-function evidence and applied to arguments absent from the history.

Latent Preference Modeling

A related line of research recovers user preferences from implicit interaction histories.
In dialogue systems, PrefEval (Zhao et al., 2025), CUPID (Kim et al., 2025), and PersonaMem (Jiang et al., 2025a; Jiang et al., 2025b)
evaluate whether LLMs recognize and apply such preferences.
Conversational recommender systems similarly model preferences as latent variables learned from behavior, generalizing beyond observed choices (Luo et al., 2020; Chen et al., 2019; Zhou et al., 2020a; Li et al., 2025a).

Table 1 compares these benchmarks along five axes: where the preference comes from, whether it remains implicit, how many decisions it governs, what kind of target is absent from the history, and whether interference is quantified per instance.
Only MPT tests whether an unstated cross-function preference transfers to an unseen argument (Preference Transfer; 29.3% of its instances).

Memory for Long-Horizon Agents

Agentic memory research studies how agents maintain and update information across interactions (Park et al., 2023; Packer et al., 2024; Shinn et al., 2023; Wang et al., 2023; Wei et al., 2025),
with work on multi-session collaboration (Mehri et al., 2026; He et al., 2026), memory compression (Liu et al., 2025), and memory policies (Zhou et al., 2025; Wang et al., 2026).
Profile-based methods organize and update user information (Kwon et al., 2023; Zhang et al., 2025; Chhikara et al., 2025); PRefine instead keeps a single preference hypothesis, revised only when verified against the accumulated history and applied to the tool schema at inference.

3 Problem Definition

Tool Calling

Let S={s1,…,sT}S=\{s_{1},\ldots,s_{T}\} denote a sequence of past dialogue sessions between a single user and an AI agent, where each session sts_{t} consists of a multi-turn dialogue in which the agent may execute API calls.
The agent operates over a tool schema ℱ\mathcal{F}, a set of available functions, where each f∈ℱf\in\mathcal{F} is a tuple (i​d,K)(id,K) of an identifier and a set of parameters.
Tool calling is then the task of producing an API call a=(i​d,{(k,v)})a=(id,\{(k,v)\}), i.e., selecting a function and assigning an appropriate argument (value) vv to each parameter (key) k∈Kk\in K, e.g., GetFlights(flight_class=‘‘Economy’’).

Let 𝒜\mathcal{A} denote the list of all API calls executed in SS.
We define the user’s interaction history ℋ=(S,𝒜)\mathcal{H}=(S,\mathcal{A}).
At timestep T+1T+1, the agent observes a query qq, consisting of the turns of a new session sT+1s_{T+1} up to the API decision point, and must produce the corresponding API call aT+1a_{T+1}.
In personalized tool calling, preference-sensitive arguments unspecified in qq must be inferred by modeling the user’s latent preference from ℋ\mathcal{H}.

Latent Preference Modeling

How the missing arguments are filled depends on a latent preference pp, a user-level variable not directly observed.
We study preferences that satisfy three conditions:
(C1) pp can be instantiated as API arguments across multiple functions, so that it can transfer between them (cross-function instantiation);
(C2) those arguments admit different preferred values across users, such that no universal default value is sufficient (variation across users);
and (C3) pp persists across a user’s sessions rather than varying with each request (persistence within a user).

For instance, a user who prefers low_cost may choose price_range=cheap when searching restaurants and flight_class=Economy when booking flights, without ever stating the preference.
We assume that calls supporting pp strictly outnumber those conflicting with it (§4.2).
The agent, however, is never told which arguments express pp and must infer it across functions.

Figure 2: Overview of MPT construction.

Each query qq often leaves preference-sensitive arguments unspecified, and pairing qq with ℋ\mathcal{H} yields a concrete instance in MPT.

Formulation

In summary, resolving an underspecified argument requires (1) inferring pp from past behavior and (2) applying it to the target function, rather than retrieving previously observed values.
Formally, the agent predicts a fully instantiated API call a∗a^{*} for aT+1a_{T+1} consistent with both qq and pp:

p^\displaystyle\hat{p}
=ψ⁡(S,𝒜≤T),\displaystyle=\psi(S,\mathcal{A}_{\leq T}),

=arg⁡maxa⁡π⁡(a∣q,p^,ℱ),\displaystyle=\arg\max\nolimits_{a}\pi(a\mid q,\hat{p},\mathcal{F}),

where ψ\psi estimates the latent preference as p^\hat{p}, π\pi generates the tool call, both implemented with LLMs, and aa ranges over API calls admissible under ℱ\mathcal{F}.

Finally, C2 and C3 restrict which arguments can express pp. Arguments specifying what is done (e.g., destination, date) vary by request, whereas those specifying how (e.g., price_range, flight_class, eco_mode) are user-specific.
Latent preferences thus inform these how-arguments.

4.1 Preprocessing

Source Corpora

We reviewed 23 dialogue corpora against multi-session structure, API calls with arguments, and satisfaction of C1–C3 (§3), selecting SGD (Rastogi et al., 2020), the English portion of DuRecDial 2.0 (Liu et al., 2021), and HomeBench (Li et al., 2025b).
See Appendix B.1 for screening and preprocessing details.

Preference Realization

We group preference-relevant arguments across functions into latent preferences.
For example, price_range=‘‘cheap’’ in GetRestaurants and free_entry=True in GetTravel both express low_cost.22
                2

              We keep the original schema definitions and apply normalization following Moghe et al. (2024); see Appendix A.7.
MPT defines each preference over multiple functions rather than a single parameter or tool (Table 1).
This requirement (C1) restricts the eligible preferences in the source corpora.
The resulting five latent preferences nevertheless cover 18 realizations over 16 function–parameter pairs in 13 functions (Table 2).
Human validation of the cost and party-size preferences yielded 89.7% and 97.4% agreement (Fleiss’ κ\kappa = 0.701 and 0.880; 19 annotators); ambiguous preferences were excluded (Appendix B.2).

4.2 History Composition

While preference realization identifies which arguments can express a preference, no single call suffices to establish it.
We thus build multi-session histories ℋ\mathcal{H}, in three steps, from which a preference emerges as a recurring behavioral pattern.
We refer readers to Appendix A.4 for further details.

(i) Composition of Users

In our setup, a multi-session history presupposes a user
behind all of its sessions.
We obtain such users by grouping dialogues by seeker in DuRecDial 2.0, splitting each multi-intent instruction in HomeBench into single-intent sessions, and assembling synthetic ones from SGD sessions, since SGD lacks user identifiers.

(ii) Assignment of Users to Preferences

To align an interaction history with a preference (e.g., a user favors affordable options), we label each user from the first step with the preference that their API calls demonstrate.
Specifically, a user is assigned to a preference pp if their calls consistently express pp across at least two functions, following C1 (cross-function instantiation) in §3.
The sessions of such users then serve as supporting evidence for pp.

(iii) Injection of Competing and Unrelated Evidence

To reflect a more realistic setting, we augment the supporting histories from the previous steps with competing sessions expressing opposing preferences (e.g., high_cost vs. low_cost) and sessions unrelated to the target preference.
To keep the target preference dominant (C3 in §3), supporting calls must strictly outnumber competing ones (strict plurality; ties excluded); 46.9% of merged histories contain competing calls.
Added sessions are randomly interleaved while preserving the original order within each source.
The counts of supporting, competing, and unrelated observations are later used to compute the interference score (§7.1).

4.3 Query Construction

For each function ff, we manually create query templates that leave one or more arguments unspecified.
Context-guided queries (qc​gq_{cg}) retain initial turns of the current session, providing direct clues for some arguments, while context-free queries (qc​fq_{cf}) omit this context, requiring tool calls based solely on p^\hat{p} inferred from ℋ\mathcal{H} (see Table 6 for examples).

4.4 Instantiation

An MPT instance pairs a query qq with a history ℋ\mathcal{H}.
Its reasoning type depends on how often ℋ\mathcal{H} instantiates the target parameter left unspecified by qq.33
              3

            Note that one history ℋ\mathcal{H} can appear in multiple instances, each with a different unspecified parameter (and hence reasoning type) or targeted preference.
Specifically, we consider three types:

Preference Recall

The target argument vv recurs in ℋ\mathcal{H}, allowing direct reuse. This setting supports comparison with retrieval-oriented benchmarks and provides a reference for the two harder types.

Preference Induction

The target argument vv occurs only once in ℋ\mathcal{H}.
Since a single occurrence may reflect either a persistent preference or an incidental choice, the agent must corroborate it with evidence of the same preference elsewhere in ℋ\mathcal{H}.

Preference Transfer

The target argument vv never occurs in ℋ\mathcal{H}, although its function may.
Resolving it requires generalization: the agent must infer pp from its realizations in other functions and apply it to an argument without direct evidence.

4.5 Benchmark Statistics

MPT comprises 4,695 instances over 459 multi-session dialogues, totaling 6,961 sessions and 95,523 turns (on average, 15.2 sessions per dialogue and 13.7 turns per session).
It includes 1,375 Recall, 1,944 Induction, and 1,376 Transfer instances.
Of the dialogues, 164 (35.7%) support two to four distinct preferences and yield 2,432 instances (51.8%; Table 7 in Appendix A.6).

5.1 Methods

We test five models: GPT-5, Claude-4.5-Haiku, GPT-OSS-20B, Gemma-4-12B-IT, and Qwen3-8B. Each is combined with the six methods below.

We further propose PRefine, a test-time memory-based method that estimates the latent preference pp with a revisable memory MTM_{T}:

MT\displaystyle M_{T}
=ψPRefine​(S,𝒜).\displaystyle=\psi^{\textsc{PRefine}}(S,\mathcal{A}).

Algorithm 1 summarizes how PRefine updates its preference memory.
After each session st+1s_{t+1} (t=0,…,T−1t=0,\dots,T-1), a generator proposes a preference hypothesis η\eta from the previous memory MtM_{t}, the session st+1s_{t+1}, and its executed tool calls at+1a_{t+1}.
A verifier evaluates η\eta against the accumulated history ℋt+1=(S≤t+1,𝒜≤t+1)\mathcal{H}_{t+1}=(S_{\leq t+1},\mathcal{A}_{\leq t+1}) for
(1) evidence support,
(2) abstraction quality,
(3) actionability, and
(4) temporal consistency.44

              Figure 7 traces the loop on a concrete example. Appendix E provides the used rubrics and prompts.
If accepted, the hypothesis is updated as Mt+1M_{t+1}. Otherwise, the verifier returns feedback ϕ\phi that is used to refine the candidate.
A single PRefine hypothesis can encode multiple preference constraints, as illustrated in Figure 10.

This generate–verify–refine procedure follows prior self-refinement methods (Madaan et al., 2023; Shinn et al., 2023) in form, but differs in what the verifier scores against.
Rather than a task outcome, the target is the accumulated behavioral record ℋt+1\mathcal{H}_{t+1}, and a hypothesis survives only if it holds as a cross-session regularity.
We allow up to K=5K=5 refinement steps (ablation in §7.2).

At inference, MTM_{T} serves as p^\hat{p} in Equation 1.
As with the other memory-based methods, we construct PRefine memories using GPT-OSS-20B.55

5.2 Metrics

Context-guided queries require both extracting explicitly stated arguments and completing omitted preference-sensitive arguments.
We report Explicit-F1 (EXP-F1) for the first subproblem and Implicit-F1 (IMP-F1) for the second.
Overall-F1 (O-F1) evaluates the complete tool call over both.
For context-free queries (qc​fq_{cf}), with no explicitly stated arguments, O-F1 reduces to IMP-F1 (no EXP-F1).

7 Analysis

7.1 Evidence Interference

Definition

To test the robustness of PRefine’s advantage to evidence composition, we define the Evidence Interference Score (II), a post-hoc diagnostic index for ranking instances by difficulty.

Given a preference pp, we classify each observation in ℋ\mathcal{H} as supporting (R)(R), competing (C)(C), or unrelated (U)(U): a supporting observation contains a parameter–argument pair mapped to pp; a competing observation contains preference-relevant evidence that is inconsistent with, or offers an alternative to, pp; and an unrelated observation contains no parameter tied to pp.
Let RR, CC, and UU denote their respective counts.
We then define,

I=β​C+γ​UR+β​C+γ​U.I=\frac{\beta C+\gamma U}{R+\beta C+\gamma U}.

(2)

Supporting observations serve as the unit-weight baseline, and we impose the qualitative ordering β>1>γ>0\beta>1>\gamma>0.
Competing evidence is weighted more heavily, as it presents an inconsistent or alternative preference signal, while unrelated evidence receives a smaller nonzero value since it primarily increases the filtering burden.
We use β=4\beta=4 and γ=0.25\gamma=0.25 as a reference parameterization
(validation and sensitivity analyses in Appendix D.3).
A higher II indicates a greater weighted burden of potentially interfering evidence.

Results

We rank instances by II and divide them into quintiles within each reasoning type, combining both query settings; Q5 denotes the highest-interference subset.
All methods perform worse at Q5 than at Q1, confirming that II reflects difficulty.
PRefine nevertheless achieves the highest IMP-F1 in all 15 reasoning-type ×\times quintile cells (Figure 3(b)), although its margin narrows on Transfer.
A-MEM is the strongest memory baseline on high-interference Recall and Induction, but its advantage does not carry over to Transfer.

Focus on Competing Evidence

Every method drops when competing evidence is present (C>0C>0; Figure 4).
Under C>0C>0, A-MEM is the strongest memory baseline on Recall and Induction but falls below Full-History Prompting on Transfer (8.58 vs. 12.29 IMP-F1), whereas PRefine reaches 17.38.
Thus, memory gains on Recall and Induction do not necessarily generalize to competing-evidence Transfer, whereas PRefine provides gains when preference inference must also support an argument absent from the history.

7.2 Effectiveness and Efficiency of PRefine

Verification and Memory Quality

Table 4 compares generation-only, unverified refinement, and full PRefine across KK.
Generation alone fails to improve on Full-History Prompting, and unverified refinement lowers context-free O-F1 from 21.51 to 13.43 at K=5K=5.
Verifier-guided refinement instead reaches 57.94, demonstrating the contribution of verification beyond repeated refinement.
Increasing the budget to K=10K=10 provides no further gain.

Table 12 shows how the verifier revises unsupported or over-specific hypotheses into evidence-grounded, reusable preference constraints.
To analyze whether these abstractions retain preferences relevant to tool calling, we conduct a manual post hoc evaluation (Table 17).
Final hypotheses capture at least one annotated preference in 82.8% of histories (380/459), indicating PRefine’s hypotheses retain relevant preference information.
Aligned histories achieve higher O-F1 than contradictory histories in both query settings (+10.78 points context-free; +3.47 context-guided), suggesting an association between preference fidelity and tool-calling accuracy.
Appendix D.5 details both analyses.

Token Efficiency

Table 15 compares memory construction costs per session.
Including the full generate–verify–refine loop,
PRefine uses 8,856 tokens per session, 6.0% fewer than Mem0 and 67.5% fewer than A-MEM.
Although RAG and LangMem remain cheaper to construct,
PRefine achieves higher O-F1.
At inference, its compact preference hypothesis adds only 26 memory tokens per instance versus 97–1,083 for the retrieval and memory baselines, with a nearly constant memory footprint across sessions
(Appendix D.4).

Generalization to Unseen Schemas

PRefine’s hypotheses express preferences as behavioral criteria that can be applied through the current API schema.
To test whether these hypotheses support argument selection in new APIs, we introduce seven functions unseen during
memory construction only at inference, keeping the original histories and memories unchanged.
Table 5
shows that PRefine achieves the highest context-guided/context-free O-F1.
These results suggest that PRefine captures reusable preferences that apply to new APIs without rebuilding the memory (Appendix D.6).

8 Conclusion

We propose MPT, a benchmark for multi-session personalized tool calling that evaluates latent preference reasoning under varying evidence interference.
We further propose PRefine, a test-time memory method that maintains a verified latent preference hypothesis.
Across five LLMs, PRefine outperforms all baselines, with gains driven by verification.
Its hypotheses also guide argument selection in unseen APIs without rebuilding memory.
These findings support verified preference abstractions as reusable memory for personalization.

Limitations

This work focuses on a controlled setting for evaluating latent preference reasoning in personalized tool-calling.
In particular, we study whether an agent can infer reusable preference constraints from interaction history and apply them to under-specified API parameters under a schema-bounded action space.

A history may reflect several preferences, but each MPT query targets only one, which persists across sessions (C3) and keeps the gold argument unambiguous.
Preferences that shift over time or combine within a query are a natural extension.
The five preferences in Table 2 can be extended by adding realization mappings, and inferred preferences transfer to seven unseen functions (§7.2).
PRefine keeps its memory as free text, so a hypothesis can state several constraints, though selecting among them per query is not evaluated.
Finally, users are composed from existing corpora, since a latent preference must be known to be scored.

Ethics Statement

MPT is derived from three publicly released corpora.
SGD is distributed under CC BY-SA 4.0 and DuRecDial 2.0 under CC BY-NC-SA 4.0.
We release the corresponding portions of MPT under terms compatible with each.
HomeBench is released publicly for research use without a license file, so for that source we distribute our annotations and augmented turns with a script that reconstructs the instances from the original release, rather than redistributing the underlying data.
All three sources consist of synthetic or crowdsourced dialogues and contain no personally identifying information.
The user identities in MPT are constructed and do not correspond to real individuals.

The preference grouping was validated in a survey of 19 participants recruited through an open call, who judged schema values from the publicly released corpora and participated voluntarily without compensation; no personal information was collected.

Beyond the benchmark, inferring preferences a user never stated is a form of user profiling.
A deployed system could apply such inferences in unintended ways, for example to steer choices rather than to complete an underspecified request.
PRefine keeps its memory as a single natural-language hypothesis that a user can inspect and correct, and we recommend exposing it this way in deployment.

A.2 Per-Source Preprocessing

We describe the preprocessing applied to each of the three adopted corpora; the selection procedure is deferred to Appendix B.1.

SGD

SGD is used relabel-only: dialogues and argument values are unchanged, and each dialogue enters our pipeline as a single session.
Per-session calls are accumulated by merging partial argument states into executed calls; when merging yields conflicting values for the same argument, the unsupported values are quarantined into a drop list, keeping gold values unique.
We keep the original schema definitions and apply schema normalization following prior work (Moghe et al., 2024), enabling coherent multi-session histories while remaining compatible with the tool schemas.
See Appendix A.7 for the full schema.
How SGD sessions are grouped into synthetic users, and how users from all three sources are composed into histories, is described in Appendix A.4.

DuRecDial 2.0

Histories are excerpted from the original dialogues rather than templated.
Speaker roles, absent from the release, are restored deterministically from greeting conventions and turn parity.
The four recommendation goal types and weather lookups are mapped to API calls (GetMovies, GetMusic, GetFood, GetRestaurants, GetWeather), reusing SGD argument names where they already exist (cast→\tostarring; title→\tomovie_name/song_name).
Because the benchmark requires preferences to be latent (§3), we discard 469 dialogues in which an utterance causally states the preference or leaks a rejection, and 2 personas whose accept-then-reject behavior is inconsistent; deferrals (“another time”) are replaced with acceptance, and explicit rejections keep the exchange but contribute no call, preserving negative evidence.
In re-recommendation chains, non-final same-function calls are kept or dropped according to the user’s recorded reaction (e.g., “I’ve watched it” drops the call; an accepted replay keeps it; 388 calls dropped).
This yields 705 single-celebrity personas whose preference rests only on accepted items’ argument values.

A.3 Preference Realization

The mapping in Table 2 distinguishes low_cost from high_cost, omitting an intermediate tier because the intermediate signals in SGD (e.g., price_range=‘‘moderate’’) are too sparse and ambiguous to serve as reliable preference evidence.
We retain solo_usage but exclude its counterpart group_usage: as noted in our human study (Appendix B.2), parties of size 2 are ambiguous between couple and group travel, making group_usage an unreliable preference signal.
Because each preference is defined at the level of a behavioral constraint rather than a specific parameter name, the mapping generalizes to APIs beyond SGD:
any new function exposing cost- or party-size-related arguments realizes the same preference without redefinition, as verified in Appendix D.6.

A.4 History Composition

Histories are composed from the preprocessed sessions of the three sources in two stages.
Session grouping differs by source: DuRecDial 2.0 identifies the seeker across dialogues, so each seeker’s dialogues form one user’s sessions, and HomeBench keeps each persona’s parsed instructions together, whereas SGD provides no user identifier and its sessions are grouped by the procedure below.
Sessions from groups outside the target’s pool serve as competing or unrelated evidence for that target (§4.2 (iii)), and a history may combine supporting groups for several preferences, subject to the constraint that the resulting history spans at least two functions.

In the first stage, we form for each preference a pool of user groups whose preference-relevant arguments consistently realize that preference, and draw the supporting sessions of a history from a single pool; the persona-level filters behind each pool are given in Appendix A.2.
In the second stage, for a preference with an opposing side, we merge in the sessions of a group drawn from the opposing pool, so that the history carries evidence for both and the agent must decide which one the user holds.
For low_cost the opposing preference is high_cost and vice versa; for prefers_star it is a second celebrity identity.
Merging follows strict plurality: the target side must carry strictly more supporting observations than the opposing side, and combinations in which the two sides tie are discarded.
This yields 46 contested groups from SGD and 115 from DuRecDial 2.0.
eco admits no such construction, since it registers a single value (eco_mode="on") and no opposing value exists in the schema; for solo_usage, the candidate counterpart group_usage is excluded from the benchmark for the reason given in Appendix B.2.

Groups that realize none of the preferences a history targets are also admitted, as distractors, drawn only from users whose preference, if any, is a different one.
Distractor sessions may still touch arguments of the target preference incidentally; such observations are a property of the source dialogues rather than injected noise, and they surface as interference (§7.1).
What we verify exhaustively over the composed set is that no preference other than the intended one is supported by repeated observations on both sides.
Within a history, each group’s internal session order is preserved and groups are interleaved uniformly at random; each contested history is released in two arrangements, one placing the minority side’s sessions before the majority’s, and one shuffle verified not to reproduce it.

A.5 Gold-Standard Annotation

Fixing the Gold Argument

How the gold value is fixed follows the reasoning type.
For Recall, the target argument itself carries a value that recurs in the accumulated calls, and that recurring value is the gold.
For Induction and Transfer, the gold is the value that the mapping in Appendix A.3 assigns to the target argument, given the preference the history’s cross-function evidence establishes.
In Transfer the target argument carries no value anywhere in the history, so the mapping is the only route to a gold value.

Because queries and histories are drawn from separate pools and combined afterwards, a query may target an argument whose preference the paired history never establishes.
The gold then leaves that argument unspecified: with no behavioral evidence to generalize from, abstaining is the correct response and filling it is penalized.
These instances are counted under Other in Table 8.

Uniqueness of the Gold

The procedure above returns exactly one gold for every instance.
For Recall, arguments in which two different values both recur are excluded from querying, so no instance admits two candidate golds.
For Induction and Transfer, each history supports exactly one preference from each opposing pair: in contested histories both sides recur, but strict plurality (§4.2) leaves one side with strictly more supporting observations and discards ties, so the mapping still returns a single value for any target argument that preference can fill.
Observations that set such an argument to a competing value are not removed;
they remain in the history and are accounted for by the interference score (§7.1) rather than by changing the gold,
so difficulty varies without the answer becoming ambiguous.
Instances whose gold omits the argument are likewise unambiguous: the paired history establishes no preference that the argument could express, so no value is admissible.

A.6 Dataset Statistics and Instance Composition

Table 7 summarizes the scale of MPT across two dimensions: interaction history and reasoning types.
Each multi-session dialogue interleaves sessions drawn from up to three source corpora into a single interaction history, with an average of 15.2 sessions per dialogue and 13.7 turns per session.
This scale reflects the practical challenge of long-horizon preference modeling: with over 95k turns across 459 dialogues, the benchmark requires models to aggregate evidence over much longer contexts than typical single-session tool-calling benchmarks.
Histories also vary in how many preferences they support: 164 (35.7%) support two to four distinct preferences, as in Figure 6, and yield 2,432 instances (51.8%); competing values of the same preference, such as two celebrities for prefers_star, are not counted as distinct.

Table 8 breaks the 4,695 instances down by reasoning type and by the preference the target argument expresses.
Every preference supports all three reasoning types, and Transfer is not carried by a single one: its largest share targets low_cost arguments (590), followed by prefers_star (372).
Recall additionally targets recurring idiosyncratic arguments that express none of the five preferences (e.g., airlines, temperature), for which the recurring value itself is the gold (Appendix A.5).

Appendix B Design Validation

B.1 Excluded Corpora

Of the 23 dialogue corpora we reviewed, three were adopted (§4.1); Table 10 reports the full audit behind that selection.
All judgments were made against the released data files rather than paper descriptions: for each candidate we downloaded the distributed release, enumerated its record schema, and computed the cited statistics directly from the data.
Criteria are checked in the order listed, and once a corpus fails one, the remaining criteria are not assessed.
A partial mark indicates a criterion that is satisfiable at additional preprocessing cost and is not by itself disqualifying.
Release terms are recorded for reference rather than used as a screening criterion.
Per-user sessions may be obtained through either of two routes: grouping real interactions by a user identifier (verifying that the identifier is global rather than dialogue-local), or composing source units, dialogues or single commands, into synthetic histories, which presupposes a consistent schema and argument values recorded within the units.
For the preference conditions we enumerate the complete argument inventory, classify each argument as what- or how-type (§3), and test whether any single preference has how-type surfaces in two or more functions (C1) whose values vary across users (C2).
MultiWOZ comes closest, failing no requirement outright, and is excluded as strictly dominated by SGD: its functions are a subset of SGD’s, and its single cross-function preference (price_range) is already covered.

B.2 Human Validation of Preference Realization

To validate that our preference realization reflects broadly shared behavioral intuitions, we conducted a human annotation study with 19 annotators.

Setup

Annotators were presented with argument values drawn from the API schemas in MPT, and asked to classify each value into one of three categories:
low_cost, high_cost, or Neither for the cost pair, and solo_usage, group_usage, or Neither for the party-size pair.
For example, given price_range=‘‘Cheap’’ in GetRestaurants and free_entry=True in GetTravel, annotators judged whether each value realizes low_cost.
The study covered 27 argument values across 12 functions for the cost pair, and the counts 1 to 4 for the party-size pair.
The study targets these two pairs because each is realized through heterogeneous arguments (price_range, free_entry, car_type for the former; passengers, number_of_tickets, number_of_seats for the latter), whereas prefers_star and eco follow from the argument value itself and admit no comparable judgment.

Results

Annotators agreed with our realization in 89.7% of cases for the cost pair and 97.4% for the party-size pair.
Inter-annotator agreement, measured by Fleiss’ κ\kappa Fleiss (1971), was κ=0.701\kappa=0.701 (substantial) for cost and κ=0.880\kappa=0.880 (almost perfect) for party size, following the interpretation scale of Landis and Koch (1977).
All 19 annotators confirmed that the names solo_usage and group_usage clearly represent the intended meaning, while 16 of 19 (84%) confirmed the same for low_cost and high_cost.

Discussion

The slightly lower agreement on the cost pair (κ=0.701\kappa=0.701 vs. 0.8800.880) likely reflects the broader semantic range of cost-related signals: whereas party size is unambiguous, cost-conscious behavior is realized through heterogeneous argument types, price_range, average_star, free_entry, car_type, and others, leaving more room for individual interpretation.
Nevertheless, substantial agreement on both pairs confirms that our preferences are not arbitrary schema choices, but reflect intuitions broadly shared across annotators, supporting their use as a task-grounded evaluation scaffold.

Several annotators noted that parties of 2 may reflect couple travel rather than group travel, suggesting ambiguity in the boundary between solo_usage and group_usage.
Given this concern, we conservatively retain only solo_usage, excluding group_usage from the benchmark to avoid introducing ambiguous preference evidence.

C.2 RAG

We implement an utterance-level RAG baseline:
(i) embed every utterance in the full dialogue history with OpenAI text-embedding-3-small and index them with user_id,
(ii) at test time, embed the current query and retrieve the top-5 utterances by cosine similarity,
(iii) append the retrieved utterances to the prompt for inference.

C.3 Mem0

We use Mem0 (Chhikara et al., 2025) as an off-the-shelf long-term memory system for our agents. Mem0 maintains a persistent, user-scoped memory store and exposes simple APIs for writing and retrieving memories.

(i) Mem0 converts the interaction history into compact memory snippets using its memory writer (GPT-OSS-20B),
(ii) at test time, Mem0 retrieves a small set of relevant memory snippets conditioned on the current query,
(iii) we append the retrieved snippets to the prompt for tool-calling inference.

Concretely, we integrate Mem0 via its cloud REST API and official Python client (MemoryClient):
we use add to log user–assistant dialog turns as memories keyed by user_id,
and search to retrieve the top-5 semantically relevant memories for a given query, which are then appended to the prompt at inference time.

C.4 LangMem

We use LangMem (LangChain AI, 2025) as an
agentic memory SDK:
(i) its memory writer (GPT-OSS-20B) generates semantic, episodic, and procedural memory snippets and
maintains a structured user profile, extracting and updating user information and preferences across sessions;
(ii) we embed the memory contents and current query with OpenAI text-embedding-3-small and retrieve the top-5 memory snippets by cosine similarity;
(iii) we append the retrieved contents to the prompt
for tool-calling inference.

C.5 A-MEM

A-MEM (i) converts each user–assistant interaction into a structured note containing the original content, keywords, tags, and a contextual description;
(ii) links semantically related notes and selectively updates existing note metadata as new notes are added;
and (iii) retrieves the top-5 notes by cosine similarity and appends them to the prompt for tool-calling inference.

C.6 PRefine

We implement PRefine as a test-time memory method that maintains a single textual preference hypothesis rather than a store of retrievable entries:
(i) after each session, a generator proposes a candidate hypothesis from the previous memory, the session, and its executed tool calls;
(ii) a verifier judges the candidate against the accumulated history under the four criteria of §5.1, and a refiner revises it under the returned feedback for up to K=5K=5 rounds;
(iii) at test time, the accepted hypothesis is appended to the prompt and inference is run for tool calling.

Concretely, the generator, verifier, and refiner are three prompted roles served by the same memory constructor LLM, with templates given in Appendix E.
Two implementation choices distinguish PRefine from the baselines above.
First, memory is updated once per session rather than once per user–assistant turn, so the verifier always scores a candidate against the accumulated record ℋt+1\mathcal{H}_{t+1} rather than an isolated exchange.
Second, the memory holds a single hypothesis that is overwritten on each accepted update, so neither an embedding model nor a top-kk retrieval step is involved; the entire memory is placed in the inference prompt, which is otherwise identical to the one shared by the retrieval- and memory-based methods.

Figure 7 traces the generate-verify-refine loop of Algorithm 1 on the running example of Figure 1.
At session s7s_{7}, the generator proposes prefers compact cars from the memory M6M_{6} and the executed call a7a_{7}.
The verifier rejects it not because the resulting tool call fails, but because the hypothesis rests on a single session and restates an argument value rather than abstracting over it.
The refined candidate, prefers budget-friendly options, is accepted once it is found consistent with the calls executed across s1s_{1} to s7s_{7}.
This is where the verification signal in PRefine differs from prior self-refinement methods (Madaan et al., 2023; Shinn et al., 2023), which score a candidate against task outcomes.
Here the candidate is scored against the accumulated behavioral record ℋt+1\mathcal{H}_{t+1}, so what survives is a cross-session regularity rather than a locally successful edit.
The memory also revises rather than accumulates: M2M_{2} holds regularly explores local spots, which later evidence overwrites instead of appending to.
At inference, M7M_{7} supplies flight_class=‘‘Economy’’ for GetFlights, a function the history never instantiates.

D.3 Weight Design and Sensitivity of Evidence Interference

Post-hoc Empirical Concordance.

The ordering β>1>γ>0\beta>1>\gamma>0 constrains the intended relation among evidence types
but does not uniquely identify the reference weights adopted in §7.1.
We therefore examine whether their qualitative ordering and approximate scale are consistent with observed performance,
using the descriptive regressions in Figure 8.
This analysis is conducted only under Full-History Prompting;
it is not fitted to PRefine or any memory method,
so the stratification in §7.1 concern methods held out from it.

We report each regression coefficient on a 0.10.1-share scale. Thus, b¯x\bar{b}_{x} denotes the fitted percentage-point difference in IMP-F1 associated with an absolute 0.10.1 increase in the share of component xx.
For example, b¯C=−22.996\bar{b}_{C}=-22.996: raising the competing-evidence share from 0.20.2 to 0.30.3 is associated with a fitted 22.99622.996-point drop in IMP-F1.

For each component, we first average the two query-setting-specific coefficients within each reasoning type, producing the three thin lines in Figure 8.
The thick line is their macro average and provides a summary coefficient for comparison with the reference weights.

Hypothesis Alignment Evaluation

We manually assess the final accepted hypothesis for each of the 459 histories against its annotated target preference and definition.
A hypothesis is labeled aligned if it semantically captures the target preference, allowing equivalent formulations (e.g., “prefers budget-friendly options” for low_cost), and contradictory if it expresses an incompatible preference.
For histories that support multiple preferences, a hypothesis is labeled aligned if it captures at least one of them.
In the example of Figure 10, a single hypothesis covers both preferences the history supports, low-cost option and a favored celebrity.
Figure 10 shows the interface used for this manual evaluation. It presents the final hypothesis alongside the annotated target preferences and their corresponding tool-call evidence for semantic comparison.

Table 17 reports the history-level alignment distribution and downstream performance in both query settings.
We group evaluation instances by the alignment label of their source history and compute O-F1 separately for each inference model within each group and query setting.
Aligned histories achieve higher mean O-F1 in both settings,
with a larger gap on context-free queries,
where current-session context is omitted.

Evaluation Setup

To test whether a memory carries over to functions it was never built from,
we introduce seven functions that appear in no MPT history:
GetCampground, GetCityTour, GetCookingClass, GetFitnessClass, GetSkiPass, GetParkingSpot, and GetThemePark.
Their parameters realize the same preferences as in Table 2 under different parameter names and argument values
(e.g., site_type=‘‘Tent site’’ in GetCampground realizes low_cost, and number_of_guests=1 realizes solo_usage).
Memories are constructed from the original histories without modification, so no memory constructor observes these functions.
The extended mappings define gold arguments for evaluation only and are not supplied to the models.
Tables 18 and 19 list their parameters and preference realizations.

Results

Table 5 reports O-F1 under the extended schema. PRefine achieves the highest scores across both query settings and inference models.
With Qwen3-8B, it exceeds the strongest baseline by 2.71 points on context-free queries and 10.29 points on context-guided queries.
With GPT-OSS-20B, the corresponding margins are 0.72 and 3.29 points.
These results support grounding preference hypotheses to previously unseen API parameters and arguments while retaining the same underlying preference semantics.

Appendix E Prompt Design

We provide the prompt templates used in our experiments.
All templates are reproduced as executed and retain the implementation-level names domain, slot, and value, corresponding to function, parameter, and argument in our terminology.

Figure 13 presents the PRefine modules.
The generator proposes a latent preference hypothesis as an abstract, decision-level constraint, and the refiner revises a rejected candidate under verifier feedback.
The verifier judges each candidate against the four criteria of §5.1, using only the accumulated dialogue and tool calls as evidence; no gold argument or task outcome enters the loop.
