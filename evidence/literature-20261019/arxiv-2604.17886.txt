Abstract
Users often omit essential details in their re-
quests to LLM-based agents, resulting in under-
specified inputs for tool use. This poses a fun-
damental challenge for tool-augmented agents,
as API execution typically requires complete
arguments, highlighting the need for person-
alized tool calling. To study this problem, we
present Multi-Session Personalized Tool Call-
ing (MPT), a benchmark comprising 4,695 in-
stances over 459 multi-session interaction his-
tories that cover three challenges: Preference
Recall, Induction, and Transfer. We further pro-
pose PREFINE, a test-time memory method
that maintains the user’s latent preference as
a textual hypothesis revised through a generate–
verify–refine loop. Across five LLMs, existing
memory systems often fail to improve on full-
history prompting; PREFINE outperforms all
baselines and alone surpasses it on Preference
Transfer. These results indicate that memory
for personalized agents must abstract behavior
into preferences, rather than simply archive it.

Introduction
LLM-based agents increasingly rely on external
tools to perform complex tasks such as deep re-
search (Xu and Peng, 2025) and computer use
(Sager et al., 2026). These tools, typically realized
as parameterized functions, are invoked with ar-
guments often missing from user requests; e.g., a
query as simple as “Book a flight for my trip” speci-
fies neither the origin, the destination, nor the price.
A direct solution to such underspecification is to
ask the user clarifying questions about the missing
arguments. A more proactive agent, however, could
infer them from user preferences with minimal in-
tervention, akin to a recommender system—the
core idea behind personalized tool calling (Moghe
et al., 2024; Xu et al., 2025).
* Equal contribution. † Corresponding author.
Prior work in this direction has largely as-
sumed that user preferences are provided explicitly.
Standing-instruction and profile-based approaches
(Moghe et al., 2024; Huang et al., 2025) inject cu-
rated preferences into the input, while retrieval- and
memory-based agents (Lewis et al., 2020; Chhikara
et al., 2025; LangChain AI, 2025; Xu et al., 2026)
assume the target arguments have appeared earlier
in the context. In both cases, personalized tool call-
ing reduces to a search problem. More challenging
benchmarks merely make the preference harder
to locate or apply: it may be indirectly phrased,
context-dependent, or later superseded (Zhao et al.,
2025; Kim et al., 2025; Jiang et al., 2025a,b); the
task nevertheless remains one of search.
In this work, we argue that user preferences are,
in reality, latent, and thus should be inferred rather
than retrieved (see Figure 1). In other words, the
cues are mostly implicit in the user’s past tool calls.
Consider a user who books a cheap restaurant, tours
a free attraction, and rents a compact car, each
choice triggering a distinct tool with no shared
parameters. To infer that this user favors affordable
options, a preference never stated, the agent must
generalize across these seemingly unrelated calls.
To evaluate this capability in LLM-based agents,
we propose Multi-Session Personalized Tool Call-
ing (MPT), a benchmark of 4,695 instances over
459 multi-session histories drawn from three cor-
pora. MPT comprises three scenarios that differ
in how much evidence prior sessions provide for
the target argument. In (1) Preference Recall, the
argument is hinted at multiple times, as in exist-
ing benchmarks, so direct reuse is sufficient; in
(2) Preference Induction, a single explicit mention
must be corroborated by cross-function evidence;
and in (3) Preference Transfer, the preference must
be applied to an argument absent from the history.
Alongside MPT, we introduce PREFINE, a test-
time memory method that maintains the estimate
of the user’s preference as a textual hypothesis,

Across five LLMs and six methods, agents
reliably recover explicit arguments but struggle
with omitted preference-sensitive ones, and perfor-
mance degrades from Recall through Induction to
Transfer. Retrieval- and organization-based mem-
ories (RAG, Mem0, LangMem) even fall below
full-history prompting, indicating that surfacing
past records is not enough unless the evidence is
abstracted into a preference. PREFINE, in contrast,
outperforms all baselines, and is the only method to
exceed full-history prompting on Transfer without
session context. Its advantage also holds as compet-
ing and unrelated observations accumulate in his-
tory, a difficulty we quantify with a new evidence
interference score: all methods degrade under high
interference, but PREFINE remains the best. Abla-
tions on PREFINE further show that verification,
not repeated refinement, drives these gains.

Problem Definition
Tool Calling
Let S = {s1, . . . , sT } denote a se-
quence of past dialogue sessions between a single
user and an AI agent, where each session st con-
sists of a multi-turn dialogue in which the agent
may execute API calls. The agent operates over a
tool schema F, a set of available functions, where
each f ∈F is a tuple (id, K) of an identifier and
a set of parameters. Tool calling is then the task
of producing an API call a = (id, {(k, v)}), i.e.,
selecting a function and assigning an appropriate
argument (value) v to each parameter (key) k ∈K,
e.g., GetFlights(flight_class=“Economy”).
Let A denote the list of all API calls executed
in S. We define the user’s interaction history H =
(S, A). At timestep T + 1, the agent observes a
query q, consisting of the turns of a new session
sT+1 up to the API decision point, and must pro-
duce the corresponding API call aT+1. In person-
alized tool calling, preference-sensitive arguments
unspecified in q must be inferred by modeling the
user’s latent preference from H.
Latent Preference Modeling
How the missing
arguments are filled depends on a latent prefer-
ence p, a user-level variable not directly observed.
We study preferences that satisfy three conditions:
(C1) p can be instantiated as API arguments across
multiple functions, so that it can transfer between
them (cross-function instantiation); (C2) those
arguments admit different preferred values across
users, such that no universal default value is suffi-
cient (variation across users); and (C3) p persists
across a user’s sessions rather than varying with
each request (persistence within a user).
For instance, a user who prefers low_cost
may choose price_range=cheap when search-
ing restaurants and flight_class=Economy when
booking flights, without ever stating the preference.
We assume that calls supporting p strictly outnum-
ber those conflicting with it (§4.2). The agent, how-
ever, is never told which arguments express p and
must infer it across functions.

Benchmark Construction: MPT
Building on §3, we present Multi-Session Person-
alized Tool-Calling (MPT),1 a benchmark that
evaluates whether an agent can infer the dominant
preference from a history H and apply it to a query
q with unspecified preference-sensitive arguments.
We construct separate pools of histories (§4.2) and
queries (§4.3), then pair them into final instances
(§4.4). Figure 2 illustrates the overall process.
4.1
Preprocessing
Source Corpora
We reviewed 23 dialogue cor-
pora against multi-session structure, API calls with
arguments, and satisfaction of C1–C3 (§3), se-
lecting SGD (Rastogi et al., 2020), the English
portion of DuRecDial 2.0 (Liu et al., 2021), and
HomeBench (Li et al., 2025b). See Appendix B.1
for screening and preprocessing details.
Preference Realization
We group preference-
relevant arguments across functions into latent
preferences. For example, price_range=“cheap”
in GetRestaurants and free_entry=True in
GetTravel both express low_cost.2 MPT defines
each preference over multiple functions rather than
a single parameter or tool (Table 1). This require-
ment (C1) restricts the eligible preferences in the
source corpora. The resulting five latent prefer-
ences nevertheless cover 18 realizations over 16

4.2
History Composition
While preference realization identifies which ar-
guments can express a preference, no single call
suffices to establish it. We thus build multi-session
histories H, in three steps, from which a preference
emerges as a recurring behavioral pattern. We refer
readers to Appendix A.4 for further details.
(i) Composition of Users
In our setup, a multi-
session history presupposes a user behind all of its
sessions. We obtain such users by grouping dia-
logues by seeker in DuRecDial 2.0, splitting each
multi-intent instruction in HomeBench into single-
intent sessions, and assembling synthetic ones from
SGD sessions, since SGD lacks user identifiers.
(ii) Assignment of Users to Preferences
To
align an interaction history with a preference (e.g.,
a user favors affordable options), we label each user
from the first step with the preference that their API
calls demonstrate. Specifically, a user is assigned
to a preference p if their calls consistently express
p across at least two functions, following C1 (cross-
function instantiation) in §3. The sessions of such
users then serve as supporting evidence for p.
(iii) Injection of Competing and Unrelated Evi-
dence
To reflect a more realistic setting, we aug-
ment the supporting histories from the previous
steps with competing sessions expressing opposing
preferences (e.g., high_cost vs. low_cost) and
sessions unrelated to the target preference. To keep
the target preference dominant (C3 in §3), support-
ing calls must strictly outnumber competing ones
(strict plurality; ties excluded); 46.9% of merged
histories contain competing calls. Added sessions
are randomly interleaved while preserving the orig-
inal order within each source. The counts of sup-
porting, competing, and unrelated observations are
later used to compute the interference score (§7.1).
4.3
Query Construction
For each function f, we manually create query tem-
plates that leave one or more arguments unspecified.
Context-guided queries (qcg) retain initial turns of
the current session, providing direct clues for some
arguments, while context-free queries (qcf) omit

4.4
Instantiation
An MPT instance pairs a query q with a history
H. Its reasoning type depends on how often H
instantiates the target parameter left unspecified by
q.3 Specifically, we consider three types:
Preference Recall
The target argument v recurs
in H, allowing direct reuse. This setting supports
comparison with retrieval-oriented benchmarks and
provides a reference for the two harder types.
Preference Induction
The target argument v oc-
curs only once in H. Since a single occurrence may
reflect either a persistent preference or an incidental
choice, the agent must corroborate it with evidence
of the same preference elsewhere in H.
Preference Transfer
The target argument v
never occurs in H, although its function may. Re-
solving it requires generalization: the agent must
infer p from its realizations in other functions and
apply it to an argument without direct evidence.
4.5
Benchmark Statistics
MPT comprises 4,695 instances over 459 multi-
session dialogues, totaling 6,961 sessions and
95,523 turns (on average, 15.2 sessions per dia-
logue and 13.7 turns per session). It includes 1,375
Recall, 1,944 Induction, and 1,376 Transfer in-
stances. Of the dialogues, 164 (35.7%) support
two to four distinct preferences and yield 2,432
instances (51.8%; Table 7 in Appendix A.6).

PREFINE
We further propose PREFINE, a test-
time memory-based method that estimates the la-
tent preference p with a revisable memory MT :
MT = ψPREFINE(S, A).
Algorithm 1 summarizes how PREFINE updates
its preference memory. After each session st+1
(t = 0, . . . , T −1), a generator proposes a prefer-
ence hypothesis η from the previous memory Mt,
the session st+1, and its executed tool calls at+1. A
verifier evaluates η against the accumulated history
Ht+1 = (S≤t+1, A≤t+1) for (1) evidence support,
(2) abstraction quality, (3) actionability, and (4)
temporal consistency.4 If accepted, the hypothesis
is updated as Mt+1. Otherwise, the verifier returns
feedback ϕ that is used to refine the candidate. A
single PREFINE hypothesis can encode multiple
preference constraints, as illustrated in Figure 10.
This generate–verify–refine procedure follows
prior self-refinement methods (Madaan et al., 2023;
Shinn et al., 2023) in form, but differs in what the
verifier scores against. Rather than a task outcome,
the target is the accumulated behavioral record
Ht+1, and a hypothesis survives only if it holds as
a cross-session regularity. We allow up to K = 5
refinement steps (ablation in §7.2).

5.2
Metrics
Context-guided queries require both extracting ex-
plicitly stated arguments and completing omitted
preference-sensitive arguments. We report Explicit-
F1 (EXP-F1) for the first subproblem and Implicit-
F1 (IMP-F1) for the second. Overall-F1 (O-F1)
evaluates the complete tool call over both. For
context-free queries (qcf), with no explicitly stated
arguments, O-F1 reduces to IMP-F1 (no EXP-F1).

Experimental Results
6.1
Overall Results
Table 3 shows that PREFINE outperforms all base-
lines on both query types, with O-F1 scores of
73.57 (context-guided) and 60.55 (context-free).
On qcf, RAG, Mem0, and LangMem underperform
Full-History Prompting (35.29) in the five-model
macro average, whereas A-MEM reaches 44.33.
PREFINE’s further improvement to 60.55 suggests
that preference-level abstraction offers benefits be-
yond retrieval and memory organization.
The largest distinction emerges on context-free
Preference Transfer: PREFINE is the only method
to outperform Full-History Prompting, while even
A-MEM falls below it. This suggests that verified
preference hypotheses are particularly valuable for
cross-function generalization.

Results by Metric and Reasoning Type

7.1
Evidence Interference
Definition
To test the robustness of PREFINE’s
advantage to evidence composition, we define the
Evidence Interference Score (I), a post-hoc diag-
nostic index for ranking instances by difficulty.
Given a preference p, we classify each observa-
tion in H as supporting (R), competing (C), or
unrelated (U): a supporting observation contains a
parameter–argument pair mapped to p; a competing
observation contains preference-relevant evidence
that is inconsistent with, or offers an alternative
to, p; and an unrelated observation contains no pa-
rameter tied to p. Let R, C, and U denote their
respective counts. We then define,
I =
βC + γU
R + βC + γU .
(2)
Supporting observations serve as the unit-weight
baseline, and we impose the qualitative ordering
β > 1 > γ > 0. Competing evidence is weighted
more heavily, as it presents an inconsistent or alter-
native preference signal, while unrelated evidence
receives a smaller nonzero value since it primar-
ily increases the filtering burden. We use β = 4
and γ = 0.25 as a reference parameterization (vali-
dation and sensitivity analyses in Appendix D.3).
A higher I indicates a greater weighted burden of
potentially interfering evidence.

Focus on Competing Evidence
Every method
drops when competing evidence is present (C > 0;
Figure 4). Under C > 0, A-MEM is the strongest
memory baseline on Recall and Induction but falls
below Full-History Prompting on Transfer (8.58 vs.
12.29 IMP-F1), whereas PREFINE reaches 17.38.
Thus, memory gains on Recall and Induction do
not necessarily generalize to competing-evidence
Transfer, whereas PREFINE provides gains when
preference inference must also support an argument
absent from the history.
7.2
Effectiveness and Efficiency of PREFINE
Verification and Memory Quality
Table 4 com-
pares generation-only, unverified refinement, and
full PREFINE across K. Generation alone fails to
improve on Full-History Prompting, and unverified
refinement lowers context-free O-F1 from 21.51 to
13.43 at K = 5. Verifier-guided refinement instead
reaches 57.94, demonstrating the contribution of
verification beyond repeated refinement. Increasing
the budget to K = 10 provides no further gain.
Table 12 shows how the verifier revises unsup-
ported or over-specific hypotheses into evidence-
grounded, reusable preference constraints. To ana-
lyze whether these abstractions retain preferences
relevant to tool calling, we conduct a manual post
hoc evaluation (Table 17). Final hypotheses capture
at least one annotated preference in 82.8% of his-
tories (380/459), indicating PREFINE’s hypotheses
retain relevant preference information. Aligned his-
tories achieve higher O-F1 than contradictory his-
tories in both query settings (+10.78 points context-
free; +3.47 context-guided), suggesting an associ-
ation between preference fidelity and tool-calling
accuracy. Appendix D.5 details both analyses.
Token Efficiency
Table 15 compares memory
construction costs per session. Including the full
generate–verify–refine loop, PREFINE uses 8,856
tokens per session, 6.0% fewer than Mem0 and
67.5% fewer than A-MEM. Although RAG and
LangMem remain cheaper to construct, PREFINE
achieves higher O-F1. At inference, its compact
preference hypothesis adds only 26 memory tokens
per instance versus 97–1,083 for the retrieval and
memory baselines, with a nearly constant memory
footprint across sessions (Appendix D.4).
Generalization to Unseen Schemas
PREFINE’s
hypotheses express preferences as behavioral crite-
ria that can be applied through the current API
schema. To test whether these hypotheses sup-
port argument selection in new APIs, we introduce
seven functions unseen during memory construc-
tion only at inference, keeping the original histories
and memories unchanged. Table 5 shows that PRE-
FINE achieves the highest context-guided/context-
free O-F1. These results suggest that PREFINE cap-
tures reusable preferences that apply to new APIs
without rebuilding the memory (Appendix D.6).
8
Conclusion
We propose MPT, a benchmark for multi-session
personalized tool calling that evaluates latent pref-
8

=== [page 9] ===
erence reasoning under varying evidence interfer-
ence. We further propose PREFINE, a test-time
memory method that maintains a verified latent
preference hypothesis. Across five LLMs, PRE-
FINE outperforms all baselines, with gains driven
by verification. Its hypotheses also guide argument
selection in unseen APIs without rebuilding mem-
ory. These findings support verified preference ab-
stractions as reusable memory for personalization.
Limitations
This work focuses on a controlled setting for eval-
uating latent preference reasoning in personalized
tool-calling. In particular, we study whether an
agent can infer reusable preference constraints
from interaction history and apply them to under-
specified API parameters under a schema-bounded
action space.
A history may reflect several preferences, but
each MPT query targets only one, which persists
across sessions (C3) and keeps the gold argument
unambiguous. Preferences that shift over time or
combine within a query are a natural extension.
The five preferences in Table 2 can be extended
by adding realization mappings, and inferred pref-
erences transfer to seven unseen functions (§7.2).
PREFINE keeps its memory as free text, so a hy-
pothesis can state several constraints, though select-
ing among them per query is not evaluated. Finally,
users are composed from existing corpora, since a
latent preference must be known to be scored.
Ethics Statement
MPT is derived from three publicly released cor-
pora. SGD is distributed under CC BY-SA 4.0 and
DuRecDial 2.0 under CC BY-NC-SA 4.0. We re-
lease the corresponding portions of MPT under
terms compatible with each. HomeBench is re-
leased publicly for research use without a license
file, so for that source we distribute our annotations
and augmented turns with a script that reconstructs
the instances from the original release, rather than
redistributing the underlying data. All three sources
consist of synthetic or crowdsourced dialogues and
contain no personally identifying information. The
user identities in MPT are constructed and do not
correspond to real individuals.
The preference grouping was validated in a sur-
vey of 19 participants recruited through an open
call, who judged schema values from the publicly
released corpora and participated voluntarily with-
out compensation; no personal information was
collected.
Beyond the benchmark, inferring preferences
a user never stated is a form of user profiling. A
deployed system could apply such inferences in un-
intended ways, for example to steer choices rather
than to complete an underspecified request. PRE-
FINE keeps its memory as a single natural-language
hypothesis that a user can inspect and correct, and
we recommend exposing it this way in deployment.

A.2
Per-Source Preprocessing
We describe the preprocessing applied to each of
the three adopted corpora; the selection procedure
is deferred to Appendix B.1.
SGD
SGD is used relabel-only: dialogues and
argument values are unchanged, and each dialogue
enters our pipeline as a single session. Per-session
calls are accumulated by merging partial argument
states into executed calls; when merging yields
conflicting values for the same argument, the un-
supported values are quarantined into a drop list,
keeping gold values unique. We keep the original
schema definitions and apply schema normaliza-
tion following prior work (Moghe et al., 2024),
enabling coherent multi-session histories while re-
maining compatible with the tool schemas. See Ap-
pendix A.7 for the full schema. How SGD sessions
are grouped into synthetic users, and how users
from all three sources are composed into histories,
is described in Appendix A.4.

A.3
Preference Realization
The mapping in Table 2 distinguishes low_cost
from high_cost, omitting an intermediate tier
because the intermediate signals in SGD (e.g.,
price_range=“moderate”) are too sparse and am-
biguous to serve as reliable preference evidence.
We retain solo_usage but exclude its counter-
part group_usage: as noted in our human study
(Appendix B.2), parties of size 2 are ambigu-
ous between couple and group travel, making
group_usage an unreliable preference signal. Be-
cause each preference is defined at the level of a
behavioral constraint rather than a specific parame-
ter name, the mapping generalizes to APIs beyond
SGD: any new function exposing cost- or party-
size-related arguments realizes the same preference
without redefinition, as verified in Appendix D.6.

A.5
Gold-Standard Annotation
Fixing the Gold Argument
How the gold value
is fixed follows the reasoning type. For Recall, the
target argument itself carries a value that recurs
in the accumulated calls, and that recurring value
is the gold. For Induction and Transfer, the gold
is the value that the mapping in Appendix A.3 as-
signs to the target argument, given the preference
the history’s cross-function evidence establishes.
In Transfer the target argument carries no value
anywhere in the history, so the mapping is the only
route to a gold value.
Because queries and histories are drawn from
separate pools and combined afterwards, a query
may target an argument whose preference the
paired history never establishes. The gold then
leaves that argument unspecified: with no behav-
ioral evidence to generalize from, abstaining is the
correct response and filling it is penalized. These
instances are counted under Other in Table 8.
Uniqueness of the Gold
The procedure above
returns exactly one gold for every instance. For
Recall, arguments in which two different values
both recur are excluded from querying, so no in-
stance admits two candidate golds. For Induction
and Transfer, each history supports exactly one
preference from each opposing pair: in contested
histories both sides recur, but strict plurality (§4.2)
leaves one side with strictly more supporting ob-
servations and discards ties, so the mapping still
returns a single value for any target argument that
preference can fill. Observations that set such an
argument to a competing value are not removed;
they remain in the history and are accounted for by
the interference score (§7.1) rather than by chang-
ing the gold, so difficulty varies without the answer
becoming ambiguous. Instances whose gold omits
the argument are likewise unambiguous: the paired

A.6
Dataset Statistics and Instance
Composition
Table 7 summarizes the scale of MPT across two di-
mensions: interaction history and reasoning types.
Each multi-session dialogue interleaves sessions
drawn from up to three source corpora into a single
interaction history, with an average of 15.2 sessions
per dialogue and 13.7 turns per session. This scale
reflects the practical challenge of long-horizon pref-
erence modeling: with over 95k turns across 459
dialogues, the benchmark requires models to ag-
gregate evidence over much longer contexts than
typical single-session tool-calling benchmarks. His-
tories also vary in how many preferences they sup-
port: 164 (35.7%) support two to four distinct pref-
erences, as in Figure 6, and yield 2,432 instances
(51.8%); competing values of the same preference,
such as two celebrities for prefers_star, are not
counted as distinct.
Table 8 breaks the 4,695 instances down by rea-
soning type and by the preference the target ar-
gument expresses. Every preference supports all
three reasoning types, and Transfer is not carried
by a single one: its largest share targets low_cost
arguments (590), followed by prefers_star (372).
Recall additionally targets recurring idiosyncratic
arguments that express none of the five preferences
(e.g., airlines, temperature), for which the re-
curring value itself is the gold (Appendix A.5).

B.2
Human Validation of Preference
Realization
To validate that our preference realization reflects
broadly shared behavioral intuitions, we conducted
a human annotation study with 19 annotators.
Setup
Annotators were presented with argu-
ment values drawn from the API schemas in
MPT, and asked to classify each value into
one of three categories: low_cost, high_cost,
or Neither for the cost pair, and solo_usage,
group_usage, or Neither for the party-size pair.
For example, given price_range=“Cheap” in
GetRestaurants
and
free_entry=True
in
GetTravel, annotators judged whether each
value realizes low_cost. The study covered 27
argument values across 12 functions for the cost
pair, and the counts 1 to 4 for the party-size pair.
The study targets these two pairs because each
is realized through heterogeneous arguments
(price_range, free_entry, car_type for the
former;
passengers,
number_of_tickets,
number_of_seats
for
the
latter),
whereas
prefers_star and eco follow from the argument
value itself and admit no comparable judgment.
Results
Annotators agreed with our realization
in 89.7% of cases for the cost pair and 97.4% for
the party-size pair. Inter-annotator agreement, mea-
sured by Fleiss’ κ (Fleiss, 1971), was κ = 0.701
(substantial) for cost and κ = 0.880 (almost per-
fect) for party size, following the interpretation
scale of Landis and Koch (1977). All 19 anno-
tators confirmed that the names solo_usage and
group_usage clearly represent the intended mean-

ing, while 16 of 19 (84%) confirmed the same for
low_cost and high_cost.
Discussion
The slightly lower agreement on
the cost pair (κ
=
0.701 vs. 0.880) likely
reflects the broader semantic range of cost-
related signals: whereas party size is unambigu-
ous, cost-conscious behavior is realized through
heterogeneous argument types, price_range,
average_star, free_entry, car_type, and oth-
ers, leaving more room for individual interpreta-
tion. Nevertheless, substantial agreement on both
pairs confirms that our preferences are not arbi-
trary schema choices, but reflect intuitions broadly
shared across annotators, supporting their use as a
task-grounded evaluation scaffold.
Several annotators noted that parties of 2 may

suggesting ambiguity in the boundary between
solo_usage and group_usage. Given this concern,
we conservatively retain only solo_usage, exclud-

LangMem
We use LangMem (LangChain AI, 2025) as an

(iii) we append the retrieved contents to the prompt
for tool-calling inference.

C.6
PREFINE
We implement PREFINE as a test-time memory
method that maintains a single textual preference
hypothesis rather than a store of retrievable entries:
(i) after each session, a generator proposes a can-
didate hypothesis from the previous memory, the
session, and its executed tool calls; (ii) a verifier
judges the candidate against the accumulated his-
tory under the four criteria of §5.1, and a refiner
revises it under the returned feedback for up to
K = 5 rounds; (iii) at test time, the accepted hy-
pothesis is appended to the prompt and inference
is run for tool calling.
Concretely, the generator, verifier, and refiner
are three prompted roles served by the same mem-
ory constructor LLM, with templates given in Ap-
pendix E. Two implementation choices distinguish
PREFINE from the baselines above. First, memory
is updated once per session rather than once per
user–assistant turn, so the verifier always scores
a candidate against the accumulated record Ht+1
rather than an isolated exchange. Second, the mem-
ory holds a single hypothesis that is overwritten
on each accepted update, so neither an embedding
model nor a top-k retrieval step is involved; the
entire memory is placed in the inference prompt,
which is otherwise identical to the one shared by
the retrieval- and memory-based methods.
Figure 7 traces the generate-verify-refine loop of
Algorithm 1 on the running example of Figure 1.
At session s7, the generator proposes prefers com-
pact cars from the memory M6 and the executed
call a7. The verifier rejects it not because the re-
sulting tool call fails, but because the hypothesis
rests on a single session and restates an argument
value rather than abstracting over it. The refined
candidate, prefers budget-friendly options, is ac-
cepted once it is found consistent with the calls
19

=== [page 20] ===
executed across s1 to s7. This is where the verifi-
cation signal in PREFINE differs from prior self-
refinement methods (Madaan et al., 2023; Shinn
et al., 2023), which score a candidate against task
outcomes. Here the candidate is scored against the
accumulated behavioral record Ht+1, so what sur-
vives is a cross-session regularity rather than a
locally successful edit. The memory also revises
rather than accumulates: M2 holds regularly ex-
plores local spots, which later evidence overwrites
instead of appending to. At inference, M7 sup-
plies flight_class=“Economy” for GetFlights,
a function the history never instantiates. Table 12
gives a longer trace over four sessions.

Post-hoc Empirical Concordance.
The order-

identify the reference weights adopted in §7.1. We
therefore examine whether their qualitative order-

under Full-History Prompting; it is not fitted to
PREFINE or any memory method, so the stratifica-

We report each regression coefficient on a 0.1-
share scale. Thus, ¯bx denotes the fitted percentage-
point difference in IMP-F1 associated with an abso-

example, ¯bC = −22.996: raising the competing-
evidence share from 0.2 to 0.3 is associated with a
fitted 22.996-point drop in IMP-F1.

query-setting-specific coefficients within each rea-
soning type, producing the three thin lines in Fig-

the reference weights.

D.5
Analysis of PREFINE Memories
Verifier-Guided Refinement
Figure 11 shows
that initial acceptance rises from 39% to approx-
imately 74% but then plateaus, while final accep-
tance increases from 84% to 95% as more sessions
accumulate. Thus, even with additional evidence,
roughly one quarter of initial hypotheses still re-
quire verification. Table 12 shows how the verifier
filters weakly supported or over-specific hypothe-
ses and revises them into reusable preference con-
straints. A manual analysis of 10% of rejected at-
tempts (n = 575; Figure 12) finds that insufficient
evidence and over-specificity account for 64.4% of
rejections. By addressing these dominant failures,
the verifier produces more reliable and reusable
hypotheses than unverified refinement.
Hypothesis Alignment Evaluation
We manu-
ally assess the final accepted hypothesis for each of
the 459 histories against its annotated target prefer-
ence and definition. A hypothesis is labeled aligned
if it semantically captures the target preference,
allowing equivalent formulations (e.g., “prefers
budget-friendly options” for low_cost), and con-
tradictory if it expresses an incompatible prefer-
ence. For histories that support multiple prefer-
ences, a hypothesis is labeled aligned if it captures
at least one of them. In the example of Figure 10,
a single hypothesis covers both preferences the
history supports, low-cost option and a favored
celebrity. Figure 10 shows the interface used for
this manual evaluation. It presents the final hypoth-
esis alongside the annotated target preferences and
their corresponding tool-call evidence for semantic
comparison.
Table 17 reports the history-level alignment dis-
tribution and downstream performance in both
query settings. We group evaluation instances by
the alignment label of their source history and com-
pute O-F1 separately for each inference model
within each group and query setting. Aligned his-
tories achieve higher mean O-F1 in both settings,
with a larger gap on context-free queries, where
current-session context is omitted.
