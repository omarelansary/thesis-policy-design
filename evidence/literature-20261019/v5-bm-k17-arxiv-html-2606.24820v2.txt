Abstract

LLM agents solve repository-level coding tasks through multi-turn tool use, but utilize half their budget on locating faults before editing.
Dedicated localization frameworks have emerged, yet are still evaluated as file retrieval rather than actionable diagnosis, producing locations without the diagnostic context a repair agent needs.
We introduce SHERLOC (Structured Hypothesis-driven Exploration and Reasoning for Localization), a training-free framework pairing a reasoning LLM with compact repository tools and self-recovery, without fine-tuning or multi-agent orchestration.
SHERLOC reaches state-of-the-art localization across model scales: 84.33%84.33\% accuracy@​1\texttt{accuracy@}1 on SWE-Bench Lite and 81.27%81.27\% recall@​1\texttt{recall@}1 on SWE-Bench Verified; at ∼30\sim 30B parameters, it matches or outperforms other agentic methods.

1 Introduction

Repository-level code repair increasingly relies on LLM agents that interleave extended reasoning with structured tool calls over a codebase [Wei et al., 2022, Yao et al., 2023, Schick et al., 2023].
A canonical benchmark for evaluating these agents is SWE-Bench [Jimenez et al., 2024], built from GitHub issues and their resolving pull requests: from a bug report and a repository snapshot, the agent must propose and verify a bug-fixing code patch.
Yet how agents allocate their interaction budget within this repair loop remains underexplored.
In a systematic study spanning 55 LLMs and 22 agent frameworks, we find that agents spend on average 18.518.5 turns (48%48\% of total interaction) locating faults before their first patch, consuming over 320320k tokens per instance (Appendix L).
This makes localization both a performance bottleneck and a dominant compute cost, consuming context and interaction budget that could otherwise support patch construction.

Most localization methods retrieve faulty files and functions [Zhou et al., 2012, Gangi Reddy et al., 2026, Yu et al., 2025]; some, e.g., OrcaLoca and SWE-Debate [Li et al., 2026], also produce free-form report text.
This view is necessary but incomplete: a file path tells the agent where to look, but not why, and a file path without a root-cause hypothesis leaves downstream repair under-specified.
We hypothesize that explicitly producing candidate locations, root-cause analysis, and actionable solution guidance yields a richer, more transferable localization, and ask: (RQ1) Can a single reasoning LLM with a compact, structured tool interface match task-specifically trained localizers without fine-tuning or multi-agent orchestration? (RQ2) When do its locations and findings transfer to code-repair agents, and how does the resolve rate and token cost shift?

We introduce SHERLOC (Structured Hypothesis-driven Exploration and Reasoning for Localization), a training-free framework coupling a reasoning LLM with a compact suite of LLM-friendly repository tools (file viewing, code search, repository-tree inspection, and import-graph navigation; Figure 1) and lightweight self-recovery mechanisms (context truncation, loop detection, malformed-tool-call repair, final-turn synthesis).
For each predicted location, SHERLOC emits a structured diagnostic finding.

For (RQ1), we evaluate SHERLOC across model families on SWE-Bench Lite and SWE-Bench Verified.
It reaches state-of-the-art file-level localization on both benchmarks and remains competitive at a matched ∼30\sim 30B scale, without supervised fine-tuning, reinforcement learning, or multi-agent debate.
Ablations show that the tool suite, self-recovery mechanisms, and reasoning mode all contribute, while implicit-knowledge controls show that the gains persist when file paths in the issue are masked.

Strong localization does not automatically translate to better repository-level issue resolution.
For (RQ2), we inject our locations and findings into two code-repair frameworks, OpenHands [Wang et al., 2025] and SWE-Agent [Yang et al., 2024], across 55 repair-agent backbones.
Across the 1010 model-framework pairs, the per-pair best of unfiltered SHERLOC and quality-filtered SHERLOC (QF SHERLOC) averages a +5.95+5.95 pp resolve-rate gain; deployable, unfiltered SHERLOC averages +4.39+4.39 pp, with 36.7%36.7\% and 23.1%23.1\% fewer localization and total tokens.

SHERLOC improves or preserves the resolve-rate point estimate in eight of ten settings and reduces localization tokens in all ten (Figures 3 and 4).
QF SHERLOC mitigates the only observed case of negative transfer.
Thus, transfer is positive on average but quality-mediated.

2 Related Work

Tool-augmented LLM reasoning.

SHERLOC builds on reasoning-augmented tool use [Wei et al., 2022, Yao et al., 2023, Schick et al., 2023] and on test-time scaling that adapts reasoning compute to problem difficulty [Wu et al., 2025, Zhao et al., 2025].
Unlike prior localization systems built on supervised fine-tuning, reinforcement learning, or multi-agent orchestration, ours uses a single LLM with a fixed, structured tool set.

LLM-based code localization.

Recent LLM-based methods explore repositories interactively or reason over code graphs: SWE-Debate adjudicates fault-propagation traces through multi-agent debate [Li et al., 2026]; OrcaLoca uses priority-based action scheduling and distance-aware context pruning [Yu et al., 2025]; CoSIL and LocAgent guide LLM search through code-graph structure [Jiang et al., 2025, Chen et al., 2025]; RepoSearcher/ToolTrain uses tool-integrated reinforcement learning [Ma et al., 2026].
SHERLOC differs in design: no training, no auxiliary structures, a compact set of LLM-friendly repository actions, and self-recovery mechanisms that stabilize extended-thinking tool use.
Whereas prior work typically targets file- or function-level entity locations, sometimes with prescriptive modification plans for downstream patching [Li et al., 2026], our method additionally produces structured diagnostic findings alongside each location.

Issue-based retrieval and ranking.

Information-retrieval localization treats the bug report as a query and source files as documents.
BugLocator [Zhou et al., 2012] ranks files using textual similarity and prior bug reports; BLUiR [Saha et al., 2013] incorporates structured source-code information; AmaLgam [Wang and Lo, 2014] combines version history, similar reports, and structure.
Recent neural rankers such as SWERank learn issue–code similarity with task-specific training [Gangi Reddy et al., 2026].
These methods output ranked locations rather than diagnostic reports; SHERLOC instead frames localization as active repository reasoning yielding structured findings.

Fault localization with execution signals.

Classical fault localization assumes access to executable tests or dynamic traces: spectrum-based methods rank by suspiciousness from coverage and pass/fail statistics [Jones et al., 2002, Abreu et al., 2007]; mutation-based methods inject synthetic faults and observe test-outcome changes [Moon et al., 2014, Papadakis and Le Traon, 2015]; learning-based extensions train neural models over coverage or graph features [Li et al., 2019, Lou et al., 2021]; AutoFL uses LLM tool calls but still requires at least one failing test [Kang et al., 2024].
Unlike these execution-dependent methods, SHERLOC operates from the issue description and repository snapshot alone, without executing tests or observing coverage.

Localization granularity.

Existing localization studies report at module, file, class, or function level [Kang et al., 2024, Chen et al., 2025].
For repository-level repair, this granularity is not always aligned with the target edit: patches may modify class-level declarations, imports, configuration logic, or coordinated regions across functions.
Several recent function-level evaluations sidestep this mismatch by discarding 2626 of the 300300 SWE-Bench Lite instances that lack an existing function or class target [Suresh et al., 2025, Chen et al., 2025, Gangi Reddy et al., 2026].
We therefore complement file-level metrics with structure-agnostic chunk-level metrics over line ranges (coverage recall, precision, and average tightness) that represent predictions and ground truth as (start, end) line-number spans, making no assumption about which syntactic unit contains the patch target while retaining all benchmark instances.

Issue-resolution agents and benchmark validity.

Issue-resolution systems target patch correctness directly: Agentless [Xia et al., 2025] and AutoCodeRover [Zhang et al., 2024] decompose the task into localization, patch generation, and validation; agentic systems such as SWE-Agent and OpenHands integrate navigation, editing, and execution in a single loop [Yang et al., 2024, Wang et al., 2025].
We instead evaluate localization directly and, in separate experiments, inject our findings into existing repair agents to test downstream transfer.
Because high file-identification accuracy on SWE-Bench can partly reflect pretraining familiarity [Liang et al., 2026], we apply implicit-knowledge, shuffled, and masked controls to separate benchmark-specific signal from tool-assisted diagnostic reasoning.

3 Method

We formulate localization as an iterative, tool-mediated reasoning problem: given a natural-language issue report and a repository snapshot, the system must identify code regions likely to require modification and produce a diagnostic finding, not merely a ranked location, that explains the suspected root cause and solution direction.
SHERLOC implements this with four components (Figure 1): a reasoning LLM, a deterministic executor mediating repository access, a compact suite of LLM-friendly tools, and lightweight self-recovery.
The model alternates between reasoning and structured actions until it has enough evidence to emit final findings and locations.
Its hypothesis state is the accumulated conversation history, including prior observations; no external memory store is maintained.

Figure 5: Example SHERLOC input and output.
Given a SWE-Bench Verified Django issue, SHERLOC predicts a line span in django/db/models/base.py and emits a structured diagnostic finding with the location explanation, root cause, solution idea, dependencies, and testing impact.

Design principle: reasoning-native tool use.

Rather than synthesizing arbitrary shell commands or Python scripts for repository actions, the model selects from a small fixed set of tools, each with a structured schema for execution (e.g., file path and optional line range) and bounded, model-readable observations such as snippets, paths, line ranges, and dependency summaries.
This keeps repository exploration legible while preserving a deterministic execution boundary: the model chooses the action, but the executor validates and runs it, avoiding incidental command construction or shell-debug failure modes that prior work has shown to derail agent trajectories under raw shell access [Yang et al., 2024].
It also lets us use reasoning models, which excel at multi-step deliberation but are not necessarily trained for external tool APIs, without task-specific tool-use fine-tuning.

3.1 Initialization and Context

Before prompting, we construct a filtered repository view that removes directories unlikely to contain production logic, such as documentation, build artifacts, dependency folders, and version-control metadata (e.g., /docs, /.git).
The initial prompt combines this filtered tree with the issue description, tool descriptions, and required output format, giving the model a global map of the project without loading source files.

3.2 Tool Suite

The suite is limited by design: enough to expose relevant repository evidence, but not so broad as to invite open-ended software-engineering actions.
View File inspects a file, optionally restricted to a line range, with fuzzy path matching that suggests corrections for near-miss names. Codebase Search performs repository-wide literal search and returns matching snippets with surrounding context. Repository Tree displays the filtered file hierarchy (like shell tree), letting the model regain global context. Connected Tree summarizes import relationships (direct and reverse) to follow dependencies across modules.

3.3 Iterative Interaction Loop

At the core of SHERLOC is a bounded interaction loop of at most 2020 turns; at each turn the model either makes a tool call or terminates with final locations and findings.
The loop has four steps.
Reasoning and action selection: the LLM receives the issue, repository context, and previous observations, then decides whether additional evidence is needed and, if so, emits one structured action. Action parsing: a parser extracts a tool call or a final answer; final answers contain a findings block (55 fields: location explanation, root cause, solution idea, dependencies, testing impact; see Figures 5 and J.1) and a locations block. Tool execution: the executor runs the action and appends the observation to the conversation history. Termination: the loop ends when a valid final answer is parsed or when the step budget is exhausted, in which case a final-turn prompt forces synthesis from gathered evidence.

3.4 Self-Recovery Mechanisms

We add recovery for common failure modes in multi-turn tool use (Appendix H): context management (truncating older observations), loop detection (warnings for repeated unproductive calls), implicit tool-call recovery (parsing malformed but unambiguous requests), response-length management (re-prompting when generation approaches safe limits), and final-turn prompting (forcing synthesis when the step budget is exhausted).

4 Results

We evaluate SHERLOC along four axes: (i) the quality of its predicted code locations and (ii) the robustness of those predictions to benchmark contamination and to LLM backbone choice (addressing RQ1; Sections 4.1, 4.3 and 4.4); and (iii) the transfer of its outputs to downstream code repair, gated by (iv) the quality of its diagnostic findings under an LLM judge (addressing RQ2; Section 4.6).
We report file-level metrics (precision, recall, F1, exact match, hit@11) over the predicted file set and structure-agnostic chunk-level metrics (coverage recall, precision, average tightness) over (start, end) line-number spans; definitions in Appendix B.

4.1 Localization Performance and Efficiency

We evaluate our framework across SWE-Bench Lite [Jimenez et al., 2024] and SWE-Bench Verified [Chowdhury et al., 2024] using 44 backbone models and 33 seeds.
Figure 2 compares against leading localizers including SWE-Debate [Li et al., 2026], SWERank [Gangi Reddy et al., 2026], LocAgent [Chen et al., 2025], SWE-agent [Yang et al., 2024], OpenHands [Wang et al., 2025], and Agentless [Xia et al., 2025].
Following prior localization work [Li et al., 2026, Gangi Reddy et al., 2026, Chen et al., 2025], we report file-level accuracy@11 as the fraction of instances whose top-ranked predicted file is a gold file and recall@11 as the mean fraction of gold files recovered by the top-ranked prediction.

On SWE-Bench Lite, our framework with Qwen3-235B-A22B-Thinking-2507 (Qwen3-235B) [Yang et al., 2025a, Qwen Team, 2025a] achieves 84.33±0.72%84.33\pm 0.72\% accuracy@11 in 5.05.0 turns on average; the strongest plotted prior result is the fine-tuned SWERank retrieve-and-rerank pipeline (83.21%83.21\%).
At the chunk level, it reaches 39.14%39.14\% coverage recall and 44.54%44.54\% precision.

On SWE-Bench Verified, the best configuration (Qwen3-235B) achieves 81.27±1.16%81.27\pm 1.16\% recall@11 with 4.74.7 average turns, a 13.213.2 pp improvement over the previous state of the art, RepoSearcher / ToolTrain-3232B [Ma et al., 2026, 68.03%68.03\%;].
At a matched ∼30\sim 30B scale and without task-specific training, Qwen3-30B-A3B-Thinking-2507 reaches 75.07±1.24%75.07\pm 1.24\% recall@11, outperforming ToolTrain-3232B by 7.07.0 pp.
At the chunk level, it reaches 41.28%41.28\% coverage recall and 53.47%53.47\% precision.
Because prior systems do not report chunk-level metrics, these span scores primarily characterize how tightly SHERLOC’s predicted regions cover the gold edit spans rather than serving as a direct baseline comparison.

DeepSeek-V3-0324 [DeepSeek-AI et al., 2024, DeepSeek-AI, 2025b] reaches 79.53±0.47%79.53\pm 0.47\% on Verified, confirming cross-family transfer.
Full per-backbone numbers (including chunk-level metrics and tool-engagement) appear in Table 3; the complete metric grid is in Appendix B.

At the trajectory level, the search remains compact while scaling with problem difficulty: turns rise from 4.224.22 (easy) to 5.055.05/5.215.21 (medium/hard) and total tokens from 21.321.3k to 32.832.8k/35.135.1k (Appendices F and G).

4.2 Component Ablations

To keep the full component grid tractable, we ablate each component of our framework and show the impact of each separate tool and mechanism on a fixed sample of 100100 instances drawn uniformly from the SWE-Gym development set [Pan et al., 2025] (full breakdown in Appendix A).
Removing any single tool or self-recovery mechanism degrades localization, with View File (−7.0-7.0 pp F1) and the final-turn prompt (−5.0-5.0 pp F1) as the largest contributors, indicating that both code inspection and synthesis pressure are central.

4.3 Implicit Knowledge vs. Tool-Assisted Reasoning

Because SWE-Bench repositories are public and widely represented in pretraining corpora, localization accuracy can reflect both active reasoning and implicit knowledge of familiar codebases [Liang et al., 2026].
We treat this as a validity concern and conduct a controlled masking study with Qwen3-235B on SWE-Bench Verified, progressively removing repository access and identifying information (Table 5).
Even when tools, the repository tree, and all file and module paths in the issue are masked, the model still achieves 57.86%57.86\% recall@11 from the issue text alone, often inferring the correct file from error messages, API names, and domain conventions.
We interpret this primarily as repository familiarity with widely used foundational libraries, not as direct evidence that individual benchmark instances are memorized.
Manually inspecting a random sample of 5050 successful instances from this setting confirms 22 patterns: reliance on (i) well-known APIs and libraries, and (ii) distinctive error messages that uniquely identify a module.
Quantitatively (Table 6), implicit recall concentrates in popular projects (85.3%85.3\% on scikit-learn, 87.5%87.5\% on requests), while less common ones like pylint and seaborn fall to 33.3%33.3\%.

Crucially, this baseline familiarity does not explain SHERLOC’s full performance.
When tools and the repository tree are retained but explicit paths are removed from the issue text, SHERLOC reaches 79.96%79.96\% recall@11, only 1.31.3 pp below the unmasked full system (81.27%81.27\%).
The ≈22\approx 22 pp gap between this masked-issue setting and the heavily-masked text-only setting estimates the contribution of active repository exploration beyond parametric familiarity.

4.4 Backbone Generalization and Tool Engagement

To separate the SHERLOC method from the backbone, we evaluate 55 models from 22 families: Qwen3-235B-A22B-Thinking-2507, Qwen3-30B-A3B-Thinking-2507, and Qwen3-30B-A3B-Instruct-2507 [Yang et al., 2025a, Qwen Team, 2025a, Qwen Team, 2025b, Qwen Team, 2025c]; DeepSeek-V3-0324 [DeepSeek-AI et al., 2024, DeepSeek-AI, 2025b]; and DeepSeek-R1-0528 [Guo et al., 2025, DeepSeek-AI, 2025a].
Runs use identical code, prompts, tools, and self-recovery; only the backbone changes.
Each uses 33 seeds on SWE-Bench Verified; recall, mean turns, and zero-tool rate are in Table 3.

First, SHERLOC transfers across model families: DeepSeek-V3-0324 reaches 79.53%79.53\% recall, only 1.71.7 pp below the Qwen3-235B ceiling and 11.511.5 pp above the best published baseline [Ma et al., 2026, ToolTrain-3232B, 68.03%68.03\%;].
Second, tool engagement matters: DeepSeek-R1-0528 makes 41%41\% fewer tool calls and 32%32\% fewer turns than Qwen3-235B, with 10%10\% producing locations without any tool call; those zero-tool instances reach 69.3%69.3\% recall vs. 73.6%73.6\% on its tool-using subset, so active exploration helps even strong reasoning models.
Third, scale alone is not enough: Qwen3-30B outperforms the larger R1-0528 (75.07%75.07\% vs. 73.63%73.63\%) while taking the most turns (7.27.2 on average, vs. 4.74.7 for Qwen3-235B and 3.23.2 for R1-0528).
R1-0528’s under-exploration is consistent with DeepSeek’s lack of a marked system-role token: the prompt is delivered as bare preamble, reducing tool-use compliance.
The Qwen3-30B-Thinking vs. Qwen3-30B-Instruct ablation (Section A.1) reinforces this: reasoning is critical for sustaining the multi-turn protocol.

4.5 LLM-as-Judge Scoring of Findings

How reliable are the diagnostic findings that SHERLOC produces? SHERLOC produced locations and findings for 499499 of the 500500 SWE-Bench Verified instances, with one instance yielding no prediction. We score these 499499 findings with an LLM-as-judge.
We use GPT-5.25.2 [OpenAI, 2025] as a ground-truth-patch-conditioned judge that rates each finding from 11 to 55 on three dimensions: root-cause correctness, location accuracy, and solution actionability (prompt details in Appendix H; full quality-scoring breakdown in Appendix J).
The composite quality score is the mean of these three dimensions, and we call a finding high-quality when this composite is ≥4.0\geq 4.0.
The scores are right-skewed: 270270 (54%54\%) fall in Very High (>4.0>4.0), 101101 (20%20\%) in High (3.03.0 to 4.04.0), 7373 (15%15\%) in Medium (2.02.0 to 3.03.0), and 5555 (11%11\%) in Low (≤2.0\leq 2.0) (Table 7).
The ≥4.0\geq 4.0 threshold therefore retains 317317/499499 scored findings (63.5%63.5\%).

4.6 Downstream Transfer to Code Repair Task

Does better localization translate into better downstream issue resolution? We measure code-repair resolve rate (fraction of generated patches that pass the held-out tests) on all 500500 SWE-Bench Verified instances [Chowdhury et al., 2024], using 22 agentic frameworks, SWE-Agent [Yang et al., 2024] and OpenHands [Wang et al., 2025], across 66 setups (Figure 3; full grid in Table 11): Baseline (vanilla agent execution); Masked (baseline with file paths and repository names masked, extending the implicit-knowledge control from Section 4.3); Shuffled findings (a SHERLOC location and finding from a different random instance); SHERLOC findings (SHERLOC’s predicted locations and findings); QF SHERLOC (retrospectively selects the SHERLOC outcome for scored findings with judge score ≥4.0\geq 4.0 and the Baseline outcome below the threshold); and Oracle GPT-5.25.2 (upper-bound finding conditioned on the ground-truth patch).

Transfer gains depend on model capability.
SHERLOC findings improve or preserve the resolve-rate point estimate in eight of ten settings and reduce localization tokens in all ten (Figures 3 and 4).
Smaller and mid-sized models gain most from SHERLOC findings.
For Qwen3-Coder-30B-A3B [Qwen Team, 2025e], SWE-Agent rises from 44.7%44.7\% to 54.0%54.0\% and OpenHands from 49.4%49.4\% to 53.0%53.0\%; Qwen3-Coder-Next [Cao et al., 2026] and Qwen3-Next-80B-A3B-Instruct [Qwen Team, 2025g] show +8+8 to +12+12 pp improvements across both frameworks (Figure 3).
These models have low baseline resolve and large localization headroom (Qwen3-Coder-Next reaches only 0.560.56 Hit@11 vs. our 0.880.88; Figure 6), so even moderate-quality findings close a real gap.
QF SHERLOC mitigates the only observed case of negative transfer.
For MiniMax-M2.5 [MiniMax, 2026], SHERLOC lowers resolve rate by 44 to 55 pp across the two frameworks (Figure 3).
QF SHERLOC raises these results to 76.6%76.6\% with SWE-Agent and 72.8%72.8\% with OpenHands, but neither differs significantly from Baseline (Section K.2).
Token efficiency improves uniformly.
Across all 55 repair models and 22 frameworks, SHERLOC findings reduce localization tokens by 99 to 66%66\% (36.7%36.7\% on average) and total tokens by 23.1%23.1\% on average (Figures 4 and L), giving the agent a targeted starting point and freeing context and interaction budget for repair.
The largest cell-level efficiency gain is Qwen3-Coder-480B-A35B [Qwen Team, 2025d] / SWE-Agent, where injecting findings cuts localization tokens from 188.9188.9k to 64.664.6k (−66%-66\%) while leaving resolve rate unchanged at 63.0%63.0\%, showing that even for already-saturated repair agents the standalone localizer pays for itself in search cost alone.
The masked and shuffled controls remain close to baseline (Table 18), so gains come from instance-relevant diagnostic guidance, not surface leakage or unrelated findings.

4.7 Understanding Downstream Transfer

Finding quality is associated with downstream success.
On the Qwen3-Coder-480B-A35B / OpenHands cell, very-high-quality findings resolve at 75.9%75.9\%, compared with 20.0%20.0\% for low-quality ones, and composite score correlates with repair outcome at r=0.45r{=}0.45 (Figure 7).
Using the ≥4.0\geq 4.0 threshold defined in Section 4.5, we divide instances by the quality of their SHERLOC findings.
Above the threshold, conditioning the repair agent on these findings raises resolve rate from 74.8%74.8\% under Baseline to 80.4%80.4\%; below the threshold, it lowers resolve rate from 38.5%38.5\% to 31.3%31.3\%.
QF SHERLOC therefore retains the SHERLOC outcome only above the threshold and falls back to Baseline otherwise, mitigating negative transfer in Section 4.6.
The pre-specified 4.04.0 threshold is the highest tested half-point cutoff retaining a majority of scored findings (317/499317/499; 63.5%63.5\%) and is within 2.12.1 pp of the best retrospective estimate at 4.54.5 (Tables 10 and 8).

Patch-free verification provides a deployable confidence signal.
Because QF SHERLOC relies on a ground-truth-patch-conditioned judge, it is retrospective.
As an optional deployable safeguard for repair agents whose validation results indicate negative transfer, our patch-free verifier evaluates the canonical finding using the issue description and five auxiliary traces.
Across 499499 findings, its confidence score correlates with retrospective quality at r=0.553r{=}0.553; at threshold 4.04.0, it selects 281281 findings with 79.0%79.0\% precision and 70.0%70.0\% recall.
This experiment measures agreement with retrospective quality labels, not downstream repair under verifier-based selection.

Solution content carries that signal.
Two independent lenses converge: by per-dimension correlation on the Qwen3-Coder-480B-A35B / OpenHands cell, solution actionability has the strongest individual association with repair success (r=0.46r{=}0.46, vs. r=0.41r{=}0.41 for root-cause and r=0.36r{=}0.36 for location accuracy); by causal field ablation on Qwen3-Coder-30B-A3B / SWE-Agent (Table 9), removing the solution idea field produces the largest single-field drop while all other reduced variants still beat the baseline.
The transferable signal therefore comes from correct root-cause and solution content, not from merely seeing a SHERLOC-formatted hint.

Chunk coverage predicts downstream repair success.
To separate chunk coverage from file identification, we restrict the analysis to the 371371 instances for which SHERLOC identifies all and only the correct files, so every file metric is 100%100\%.
Among these, 144144 instances have complete coverage of the gold edit chunks and 227227 have incomplete coverage.
Across the ten SHERLOC repair settings, the complete coverage group resolves at 82.5%82.5\%, compared with 59.9%59.9\% for the incomplete coverage group, a +22.6+22.6 pp difference.
The gap is positive in every setting and ranges from +18.8+18.8 to +27.4+27.4 pp (Table 13).
Thus, chunk coverage provides information about downstream repair success even when file identification is perfect.
Chunk metrics complement rather than replace standard file metrics.

Findings help most on multi-file bugs.
On the 7171 Verified instances requiring 22 or more file changes, SHERLOC findings improve resolve rate by +5.6+5.6 pp (32.4%32.4\% vs. 26.8%26.8\%).

Finally, we separate accuracy from efficiency transfer by injecting findings from the weaker Qwen3-30B SHERLOC (Hit@11 0.7860.786 vs. 0.8840.884; Table 19).
These weaker findings no longer improve Qwen3-Coder-30B-A3B but still improve Qwen3-Coder-Next (SWE-Agent 45.2%45.2\%→\to49.2%49.2\%; OpenHands 44.6%44.6\%→\to45.4%45.4\%; Table 12), and still reduce localization tokens by 1616 to 32%32\% (24.5%24.5\% on average) and total tokens by 11 to 17%17\% (7.5%7.5\% on average) across all 44 cells (Table 16).
Localizer quality thus governs accuracy transfer; even imperfect findings reduce search cost by anchoring initial exploration.

5 Conclusion

Our work on SHERLOC shows that structured diagnostic output, not just location retrieval, is the operative unit of useful localization.
For RQ1, a single reasoning LLM with compact repository tools and self-recovery can reach state-of-the-art file-level localization without task-specific fine-tuning or multi-agent orchestration: 84.33%84.33\% accuracy@11 on SWE-Bench Lite and 81.27%81.27\% recall@11 on SWE-Bench Verified, with matched-scale performance competitive with other agentic methods.
For RQ2, injecting these locations and diagnostic findings into existing code-repair agents yields an average +5.95+5.95 pp resolve-rate gain from the best SHERLOC result per setting; On average SHERLOC cuts localization and total tokens by 36.7%36.7\% and 23.1%23.1\% across 55 repair backbones and 22 frameworks. A retrospective QF SHERLOC analysis shows that excluding unreliable findings can mitigate negative transfer.

We conclude that localization should be evaluated not just by file or function retrieval but by diagnostic actionability: a correct file with a misleading diagnosis still misleads the downstream agent.
Beyond bug localization, structured findings may benefit repository-scale tasks such as test generation, regression triage, refactoring, and migration planning, where intermediate reasoning matters as much as the final action.

Limitations

Implicit-knowledge confound.

Our implicit-knowledge controls show that ≈58%\approx 58\% of localization recall on SWE-Bench Verified is achievable from issue text alone, with strong per-repository concentration: scikit-learn and requests reach 8585–88%88\% masked recall while pylint and seaborn fall to 33%33\% (Appendix E).
Headline SWE-Bench localization numbers, ours included, therefore partly reflect LLM pretraining familiarity with widely distributed open-source code rather than transferable code reasoning.
Our masked-issue control (79.96%79.96\% with tools retained) bounds but does not eliminate this confound; fully isolating pretraining familiarity would require evaluation on demonstrably unseen repositories.

Benchmark and framework scope.

Code-repair transfer is measured on SWE-Bench Verified through two repair frameworks (SWE-Agent, OpenHands) and five repair backbones.
Generalization to private or demonstrably unseen repositories, other benchmarks such as SWE-Bench Multimodal [Yang et al., 2025b] and multilingual variants, newer benchmark snapshots, additional agent frameworks, and non-Python repositories (JavaScript, Java, C++) remains open.
The Connected Tree tool relies on a thin language-specific import parser that must be adapted for each supported language; the rest of SHERLOC is language-agnostic.

Compute cost of the headline configuration.

Our best numbers use Qwen3-235B-A22B-Thinking-2507 with up to 2020 reasoning turns per instance, so the headline localization rows are not directly comparable on serving cost to the fine-tuned 3232B baselines we cite.
The matched-scale 3030B row (75.07%75.07\% on Verified, +7.0+7.0 pp over ToolTrain-3232B) is the most cost-comparable point of evidence for the method itself; the +6.2+6.2 pp from 235235B over 3030B partly reflects model scale.

Cross-model prompt sensitivity.

Identical prompts elicit different tool-use behavior across model families: DeepSeek-R1-0528, which does not support marked system roles, exhibits 10%10\% zero-tool shortcutting under the same prompt text (Section 4.4).
Systematic evaluation of commercial models such as GPT, Claude, and Gemini remains future work; they can be connected through a model/API adapter without changing the localization workflow, with the required integration points documented in the released code.
Picking a backbone with system-prompt support sidesteps this; otherwise, reaching the reported numbers on a new backbone may require model-specific prompt adaptation rather than a strictly drop-in deployment.

Retrospective QF SHERLOC and patch-free verification.

The QF SHERLOC analysis uses GPT-5.25.2 [OpenAI, 2025] as an external judge that is shown the ground-truth patch.
The judge-independent cells in Figure 3 (baseline, masked, shuffled, SHERLOC, Oracle GPT-5.25.2) provide non-judge evidence for the 22 transfer regimes, but the per-instance reliability analysis and the threshold sweep in Section J.3 depend on this external supervision.
The QF SHERLOC row should therefore be read as an analysis-time selection experiment.
Our patch-free verifier removes the ground-truth requirement, but we evaluate only its agreement with retrospective quality labels, not downstream repair under verifier-based selection.

Model names and versions are listed above, and the sampling parameters for every run are given in the Sampling parameters paragraph below.

Computing infrastructure and budget.

All experiments are inference-only and run on internal compute clusters of NVIDIA H100100 (8080 GB) and A100100 (8080 GB) GPUs.
Backbones are served via SGLang [Zheng et al., 2024] for localization and vLLM [Kwon et al., 2023] for downstream code repair.
Approximately 7,9007{,}900 GPU-hours were used for the downstream repair experiments (55 repair backbones ×\times 22 frameworks ×\times 66 conditions), approximately 2,5002{,}500 GPU-hours for the multi-backbone, multi-seed localization evaluations, and a few hundred GPU-hours for the component and reasoning-mode ablations and implicit-knowledge controls.
The Qwen3-235B-A22B-Thinking-2507 localization runs used 1616 GPUs for serving and averaged approximately 107107 GPU-hours per 500500 tasks, or 0.210.21 GPU-hours per task.
Standard SHERLOC requires one localization run per issue; the optional patch-free verifier additionally requires five auxiliary localization runs and one verifier call.

Sampling parameters.

Every SHERLOC localization run uses temperature =0.99=0.99, top-p=0.95p=0.95, top-k=0k=0 (disabled), a per-call generation cap of 81,92081{,}920 tokens, and at most 2020 interaction turns.
All downstream code-repair backbones use temperature =0.7=0.7, top-p=0.8p=0.8, and top-k=20k=20 under the stock SWE-Agent and OpenHands configurations.
The LLM-as-judge quality scorer (GPT-5.25.2) uses temperature =0.1=0.1 and a 300300-token output cap.

Part I: Localization Analyses

Appendix A Component Ablations: Tools and Self-Recovery

Tables 1 and 2 evaluate the localization agent on the same 100100 uniformly sampled SWE-Gym development issues. We ablate one component at a time while holding the base model, prompts, sampling setup, and all other tools or self-recovery mechanisms fixed.

The sample covers 1010 of 1111 repositories, with repository shares differing from the full development split by at most 4.34.3 pp. SWE-Gym follows the SWE-Bench instance-extraction and execution-based validation pipelines on separate Python repositories [Pan et al., 2025], providing a comparable development setting. We therefore interpret the ablation as evidence for qualitative component trends; exact effect sizes may vary on the full distribution.

File-level metrics (precision, recall, F1, exact match, and set accuracy) are computed over the predicted file set; chunk-level metrics (coverage recall and average tightness) are computed over (start, end) line-number spans. Parenthesized values are absolute-point deltas relative to the corresponding full-system row in the same table.

Across both ablations, the largest performance drops come from removing View File (tool suite) and the final-turn prompt (self-recovery), confirming that code inspection and forced final-turn synthesis are the two most load-bearing components.

A.1 Reasoning-Mode Ablation: Thinking vs. Instruct

To isolate the contribution of extended reasoning, we compare Qwen3-30B-A3B-Thinking-2507 against its non-thinking counterpart Qwen3-30B-A3B-Instruct-2507, which shares the same parameter count, architecture, prompts, and tools.
The Instruct model achieves only 10.2%10.2\% recall on Verified and 11.7%11.7\% on Lite, versus 74.0%74.0\% and 76.7%76.7\% for the Thinking model: a ∼65\sim 65 pp gap.
The failure is not gradual degradation but near-total collapse: 87%87\% of Instruct samples fail to produce any valid output (success rate 13%13\%), with the model averaging 0.20.2 predicted locations per instance versus 1.31.3 for the Thinking variant.
Without extended chain-of-thought, the model cannot sustain the multi-turn tool-use protocol that SHERLOC requires.
This ablation, controlled within a single model family, shows that thinking-mode reasoning is critical for this multi-turn exploration and diagnosis protocol.

Metric definitions.

At the file level, we report Precision, Recall, and their harmonic mean (F11-Score), alongside Exact Match, a binary indicator of perfect set equality, and Set Accuracy, the Jaccard index (intersection over union) of predicted and ground-truth file sets, averaged across instances.
At the chunk level, using a strict containment criterion, Coverage Recall measures the fraction of ground-truth chunks fully contained within predictions, Precision measures the fraction of predictions that contain at least one ground-truth chunk, and Average Tightness measures the ratio of ground-truth chunk size to prediction size for correctly covered chunks.
Mean turns is the average number of reasoning turns per trajectory, and Zero-tool is the fraction of trajectories that produce locations without making any tool call.
For SWE-Bench Lite, all reported metrics are averaged over the same seeds used in Figure 2.
For SWE-Bench Verified, recall is a multi-seed mean (±\pm std) over 33 seeds; remaining file/chunk metrics are reported on the seed used in Section 4.4.

Appendix C Failure Taxonomy on Zero-Recall Instances

To understand SHERLOC’s limitations, we manually categorize all 5555 instances where the system achieves zero recall@11 on SWE-Bench Verified (Table 4).
The dominant failure mode is reasoning error (40%40\%): the model explored the correct area, often viewing the ground-truth file, but ultimately selected a different file in its final answer.
Combined with close misses (27%27\%, correct directory but wrong file), 67%67\% of failures stem from picking the wrong file among nearby candidates rather than from failing to reach the right area.
Only 4%4\% involve genuinely multi-file bugs where the ground truth spans 33+ files.
By repository, failures concentrate in matplotlib (21%21\% failure rate), sympy (19%19\%), and xarray (14%14\%), while django, the most represented repository, has a lower 11%11\% failure rate, consistent with higher implicit familiarity.
These patterns suggest candidate reranking and self-consistency during final selection as promising future work.

Appendix F Token Composition of Localization Trajectories

To complement the trajectory-level results, we report detailed token usage statistics from SHERLOC’s reasoning traces on SWE-Bench Verified with Qwen3-235B-A22B-Thinking-2507.
Figure 9 shows that the majority of tokens are consumed by the model’s reasoning process itself (19.519.5k tokens on average), followed by tool outputs (9.09.0k) and input messages (4.54.5k).
This indicates that computation is dominated by internal deliberation rather than excessive tool querying.

The total token distribution per trajectory (Figure 10) is centered around 28.628.6k tokens (median 24.024.0k), suggesting a compact yet expressive reasoning process.
These results confirm that SHERLOC’s trajectories remain computationally efficient while capturing detailed reasoning traces.

Appendix H Implementation Details

System Prompt.

The system prompt instructs the model to act as a bug-localization assistant, providing structured output via <think>, <tool_call>, and <locations> tags.
The prompt emphasizes exhaustive exploration (“prefer over-inspecting code to missing a second edit site”) and prohibits code fixes.
The user message contains the problem statement followed by the filtered repository tree.

Key instructions (abbreviated):

You are a bug-localization assistant.

Primary Goal: Locate every file and precise line-number range that must be edited. Never propose code changes. Return locations only after inspecting enough source code to be certain you have found all of them.

Interaction protocol: (1) Read the Problem Description. (2) First response must be a tool call, never locations. (3) Keep issuing tool calls until fully confident. (4) Only then reply with a <locations> block.

Tool Descriptions.

Four tools are described in natural language within the system prompt:

• 

view_file: Inspects file contents, optionally restricted to a line range (view_range: [start, end]). Includes dependency metadata showing import relationships.

• 

codebase_search: Repository-wide case-insensitive literal search. Returns matching files with line numbers and 2020-line context windows.

• 

repo_tree: Displays the repository file structure with per-file line counts.

• 

connected_tree: Shows import dependencies. With a file argument, shows direct imports and reverse imports; without, shows repository-wide import overview.

Final-Turn Prompt.

When the remaining interaction steps reach a threshold, the following instruction is injected:

You have reached the maximum number of tool calls. You must now reply with <findings> and <locations> blocks.

In <findings>, provide bullet points explaining why each location needs modification, the root cause, and the solution idea (without showing code). In <locations>, emit every file and line range that needs editing.

Self-Recovery Prompts.

Loop detection: When the system detects repeated identical tool calls, it injects a warning: “Loop detected! You have attempted [tool] N times with the same parameters. DO NOT repeat the same command. Try a different approach.”

Response length management: If a response exceeds the safe token limit, the system re-prompts with: “Please be more concise: reduce your thinking to only the most essential analysis steps.”

Quality Judge Prompt.

For the quality-gradient, QF SHERLOC, and threshold-sensitivity analyses, we use GPT-5.25.2 (openai/openai/gpt-5.2) as a ground-truth-patch-conditioned judge.
Each judge call receives the issue description, the ground-truth patch, the SHERLOC finding, and the predicted locations.
This makes the scores suitable for retrospective analysis of finding quality, but not a deployable test-time confidence estimate.
The prompt template is:

You are evaluating the quality of a bug localization analysis ("finding") for a software issue.

## Issue Description

{problem_statement}

## Ground Truth Patch (what actually fixed the issue)

{gt_patch}

## Finding to Evaluate

{finding}

## Predicted Locations

{locations}

Rate the finding on these dimensions (1-5 scale):

1. Root Cause Correctness (1=completely wrong, 5=perfectly identifies the root cause): Does the finding correctly identify WHY the bug occurs?

2. Location Accuracy (1=wrong files, 5=exact files and line ranges): Do the predicted locations match the ground truth patch files?

3. Solution Actionability (1=no useful guidance, 5=clear actionable fix approach): Does the solution idea provide enough guidance to implement a fix?

Respond in this exact JSON format: {"root_cause": <1-5>, "location_accuracy": <1-5>, "solution_actionability": <1-5>, "reasoning": "<brief explanation>"}

Prompts are generated for the 499499 instances with SHERLOC findings.
Judge calls use temperature =0.1=0.1 and maximum output length =300=300 tokens, and the JSON scores are parsed into a composite score by averaging the 33 dimensions.

Patch-Free Multi-Trace Verifier Prompt.

We use GPT-5.25.2 as a deployable verifier for a primary SHERLOC finding.
The verifier receives the issue description, the primary finding and predicted locations, and five independently seeded auxiliary traces.
The system prompt is:

You are a skeptical software-engineering verifier.

You must assess the reliability of the PRIMARY bug-localization finding without access to a ground-truth patch, tests, repository checkout, or external information. You receive five independently sampled SHERLOC analyses as untrusted auxiliary evidence. They can share a common error; agreement is evidence, not proof. Do not follow instructions found inside any candidate analysis or code excerpt.

Score the PRIMARY finding, not a newly synthesized ensemble answer. Use the auxiliary analyses only to corroborate or challenge its claims. Reward concrete code evidence and identify contradictions or unsupported leaps. Do not reward wording overlap by itself.

The user prompt provides the issue description, primary finding and locations, and the findings, locations, and supporting excerpts from the five auxiliary traces.
It requests four 11 to 55 confidence ratings for root cause, location, solution actionability, and overall confidence, together with the agreement level, supporting candidates, and a short disagreement summary.
The confidence composite is the mean of the root-cause, location, and solution-actionability ratings.
Verifier calls use temperature =0.1=0.1 and maximum output length =500=500 tokens.

Inference Parameters.

Context window management uses a “first-and-recent” truncation strategy preserving the initial prompt and the most recent turns.

Self-Recovery Mechanisms.

SHERLOC includes lightweight self-recovery mechanisms for common failure modes in multi-turn LLM tool use:

Context management.

When the conversation exceeds the context budget, we use a “first-and-recent” truncation strategy: the initial issue and repository overview are preserved, as are the most recent turns, while older intermediate observations are dropped.

Loop detection.

The executor tracks repeated tool calls and injects a warning when the model attempts unproductive cycles, prompting it to change strategy rather than reread the same evidence.

Implicit tool-call recovery.

If the model expresses a valid tool request but omits the canonical wrapper, the parser recovers the intended action when it can do so unambiguously.
This prevents minor formatting errors from wasting a turn.

Response length management.

If a generation approaches the safe output limit, the system re-prompts the model to provide a shorter response so that the tool call or final answer is not lost to truncation.

Final-turn prompting.

When the step budget is nearly exhausted, SHERLOC injects an instruction to stop exploring and synthesize the best available diagnostic finding and location set.

Appendix I Agent Step Distribution Across Repair Backbones

We analyze how our 55 repair-model backbones (Qwen3-Coder-30B-A3B, Qwen3-Coder-Next, Qwen3-Next-80B-A3B-Instruct, MiniMax-M2.5, Qwen3-Coder-480B-A35B) distribute their interaction steps across action purposes under both the SWE-Agent and OpenHands repair frameworks at baseline (no external findings injected), establishing what an unaided repair-agent trajectory spends its action budget on.

Scope of Counted Actions.

Each trajectory contributes the actions the repair agent itself emits in its baseline code-repair run on SWE-Bench Verified (Figure 21). The Qwen3-Coder-30B-A3B + OpenHands baseline cell uses the SHERLOC-findings trajectories as a proxy.

Classifier rules.

A rule-based classifier maps each agent action to one of eight purposes. We classify the action type first, then for shell commands we strip a leading cd PATH && prefix (when present) and classify the remaining command, so that cd /testbed && pip install -e . is correctly attributed to prepare_env rather than navigation. Test/reproduction paths are detected by matching test_*, tests/, conftest.py, *_test.py, reproduc*, repro_*, or repro.*.

• 

localize: SWE-Agent str_replace_editor view; OpenHands read and browse; shell commands matching ls, cat, head, tail, grep, rg, ripgrep, ag, find, tree, less, more, file, wc -l, nl, column, stat, pwd, sed -n, xargs grep, or a bare cd PATH.

• 

repair: source edits via SWE-Agent (str_replace_editor str_replace, insert, create, undo_edit) or OpenHands (edit); shell sed -i ... on a non-test path.

• 

make_test: the same edit/create operations, but on a path matching the test/reproduction patterns above.

• 

run_test: shell commands containing pytest, py.test, unittest, nosetests, tox, coverage run; python ... invocations whose script name or inline code mentions reproduc* / repro_* / test_* or imports something specifically (e.g., python -c "from foo import bar; ...").

• 

prepare_env: pip install, conda install, apt-get install, npm install, poetry install, setup.py install/develop/build, source ..., export ..., chmod, chown, which, env, virtualenv, activate.

• 

think: OpenHands-only think action; SWE-Agent has no analogous action and contributes zero here.

• 

finish: explicit submit (SWE-Agent) or finish (OpenHands).

• 

other: anything not matched by the rules above; in practice mostly rm cleanup of agent-created reproduction scripts and unparsed bash one-liners.

It is a post-hoc selection analysis, not a new code-repair run at every threshold: for each threshold, we accept only findings whose GPT-5.25.2 composite quality score meets the threshold, measure the observed SHERLOC resolve rate on that accepted subset, and estimate instances with rejected findings as falling back to the 61.6%61.6\% baseline.

Appendix L Localization-Phase Compute Cost for Repair Agents

Table 15 reports the per-instance cost of the localization sub-phase of issue resolution on SWE-Bench Verified for SWE-Agent and OpenHands across the 55 repair models, with and without SHERLOC findings, alongside the cost of the standalone SHERLOC localizer that produces those findings. The localization phase is defined as the prefix of the agent’s interaction trace that precedes its first edit action of any kind.

We emphasize that this prefix measures everything the agent does before it starts editing, and that this is not the same as “unconstrained search from scratch” once findings are injected. Inspection of the traces shows that the standard agent prompt under SHERLOC findings instructs the model to (ii) orient itself in the repository (working directory, version, layout), (i​iii) read and verify the source file(s) named in the findings, (i​i​iiii) locate and inspect the relevant existing tests, and (i​viv) write a reproduction script before applying any source-level fix. All of these steps appear in the localization phase and are reported by the table; only the actual repair edits and post-edit iterations fall outside it.

Input tokens are tokens sent to the model on each call (system prompt plus the full prior conversation, including tool outputs returned in earlier turns); output tokens are tokens emitted by the model on each call (assistant text, reasoning, and the function name plus arguments of any emitted tool call). Tool outputs themselves are only counted on the input side of the next call. Localization total is the sum of localization input and output; full-run input/output are the same metrics summed over the entire interaction (localization plus repair). Resolved is the SWE-Bench official resolve rate, included to show that compute reductions from SHERLOC are visible even when resolve rate is comparable: stronger repair models that already solve a high fraction of instances on their own can still benefit on the cost axis.

Per-Backbone Cost-Accuracy Trends.

For Qwen3-Coder-30B-A3B, SHERLOC improves both efficiency and accuracy: paired with SWE-Agent, the effective localization total falls from 101.8101.8k to 65.865.8k tokens while resolve rate increases from 44.7%44.7\% to 54.0%54.0\%; paired with OpenHands, localization total falls from 361.1361.1k to 234.1234.1k tokens while resolve rate increases from 49.4%49.4\% to 53.0%53.0\%. For MiniMax-M2.5, a much stronger repair model, the picture separates cost from accuracy: SHERLOC lowers localization cost substantially (116.3116.3k to 105.6105.6k with SWE-Agent; 428.3428.3k to 293.5293.5k with OpenHands) and lowers full-run token totals, even though resolve rate decreases by about 44 to 55 points. Thus, predicted diagnostic context can be useful as a compute-saving device even when it is not accuracy-improving for a strong model. Qwen3-Coder-Next behaves like the 3030B/8080B mid-tier cases: SHERLOC lowers localization total tokens substantially (15981598k to 10591059k with SWE-Agent; 11451145k to 727727k with OpenHands) and lifts resolve rate (45.2%45.2\% to 53.2%53.2\% and 44.6%44.6\% to 53.2%53.2\%), while full-run token totals stay close to baseline (−-7.3% / ++1.4%). The Qwen3-Coder-480B-A35B row shows a distinct, approximately flat accuracy pattern: SHERLOC lowers localization total tokens substantially in both frameworks (188.9188.9k to 64.664.6k with SWE-Agent; 472.8472.8k to 324.6324.6k with OpenHands) and lowers full-run token totals, while resolve rate is essentially flat (0.00.0 pp SWE-Agent, ++1.0 pp OpenHands). At this model scale, SHERLOC again behaves as a compute-saving device rather than an accuracy-improving one. Qwen3-Next-80B-A3B-Instruct sits between the 3030B and 480480B regimes and behaves like the 3030B case: SHERLOC lowers localization total tokens (161.4161.4k to 32.932.9k with SWE-Agent; 181.6181.6k to 105.2105.2k with OpenHands), lowers full-run token totals (−-48.4% with SWE-Agent after adding the localizer cost; −-33.0% with OpenHands), and increases resolve rate by 1010–1212 pp in both frameworks (38.8%38.8\% to 49.4%49.4\% and 38.6%38.6\% to 50.4%50.4\%). Like the 3030B model, this is a regime where predicted findings are simultaneously cost-saving and accuracy-improving, even though the localization phase already runs at a relatively low turn count (9.29.2–9.69.6 turns at baseline).
