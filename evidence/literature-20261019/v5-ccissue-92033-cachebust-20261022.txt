Summary

In a single long-running Claude Code session (resumed intermittently over ~36 hours on the 5x Max plan), the prompt cache was repeatedly and fully invalidated by mid-conversation changes to the tool/MCP/agent list — not by idle/TTL expiry. This caused multiple full-price cache rewrites (each ~780K-860K tokens, billed at the 2x cache-write rate) within minutes of each other, including one pair only 1 minute apart, burning what looked like an entire 5-hour session budget in under 10 minutes.

The cache was demonstrably working correctly for three consecutive turns (reads climbing 897K → 900K → 903K, writes near-zero). It was then invalidated specifically at the moment new tool/agent/MCP-server definitions were loaded into the session (visible in the transcript as deferred_tools_delta, agent_listing_delta, and mcp_instructions_delta attachment events), forcing the very next turn to eat a full-price, 2x-weighted rewrite of the entire accumulated context (~800K+ tokens) — despite that context having just been cached a minute prior.

This is distinct from (and in addition to) cache expiry after idle gaps, which also repeatedly hit the same session across resumes spanning Sep 2–4, each time re-billing an ever-larger context (300K tokens growing to 860K+ tokens over the session's lifetime) at full 2x cache-write cost.

Impact

No warning is surfaced to the user before an action (e.g., a background ToolSearch call, a new MCP server connecting) triggers a full cache invalidation.

No setting exists to prevent tool/MCP-list changes from invalidating the cache prefix mid-conversation.

No setting exists to cap or warn on an unusually large single-turn cache-write.

Combined with no context-compaction/summarization that persists in the cache, a single long-lived session (common in real usage, e.g., a standing project thread resumed over days) can silently accumulate an ever-growing context that gets fully, repeatedly rebilled at 2x cost every time anything touches the tool/instruction prefix — even seconds after the last rebuild.

Concretely: this pattern consumed what appeared to be an entire 5-hour Max-plan session budget in under 10 minutes of actual interaction.

Requested

Avoid invalidating the prompt cache prefix when only the available tool/agent/MCP list changes (e.g., via deferred tool loading) — ideally by structuring the system prompt so tool/instruction deltas don't sit ahead of the cached conversation history in the prefix.

Surface a warning (or at least a /context-visible flag) when an action is about to force a full cache rewrite, especially when the rewrite size is large relative to recent turns.

Expose a setting to control or defer tool/MCP-list changes mid-session so they don't retroactively invalidate an expensive, already-paid-for cache.

Consider a persisted, compacted-context mechanism so resuming a long session doesn't require re-paying full price for the entire accumulated history every time the cache is invalidated.

Environment

Claude Code desktop app, version 2.1.255

Plan: Claude Max 5x

Follow-up correction: I initially believed a promptCacheTtl / subagentPromptCacheTtl setting existed to at least partially mitigate this. That was wrong. I checked the actual installed claude-code-settings.schema.json directly — there is no cache-TTL setting, and no setting anywhere that prevents mid-session tool/MCP-list changes from invalidating the prompt cache.

The closest related settings are autoCompactEnabled/autoCompactWindow (size-based compaction when context fills, unrelated to the mid-conversation cache-busting behavior described above) and awaySummaryEnabled (cosmetic recap only, no cost impact).

So to be precise about the ask: there is currently no user-facing mitigation at all for the tool/MCP-list cache invalidation described in this issue — not a hidden setting, not a flag. This strengthens request #3 in the original report (expose a setting to defer mid-session tool-list changes) since right now there is nothing to reach for.

Independent aggregate evidence from 506 local Claude Code session logs (~3.2 GB corpus) confirms this is systemic rather than isolated:

2,766 cache-bust events re-billed 224.4 million input tokens

approximately 81,000 tokens re-billed per bust

1,399 mid-session tool/skill/MCP-list mutations

mutations occurred across 191 of 506 sessions (38%)

measured impact: 13.5% of total Claude spend in the corpus

Method: counts came from Anthropic's own message.usage fields (cache_creation_input_tokens / cache_read_input_tokens) and the transcript attachment/delta events, not character-based token estimates. The ~81K average delta is substantially larger than the instruction and skill manifests alone and is consistent with MCP tool schemas entering after the first request. Relocating rarely used MCP servers reduces exposure but does not fix the client behavior; there is no local setting that makes startup tool discovery stable before the first request or prevents the resulting full-prefix rewrite.

Environment observed: Claude Code 2.1.260 on Windows 11, including sessions launched by Claude Desktop.

Averaged over one server changing: ~12,500 tokens, ~8.7 s on this machine, on

top of the messages block that follows and is invalidated regardless.

The sharp edge is adding a new server. Under an alphabetical sort, a server

whose name starts early — say airtable — inserts right after the built-ins and

invalidates 52 %+ of the tool block even though nothing else changed. The

damage is a function of the new server's name, which is not a property anyone

would expect to matter for performance.

Suggested fix, cheapest first:

Order MCP servers by first-seen / registration order, appending new ones at

the end, rather than sorting by name. A newly added server then costs only

its own definitions. On this config that turns an average change from ~12,500

tokens into ~4,900.

Register every configured server before issuing the first request, so the

list cannot change between turn 1 and turn 2 — which is the original report

here.

If a stable order is impossible, emit the largest and most stable sources

first (built-ins, then long-lived servers) so that whatever does churn sits

in the tail.

None of this needs block-level KV surgery — the runs are already contiguous, so

plain prefix caching captures nearly all of it once the order stops moving.

Measured on Claude Code 2.1.260 against a local model, where usage.input_tokens

is directly observable. The same prefix layout goes to the hosted path, so the

ordering effect should be identical there; I just cannot see the cache to confirm.

Related: I filed #92524 for the other cross-session invalidator — the per-session

scratchpad UUID sitting in the system prompt, ahead of this whole tool block.
