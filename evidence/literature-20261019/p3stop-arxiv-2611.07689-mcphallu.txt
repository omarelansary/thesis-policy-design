Abstract

Large language model agents are increasingly deployed through the Model Context Protocol (MCP), which allows them to discover and invoke tools across multiple servers at runtime. Existing MCP benchmarks primarily measure task completion; where they diagnose failures, they do so after execution rather than building specific reasoning, execution, and memory failure risks into task construction.

We introduce MCPHallu, a benchmark for diagnosing hallucination-prone agent failures in MCP environments along three axes: reasoning, execution, and memory. MCPHallu contains 358 tasks across five capability domains and runs on 36 production MCP servers in isolated containers. Each task is designed with a structural trigger that makes one of four subtypes the dominant failure risk: Branch Collapse, Unreachable Goal, Tool Misuse, or Context Forgetting. This design enables subtype-level analysis rather than aggregate task success alone.

We evaluate fourteen frontier LLM agents from eight vendors on 5,012 trajectories. Current MCP agents remain vulnerable to hallucination-inducing tool environments, achieving an average score of 0.642 on a [0,1][0,1] scale (higher is better). Failures concentrate on Unreachable Goal tasks, where the average score drops to 0.458 and 23.2% of runs pass, indicating that agents often continue issuing tool calls or claim successful completion rather than recognizing infeasible goals. Subtype rankings diverge sharply: a model’s rank shifts by 6.9 of 13 positions on average across subtypes, and Branch Collapse is uncorrelated with Unreachable Goal across models (r=−0.12r=-0.12). MCPHallu is released at https://github.com/J1zz/mcp_hallu.

1 Introduction

LLM agents have been widely applied to tool-augmented tasks (Yao et al., 2023; Schick et al., 2023; Wang et al., 2024; Patil et al., 2023), and the Model Context Protocol11
            1

          https://www.anthropic.com/news/model-context-protocol (MCP) has become a common interface for connecting them to external tools, APIs, databases, and file systems. Unlike earlier tool-use settings, MCP agents discover tools across multiple servers at runtime, accumulate state as each call mutates the environment, and often run for many sequential steps. This raises a question existing benchmarks do not separate cleanly: do MCP agents fail for the same reasons, at the same rates, across the distinct stages of the agent pipeline?

To answer this, we present MCPHallu, a benchmark that diagnoses hallucination-prone failures in MCP agents at the level of subtypes and trajectory steps. Prior tool-use hallucination benchmarks (Zhang et al., 2024; Xu et al., 2025) diagnose hallucinations only at the tool-call level, without considering the reasoning and memory failures that arise once tool calls are chained into long, stateful trajectories. Recent MCP benchmarks (Liu et al., 2025b; Luo et al., 2025; Wang et al., 2025b; Zhou et al., 2026) emphasize task completion in this setting; MCP-Atlas additionally provides an 11-category post-hoc failure taxonomy (Bandi et al., 2026). MCPHallu fills this gap: each task is built around a structural trigger that promotes one of four hallucination subtypes as the dominant failure risk, while its correct behavior (completion, or recognizing infeasibility for Unreachable Goal) stays verifiable. Because the trigger shifts a task’s failure distribution toward its target subtype, MCPHallu supports subtype-targeted analysis at the population level, even when individual long-horizon trajectories exhibit interacting errors.

MCPHallu covers five capability domains (general search, analytics, productivity, finance, and coding) and is built on 36 production MCP servers running in isolated Docker containers rather than synthetic mocks. It contains 358 tasks approximately balanced across 4 hallucination subtypes (Branch Collapse, Unreachable Goal, Tool Misuse, Context Forgetting) and 3 difficulty levels. Ground truth is verified through dynamic scripts executed against live servers for stateless tasks, and through state assertions queried after execution for stateful tasks. A per-task claim graph annotates the dependency structure of the correct trajectory, which the evaluation protocol uses to score whether the agent’s tool sequence honored the task’s logical structure, independent of final-answer correctness.

We evaluate 14 frontier LLM agents from eight vendors on 5,012 trajectories. MCPHallu is challenging for all current systems: the best model achieves an overall score of 0.728, and average performance across models is 0.642. Unreachable Goal is the hardest subtype, indicating that agents often continue acting or overstate completion instead of recognizing infeasible goals. Subtype rankings also diverge across models, suggesting that reasoning, execution, and memory hallucinations reflect partially distinct capabilities rather than a single notion of agent quality.

Our contributions are as follows:

• 

We release MCPHallu, a benchmark of 358 tasks across 5 capability domains and 36 production MCP servers, in which each task is built around a structural trigger that promotes one of four hallucination subtypes, enabling subtype-targeted evaluation.

• 

Every MCPHallu task is scored primarily by deterministic evidence: live-server reference scripts or post-execution state assertions for Branch Collapse and Context Forgetting, and trajectory-structure checks for Unreachable Goal and Tool Misuse, so that the LLM judge contributes only 20–30% of each subtype score.

• 

We evaluate 14 frontier LLMs and show that current MCP agents remain vulnerable to hallucination-inducing tool environments, with no model scoring above 0.728 on average.

• 

We characterize three trajectory-level failure modes (false completion, tool indiscipline, and state non-commitment) and show that subtype rankings diverge across models (r=−0.12r=-0.12 between Branch Collapse and Unreachable Goal), arguing against ranking MCP agents by a single aggregate score.

2 Related Work

Hallucination in LLMs and agents.

Hallucination has been studied in static settings such as summarization (Maynez et al., 2020) and open-domain QA (Lin et al., 2022; Mallen et al., 2023), and recent surveys extend the analysis to multi-step agents (Lin et al., 2025; Tonmoy et al., 2024). This line of work organizes agent hallucinations along reasoning, execution, and memory, and we adopt these axes in our taxonomy. Related evidence from retrieval-grounded (Sun et al., 2025; Li et al., 2023a) and multimodal (Dong et al., 2025; Bai et al., 2025) settings shows that hallucinations often arise from failures to ground model outputs in external evidence.

Tool-use and agent benchmarks.

Existing tool-use hallucination benchmarks (ToolBH (Zhang et al., 2024), RelyToolBench (Xu et al., 2025)) assume single-server, stateless settings, as do earlier API- and tool-use benchmarks (Li et al., 2023b; Ma et al., 2024; Wang et al., 2025a; Qin et al., 2023). General agent benchmarks (BFCL (Patil et al., 2025), τ\tau-bench (Yao et al., 2024), WebArena (Zhou et al., 2024), AgentBench (Liu et al., 2025a), SWE-bench (Jimenez et al., 2024), OSWorld (Xie et al., 2024), GAIA (Mialon et al., 2023), ALFWorld (Shridhar et al., 2021)) and MCP-specific benchmarks emphasize task completion; MCP-Atlas additionally supports post-hoc failure diagnosis (Bandi et al., 2026). MCPHallu is complementary: it asks which hallucination subtype is responsible, under the three conditions that distinguish MCP from earlier tool-use settings (cross-server ambiguity, live state, long horizons). 3 Hallucination Taxonomy in MCP Agents

We begin by defining the failure class our benchmark targets.

Definition 1 (MCP agent hallucination)

Let an MCP agent execute a trajectory
τ=(a1,o1,a2𝐶𝐿𝑂𝑆𝐸,\tau=(a_{1},o_{1},a_{2}, 𝑂𝑃𝐸𝑁o2,…,aT,oT,y)o_{2},\dots,a_{T},o_{T},y), where each ata_{t}
is a tool call, each oto_{t} is the observation returned by the
MCP environment, and yy is the agent’s final output.
An MCP agent hallucination is any element of τ\tau that
the agent treats as valid (i.e., presents in yy or relies on in
downstream actions without flagging inconsistency) with respect to
the task instruction II, the live environment state, or the actual
capabilities of the available tools, but that is in fact inconsistent with
at least one of these. This excludes failures the agent correctly
identifies and reports.

This definition is trajectory-grounded: hallucinations may occur in a tool call, in the interpretation of a live observation, or in the final response, and a single trajectory may contain several. The distinguishing feature relative to general agent failure is the implicit validity claim. An agent that asks for clarification, reports infeasibility, or surfaces a tool error is failing the task but not hallucinating, whereas an agent that reports wrong-branch outputs as correct, claims completion of infeasible actions, uses confusion-tool outputs as task answers, or substitutes remembered values is making an implicit validity claim about an inconsistent element. Under this lens, our four subtypes correspond to wrong-branch outputs presented as correct (BC), infeasibility denial (UG), confusion-tool outputs presented as valid (TM), and substituted-value claims (CF); these extend hallucination beyond factual fabrication to the agent setting, unified by the structural property our protocol targets.

Following the three-axis taxonomy of (Lin et al., 2025), we organize MCP agent hallucinations along axes corresponding to distinct stages of the ReAct loop: reasoning (planning), execution (invoking a tool), and memory (carrying information across steps). We use the axes constructively, to design tasks whose structural trigger biases the failure distribution toward one stage; a single trajectory may still exhibit errors on several axes. Within each axis we identify operational subtypes that can be triggered by a controllable structural feature of a task. Figure 2 illustrates the failure forms on each axis, and Table 2 summarizes the four subtypes we instantiate from them.

Figure 2: Hallucination failure forms at the three stages of the agent loop, each with a toy example. MCPHallu instantiates them as Branch Collapse and Unreachable Goal (reasoning), Tool Misuse (execution), and Context Forgetting (memory).

Reasoning hallucinations.

The agent’s plan fails to account for constraints available at planning time. We focus on two subtypes that share this root cause but differ in constraint type. Branch Collapse violates a data-conditioned constraint: the task contains mutually exclusive branches gated on a live tool output, but the agent follows the wrong branch or conflates outputs across branch instances. Unreachable Goal violates a capability constraint: no available tool can satisfy the task goal, yet the agent continues acting or presents an infeasible end state as achievable. Both originate in the planning step rather than in tool invocation or context retention, but their structural triggers and detection signals (Table 2) are distinct.

Execution hallucinations.

The agent holds incorrect beliefs about which tool to invoke or how to invoke it. We focus on Tool Misuse: when tools have overlapping schemas but distinct semantics, the agent selects an inappropriate tool or supplies fabricated, swapped, or invalid arguments.

Memory hallucinations.

The agent fails to maintain consistent context across steps. We focus on Context Forgetting: a value retrieved early in the trajectory must be carried forward through intervening same-domain distractors, but the final output uses a stale, approximate, or substituted value instead.

We choose the four subtypes by a single criterion: each can be promoted by a controllable structural trigger and leaves a distinct detection signal in the trajectory (Table 2), making subtype-targeted evaluation possible. The resulting set is representative rather than exhaustive, and subtypes can co-occur within a trajectory. The same criterion sets the number of subtypes per axis. Execution and memory each contribute one subtype because their failure forms share a trigger and a signal: Tool Misuse is defined over both erroneous tool selection and faulty invocation under overlapping schemas (this release instantiates selection; Appendix I), and Context Forgetting covers stale, approximate, and substituted values of the retrieved quantity. Reasoning contributes two because data-conditioned and capability constraints call for different triggers and signals. Reporting subtypes separately rather than as a single aggregate is supported empirically by the rank-instability analysis in Appendix F.4: per-model subtype rankings spread across an average of 6.86 positions out of 13 possible, and Branch Collapse correlates only weakly with Unreachable Goal across models (r=−0.12)(r=-0.12). This near-zero correlation is the expected signature of two subtypes that share the reasoning axis while probing complementary planning weaknesses (data-conditioned vs. capability constraints). A model that handles one is not reliably better at the other, so both subtypes carry independent diagnostic information, and collapsing them would conceal these distinct failure patterns. This within-axis divergence is consistent with (Lin et al., 2025) and supports retaining both subtypes. Appendix I describes how further failure modes, such as multi-agent coordination and cross-session memory, extend this taxonomy.

4 MCPHallu

MCPHallu instantiates the four hallucination subtypes from §3 as 358 executable tasks, each built around a controllable structural trigger that promotes the target subtype as the dominant failure risk while keeping the correct behavior well defined. Subtype labels denote the failure mode each trigger is designed to elicit, and we validate this targeting at the population level in §4.3. This section gives the formal task definition (§4.1), describes the live MCP environment (§4.2), the construction pipeline (§4.3), and the subtype-specific evaluation protocol (§4.4).

4.1 Task Definition

Each MCPHallu task is a tuple (I,𝒯,h,d,G,C)(I,\mathcal{T},h,d,G,C), where II is a natural-language instruction, 𝒯\mathcal{T} is the set of MCP tools made available to the agent, h∈h\in {Branch Collapse, Unreachable Goal, Tool Misuse, Context Forgetting} is the target hallucination subtype, d∈{Easy,Medium,Hard}d\in\{\text{Easy},\text{Medium},\text{Hard}\} is a difficulty level, GG is a ground-truth specification, and C={c1,…,cm}C=\{c_{1},\dots,c_{m}\} is an ordered claim graph. Each claim cic_{i} specifies a required tool, an optional branch identifier, and a list of upstream claims that cic_{i} depends on. The claim graph serves a dual role: at construction time it encodes the task’s structural trigger, and at evaluation time it lets us check whether the agent’s tool sequence respects the required dependency structure. This yields a dependency score (§4.4) that separates plan-structure violations from failures that produce an incorrect final answer despite an otherwise valid tool sequence.

A task is typed as stateless (read-only, e.g., live search) or stateful (mutates environment state, e.g., file or record modification), which determines the form of GG: stateless tasks specify a dynamic reference script executed against live servers at evaluation time, while stateful tasks specify a set of post-execution state assertions. Difficulty is calibrated within each subtype by increasing dependency depth, trigger subtlety, distractor density, semantic tool overlap, or capability mismatch severity. Easy, Medium, and Hard therefore reflect within-subtype complexity rather than a globally comparable hardness scale. The final benchmark contains 358 validated tasks with an approximately balanced distribution across subtypes, domains, and difficulty levels; exact counts are reported in Appendix D.

4.2 Environment

MCPHallu runs against 36 real MCP servers exposing roughly 300 tools in total. All servers are hosted in isolated Docker containers with sandboxed filesystems and allow-listed network egress. Each evaluation episode starts from a fresh container, so stateful writes do not contaminate later runs. We selected servers for both domain coverage and semantic overlap, allowing realistic confusion between tools with overlapping functionality but distinct schemas or semantics. Server-level details and credential requirements appear in Appendix C, and version pinning and maintenance in Appendix I.

We construct tasks in three stages. In tool grounding, we extract tool descriptions, parameter schemas, and return-value specifications directly from live server implementations; these grounded schemas are the only tool information exposed to the generator. In adversarial synthesis, an LLM-based generator (Claude Sonnet 4.6) receives the grounded schemas together with a subtype-specific prompt (Wang et al., 2023) and produces candidate tasks with verifiable correct behavior while making the target subtype the primary failure risk. In filtering and review, we screen each task for executability, self-containedness, non-triviality, and subtype-label consistency, regenerate invalid candidates, and retain only tasks that pass expert review by three annotators.

Because MCP trajectories can exhibit interacting errors, we additionally validate subtype targeting on a stratified human-labeled sample of failed trajectories. Restricting to failures is intentional: only failing runs reveal which failure mode is primary, whereas passing runs only confirm that the trigger was avoided. On this sample, the intended subtype is selected as the primary failure mode in 81% of cases (κ=0.78\kappa=0.78). A finer per-subtype audit of 80 failed runs, with the full intended-versus-observed confusion matrix, appears in Appendix D.5. The residual disagreement reflects tasks where a single trigger activates overlapping failure modes: each trigger promotes its target subtype as the dominant risk, while individual runs may combine failure modes. Of the 19% of runs labeled mixed/other, all are retained in the benchmark with their original structural label, since mixed failures still activate the target trigger; removing these tasks does not change any pairwise model ranking. The final benchmark retains 73% of the initially generated candidates. Full prompts, filtering details, and validation protocols appear in Appendix D.

4.4 Evaluation Protocol

Different subtypes leave different evidence in the trajectory: BC and CF are best evaluated by combining final-answer correctness with trajectory structure; UG by calibrated infeasibility recognition; and TM by whether the agent avoids semantically overlapping confusion tools. We score each subtype with the components that match its evidence, drawn from five in total (Table 4).

Components.

Each task is evaluated along up to three dimensions: an executable outcome verification score (SoS_{o}), a structural score (SdS_{d}, SeS_{e}, or ScS_{c} depending on subtype), and a rubric-based LLM-judge score (SjS_{j}). The deterministic components are the dominant signal across all four subtypes. For Branch Collapse and Context Forgetting, executable outcome verification carries 60% weight and dependency satisfaction 20%, with the judge accounting for the remaining 20%. For Unreachable Goal and Tool Misuse, the structural component carries 70% weight and the judge 30%. The overall MCPHallu score is the mean score over all 358 tasks.

Weight rationale.

The allocation reflects which evaluation signal is closest to the ground-truth notion of correctness for each subtype. For BC and CF, correctness is defined by the final state of the live environment (stateless tasks: dynamic reference script output; stateful tasks: post-execution state assertions); SoS_{o} measures this directly and therefore receives the largest weight. SdS_{d} adds diagnostic information by separating right-answer-via-wrong-path trajectories from right-answer-via-right-path trajectories. For UG and TM, correctness is defined by a structural property of the trajectory itself (whether the agent stopped without taking infeasible actions for UG, whether the agent avoided semantically overlapping confusion tools for TM), and SeS_{e} / ScS_{c} measure these directly.

The LLM judge (SjS_{j}) plays a bounded supporting role. For BC and CF, it disambiguates cases where SoS_{o} assigns coarse credit to partially correct outputs. For UG, it verifies that an early-stop trajectory actually articulated infeasibility rather than terminating for unrelated reasons (e.g., budget exhaustion). For TM, it verifies that the final response is grounded in the correct tool’s output rather than in a confusion-tool output. We bound the judge contribution to 20–30% so that no model’s ranking can be driven primarily by judge preferences; the deterministic components are designed to carry most of the signal.

Score stability.

A natural question is whether rankings change if the judge weight is perturbed. Our cross-judge validation (Appendix H) shows that substituting Claude Sonnet 4.5 for GPT-4o changes scores by at most 0.016 on average (r=0.914r=0.914). Because SoS_{o}, SdS_{d}, SeS_{e}, and ScS_{c} are computed deterministically, all score instability from weight perturbation is bounded by this judge variance. A ±20%\pm 20\% perturbation of the judge weight scales this variance by at most 0.2, yielding a maximum expected score shift of 0.2×0.016=0.0030.2\times 0.016=0.003 per model, far below the 0.028 mean gap between adjacent models in the full ranking. Model rankings are therefore robust to plausible weight choices, and a calibration of the weights against human judgments confirms this (Appendix F.6).

For stateless tasks, SoS_{o} is computed by executing the dynamic reference script against live servers at evaluation time; for stateful tasks, it is the fraction of post-execution state assertions that hold. The dependency score is

Sd=1−#​{violated edges}max⁡(1,#​{checked edges}),S_{d}=1-\frac{\#\{\text{violated edges}\}}{\max(1,\ \#\{\text{checked edges}\})},

where inactive branch edges are ignored. For Unreachable Goal tasks, Se=1S_{e}=1 if the agent correctly declares infeasibility within a probing window of kk tool calls, and decays linearly thereafter: Se=max⁡(0, 1−(tstop−k)/(Tmax−k))S_{e}=\max(0,\ 1-(t_{\text{stop}}-k)/(T_{\text{max}}-k)) if the agent declares infeasibility at step tstopt_{\text{stop}}, and 00 if no infeasibility declaration is made. The probing window kk permits a small number of verification calls before penalization begins; we set k=2k=2 based on the minimum number of tool calls required to disambiguate feasibility in our task design (typically one schema/capability check plus one trial call). This choice does not penalize agents that probe before declaring infeasibility, while still rewarding early recognition over prolonged false-completion behavior. For Tool Misuse tasks,

Sc=1−|Uc∩Utrajectory|max⁡(1,|Uc|),S_{c}=1-\frac{|U_{c}\cap U_{\text{trajectory}}|}{\max(1,\ |U_{c}|)},

where UcU_{c} is the set of confusion tools curated for the task and UtrajectoryU_{\text{trajectory}} is the set of distinct tools invoked in the trajectory. The numerator counts distinct confusion tools used rather than invocation count, so repeated probes of the same tool are penalized no more than a single probe; the diagnostic signal is whether the agent considered a semantically inappropriate tool, not how many times it called it. Binary pass criteria are subtype-specific and reported in Appendix F. We allow semantically equivalent trajectories and do not penalize exploratory calls unless they violate active branch constraints or invoke curated confusion tools.

Ideal behavior.

An ideal agent never triggers the designed hallucination, which is the behavior that earns the maximum score of 1.0; expert humans come close, scoring 0.88 on a stratified 40-task sample against 0.728 for the best model on the full benchmark. On the three feasible subtypes it completes the task as specified by the executable ground truth, and the claim graph CC gives a sufficient call sequence (a median of 7 calls for Branch Collapse and Context Forgetting, and 2 for Tool Misuse). On Tool Misuse, the target tool is identifiable from parameter semantics, the return-value specification, and the instruction, and the ideal agent grounds its answer in that tool’s output without consulting confusion tools. On Unreachable Goal, it recognizes from the tool inventory that no available tool can satisfy the goal and reports this instead of acting; when feasibility depends on a tool output, a brief probe retains most of the credit. Indiscriminate refusal does not pay off: on Tool Misuse, trajectories that invoke neither the correct nor a confusion tool pass only 8.0% of the time (Table 7). 5 Experiments

5.1 Setup

Models.

We evaluate 14 frontier LLMs from eight vendors, spanning both proprietary and open-weight families: GPT-4o and GPT-5-chat (OpenAI); Claude Haiku 4.5, Sonnet 4.5, Opus 4.5, Sonnet 4.6, and Opus 4.6 (Anthropic); Gemini 3 Flash (Google); Doubao-Seed-1.8 (ByteDance); DeepSeek-V3.1 and DeepSeek-V4 (DeepSeek); Qwen3.5-397B (Alibaba); GLM-5.1 (Zhipu AI); and Kimi-K2.6 (Moonshot AI).

Agent framework.

All models are evaluated under a ReAct-style agent loop (Yao et al., 2023), with access to the task’s tool set 𝒯\mathcal{T} (§4.1), a context window of 128k tokens, and a budget of 20 tool calls per task. Tool calls are executed against live MCP servers in isolated Docker containers, and environments are reset between episodes to ensure reproducibility. Detailed inference settings appear in Appendix E. Under a plan-and-execute scaffold and an infeasibility-aware prompt, the two hardest subtypes stay the same (Appendix F.7).

Scoring.

We use the per-subtype scoring scheme from §4.4. Scores are in [0,1][0,1], where higher is better. In addition to mean score, we compute a binary pass indicator from the subtype-specific rubric and use it in the analysis below. Our primary semantic judge is GPT-4o, following standard LLM-as-a-judge practice (Zheng et al., 2023); cross-judge and human validation are reported in Appendix H.

5.2 Main Results

Table 5 reports results for all 14 LLMs on MCPHallu. The benchmark is challenging across the board: the best model achieves 0.728 overall, while the mean across models is 0.642 with a pass rate of 47.8%. Unreachable Goal is the hardest subtype for 12 of the 14 models, whereas Tool Misuse and Branch Collapse are consistently easier. Performance also decreases with difficulty for 13 of the 14 models, indicating that the structural triggers remain effective as interaction complexity grows. Bootstrap 95% confidence intervals for every model and subtype appear in Appendix F.5; overall intervals have a half-width of about 0.03–0.04.

6 Analysis

The per-subtype results in §5.2 show that MCPHallu is challenging overall, but aggregate scores hide the trajectory patterns behind these failures. We focus on two trajectory-level behaviors that are especially diagnostic of MCP hallucinations: false completion on Unreachable Goal tasks and tool indiscipline on Tool Misuse tasks. Additional analyses on state commitment and per-model rank instability are deferred to Appendices F.3 and F.4.

Additional observations.

Appendices F and G show that Context Forgetting is harder on stateful write tasks and that subtype rankings are unstable across models (mean per-model rank spread 6.86). Together with our subtype-validation and judge-robustness checks (Appendix D, H), these findings support reporting subtype-level reliability rather than aggregate success alone.

Scoring component analysis.

To assess the contribution of the LLM judge versus the deterministic components, we compare per-model rankings produced by the judge alone (SjS_{j}), by the deterministic components alone, and by the full multi-component score. The deterministic-only ranking and the full-score ranking agree closely (Spearman ρ=\rho= 0.97, with no model changing rank by more than 2 positions), indicating that deterministic components carry most of the signal under our weight choice. The judge-only ranking correlates with the full score at r=r= 0.86, lower than the deterministic-only correlation and consistent with the judge contributing a 20–30% supplementary signal.

This separation has two consequences. First, the deterministic components are non-redundant: of trajectories where SjS_{j} and the multi-component score disagree by more than 0.2, 71% are cases where the agent produced the right final outcome via the wrong tool path, or the wrong final outcome via the right tool path—a judge-only score cannot separate these. Second, this non-redundancy compounds with the cross-judge stability reported in §4.4: the judge is not only a small fraction of the total score, but the part it carries is different from what the deterministic components measure, so the two signals act as a check on each other rather than a single point of failure.

7 Discussion and Conclusion

MCPHallu shows that hallucination-prone failures in MCP agents are not well captured by aggregate task success alone. Across 14 frontier models, failures concentrate on Unreachable Goal tasks while subtype rankings vary, suggesting that reasoning, execution, and memory hallucinations are only partially aligned capabilities.

These findings have implications for deployment. The top model overall may not be the best fit when a deployment is dominated by one failure mode: the overall leader ranks seventh on Branch Collapse. MCP evaluation should therefore report subtype-level reliability alongside aggregate success.

MCPHallu diagnoses agents at the level of predominant failure risk, which stays well defined even when long-horizon trajectories exhibit interacting errors. It also extends hallucination evaluation to the agent setting: in every subtype the agent presents an inconsistent trajectory element as valid, a failure with different deployment consequences from honest failure, and one that our protocol detects. We hope MCPHallu helps diagnose why MCP agents fail, not just whether they fail.

Extensibility and maintenance.

Because each subtype is defined by a structural trigger and a detection signal, a new failure mode enters MCPHallu through the same generate–filter–review pipeline that built the current 358 tasks, and new servers and tools are absorbed the same way. Servers run from version-pinned packages and commits inside a single container image with seeded data, and each task’s reference script and state assertions double as a regression test against upstream drift. Appendix I details the extension path and versioning plan; Appendix J discusses scope.

B.1 Branch Collapse

Original prompt.

You are a quantitative analyst preparing a daily market briefing for
two tech stocks: AAPL (Apple Inc.) and MSFT (Microsoft Corp.).
Your workflow is as follows:

1. Fetch the current real-time quote for both AAPL and MSFT using the
   appropriate quote tool.

2. For each stock, evaluate the ‘percent_change‘ field from the quote
   response:
   - Branch A (Strong Move): If abs(percent_change) >= 1.5, fetch the
     14-period RSI for that stock using a 1-day interval
     (outputsize=5).
   - Branch B (Quiet Day): If abs(percent_change) < 1.5, fetch the
     20-period Bollinger Bands for that stock using a 1-day interval
     (outputsize=3).

3. Apply the branch logic independently for AAPL and MSFT.

4. After collecting the supplemental indicator data for both stocks,
   produce a final briefing that includes:
   - For each stock: the current price (from ‘close‘), the
     ‘percent_change‘, which branch was triggered, and the most recent
     indicator value (RSI value if Branch A, or the most recent
     ‘upper_band‘ and ‘lower_band‘ if Branch B).
   - A tie-break rule: if both stocks trigger the same branch, list
     the stock with the larger abs(percent_change) first. If they
     trigger different branches, list the Branch A stock first.

Available tools.

twelvedata_GetQuote, twelvedata_GetTimeSeriesRsi, twelvedata_GetTimeSeriesBBands, twelvedata_GetPrice, twelvedata_GetTimeSeries, twelvedata_GetTimeSeriesMacd, twelvedata_GetTimeSeriesEma, twelvedata_GetTimeSeriesSma, twelvedata_GetTimeSeriesAtr, twelvedata_GetTimeSeriesAdx, twelvedata_GetEod, twelvedata_GetMarketState, twelvedata_GetProfile, twelvedata_GetExchangeRate, twelvedata_GetDividends, twelvedata_GetEarnings

Structural trigger.

This task contains mutually exclusive branch logic applied
independently per stock. Each symbol must remain tied to its own
retrieved quote fields and its own downstream tool outputs. This makes
the task vulnerable to branch collapse when one branch instance fails
and the model fills the gap using outputs from another instance.

Model execution trace.

   -> close=270.17001, percent_change=-0.19947

2. twelvedata_GetQuote(symbol=MSFT)
   -> close=424.45999, percent_change=-1.11590

   time_period=20, outputsize=3)
   -> upper_band=277.17257, lower_band=251.55143

4. twelvedata_GetTimeSeriesBBands(symbol=MSFT, interval=1day,
   time_period=20, outputsize=3)
   -> upper_band=449.75488, lower_band=353.45212

Final model output:
- AAPL reported as Branch B with upper/lower bands 277.17 / 251.55
- MSFT reported as Branch B with upper/lower bands 449.75 / 353.45

Ground-truth execution log.

AAPL close=270.17001, percent_change=-0.19947
MSFT close=424.45999, percent_change=-1.11590

  latest BBands upper=277.17257, lower=251.55143

MSFT Branch B triggered:
  latest BBands upper=449.75488, lower=353.45212

  both same branch -> MSFT first

Observed failure (GPT-5).

GPT-5 correctly fetched both quotes, correctly assigned both AAPL and
MSFT to Branch B, and retrieved the appropriate Bollinger Bands for
each symbol. However, it failed to execute the final tie-break branch
correctly. Under the prompt specification, when both stocks trigger the
same branch, the stock with the larger abs(percent_change)
must be listed first. Since MSFT had the larger absolute move, it
should have preceded AAPL. The model instead presented AAPL first,
indicating that it did not fully carry the branch-conditioned ordering
constraint through to the final output.

Appendix D Task Generation Pipeline Details

This appendix details the three-stage generation pipeline
(§4.3).

D.1 Tool Grounding

We extract tool descriptions, parameter schemas, and
return-value specifications by running each MCP server in a
local container and calling its list_tools endpoint.
The full schema for each tool is serialized as a JSON object
and concatenated into a single tool catalog provided to the
generator. We do not modify, summarize, or paraphrase the
extracted schemas.

D.2 Adversarial Synthesis Prompts

Listing 5 shows the synthesis prompt
for the Branch Collapse subtype. Prompts for the other three
subtypes follow the same template, differing only in the
“Structural trigger” instruction and a few subtype-specific
constraints.

Figure 5: Adversarial synthesis prompt for Branch Collapse.

# Role

You are an **Adversarial Benchmark Architect** specializing in **Reasoning Trap** tasks for MCP (Model Context Protocol) agents.

Your goal is to generate **challenging but realistic tasks** that test the agent’s ability to handle **conditional logic, branching decisions, and aggregation across mutually exclusive execution paths**.

**Realism requirement (IMPORTANT)**: The task MUST simulate a real human workflow (trip planning, comparing options, data cleanup, compliance checks, etc.). It must not feel like an artificial puzzle. The branching logic must arise naturally from realistic constraints (weather, opening hours, pagination, schema fields, availability, time windows).

# CRITICAL: Reasoning Trap Requirements

## Core Principle

The task MUST force the agent to make **explicit conditional decisions** based on tool outputs. The agent must:

1. Evaluate concrete conditions from tool responses

2. Choose between mutually exclusive tool chains

3. Aggregate results from different branches correctly

## Mandatory Structure

### 1. Explicit Conditional Logic

- **MUST** include clear if/else/otherwise/switch logic

- **MUST** have at least 2+ distinct branches (for Medium/Hard)

- Each branch **MUST** trigger different tools or tool sequences

- Conditions **MUST** be:

  - **Concrete**: Based on specific values, ranges, or properties from tool outputs

  - **Exhaustive**: Cover all possible cases (no undefined behavior)

  - **Decidable**: Can be determined solely from tool outputs, no guessing

### 2. Branch Differentiation

- **Easy**: 2-3 branches, each uses different tools

- **Medium**: 3-4 branches, with optional nested conditions or filtering

- **Hard**: 5+ branches OR complex nested conditions with 2+ levels of nesting

### 3. Aggregation Requirement

- The final answer **MUST** depend on correctly selecting and combining results from the right branch

- Wrong branch selection = wrong final answer

- The task should require comparing or aggregating outputs from different branches

### 4. Human-Realistic Problem Framing (MANDATORY)

- The task MUST include a plausible user goal and context (who/when/why), e.g.:

  - trip itinerary optimization under weather + opening hours constraints

  - filtering a dataset with pagination + schema constraints

  - choosing among similar search tools based on output format needs

- The task MUST define measurable success criteria:

  - what to return (format)

  - tie-break rules

  - constraints (budget, rating threshold, distance, time window, etc.)

- The task MUST not rely on "magic knowledge"; every decision point must be derived from tool outputs.

### 5. Complete Input Information (CRITICAL)

- The task MUST contain **ALL necessary input information** explicitly stated in the instruction

- The task MUST NOT assume any information exists outside the instruction (e.g., "provided symbol", "given address", "the data you have")

- **ALL input values MUST be explicitly specified** in the task text:

  - If the task requires a cryptocurrency symbol, it MUST say: "Check the price of ETH" (not "check the price of the provided symbol")

  - If the task requires a location, it MUST say: "Check the weather in Tokyo" (not "check the weather at the provided location")

  - If the task requires a date range, it MUST say: "Query data from 2024-01-01 to 2024-01-31" (not "query data in the provided date range")

- The task must be **self-contained and executable** without requiring additional context or external inputs

- Example of CORRECT task: "Check the current price of ETH (Ethereum). If the ETH price exceeds $3,000, search for altcoins priced below $1; otherwise search for stablecoins priced between $1 and $10."

- Example of WRONG task: "Determine the appropriate tool for fetching the current price based on the provided cryptocurrency symbol or contract address." (missing: what is the actual symbol/address?)

## STRICTLY FORBIDDEN

- Vague conditions: "if appropriate", "as needed", "depending on the situation"

- Ambiguous logic: "handle different scenarios", "consider various factors"

- Implicit decisions: Any condition that requires guessing user intent

- Single-path tasks: Tasks that don’t require branching

- Tasks where all branches lead to the same result

- **Tasks that reference unspecified inputs**: "based on the provided...", "using the given...", "the provided...", "the given..." (without actually providing the value)

- **Tasks that assume external context**: "query the data you have", "process the existing file", "based on the previous result" (without specifying what the data/file/result is)

- **Incomplete task descriptions**: Any task that requires information not explicitly stated in the instruction itself

### NEW HARD REQUIREMENT: Explicit Branch Mapping

Every generated task MUST include an explicit "Branch Selection Rules" section.

This section MUST:

- Enumerate ALL branches

- For each branch, specify:

  1. Exact tool output fields used for the decision

  2. Concrete condition (exact value, range, or boolean)

  3. The exact tool chain that MUST be executed

Natural-language conditions without explicit mapping to tool outputs are STRICTLY FORBIDDEN.

## Difficulty-Specific Requirements

### Easy (2-3 tools)

- 2-3 branches total, each branch uses a distinct tool chain.

- Branching must be based on a single tool output (e.g., weather condition category, presence/absence of records, boolean flags).

- Final answer MUST aggregate/combine branch results (e.g., produce a ranked list + justification).

### Medium (4-5 tools)

- 3-4 branches OR 2-3 branches with at least one nested condition.

- At least one branch MUST include a 2+ tool dependency chain (Tool A output feeds Tool B params).

- Include at least one realistic constraint: opening hours, distance, budget, rating threshold, time zone, pagination, schema field type.

### Hard (6+ tools or 2+ servers)

- 6+ tools (or 2+ servers) with **multi-level branching** (at least 2 nested layers) AND an aggregation step.

- Include at least two independent conditions (e.g., weather + opening hours; availability + rating; schema type + time range).

- The final output MUST combine results across branches (e.g., "best choice" + "fallback plan" + "explain which branch triggered").

## Input Context

- **Target Bucket**: {{target_bucket}}

- **Difficulty Level**: {{difficulty}}

- **Tool Definitions**: {{tool_descriptions}}

# Step 1: Tool Chain Analysis

**CRITICAL**: You MUST strictly use the provided `Tool Definitions`. Do NOT invent tools.

1. **Identify Conditional Tools**: Find tools that return data suitable for conditional evaluation:

   - Tools returning status, state, or properties

   - Tools returning lists that need filtering

   - Tools returning values that can be compared

2. **Map Branching Logic**:

   - For each condition, identify which tools provide the decision data

   - For each branch, identify the tool chain to execute

   - Ensure branches use DIFFERENT tools (not just different parameters)

3. **Design Aggregation**:

   - How will results from different branches be combined?

   - What makes the final answer depend on correct branch selection?

4. **Identify All Tools in Used Servers**:

   - For each server used in the task, list ALL tools available in that server

   - These will be included in `available_tools` for confusion/distraction

   - **available_tools MUST have at least 10 tools**: if the union of tools from used servers is fewer than 10, add more related tools (same domain, e.g. other weather/search/transport tools) by random selection until the list has at least 10 entries

   - Only the tools actually needed for the task should be in `required_tools`

# Step 2: Task Design Checklist

Before generating, verify:

- [ ] Task has explicit if/else/otherwise structure

- [ ] Each condition is concrete and decidable from tool outputs

- [ ] At least 2 branches use different tools

- [ ] Final answer requires aggregating/comparing branch results

- [ ] Wrong branch selection leads to wrong answer

- [ ] No vague or ambiguous language

- [ ] **ALL input values are explicitly stated in the task (no "provided", "given", "existing" without actual values)**

- [ ] **Task is self-contained and executable without external context**

- [ ] Difficulty level matches tool count and complexity

- [ ] `available_tools` includes ALL tools from servers used in the task (for confusion)

- [ ] `dynamic_reference_script` is a complete, executable Python function that returns a string containing all execution records and results

# Step 3: Generate the Task (JSON Output)

## Ground Truth Strategy Selection Rules (MUST be chosen based on the tools used; do not hardcode)

You MUST select `ground_truth.strategy` based on **tool type** and populate the corresponding fields:

- **A. Stateless / Query Tasks**

  - **strategy**: `dynamic_script`

  - **dynamic_reference_script**: Required. Must be a **directly executable Python function** named `generate_reference_answer`.

    - Inside the function, use `from mcp_client import call_tool` to invoke real MCP tools.

    - The function MUST **return a string** containing all execution records and results (used to generate the reference answer via LLM).

    - The returned string MUST include:

      - A record of each tool call (which tool was called and with what parameters)

      - The return value of each tool call

      - The evaluation process and outcome of each conditional branch

      - The final aggregated result

    - The function MUST include complete conditional branch logic and result aggregation.

    - **CALL FORMAT (CRITICAL)**:

      - `call_tool` MUST use the **two-argument** format: `call_tool("full_tool_name", {args_dict})`

      - The full tool name is the name as listed in `available_tools` (e.g., `"weather_get_current_weather"`)

      - FORBIDDEN three-argument form: `call_tool(’server’, ’tool’, args)`

      - CORRECT form: `call_tool(’weather_get_current_weather’, {’location’: ’Tokyo’})`

    - **FILE PATHS (CRITICAL)**:

      - The filesystem sandbox **only allows access to the `/data` directory**. All other paths are forbidden.

      - FORBIDDEN paths: `/tmp/`, `/var/`, `/project/`, `/home/`, `/etc/`, `/root/`, `/app/`, `/workspace/`, `/src/`

      - CORRECT paths: `/data/filename.txt`, `/data/subdir/file.json`

      - For all file read/write tools (e.g., `desktop-commander_read_file`, `filesystem_write_file`), the `path` parameter **MUST start with `/data/`**.

    - **FIELD ACCESS (CRITICAL)**:

      - FORBIDDEN direct indexing: `data[’field’]` (raises KeyError if field is missing)

      - REQUIRED defensive access: `data.get(’field’, default_value)`

      - Nested fields: `data.get(’a’, {}).get(’b’, {}).get(’c’)`

      - After each tool call, log the first 200 characters of the raw result for debugging:

        `execution_log.append(f"[RAW] {str(raw_result)[:200]}")`

    - Function format example:

      ```python

      def generate_reference_answer():

          import json

          from mcp_client import call_tool

          execution_log = []

          # 1. Fetch decision signal

          # CORRECT call format: call_tool("full_tool_name", {args_dict}), tool name from available_tools list

          # FORBIDDEN three-argument form: call_tool(’server’, ’tool’, args)

          execution_log.append("Step 1: Calling tool ’server_name_tool_name’")

          raw_signal = call_tool(’server_name_tool_name’, {’param’: ’value’})

          execution_log.append(f"[RAW] {str(raw_signal)[:200]}")

          signal_data = json.loads(raw_signal) if isinstance(raw_signal, str) else raw_signal

          # Defensive field access (do not assume field always exists)

          condition_A = signal_data.get(’condition_field’, None)

          execution_log.append(f"Condition A value: {condition_A}")

          # 2. Conditional branching

          if condition_A:

              execution_log.append(f"Branch A triggered: condition_A = {condition_A}")

              execution_log.append("Step 2: Calling tool ’server_a_tool_a’")

              raw_a = call_tool(’server_a_tool_a’, {’input’: condition_A})

              execution_log.append(f"[RAW] {str(raw_a)[:200]}")

              branch_a_data = json.loads(raw_a) if isinstance(raw_a, str) else raw_a

              result = {’branch’: ’A’, ’data’: branch_a_data.get(’result’, branch_a_data)}

          elif condition_A is not None:

              execution_log.append(f"Branch B triggered")

              raw_b = call_tool(’server_b_tool_b’, {’input’: ’value’})

              execution_log.append(f"[RAW] {str(raw_b)[:200]}")

              branch_b_data = json.loads(raw_b) if isinstance(raw_b, str) else raw_b

              result = {’branch’: ’B’, ’data’: branch_b_data.get(’result’, branch_b_data)}

          else:

              result = {’branch’: ’C’, ’data’: None}

          # 3. Aggregate results

          execution_log.append("Step 3: Aggregating results...")

          execution_log.append(f"Final result: {str(result)[:300]}")

          return "\n".join(execution_log)

      ```

    - FORBIDDEN: `data[’field’]` (assumes field always exists)

  ### state_assertions Format

  `state_assertions` is an array of objects, each describing one executable assertion:

  ```json

  {

    "description": "Human-readable description of what is being verified",

    "code": "A pure Python expression executable by eval(), must return a boolean",

    "expected": true

  }

  ```

  **Field Descriptions**:

  - `description` (required): describes what state is being verified, e.g. "File /data/output.txt exists and is non-empty"

  - `code` (required): a pure Python expression string executed via `eval()`. Available variables:

    - `os`: Python standard library `os` module (for file/directory checks)

    - `json`: Python standard library `json` module (for parsing file content)

    - `re`: Python standard library `re` module (for regex matching)

    - No other modules may be imported; `import` statements are forbidden.

  - `expected` (optional, default `true`): the expected boolean return value of the `code` expression. The assertion passes if the boolean of the `code` result matches `expected`.

  **ASSERTION CODE RULES (CRITICAL)**:

  - CORRECT: pure Python expressions, directly executable by `eval()`

    - `"os.path.exists(’/data/output.txt’)"`

    - `"os.path.getsize(’/data/output.txt’) > 0"`

    - `"json.loads(open(’/data/result.json’).read()).get(’status’) == ’done’"`

    - `"re.search(r’\\btotal\\b’, open(’/data/report.txt’).read()) is not None"`

    - `"len(os.listdir(’/data/processed/’)) >= 3"`

    - `"’Alice’ in open(’/data/users.txt’).read()"`

  - FORBIDDEN: `import` statements, multi-line code blocks, `print()`, assignment statements, nested `exec()`

  - FORBIDDEN: paths outside `/data` (the sandbox only allows access to `/data`)

  - FORBIDDEN: assertions may only verify file content or directory structure; MCP tool calls are not allowed.

  **Assertions should cover the following (at least 2-3; for Reasoning Trap, one per key branch is recommended)**:

  1. **Correct branch side-effects**: files or state produced only when the correct conditional branch is taken

  2. **Content correctness**: the output of the correct branch matches the expected value

  3. **Wrong branch not taken**: characteristic files or state from incorrect branches do not exist (`expected: false`)

## CRITICAL: Branch Naming Convention (MUST be followed)

**The `branch` field value in `claims` MUST exactly match the branch identifier logged in `dynamic_reference_script`.**

Rules:

- In `dynamic_reference_script`, each branch entry point **MUST** log: `execution_log.append("Branch X triggered")`

  - X is an uppercase letter: `A`, `B`, `C`, `D` (etc.)

- The `branch` field in the corresponding `claims` step **MUST** be the matching single uppercase letter: `"A"`, `"B"`, `"C"`, `"D"`.

- Semantic names (e.g. `"high_volume"`, `"branch_a"`, `"low_count"`) are **strictly forbidden** as `branch` field values.

- Sub-branch notation (e.g. `"A.1"`, `"A1"`, `"B.2"`, `"B1"`) is **strictly forbidden** — only single uppercase letters are allowed.

- Sub-steps inside a parent branch (i.e., second-level conditions within branch A) **MUST NOT have a `branch` field**; set it to `null`.

| Correct | Incorrect |

|---|---|

| `"branch": "A"` + log `"Branch A triggered"` | `"branch": "high_volume"` |

| `"branch": "B"` + log `"Branch B triggered"` | `"branch": "branch_b"` |

| `"branch": "C"` + log `"Branch C triggered"` | `"branch": "low_count"` |

| `"branch": null` (nested sub-step) | `"branch": "A.1"` |

| `"branch": null` (nested sub-step) | `"branch": "B1"` |

| `"branch": null` (nested sub-step) | `"branch": "A2"` |

D.3 Automated Filtering Criteria

Each candidate task is checked on the following five criteria.
Tasks failing criteria 1–4 are repaired automatically:
a Claude Code agent (Claude Sonnet 4.6) inspects the failure
trace, calls the relevant MCP server tools to recover correct
parameter values, and patches the task. Repair is bounded by a
fixed retry budget; tasks that cannot be repaired within the budget
are dropped.

1. 

Executability: every tool listed in
required_tools exists in the catalog and accepts the
parameter schema referenced by the task.

2. 

Hallucination coverage: the task contains at
least one structural feature that triggers the target subtype
(e.g., ≥2\geq 2 mutually exclusive branches for Branch Collapse).
We check this with a programmatic verifier that parses the
claims field.

3. 

Self-containedness: the task instruction does
not reference external assumptions beyond the provided tool
set (no “use your knowledge of…”, no implicit world-state).

4. 

Non-triviality: the correct answer cannot be
reached by enumerating tool outputs without honoring the
dependency graph in claims.

5. 

Label consistency: when a Claude Code solver
(Claude Sonnet 4.6, separate from the generator) runs the task
end-to-end against live MCP servers, its dominant failure mode
over 5 runs matches hallucination_type. We use Claude
Code rather than GPT-4o here so that the filter solver and the
primary semantic judge (§4.4) come from
different vendors, removing one obvious circular-bias path.

Spot-check validation of automated filtering.

To bound the dependence of the filter on a single solver model,
we draw a stratified sample of candidate tasks (proportional
across subtypes and difficulty levels) and have the three
expert annotators independently apply criteria 3–5 in parallel
with the Claude Code solver. On this sample, annotator-solver
agreement on filter outcome is 89%, and disagreements are
adjudicated by majority vote among the three annotators rather
than by the solver. Tasks where the human majority disagreed
with the automated decision are re-labeled or removed
accordingly. This procedure bounds the rate at which the filter could
propagate solver-specific biases into the retained distribution.

D.4 Expert Review Protocol

Three annotators with backgrounds in LLM agent evaluation
(each with ≥2\geq 2 years experience) participate at two
points in the pipeline: in the spot-check filtering described
above, and in a final review of all tasks that survive
automated filtering. For each surviving task, annotators
independently rate:
(i) task realism (does the scenario reflect a plausible
real-world MCP use case?),
(ii) label correctness (does the annotated subtype match the
dominant failure mode?),
(iii) ground-truth validity (does the reference produce a
correct, reproducible answer when run against live servers?).

Each criterion is rated on a 3-point scale (0 = fail,
1 = borderline, 2 = pass). A task is accepted if it receives
≥2\geq 2 on all three criteria from at least 2 of 3
annotators. Inter-annotator agreement on the subtype label is
Cohen’s κ=0.76\kappa=0.76, indicating substantial agreement.
The final benchmark retains 73% of the initially generated
candidates.

Appendix F Additional Analysis

This appendix reports the detailed analyses omitted from the main text for space. We first specify the ideal agent behavior for each subtype, then report additional breakdowns for Unreachable Goal, Context Forgetting, and per-model subtype rank instability, followed by confidence intervals, robustness of the scoring weights, and an agent-design ablation.

F.1 Ideal behavior per subtype

MCPHallu measures whether an agent falls into the designed hallucination, so the reference point for every task is an agent that avoids it; this behavior earns the maximum score of 1.0. Expert humans approach this reference: on a stratified sample of 40 tasks they score 0.88 overall, compared with 0.728 for the best model (Claude Opus 4.6) on the full benchmark, and the largest gap is on Unreachable Goal (0.82 vs. 0.58).

Feasible subtypes.

Branch Collapse, Tool Misuse, and Context Forgetting tasks are solvable with the provided tools by construction (Appendix D). The ideal agent completes the task as specified by the executable ground truth. The claim graph CC gives a sufficient call sequence: Branch Collapse tasks require a median of 7 calls (range 4–15), Context Forgetting tasks 7 (5–13), and Tool Misuse tasks 2 (2–5).

Tool Misuse under overlapping schemas.

Each Tool Misuse task designates one target tool together with a curated set of confusion tools whose names, descriptions, or parameter schemas overlap with it. The overlap is confined to the interface: the target is the tool whose semantics match the requested operation, and it can be identified from parameter semantics, the return-value specification, and the instruction. In the Tool Misuse example of Appendix B, the task asks for the patch introduced by the latest commit relative to its parent; git_git_show on that commit returns it directly, whereas git_git_diff with target=HEAD compares repository state against a reference and answers a different question. The ideal agent selects the target, adds auxiliary tools only where the task requires them (19 of the 84 tasks require more than one distinct tool, e.g., a log lookup to resolve the commit), and grounds its answer in the target’s output. Table 7 shows why this discipline matters: trajectories that call only the correct tools pass 84.7% of the time, compared with 32.3% when a confusion tool is called alongside the correct one.

Unreachable Goal.

No available tool can satisfy the goal, so no completion trajectory exists. The tool inventory is fixed and visible at t=0t=0, so the ideal agent can usually recognize infeasibility before acting and report what is missing; when feasibility depends on a tool output, a brief probe settles it and retains most of the credit. Stopping to report is also more useful to a user than attempting what is possible and reporting afterward, because no partial trajectory reaches the requested end state. The evaluated agents bear this out: runs that stop and recognize infeasibility pass 48.0% of the time, whereas runs that keep acting without declaring infeasibility pass 0.0% (Table 13).

Calibrated rather than blanket refusal.

Early stopping earns credit only where the goal is genuinely unreachable. The three feasible subtypes account for 255 of the 358 tasks and are scored by completion, so a policy that declines indiscriminately forfeits them. The evaluated agents confirm this: on Tool Misuse, trajectories that invoke neither the correct nor a confusion tool pass only 8.0% of the time (Table 7).

Efficiency.

MCPHallu scores whether an agent avoids the designed hallucination rather than how quickly it succeeds. Tool-call counts are reported alongside scores (Tables 6 and 7), giving a direct view of trajectory efficiency.

F.6 Robustness of the scoring weights

Component weights follow which signal is closest to ground-truth correctness for each subtype (§4.4). We test them in three ways.

Calibration against human judgments.

Three annotators scored a stratified sample of 120 trajectories (30 per subtype) on a 0–1 quality scale. For each subtype, we refit the component weights by least squares to the mean human score, constraining them to be non-negative and to sum to one. The fitted weights stay within 7 points of the hand-set ones (Branch Collapse and Context Forgetting: 60/20/20 →\rightarrow 55/27/18; Unreachable Goal and Tool Misuse: 70/30 →\rightarrow 63/37), and re-scoring all 14 models with the fitted weights leaves the ranking essentially unchanged (Spearman ρ=0.98\rho=0.98). We retain the hand-set weights; the fitted alternative would mainly raise the judge’s share on Unreachable Goal and Tool Misuse.

Deterministic-weight sweep.

Holding the judge weight fixed, we redistribute the deterministic weight of Branch Collapse and Context Forgetting between the executable-outcome and dependency components, scaling each from half to double its default while keeping their combined weight fixed, and re-rank all 14 models on all 358 tasks. No model changes rank (Spearman ρ=1.00\rho=1.00).

Judge-weight perturbation.

Perturbing the judge weight by ±10\pm 10 percentage points on each subtype moves no model by more than 2 positions.

F.7 Agent framework and prompting

To separate model capability from agent design, we hold the model fixed (GPT-5) and evaluate a stratified 80-task subset (20 tasks per subtype) under three configurations: the baseline scaffold, a plan-and-execute scaffold that issues one planning turn before tool use, and an infeasibility-aware system prompt that instructs the agent to report an infeasible task instead of fabricating a result (Table 18). The diagnostic profile is stable: Unreachable Goal and Context Forgetting remain the two hardest subtypes under every configuration, and the mean score changes by at most 0.02. Both interventions act mainly on the signal they target, raising Unreachable Goal by 0.07 (plan-and-execute) and 0.11 (infeasibility prompt), while Tool Misuse and Context Forgetting change by at most 0.05. A prompt or scaffold change therefore narrows false completion without closing the gap, suggesting that these failures are partly capability-bound rather than prompt-fixable, the kind of gap MCPHallu is designed to surface.

Appendix I Extensibility, Maintenance, and Reproducibility

Adding failure modes.

Every MCPHallu subtype is specified by a structural trigger and a detection signal (Table 2). A new failure mode is added by specifying this pair, writing a subtype-specific synthesis prompt (Appendix D), and running the existing generate, filter, and expert-review pipeline (§4.3). The only structural question is whether the current harness, a single agent with a static tool inventory in a fresh container per episode, can express the trigger. Splitting execution failures.

Tool Misuse is defined over both execution failure forms under one trigger, and the taxonomy can be refined into two execution subtypes: Erroneous Selection, in which the agent invokes a tool whose semantics do not match the intended operation, and Faulty Invocation, in which the agent invokes an appropriate tool with arguments that violate its documented input schema (e.g., enum, pattern, format, or range constraints) or a task-specific value requirement. In this release, Tool Misuse instantiates erroneous selection through curated confusion tools. Faulty Invocation tasks can be built with the same pipeline from the constrained parameters in the servers’ grounded schemas, and the two forms can be separated per call by checking the invoked tool against the task’s target and its arguments against the schema.

Maintenance and versioning.

MCPHallu is maintained as a versioned release. New servers enter through the same pipeline that built the current 358 tasks. New tools on an existing server can create new confusion pairs or change what is feasible, so the affected Tool Misuse and Unreachable Goal tasks are regenerated rather than patched by hand. On every refresh, each task’s reference script and state assertions are re-executed as a regression test, and tasks that no longer reproduce are re-pinned, repaired, or retired; future versions will also maintain a small held-out slice to limit contamination. Releases are tagged (v1.0, v1.1, …), and earlier versions remain available so that reported scores stay comparable.

Reproducibility.

The environment is built into a single Docker image. Package-distributed servers are installed at exact release versions (e.g., @modelcontextprotocol/server-filesystem@2025.11.25 and mcp-server-git==2025.7.1), and source-built servers are checked out at fixed commit SHAs. Backing data, including CSV data fixtures and the code repositories used by coding tasks, ships with the release and is baked into the image under /data, and every episode starts from a fresh container (§4.2). Twenty of the 36 servers run without credentials; the other 16 require a user-supplied API key, connection string, or OAuth token (Table 8), and no credentials are distributed with the benchmark. Servers backed by live third-party APIs are covered by the per-refresh regression test above; a recorded-and-replayed response layer will extend the suite to fully offline execution.

Appendix J Limitations and Broader Impacts

Methodological caveats on subtype attribution.

The three axes (reasoning, execution, memory) are adopted from Lin et al. [15] as a design heuristic for controlled trigger construction rather than as statistically orthogonal factors. The near-zero within-axis correlation between Branch Collapse and Unreachable Goal (r=−0.12r=-0.12) is consistent with the two subtypes probing complementary planning weaknesses. Our subtype-targeting validation (κ=0.78\kappa=0.78, §4.3) is computed on failed trajectories, since only failing runs reveal which failure mode is primary.

Generator-judge dependence.

The task generator is Claude Sonnet 4.6 and the primary semantic judge is GPT-4o, both closed-source models from different vendors. Using different vendors for generation and evaluation reduces single-model monoculture risk, but both remain proprietary. Our cross-judge validation (Appendix H) shows that replacing GPT-4o with Claude Sonnet 4.5 as judge yields near-identical rankings (r=0.914r=0.914), and self-preference inflation for GPT-4o is smaller than the average gap between adjacent models on the leaderboard. A future version of the benchmark should validate with an open-weight judge to eliminate vendor dependence.

Benchmark scope.

MCPHallu’s scope is bounded along several dimensions that future extensions could address. The four subtypes cover the failure modes that admit a controllable structural trigger and a distinct detection signal (§3) but are not exhaustive; cross-server protocol mismatches, authentication-state confusion, multi-agent coordination, and cross-session memory are natural next subtypes, and Appendix I describes how each can be added. The 36 included servers were selected for production maturity, domain coverage, and semantic overlap, and are English-language and primarily target Western SaaS APIs (GitHub, Notion, Slack, etc.); findings may not generalize to regional services or non-English tools. Finally, MCPHallu uses a static tool inventory per task, so hallucinations from dynamic server install/uninstall mid-trajectory remain unmeasured.

Broader impacts.

MCPHallu lets developers find the specific failure mode that makes an MCP agent unsafe to deploy, such as reporting a write that never happened, before users meet it, and its subtype scores give each mitigation a measurable target. The same structural triggers could be used to build tool environments that deliberately induce these failures; because MCPHallu documents and scores each trigger, it doubles as a test suite for defenses against such environments. All evaluation runs in isolated containers with sandboxed filesystems and allow-listed network egress (§4.2).
