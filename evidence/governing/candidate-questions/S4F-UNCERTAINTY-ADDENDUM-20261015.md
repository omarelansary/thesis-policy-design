## 2. Shared vehicle and supporting-experiment implications (no merging, no selection)
- F/I: C1 (presence term), C3 (rag/hier/flat), C6 (partly) and C5 (logs) can use existing flags of the same vehicle; C1 (absence), C2 and C6 need small to moderate additions that overlap: a forced-absence pool mode, a deterministic search/describe tool with a dynamic surface, per-call usage logging, and retained real schemas. Building these once would serve several candidates; building them is implementation and is not authorised.
- I: the attempt volume of any flat-catalogue condition is large: the full catalogue is about 292k tokens of schema (dev document), the paper reports 1.5 to 5 model calls per attempt, so one flat attempt carries on the order of 0.4 to 1.5 million input tokens before caching (S; the 1.5-5 calls were measured under curated pools, so flat attempts may use more), and 750 tasks are on the order of 0.3 to 1.1 billion input tokens for a single flat condition (S). The paper states that flat prompts are 10-30 times the others, about one order of magnitude.

## 3. Coverage safeguard: two families checked against existing evidence only (no new search)
**3.1 Content-level tool-context reduction (compression, minification, description or schema content).**
- F: description-component ablation (smells paper; 25 runs; compact component combinations "often preserve behavioral reliability"; augmentation raises median input tokens by 21.85% to 41.43% in the one model where tokens were measured); schema minification and JIT loading (on-device: 3,246 to 2,120 to 347 tokens); a description-stripped profile with equivalent accuracy (TSCG: +0.8 points, n=400, two models, synthetic); skill-description compression of 48% and body compression of 39% with +2.8% functional quality over 600 skills and five models (SkillReducer); learned compression (NTILC); enrichment raises Match@1 most when only names are exposed (+25.6 points at name-only versus +5.8 at full exposure under a controlled degradation of public ToolRet metadata, about 0 on the undegraded public data; Enrich-Retrieve-Rank, retriever input rather than agent exposure); the vehicle has a description-normalisation option (`--desc-level`).
- I: the *methods* are crowded and in part strongly evaluated (SkillReducer for skills), and description rewriting and compact formats were rejected as directions in Stage 4b; fixed-tier compression or minification is a different lever from tier withholding, so the mapping below covers only the tier-by-richness interaction. A concrete scientific question remains: the interaction between content richness and exposure tier (name only, description, schema) as catalogue overlap grows, with end-to-end success. This is a **component-granularity extension of C4's detail-level factor and of C6's withheld-detail factor**, not a distinct contribution family. Evidence-based explanation for retaining the current coverage: the residual question is an interaction between factors already present; adding it as a candidate would duplicate C4(iv) and C6. **Suggested wording amendment (not applied to frozen records):** C4 factor (iv) and C6's detail factor may be read to include content-component granularity (purpose, guidance, examples, parameter documentation) crossed with tier. Flagged for your decision; no new candidate.

**3.2 Session working-set management (adding and evicting tool schemas over a multi-turn session).**
- F: MemTool (13+ models, ScaleMCP, 100 consecutive interactions): average removal ratios from 0.000 to 0.941 depending on model and mode, a residual tool count ("Avg Residual", a proxy for working-set size), tool correctness and task completion from 0.59 to 0.90; it reports no token or cost accounting. Pichay evicts stale content from the message stream (1.4 million simulated evictions, fault rate 0.0254%; thrashing in an extreme case; a single-user setting) and uses tool-definition stubs in one standardised task. The Anthropic mid-conversation primitives (beta) declare the full tool set up front and "never change" the tools array; `tool_removal` withdraws a tool "from this point onward" by name so that earlier turns stay byte-identical and the cache still hits, and `defer_loading` keeps a tool withheld until a `tool_addition` surfaces it (`r3-anthropic-midconv` L83, L98-L102). ITR's horizon table shows percentage savings falling from 95.0% to 39% over 20 loops (arithmetic over assumed sizes).
- I (revised after review): under that primitive, removal does not remove tokens already in context, so the question "does evicting reduce cumulative model-visible tokens" is in tension with its own premise. Token-reducing eviction requires either never loading (deferral) or rewriting the prefix (cache loss); the substantive question is therefore the trade-off between prefix mutation and cache loss over a session, which overlaps C5's untested prefix-mutating regimes and C3's classes. Session eviction was also already recorded as a scope boundary in the quality addendum, and MemTool is in C3's prior art. **Status: a flagged scope boundary (W1) with a narrower, re-stated question, not a distinct omitted question and not a candidate.** Whether to include it is your scope decision; Step 2 gave no basis to rank it.

**3.3 An unexamined boundary raised in review: tool-output and interaction-history overhead.** Brief R3 counts execution overhead, and the brief leaves open whether tool outputs count toward the target (U2). Stored evidence bears on it: r3-tokennotcost (delivered tool-output tokens down 38.4%, billed cost up 6.8%), the on-device Memory-Efficient variant, and Pichay. No candidate targets reducing these tokens, and the thesis target as approved is tokens "associated with accessing large tool catalogues". This is a scope question for you and the supervisor, not a candidate.
