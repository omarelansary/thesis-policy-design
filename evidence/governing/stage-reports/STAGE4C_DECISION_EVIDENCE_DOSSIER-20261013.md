## C. New findings (material, not already settled in Stage 4b)
Items marked * contain my interpretation of a source I read directly.

- **N1. Adaptive-depth exposure is published prior art; its only downstream test is single-step and inconclusive.** F: Meta's "How Many Tools Should an LLM Agent See?" (arXiv 2605.24660) trains a small RL policy to choose the shortlist depth per query (howmanytools L8-L36, L242-L265). Downstream, one forced-choice selection step with Claude Sonnet 4.6 on BFCL (N=370 registry, 120 test queries, 3 seeds of the RL agent, BM25 scorer): presented% 76.9 vs 84.2, choice accuracy given the gold tool is present 93.1 vs 87.1, end-to-end 71.7 vs 73.3, mean K 2.2 vs 5 for the adaptive vs fixed-5 arms (Table 1, L407-L440; the paper says fixed K=5 "achieves the highest end-to-end accuracy (73.3%)", L439). O*: the abstract's "improve the LLM's ability to select" is conditional on the gold tool being presented; unconditionally the arm used 56% fewer tools at 1.6 points lower accuracy (no interval; about two queries of 120; the adaptive agent was retrained with a different step cost, L419-L421). This supports neither a gain nor a null for adaptive depth. MagicSelector (arXiv 2607.17751): dynamic Top-K; completeness gains of 1.34 / 2.13 / 1.17 points over fixed-10 on ToolRet / ToolBench / MTDTool with mean K of 12.41 / 8.19 / 11.69 (Table 6, L1484-L1500, coordinator-checked); the abstract's "token efficiency" is not backed by a token measurement. Neither paper counts cumulative tokens, discovery overhead or recovery.
- **N2. A public deterministic effect-scored benchmark reports retrieval loss across four models and a distraction estimate for one.** F: DynamicMCPBench (arXiv 2607.20531; code Apache-2.0, dataset CC-BY-4.0, existence checked by API 2026-10-13, not executed). Appendix N, pre-registered 150-task subset, single attempts, 95% Wilson half-width about 8 points per cell (L1028-L1029): minimax-m3 pass rates curated (about 8 tools) 44.0, rag:8 24.0, rag:32 36.7, hier 32.7, flat (all 1,168 schemas, minimax only) 36.0 (Table 7, L1014-L1023, coordinator-checked). Reachability (all required effects present in the exposed pool) is a property of the retriever and tasks, identical across the four models: 36.7/48.0/62.7/75.3/100% at k=4/8/16/32/flat; at k=8 it is 82.7/55.9/50.2% for short/medium/long chains; across 1,905 attempts (pooled) on unreachable tasks one passed (L1036-L1043). The k=8 loss versus curated ranges from -16.0 (haiku) to -23.3 (qwen) across the four models, ranks exactly with curated capability (rho +1.000), and compresses the spread between best and worst model (L1051-L1058). The authors decompose minimax's drop into 20.0 points of "retrieval loss" (curated to rag:8) and 8.0 points of "distraction alone" (curated to flat) and describe the rag:32 vs flat tie as these effects "cancelling" (L1043-L1051). O*: this is descriptive, not an additive causal split: the rag:k pools are the k nearest neighbours of the task prompt (harder distractors than a curated pool, L996-L997); reachable tasks are an easier subset skewed to short chains; the 8.0-point term has a per-cell interval of about +-8 and no paired interval; "1 pass in 1,905" is close to tautological under effect scoring, since a task whose required tool is absent cannot produce the effect. The scorer is one-sided conservative (rates are lower bounds, L984-L991), and the authors state that the headline benchmark "does not measure retrieval over a large catalog" (L208-L209). Within these limits, it is the closest direct evidence that, at about a thousand tools and aggressive cuts, missing a required tool can matter more than seeing everything. A replicate draw of the k=8 condition (for the qwen row: deficit 20.6 vs 23.3 here) agrees to 2.7 points (L1043-L1048).
- **N3. The all-tools baseline cannot be run at the largest catalogue scale.** F: SING reports 693,574 average schema tokens against 1,298 in its full-corpus setting (L486-L491) and compares success against Embedding-only, MCP-Zero and the ground-truth servers, not all-tools (Table 3 and text, L431-L463). On MCP-Atlas it remains below the ground-truth-server arm (L460-L464). On MCP-Universe it exceeds the ground-truth arm (45.1/47.1% vs 40.3%, Table 1, L340-L346, checked).
- **N4. Provider accounting is request-level; server-side mechanisms are accounted differently.** F (stored official documentation): Anthropic usage returns `input_tokens`, `cache_creation_input_tokens`, `cache_read_input_tokens`, total = sum (r4-anthropic-prompt-caching L664-L675); tool search "isn't metered as a separate server tool" and loaded definitions "count as input tokens like any other tool definition" (r4-anthropic-tool-search L826-L828); the token-counting endpoint accepts client tools, is free, is an estimate, ignores caching logic, and returns an error for server tools including tool search and for the MCP connector (s4c-g4-anthropic-token-counting-20261013 L85, L88, L121, L297); results of programmatic tool calls "do not count toward your input/output token usage" (r4-anthropic-ptc L1433); a newer tokenizer yields about 30% more tokens for the same text (token-counting L96, r4-anthropic-pricing L54, L510). ## D. Technical probe results
Pre-registered in `probes/S4C/PROBES-PREREGISTRATION-20261013.md`; results and limits in `probes/S4C/PROBE-RESULTS-20261013.md`. No LLM or API was called. These are feasibility checks supporting no inferential claim.

- **P2, power (G5).** Closed form n = 7.84 (d/R + tau^2) / M^2, checked by simulation on two seeds (power 0.79-0.81 at tau=0). One run per task, discordance d=0.20: 1,744 / 628 / 279 / 157 paired tasks for margins 3 / 5 / 7.5 / 10 points; d=0.10: 872 / 314 / 140 / 78; d=0.30: 2,616 / 942 / 419 / 235. Repeats help only the within-task part; the policy-by-task interaction tau sets a floor (5-point margin, d=0.20: 209 tasks at R=3, tau=0; 241 at tau=0.10; 659 at R=1, tau=0.10). Minimum detectable margin at 80% power, R=1, d=0.20, tau=0: n=95: 12.9 points; 104: 12.3; 175: 9.5; 231: 8.2; 250: 7.9; 1,000: 4.0. A 5-point margin at n=628 accepts a policy that is truly 2 points worse 41% of the time. Limits: d and tau are assumptions (d=0.20 implies an intra-task correlation of about 0.58; agentic tasks with sampling noise could be higher); independence given the task, so clustering by server or category would raise n; repeats need non-zero sampling temperature; the normal approximation is 10-20% optimistic at small n with tau>0; one-sided alpha 0.025, binary outcomes; a true benefit, partial-credit scoring or exact paired tests would change the numbers. I: with these assumptions, margins under about 8 points are not demonstrable at one run per task on benchmarks of 95-250 tasks; a 10-point margin is attainable on 157-250 tasks; the constraint binds on all stored benchmarks except the 1,000-task MCP-Atlas and the 1,845-task DynamicMCPBench corpus. Whether a 10-point margin can be called "maintained" is a decision for the user and the supervisor.
- **P1, identifiability (G6).** Public BFCL v4 specifications, 1,095 unique user-contributed functions (1,729 across four files); tokens by tiktoken o200k_base on minified JSON. Schema tokens median 142, CV 0.56, 5th-95th percentile 57-307 (ratio 5.4). At a 6,000-token total, selecting shortest-first reaches 108 tools and longest-first 8 (random draw 37). Token length is explained by total descriptive text including per-parameter descriptions (Spearman 0.94) and by parameter count (0.86); these two are themselves correlated (0.78 live; 0.65 all). The earlier statement that length "tracks parameter count, not description" was wrong (post-hoc supplement `p1_supplement.py`, after the review). Length is nearly independent of the lexical overlap proxy (rho -0.01 / 0.10). Overlap at N=50: 51 of 60 (live) and 56 of 60 (all four files) seeded high/low-overlap pairs could be matched within 3% total tokens by a swap procedure while retaining about 6x the random similarity contrast; this demonstrates that the selection can be constructed, and it is circular for validity because the lexical proxy is the optimisation target. I: (a) overlap at fixed count and tokens is constructible without padding by this proxy; (b) count at fixed tokens by selection changes schema complexity and the amount of descriptive text together, and padding would define its own construct (Du et al.); they answer different questions. Limits: short single-purpose functions rather than typical MCP tools; the proxy is lexical; extreme selections overstate a realistic design; N=50 only; the registered decision rule was extended post hoc.
- **P3, Executor (G10).** Source read, not run (MIT; 4,166 stars; last push 2026-10-13). The `execute` tool description lists integration names only and points to a separate `skills` how-to; inside the sandbox, `search` (lexical, field weights path 12, name 10, integration 8, description 5; paged) and `describe.tool` (compact TypeScript shapes) plus an integration list; a missed path returns `tool_not_found` with up to 5 suggestions; usage tracking counts executions, not tokens (six files and the tree read). I: names-first disclosure with describe-on-demand and a miss path, via a code-execution tool; any token or accuracy comparison needs an external harness. Limits: MCP-path behaviour, the `skills` text and client prompting were not read.

## F. Research contribution possibilities (types distinguished; none chosen, none ordered)
- **Evaluation contributions.** (i) A non-inferiority and loss-decomposition evaluation of exposure policies on a public deterministic benchmark: loss reported by cause (misses, distraction, overhead) with cumulative tokens by category over a stated horizon (support: N2, N4, N8, P2). Risks: single-benchmark dependence; a tight margin is attainable only with several hundred tasks (P2); the decomposition is not identified without paired multi-model data; vendor-feature drift. (ii) A measurement protocol for model-visible tokens comparable across client retrieval, provider search and code-mediated access (support: N4). Risk: mostly engineering unless it exposes misleading comparisons.
- **Mechanistic contributions.** (i) Overlap at fixed count and tokens (constructible, P1); count with schema size and descriptive text varying together, versus a padded control (distinct questions). (ii) What a fallback restores when the first exposure misses (N2). Risks: frontier saturation; the general length effect; single-model results; a lexical overlap proxy.
- **Policy/method contributions.** A stepwise exposure policy with recovery whose components (initial visibility, reveal rule, fallback, adaptive depth) are experimental factors. Risks: the mechanisms are published or shipped (N1, P3, vendor documentation); a new method would need an end-to-end, cumulative-token advantage over strong baselines, and no end-to-end evidence for adaptive depth was found in either direction (N1).
