## 2. Findings against the five questions

### Q1. Can tool-pool size and composition be manipulated independently?
| Factor | Existing control (F) | Limits |
|---|---|---|
| Pool mode | `dmcp eval --pool {gold, target, full}` (replay only): gold = only required tools; target = required + distractors; full = required + the entire catalogue (pools.py L3-L12, cli L1924-L1927) | the default (no `--pool`) is the reference trace's own tools |
| Seed and strategy | `eval` has no seed flag: the pool seed is `task_id` modulo 2^31 (cli L2108-L2113); strategies beyond same_name/hard_neg are reachable only through the `ablate` command (reviewer-reported: it runs all six strategies with that seed and has no repeat, architecture or desc-level options) | no independent seeding of pools across attempts |
| Number of distractors | `--pool-size N` (integer, default 8; cli L1936-L1938); `build_eval_pool(..., pool_size, p_alt, seed)` is deterministic given (spec, catalogue, mode, p_alt, pool_size, seed) (pools.py L8-L10, L44-L77) | upper bound is the catalogue (1,168 tools per the paper); no code limit seen |
| Composition | `--p-alt` = fraction of distractors that are same-name tools on other servers; the rest are near-misses chosen by `hard_neg` (pools.py L65-L75); `build_strategy_pool` offers six strategies (random, hard_neg, cross_domain, same_name, sibling, stratified; sampling.py L50) for the ablation harness | `target` mode uses only same_name and hard_neg; other strategies via the ablation path |
| Exposure architecture | `--architecture flat | rag | hier`, `--rag-k` (cli L1949-L1960); pure functions over the tool surface, composed after the pool and `--desc-level` (architecture.py header) | `rag` and `hier` require `--replay`; each run uses one static surface |
| Description content | `--desc-level a | b`: normalise offered descriptions, `a` surface, `b` LLM-based semantic (cli L1942-L1948, L2116-L2122) | `b` makes extra LLM calls; its token effect is not recorded as such (I) |
**Verdict (I):** pool size and same-name fraction can be varied independently of each other, deterministically, with existing `eval` flags (strategies via `ablate`). Caveat found in review: `hard_neg` fills from highest similarity downward (sampling L170-L178), so a larger pool has lower mean similarity (size and overlap co-vary), and shortfalls in the same-name draw are refilled with hard negatives (realised `p_alt` can fall below nominal). **Not controlled:** total tokens (no padding or length matching; token load follows descriptions), tool schema realism (see Q4: distractors are rendered with a minimal permissive schema unless the tool is in the task's reference trace, pools.py L106-L123), and any separation of "count" from "tokens" (P1 problem). **Needs implementation:** token-matched variants; real schemas for distractors (the trace carries `input_schema` in `ToolSpec`, trace.py, but `ToolCatalog.from_traces` keeps only name and description, sampling.py L85-L100, so a small change would retain them). **Correction (review):** real schemas come from the task's reference-trace `tool_specs` (pools.py L106-L123), so distractors on the same server as a required tool can carry real schemas while same-name look-alikes on other servers get stubs; schema richness therefore varies with distractor type and could act as a cue, and the token load of curated, rag and flat pools is understated by an unknown amount.

### Q2. Can required-tool inclusion and alternative paths be controlled?
- F: required tools = the union of every `tool_effect` checkpoint's `equivalence_set` (pools.py L29-L42); `target` and `full` always include them; `gold` is exactly them. Alternative tools count only if they are in the recorded equivalence set; any other tool or argument shape falls through the replay cache (Tier-1 exact key (server, tool, canonical args); Tier-2 deterministic fuzzy on arguments; Tier-3 LLM simulator off by default; otherwise a synthetic error result) (replay.py header L14-L27, L161, L363-L375).
- F: the offline reachability computation (is at least one member of each checkpoint's equivalence set exposed) is in `scripts/cr_recall.py` on `dev`; the repo document reports that it "comes out identical across all four models" and that the decomposition into reachability and distraction is "post-hoc... not pre-registered" (e9.1 doc).
- **Added after review (F):** calls to tools that are not exposed are rejected with an error listing the first 20 valid names (explorer L193-L198); the replay cache is built from the single reference trace of the task (`cache_traces=[ref]`, cli L2096-L2104); a tool-effect checkpoint needs a successful agent step on a member of the equivalence set (evaluator L186-L199). Therefore an equivalence-set member that the reference trace never called successfully cannot pass: "alternative path available" is realisable offline only for alternatives the reference actually exercised, and removing every recorded alternative is failure by construction. A cache miss also reveals up to five known working argument shapes for the tool (replay L363-L372).
- **Verdict (I):** presence can be controlled exactly. A **forced-absence arm** (drop required tools from the pool while keeping distractors) is not a built-in mode; absence arises only through `rag`/`hier` retrieval. It is a small change to `build_eval_pool` (remove entries); because of the replay design above, the absence-by-presence interaction on this vehicle is largely mechanical (absence means failure) unless the reference traces exercised alternatives. Alternative paths beyond the recorded equivalence sets are structurally unobservable offline without enabling the Tier-3 simulator, which trades away determinism.

### Q3. Can recovery mechanisms be introduced and evaluated?
- F: no recovery or discovery mechanism exists. The agent loop computes the tool list once before the loop (`openai_tools = specs_to_openai_tools(tool_surface ...)`, explorer.py L155-L156) and passes it unchanged at every `llm.chat(messages, tools=openai_tools)` call (L162). Tools are offered as OpenAI function schemas, namespaced by server.
- F: `dmcp/discovery/registry.py` is a client for the official MCP Registry (a crawl for building the catalogue), not an agent-facing search tool.
- **Verdict (I):** recovery must be implemented, in either of two families: model-initiated (a deterministic catalogue-search and describe tool plus a loop change so that the tool list can grow after a call) or system-initiated (re-retrieval or escalation triggered by a miss or an unknown-tool error, which the existing error signals could drive with a smaller change; its cost is not assessed, U). The replay world would serve any recovered required tool (it is in the recorded cache), so evaluation stays deterministic if the search backend is deterministic (for example lexical or fixed-embedding). The provider-native tool-search arms of C3 cannot be run in this loop (function-calling API through a router; U for provider-specific features).

### Q4. Are per-call token and trajectory accounting available or instrumentable?
- F: `UsageAccumulator` in `dmcp/llm.py` keeps lifetime totals of prompt tokens, completion tokens and cost per client, plus a latency list, with snapshot/delta helpers; cost = two-tier input/output price per million tokens, and the pricing module states "No tiered pricing, no cache-discount" (llm.py L55-L103, pricing.py L9-L10, L60-L68). Per-run summaries carry a `cost` dictionary taken from `seed_metadata` (evaluator.py L540-L542).
- F: `Trace` steps record kind, tool, arguments, results, latency and status, not tokens (trace.py); the number of agent calls and success per call is in the result.
- I: not available: cached-token fields, token categories (definitions versus history versus tool outputs), and individually stored per-call usage. Added after review: the embedding calls of `rag` and the router calls of `hier` happen in `apply_architecture` (cli L2123-L2136) before the agent loop takes its `usage_before` snapshot (explorer L152), so their tokens are absent from per-run usage deltas, and embeddings are not priced; this matters for any C3 or C5 comparison involving rag or hier. Instrumentable: the usage dictionary is returned on each `chat` call, so a thin wrapper can store it per call; categories need local tokenisation of the rendered tool surface (the vehicle already knows what it renders).
- F (dev doc): the repo's own hypothesis H5 states that the full catalogue "serialises to ~292k tokens of tool schema", which exceeds the contexts of kimi-k2.6 (262,144), glm-5.1 (204,800) and claude-haiku-4.5 (200,000); H5 is registered as a finding to report, not tested. Of the four models in the matrix (minimax-m3, kimi-k2.6, claude-haiku-4.5, qwen3.7-max), two (kimi, haiku) are below that figure and two (minimax, qwen) have 1M contexts; glm-5.1 is in the wider leaderboard pool, not the matrix. `flat` was run on minimax-m3 only; the doc lists the qwen `flat` cell as the missing confirmation (L292-L295), so the one-model limit was not forced by context length. (U) whether ~292k equals what the code actually renders, since distractors outside the reference trace are rendered with stub schemas.

### Q5. Grading, replay and licensing limits
- Deterministic scoring (F): Tier-1 effect checkpoints (tool-effect with argument predicates, value-produced predicates, minefields, partial ordering); `state_condition` checkpoints are reserved and not emitted (spec.py L16-L18, L97-L104). Tier-2 LLM equivalence judge is optional and was not enabled for any released number (dataset card). The paper reports 230 runs a human would pass that the scorer failed (so rates are lower bounds; 4c dossier N2, via the paper).
- Replay (F): deterministic given the reference traces; cache misses return a synthetic error and are counted (`replay_meta["cache_miss_count"]`); live mode needs the docker substrate and credentials and is "subject to upstream nondeterminism" (cli L1986-L1996). `--repeat` supports pass^k; `--budget` caps LLM turns per run (default 12) (cli L1870, L1917).
- Licences (F): code Apache-2.0; data CC BY 4.0. Substrate servers keep their own licences (U; not read).
- Released-run limitation (secondhand, U): the dataset card, read only through an unstored triage fetch (S4F-Q001), says candidate traces are incomplete; per-call trajectories of the released runs may therefore not be fully available. The 1,845-task count is corroborated by the stored paper (`s4c-g2-dynamicmcpbench-2607-20531` L1102-L1103). The Apache-2.0 licence field was read in the Stage 4c direct call (`searches/stage4c/DIRECT-CALLS.md`).
- Planner (F, unread): `benchmark_advisor/` is a pre-run statistical planner (minimum detectable effect, power) with a 47 KB guide; I did not read it.

## 4. What this does and does not establish
- Established (from code and documentation, not by running): the existence and parameters of pool controls; deterministic replay design; absence of recovery, dynamic surface, absence mode and cache-aware accounting; the licences; the `main`/`dev` split.
- Added after review: the `main` files read may differ from the dev code behind the cited experiments (e9.1 cites `dmcp/cli.py:1960` for the resume rule while the stored main file has the resume skip elsewhere); e9.1 describes deterministic replay in its scoring section but also says the tasks "run against live MCP servers" in its drift paragraph (L70-L74, L489-L496), a tension left unresolved (U); resume is per task, not per attempt.
- Not established: that the code runs as documented on any machine or model; the behaviour of `rag`/`hier` with a given embedder; the contents of `traces.jsonl` (whether every task's trace includes complete `tool_specs` for the tools needed); whether the pool-size parameter behaves sensibly at hundreds of distractors beyond the `full` mode; the cost per attempt; whether substrate dependencies are needed for replay (the CLI indicates replay needs only reference traces).
- Next-level checks (not performed, would need authorisation): smoke execution of `dmcp eval --replay` with a small local model on a few tasks to confirm the pipeline and usage fields; reading `cr_recall.py` and the matrix runner on `dev`.
