- Inputs: 24 primary texts stored in Stage 4 (`evidence/source-text/s4-*-20261013`), extraction reports `audits/S4-W1…`, `S4-W2…` (Sonnet research-workers, verbatim), coordinator spot-check `audits/S4-V1…`, Stage 3 ledger anchors (`stage-reports/STAGE3_CLAIM_LEDGER-20261013.md`), and one directly read source (TheMCPCompany, read by me).

- This document compares sources. It does not select a direction or claim novelty.

## 1. Dimensions

Each source is classified on eight separable quantities: retrieval quality (recall/nDCG of a retriever), tool-selection accuracy (right tool called), end-to-end task success, tool exposure (count or tokens of definitions the model sees, as a measured variable), token counts (how obtained), cost (list-price reconstruction, estimate, or billed), cache behaviour (measured from provider fields, asserted, or absent), and multi-turn/discovery overhead (extra turns, calls, latency). Savings in one dimension are not carried to another.

## 5. Cross-cutting observations

1. **F/W** Only CAPC reconciles a computed cost to a provider billing total (within 1% on three characterisation runs). Every other source that reports dollars reconstructs from usage or tokens × published prices (HAL, AI Agents That Matter, TheMCPCompany, ITR, compression-gateway, TokenPilot, CacheRouter) or does not report dollars. No stored Stage 4 source reports an invoice for its main comparison. *Consequence for terminology:* "provider-billed cost" in a future design must be defined as provider-reported usage priced at the account's actual per-tier rates and reconciled to the invoice, as CAPC did; list-price token arithmetic is a weaker claim.
2. **F/W** Five sources measure cache behaviour from provider fields (CAPC, TokenPilot, CacheRouter, Copilot traces serving-side, compression-gateway tier pricing). None compares tool-exposure policies (full static, per-turn retrieval, append-only discovery, frozen selection) on cache behaviour *and* task success under the same workload. CacheRouter has no comparison arm. CAPC compresses rather than withholds definitions. Compression-gateway has no success measurement for gateway runs.
3. **F** TheMCPCompany is the closest published joint measurement of success, steps and list-price cost for a tool-finder over a very large catalogue against oracle and browser arms. It has no all-tools arm, no cache reporting and (as far as I located) no repeated runs. Earlier summaries that said no source jointly reported success and cost for catalogue filtering must be read with this exception (Stage 3 C3-19 was a bounded negative; this source was outside its bounds).
4. **F/W** Implementations (Spring AI advisor, langgraph-bigtool) change the `tools` parameter as discovery proceeds; Manus reports advising against this on cache grounds without data; Anthropic/OpenAI document provider-native designs intended to preserve the cache; CAPC reports implicit caching of a large `tools=` array. These statements are mutually compatible only if cache stability depends on *where* discovered definitions are placed and *whether* previously sent tools are altered. No stored source measures that dependence for discovery.
5. **W** Reported savings in the retrieval papers are in retrieval metrics or token counts (MCP-Zero −98%; CloudUse 23.8×; ITR 20×); success-bearing evidence is thin and uses LLM-aligned or internal metrics (ScaleMCP, MemTool, ITR) or small live tests (CAM-DF). CAM-DF's own authors say equivalence is not shown.
6. **F/W** Run-to-run variation is documented as large in at least one place (same task 7–18 turns; compression-gateway) and ignored in several (HAL single runs; ITR, TokenPilot run counts NR). AI Agents That Matter and tau-bench provide the reporting precedents (error bars; pass^k).
7. **O** Several papers have abstract-versus-body mismatches or internal numeric inconsistencies (listed in S4-W1/W2). Where a figure is used in a candidate-question record it must be re-read first.

## 8. Corrections made after the independent review (S4-R1) and coordinator checks (S4-V2)

Original text above is kept except where marked. Changes:
1. The compression-gateway "recall disabled → 46 turns / $1.85 / 3.2×" result is from a content-compression experiment run with "MCP off, tool filter off" (s4-compgateway L.314, L.346-351). It is evidence about recalling compressed file content, not about tool-retrieval recall, and must not be used for recall-versus-outcome claims (it was so used in `audits/stage4-handoff-20261013/CLAIMS.md` claims 3 and 12 and in the pre-review draft; those files are preserved unchanged).
2. TheMCPCompany's TheAgentCompany runs used "an earlier version of our Azure MCP server, with about 13,000 tools" (L.1390), not the full 18,000+ catalogue; cost is token-priced with no cache accounting and no run count located.
3. CAPC's production path ran with `USE_LAZY_TOOLS=True` in all strategies (L.703), so lazy loading was a constant background condition, not an arm. Its implicit-tools-caching inference is the authors' and a harness-side explanation is not excluded.
4. CAM-DF already contains a one-required-tool-dropped condition: oracle 0.67 (45/67), insufficient (oracle minus one) 0.24 (16/67), full 0.58 (39/67), no fallback (Table A5, p.16; re-read by coordinator).
5. Claim 13 in the handoff ("no stored source tests a names-only or graded tier") is too strong: weak tests with success exist (Speakeasy progressive discovery, vendor-run, a handful of runs; Missing-Memory stubs, one task) and vendor designs exist (OpenAI tool search shows name and description and defers the schema, r4-openai-tool-search L.22). Defensible wording: no adequately powered, independent, per-arm-success comparison of a graded tier against full exposure was found in the corpus.
6. ITR's success and cost figures are episode metrics for its T2 subset, no model is named, and its "cache" refers to retrieval caching (S4-R1 claim 8); ITR figures are treated as unreliable.
