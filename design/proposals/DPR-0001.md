# DPR-0001: The decision problem and the signal register (no solution proposed here)

**Proposal.** A specification of the problem a tool-access policy must solve, to be fixed before any mechanism is compared (DPR-0002) or any policy drafted (DPR-0003). Working statement of the objective, quoted from AUTH-004 and not narrowed: "reducing unnecessary tool exposure to LLM agents while preserving task performance and accounting for the costs of deciding, discovering and using tools." Labels: [F] fact in a cited source, [O] observation, [I] interpretation, [U] unknown, [S] speculation. No numbers: symbols are unset parameters.

**Requirements it answers (by id).** AUTH-004 "Establish the decision problem before proposing its solution", and the instruction to examine "what information is actually available when the policy must make a decision, what it can legitimately infer, and which information would only become available after execution". Also REQ-S1 (EXT-0002 s1.1: save input tokens while maintaining accuracy relative to all tools; net of selector cost; judged globally, not per turn), REQ-S2 (policy, stepwise, fallback, graded exposure as a lens: EXT-0002 s1.2), REQ-O14-03 (one scorer for all methods), REQ-O14-08 (a fixed top-N cut-off "is not a policy"). REQ-O14-12 (steps, each asking a question) is of class `unclear` and is not used as a premise.

## 1. Entities and notation
- Catalogue `K` (all tools the agent could be given), size `n = |K|`. Each tool `t` has metadata `m(t)` (name, description, schema), whose model-visible token length is `L(t)`.
- A session is a sequence of turns `1..T` (T is bounded by a turn budget `T_max`, unset). Task `x` arrives as a user request `q`.
- Exposure at turn `s`: a set `E_s` of tools, each at a disclosure grade `g in G` (for example absent, name only, name plus short description, full schema; the grade set `G` and its size are unset and are not proposed here).
- The agent model `M` acts on what it can see: `E_s` and the transcript `h_s`.
- A policy `pi` maps the information available at a decision point to an action on `E`.

## 2. Decision points
Where a policy could act. Listing a point does not mean a policy should act there.
- **D0, before the first turn**: set `E_1` from `q`, `K`, and any offline artefacts.
- **D1, between turns**: revise `E_{s+1}` from `h_s` (including the model's last call, tool result or error).
- **D2, inside a turn at the model's request**: the model asks the system for tools (a search or describe call) and the system answers.
- **D3, regime gate (before D0)**: decide whether any restriction is worth performing for this catalogue/model/provider regime at all. [I] This is a real decision only if its cost and determinants can be stated; see 5.
- **D4, end of session or between sessions**: update persistent artefacts (offline index, working set carried over). [U] Whether the thesis scope includes sessions beyond one trajectory: open (S4I decision sheet section 6 item 3 "Regime: ... trajectory versus session horizon"; S4G records session length as unavailable on the vehicle; corrected from "section 5" per CH-0006, pointers as given by the challenger and checked against S4I section 6 only).
Each of D0-D4 is optional for a given policy. "Change nothing after D0" (static) and "no D0 either" (expose all) are both policies in the space.

## 3. Action set `A`
At a decision point the available actions, as a space and not a recommendation:
1. **Expose all**: `E_s = K` at full grade for all `s`. (Baseline required by REQ-S4: all-tools baseline, EXT-0002 s1.4.)
2. **Change nothing**: keep the previous `E`; the policy is inert at that point.
3. **Remove** a subset (irreversible unless a re-add path exists).
4. **Add / re-add** a subset (needs a source of candidates: the system's own ranking, a model request, or a stored removed list).
5. **Regrade** a tool: change its disclosure grade `g` (graded exposure; REQ-S2 "lens").
6. **Provide an access path without exposure**: expose a discovery interface (search / describe) in place of or in addition to tool schemas; the model, not the system, then decides what to load.
7. **Provide a mediated path**: expose a programmatic or gateway interface through which tools are invoked without their schemas being in context. [U] Whether this is "exposure" at all for the objective is a definitional choice to be stated; counts differ by accounting convention (8).
8. **Ask**: spend an extra model or user turn to resolve ambiguity before acting.
The grade set, the number of grades, subset sizes and stage counts are unset (`G`, `k`, `m`).

## 4. Information set at each decision point (classes R, D, X, P)
Class definitions (TASK.md): **R** available at decision time by construction; **D** derived from separate offline data, with a stated leakage risk; **X** exists only after execution; **P** prohibited as a runtime signal (gold tools, reference trajectories, benchmark annotations) unless legitimate availability is demonstrated (AUTH-004). A signal that is R at D1 may be X at D0: class is relative to the decision point.

### 4.2 What each decision point may use
- **D0**: S1-S4, S10, S11, S15. Not S5-S9 (they do not yet exist), not S12-S14.
- **D1**: S1-S11, S15. S13 only via S6-S8.
- **D2**: as D1 plus S8 (the request itself).
- **D3**: S2-S4, S15 and any pre-measured regime facts from S10-like offline data. [I] It needs the least information of any point and is where a conclusion "restrict nothing" can be reached.

## 5. Cost structure (who pays, for what, and what is cached)
Quantities (all distinct; no one is a proxy for another a priori):
- `c_tools`: number of tools exposed at a turn (`|E_s|`, weighted by grade).
- `c_vis(s)`: model-visible tokens at turn `s` attributable to tool metadata: `sum over t in E_s of L_g(t)`.
- `c_cum`: cumulative tokens consumed over a session, **by category**: tool metadata in context, selector/judge tokens, model reasoning, tool results/outputs, discovery calls, recovery calls; with a record of which were served from cache.
- `c_bill`: billed cost under stated conventions: uncached input, cached input (read), cache write, output, per-call fees, and any selector model priced separately.
- `c_turn`: extra turns taken (discovery or recovery turns), each re-reading context.
- `c_lat`: latency [U, not measured on the vehicle].
- Payers: the **agent model** pays tokens for metadata it reads; the **selector** (if an LLM or embedding model) pays for deciding; **discovery** costs turns and tokens whenever the model must ask; **using** costs tokens for correct and incorrect calls and for error recovery.
- Caching (revised after CH-0006 item 1): vendor documentation states that modifying tool definitions invalidates the cache (Anthropic, EXT-0008 "What invalidates your cache": "Modifying tool definitions | Entire cache") and that adding or removing definitions mid-conversation "can cost more tokens than the definitions you removed" (MCP client guidance, EXT-0014). These are documentation statements, not measurements [vendor claim]. Whether a given restriction saves billed tokens is [U]: it depends on whether the exposed schemas sit in a cached prefix, on reads priced below input price, and on turns (see DPR-0002 section A). The earlier seed-row reading (C3-03b/09/24/27) remains [U] ledger-level; I cite the EXT ids instead.
- What turns cost: each extra turn re-sends the transcript (cached or not by convention).
- Convention-dependence: the same run has different `c_cum` and `c_bill` under different conventions (CAVEATS row 5: "each step saves tokens" has two readings; S4I section 5 open items).

### Implications [I] (each needs support at Phase 2)
1. `|E|` falling does not imply `c_vis` falling (heavy tools removed vs light), `c_cum` falling (extra turns, selector tokens), or `c_bill` falling (cache). The converse also holds: the user wants no assumption in either direction (AUTH-004 "Do not assume that fewer exposed tools necessarily means fewer cumulative tokens or higher task success").
2. A policy's cost is `C(pi) = decide(pi) + discover(pi) + use(pi) + recover(pi)`; the objective cannot be stated on `use` alone.

## 6. Objective formulations compared (none chosen)
Let `P(pi)` be task performance (success rate under the one scorer of REQ-O14-03), `C(pi)` the chosen cost quantity from section 5, `pi_0` the expose-all baseline.

| Formulation | Statement | Assumes | Weakness / what it hides |
|---|---|---|---|
| F1 Constrained (non-inferiority) | minimise `C(pi)` subject to `P(pi) >= P(pi_0) - delta` | A margin `delta` (unset) can be justified; success is a scalar | "Maintaining" is the student's word accepted by the supervisor (EXT-0002 s1.1); a justified `delta` is a scientific choice (S4I section 5, open); small `delta` needs large samples |
| F2 Constrained (budget) | maximise `P(pi)` subject to `C(pi) <= B` | A cost budget `B` (unset) | `B` is arbitrary unless it comes from a deployment; hides marginal value |
| F3 Scalarised | minimise `C(pi) - lambda * P(pi)` | An exchange rate `lambda` (unset), linear trade-off | `lambda` is arbitrary and results flip with it; contradicts "do not insert arbitrary numeric thresholds" unless `lambda` is swept and reported |
| F4 Pareto reporting | report the non-dominated set over `(P, C_1, ..., C_r)` across policies and regimes | Nothing about trade-off; outcomes are measured | Does not by itself yield "a policy"; REQ-O14-08 asks for one; mapping from frontier to rule needs a regime variable |
| F5 Per-step | each step must reduce `C` (one reading of REQ-S2 "each step saves tokens", EXT-0002 s1.2) | Savings are separable by step | Open as to its reading; could reject beneficial multi-step wholes; CAVEATS row 5 |
| F6 Global-over-session | `C` summed over the whole session, not per turn (EXT-0002 s1.1 "judged globally, not per turn") | A session is the unit; the horizon is fixed | "Turns within one session" vs "aggregate over many requests" is open (EXT-0002 U4) |
These can be combined (for example F6 as the accounting unit, F1 as the decision rule, F4 as the report). [I] Recording a combination is not choosing one: the human/supervisor decides. The cost quantity in `C` (one of `c_vis`, `c_cum`, `c_bill`, or a vector) is a separate choice from the formulation and also unset.

## 7. Regimes (the conditions that may change the answer)
Variables that may move the optimum: catalogue size `n` and tool-length distribution; model strength; whether the provider offers native deferred search or caching; session length `T` and repetition of requests; tool overlap/redundancy; description quality. [U] None of the thresholds between regimes is known. The regime gate D3 is only a real decision if some of these are observable at runtime (S2-S4, S15 are) and a rule connecting them to "restrict or not" is justified by evidence or by measurement; neither is established.

## 8. Accounting boundaries that must be stated, not assumed
- Whether a discovery/search tool's own schema, a gateway's schema, or a code-sandbox prompt counts as "exposed tools".
- Whether tool outputs, history, and reasoning tokens are in scope (S4I section 1 item 2 records exclusion of tool-output and history overhead as a candidate scope boundary; this workspace has not adopted it).
- Whether selector tokens and offline index construction count (REQ-S1 says selector cost must not cancel the savings; offline cost amortisation is unaddressed [U]).
- Whether tokens are priced or counted raw.

## What stays unspecified (and who may specify it)
Thesis-question wording (human); margin `delta`, budget `B`, exchange rate `lambda` (human/supervisor); grade set `G`, stage count `k`, subset size `m`, threshold `tau`, turn budget `T_max` (none selected; any value requires a human decision or measurement); cost convention; session horizon; whether code-mediated access counts as exposure; which models and catalogues.

## Alternatives considered (for this specification)
- Define the problem as pure retrieval (maximise recall@k): rejected here because REQ-O14-08 says a fixed top-N is not a policy and AUTH-004 asks for cost accounting of deciding and discovering; recall alone omits section 5.
- Define the objective as `c_tools` alone: **withdrawn as a rejection** (CH-0001 item 2). The earlier reason (the user says the four quantities are distinct) did not follow. `c_tools` stays a live candidate primary quantity; REQ-O14-01 states the supervisor's restatement in count-of-tools terms; REGISTER G.3 Q1 (restatement or replacement of the token wording) stays open and is not resolved here.
- Merge D0-D3 into one "filter" step: rejected because the signal sets differ (4.2) and a policy may legitimately act at only one of them.

## Falsifier and assumptions
- **Falsifier of this specification's adequacy:** a plausible policy whose behaviour cannot be placed at some D-point with a signal from the register, or a cost the policy incurs that none of `c_vis, c_cum, c_bill, c_turn` records. Either shows the decision problem is under-specified.
- **Assumptions:** (a) the decision structure is turn-based; (b) cost quantities can be recorded per category; (c) signals can be classified R/D/X/P without dispute; the classification of S6/S7/S13 is the most contestable and is posted for challenge; (d) a regime gate is a decision worth modelling.

## Revision 2: additions made in response to CH-0001..CH-0006

### R1. "Unnecessary exposure" (CH-0001)
Three non-equivalent definitions, with class and use:
- **U1 (required-set):** a tool in `E_s` that no successful reference or successful run requires. Needs the success set or gold: class P at runtime; legitimate **only in the scorer/analysis**.
- **U2 (uncalled):** a tool in `E_s` not called in the run. Class X, and policy-dependent (calls are conditional on `E`, so the denominator moves with `pi`); descriptive only, and a poor denominator for comparing policies.
- **U3 (excess over a sufficient set):** the share of `c_vis` beyond a declared sufficient set. Requires a definition of "sufficient" (itself U1 or a curated pool); unset.
Rule: no runtime component may use U1-U3. A policy that learns "tools like this are rarely called" from offline data is class D (S10) and inherits the policy-dependence of U2; it must be listed under S10 with its training data. Which of U1-U3 the scorer reports is unset; the thesis needs one stated before any run. Prior position that `c_tools` is not primary is withdrawn (see Alternatives). Q1 stays open.

### R2. The reference `pi_0` and the formulations (CH-0002)
Facts: the flat catalogue on the closest vehicle is about 292k tokens by the repo's own estimate, "over the context of 2 of the 4 matrix models"; "the all-tools baseline exists only for long-context models" (S4G table row, line 28, read directly). The curated reference arm "does not meet the all-tools baseline" (S4D addendum L37, per CH-0002; not re-read by me). Therefore: define `pi_ref`, a declared reference. When expose-all is feasible, `pi_ref = pi_0`. When it is not, `pi_ref` is a named substitute (for example expose-all on the subset of models whose context fits, or a larger-context static pool). The claim "maintained" then means "relative to `pi_ref`" and must say which; a gold-derived pool (U1) is acceptable as a scorer-side reference but is a weaker and different claim and favours restriction. Per formulation:
- F1 needs `pi_ref`; undefined where none exists, and then only the weaker claim is available.
- F2 (budget) and F4 (Pareto) do not need `pi_0`; [I] these are the ones usable when no reference exists.
- F3 needs none but needs `lambda`.
- **F7 (stratified), added:** the F1/F2 constraint applied per stratum (miss / no-miss; tasks requiring a rarely used tool), or to the worst stratum, because a mean can be maintained while a stratum is sacrificed and an omitted tool is a hard failure while an extra tool is a soft cost (S4G s5.1 miss/no-miss separation, per CH-0002; not re-read). Stratum definitions require U1-type information and are scorer-side.
- `delta` in F1 is a free parameter of the same kind as `lambda` (CH-0002 item 3 accepted): neither is justified here.

### R3. Signals for a removed tool, and additions (CH-0003)
Conceded in substance. For a tool **not exposed**, S6 and S7 cannot occur for it: on the closest vehicle "unexposed tools are rejected" and the unknown-tool error lists names from the exposed surface, so it "cannot reveal an omitted tool" (S4G L21, L26, read directly). Hence S13 for a removed tool reaches the policy only by (i) the model's own request, S8, or (ii) a system-side inference from R signals, which is a derived reading with its own error. Added to the register (all derived readings of R signals; each has false positives and false negatives whose cost enters `recover(pi)`):
| # | Signal | Basis | Class | Error cost |
|---|---|---|---|---|
| S16 | Model text expressing inability or asking for a missing capability | S5 + classifier (S11-type) | R input, derived output | FP: needless recovery; FN: missed trigger |
| S17 | Termination event: the model ends or answers without success evidence | S5/S6; new decision point **D5 (at termination)** | R; success itself is X | FP: extra turn when finished; FN: stopped early. Stored sources report agents that "acknowledge and terminate" (cited by CH-0003 from S4F L32-33, second-hand; not re-read by me) |
| S18 | No-progress or repeated-failure pattern over S6/S7 of other exposed tools | S6, S7 | R | FP on genuinely hard tasks |
| S19 | System re-ranking of `K` with the evolving context `h_s` (a re-retrieval over the evolving context as in FitText, whose initiator mechanism is [U]) | S1, S2, S5 | R input; ranking quality unmeasured outside FitText | Retrieval cost per turn; FP re-adds |
EXT-0035/0036 show re-retrieval over the evolving context raising pass rate and top-5 correct-tool availability after a wrong first pick (one benchmark, limits in the evidence map); who initiates in FitText is [U]: an agent-emitted pseudo-tool description with system-executed retrieval appears (EXT-0050/0051) and a system-side novelty condition appears (EXT-0052, as quoted by the challenger); whether they are one mechanism is unknown and FitText section 4.2 is unread (CH-0012, CH-0019; the lead's earlier "system-initiated" label was corrected). Non-initiation: EXT-0047 (MCP-Atlas Table 3; "No Tool Use" share of diagnosed failures, e.g. 25.7% for Claude Haiku 4.5, 9.1% for Opus 4.7) concerns the task's own visible tools (per the lead's reading of EXT-0048/0049, not re-read by me); whether a model would call a search tool when a needed tool is absent is [U] in the stored corpus. It is silent on discovery initiation (correction after CH-0012: not "both ways"); it is not used to prefer system- or model-initiated recovery. S17 means the model's own end-of-attempt event; its firing rule and any verifier are defined in the N4 row of the node table in DPR-0003 section 1 (CH-0011); derived signals S16-S19 inherit the vehicle-contamination rule of R5.

### R4. The regime gate D3 (CH-0005)
Position: **reading (A) is adopted for the specification**: D3 is a configuration choice made once by the operator from regime facts (an evaluation stratification variable), not a runtime node of the policy, unless and until a runtime determinant is demonstrated. Reason: the quantities that plausibly decide whether restriction pays (load probability and reloads, expected session length and repetition, cache share of cost, achievable cache hit rate) are future or provider-internal quantities, not R at D3; S9 appears only after the first call. Importing a vendor threshold would be a fixed cut-off (REQ-O14-08, AUTH-004). Consequences: (i) DPR-0003 shows the gate as a pre-policy configuration box, not a policy decision; (ii) reading (B) survives as hypothesis HYP-0001 with a falsifier. EXT-0041 gives a break-even form for skills, not tools (transfer assumed [U]).

### R5. Leakage routes (CH-0004)
Accepted additions:
- **Vehicle-conditioned classes.** S2 is R in deployment, but on the closest vehicle distractors outside the reference trace carry `{"type":"object"}` stubs while same-server siblings can carry real schemas, and "schema richness can act as a cue for the right tool" (S4G L23, read directly): there S2 has a gold-membership proxy. S7 content on that vehicle (cache-miss and unknown-tool messages) steers "toward the reference route in every arm" (S4G L26). Rule: on any benchmark vehicle, S2 and S7 are marked "vehicle-contaminated" until it is shown which metadata fields are controlled.
- **D-class routes added to S10:** tuning policy parameters (`k`, `tau`, `m`, `G`) on the evaluation tasks (same-data composition; S4D addendum L19 per CH-0004, not re-read); catalogue overlap between offline data and test catalogue; pretraining contamination of selector or embedder by the public benchmark [S: no measurement found in the workspace]; D3-style regime facts measured on the evaluation tasks. Rule: all policy parameters and offline artefacts are fixed on data disjoint from the evaluation tasks, and the split is recorded.
- **What would demonstrate legitimate availability of a P-class signal:** the signal is shown to exist at decision time in a described deployment without the benchmark's annotation (for example, produced by a component that has no access to gold and that would exist outside the benchmark), and its production does not depend on the reference solution. Without both, it stays P. This makes the escape clause testable. **Checkable form adopted from CH-0016 item 2:** run the component with the benchmark annotation fields removed or permuted; if its output changes, it uses them and the signal is P in that component. This is a necessary test only: it catches direct use, not leakage through correlated fields (for example schema richness as a cue), which the vehicle-conditioned notes above address.

### R6. Smaller defects (CH-0006)
- Label fixed (caching bullet now cites vendor documentation EXT-0008/0014 as vendor claims).
- `L(t)` and `c_vis` are conventions: they depend on the tokenizer and on how the provider renders the tools block (Anthropic bills the `tools` parameter plus a tool-use system prompt: EXT-0022 per the map, not re-read). Any run states its tokenizer or uses provider-reported counts; cross-model comparison needs a stated convention [CH-0006 item 2 accepted].
- **Cost of deciding** is not a single term: `decide(pi) = sum over decider invocations of cost(candidates read, text length per candidate, decider model)`. This dependence is what any multi-stage argument turns on (DPR-0002 section C). `P` depends on `E_s`, the model and `h_s` (distraction by other tools), not on `pi` alone.
- **Legitimate inferences** (with input signals; each carries classifier/inference error as a cost): task category and required capabilities from S1 (S1+S2, S11); whether a needed capability probably exists in `K` (S1+S2); expected session length from S1 (weak, future-facing, S1); degree of redundancy among tools (S2, offline S10); the model's remaining uncertainty (S5, S16-S18).
