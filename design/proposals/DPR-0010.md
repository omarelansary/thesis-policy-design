# DPR-0010. Independent ranking of benchmark candidates per V5 experiment

Status: **proposed**. Nothing here is approved, validated or final. Choosing a benchmark is the human's decision. I did not look for or read the lead's ranking (section 7 of `17` is empty in the copy I read). Labels: [F] a fact in a cited source (register row, inspector report, summary), [I] my interpretation, [U] unknown, [S] speculation. Stored ids omit the prefix `v5-bm-`. Register rows are cited as "17 s5" (property cards), "17 s6" (criticism), "17 s4" (constructs). I have read the register's rows, inspector reports I1 and I2 and `05`; I did not re-read the stored pages themselves, so every [F] below is as good as the register's and the inspectors' wording, with the limits they state (the inspectors' quotes are a small model's renderings; I1 used raw GETs outside its named tools).

## 0. Reading and method

**Claim.** For each experiment I rank candidates by (1) the hard requirements of `17` s4, applied as written, (2) construct fit, (3) the scored properties. A candidate is described by where its tasks (T), tool definitions (D), environment (E) and scorer (S) come from, as `17` s1.2 requires. Every candidate needs M0 (V5's own harness, `17` s4 "Common to every option"), so M0 is not repeated per candidate.

**Method choices of mine [I].**
- I do not prefer existing over constructed material, or the reverse. Where constructed material wins it is because it is the only way to meet a hard requirement, and then I say so.
- The biggest finding of the cards for my purposes: **only one stored candidate is offline, deterministic, has no judge, no simulator, no keys, ships a train/dev/test split and holds a real definition catalogue as files: AppWorld** (17 s5: 457 API definitions as files in `api_docs/function_calling/`, in-process, reset per task, unit-test state checks, Apache-2.0 with encrypted bundles; I1 section 6). Every MCP-native candidate (MCP-Atlas, MCPVerse, Toolathlon, TheMCPCompany, LiveMCPBench, MCP-Universe, MCP-Bench, LiveMCP-101) either has no definitions file, depends on live services or keys, uses an LLM judge, lacks a licence, or has no open-weight evaluation (17 s5). That is the reason AppWorld appears in many rankings below, not a wish for diversity or concentration. The cost is a construct mismatch: AppWorld's APIs are Python-style API definitions in OpenAI function format, not MCP servers [F, 17 s5, I1 s6]; whether that matters for the thesis question is not decidable here because the question is not supplied [F, `17` s1.2 flag].
- Facts about AppWorld not in the register that I use are marked [U: from memory, steward to check]: that its 750 tasks derive from scenario templates with several variants each. I do not rely on it for a ranking; it only affects how the P1/E2E session construction is done.
- Sample-size remarks use arithmetic only [I]: a paired difference in success has standard error about sqrt(d/n), where d is the share of discordant pairs; for n = 168 and an assumed d of 0.2 this is about 3.5 points (interval about plus or minus 7). The assumed d is not from any source.

## 2. P5. Break-even n* and billing of deferred definitions

**Construct (17 s4).** Billed input per request as a function of definitions offered, token sizes and offering mode, on this route; whether deferred definitions are billed. Accuracy not measured. Hard: H1 real or size-matched definitions; H2 sizes span D-01's n* per tokenizer; H3 stub tool results; H4 licence.

### Ranked candidates
**P5-1. Real definitions from AppWorld, swept, plus constructed filler for sizes above 457.** D: AppWorld `api_docs/function_calling/` (457 OpenAI-style definitions, 9 apps) for sizes 5 to 457; beyond that, copies with renamed identifiers and perturbed descriptions (constructed; labelled). T: one constructed short instruction per size (no gold needed; accuracy not measured). E: none; a stub returns fixed text (H3). S: none, billing read from usage records.
- Modification: a stub environment, my own harness; the definitions are used locally only.
- Hard requirements: H1 real [met, 457 as files; format is not MCP: partial]; H2 457 spans n* (11-77 at d = 250) and gives a size-by-size sweep including the window question (D-01 section D lists window effect) [met]; H3 [met]; H4 Apache-2.0, bundles encrypted, and a request not to post derived plain text [F, I1 s6] [met for local use; must not store definitions in the repo].
- Trade-offs: real definition length varies per app, so n and total tokens are confounded unless sizes are drawn at fixed token budgets as well as fixed counts [I]. AppWorld definitions have not been measured for tokens (I1: "size unmeasured") [U]. Not MCP format; MCP adds fields (annotations, outputSchema) and a different description style [S].
- Would change my ranking: a measured AppWorld mean definition length far from 250 tokens (either way) lowers P5-1 relative to P5-3.

**P5-2. Fully constructed catalogue with controlled token sizes.** D: generated definitions at fixed token counts (e.g., a grid around the anchors in X6), counted on the route. T/E/S: as P5-1.
- Meets H1 only through "size-matched to a documented distribution" (thin, see X6); H2, H3 met perfectly; H4 trivially.
- Trade-offs: the best isolation of the variable [I] and the only way to fix d exactly; weakest in realism. The register itself says a constructed catalogue "may isolate the variable better than any benchmark" (17 s4). If the aim is only the break-even and the cache behaviour, realism of descriptions matters little because billing counts tokens [I]; it matters for whether a text shape (JSON schema nesting) changes the tokenization ratio [U].
- I rank it second only because P5-1 adds real text at small cost; I would run both and report them separately (the difference between them is itself informative).

**P5-3. Real MCP schemas read from running servers (MCP-Atlas image, 20 keyless servers; or LiveMCPBench `all_config.json` keyless set).** D: `POST /list-tools` on the sandbox [F, I1 s1(c),(g)]; the schemas are the servers' own, in MCP format. T/E/S: stub as above.
- H1 met best in kind (real MCP). H2: the keyless set is probably under the full 220/307 tools [I]; spans n* (11-77) but not R-large. H3 met (tools are never called). H4: code MIT, data CC-BY-4.0, no image terms found [F, I1 s1(h)].
- Cost: Docker image, 4 data prefixes missing from the image, 220 vs 307 unreconciled [F]; schemas obtainable only by running servers. Cost to run is the highest of the three, for a gain only in format fidelity.
- Would change my ranking: a measured token-size difference between AppWorld-style and MCP-style definitions above, say, 20% (threshold mine, to be set by the human) would move P5-3 to rank 1.

### Rejected for P5
- MCP-Zero tool set (2,797 tools): fails H1 strictly; definitions are LLM-extracted from READMEs, not MCP schemas (I1 s3, i16, i17). Hosting also blocked (LFS quota exhausted) [F].
- TheMCPCompany (18,505 tools): no licence file, definitions file not found (17 s5, I1 s5) -> H4 fails; also its Azure REST-spec tools are generated, not authored.
- Toolathlon (604 tools): no licence file; definitions only through running servers, 52 tasks need accounts [F]. H4 fails.
- MCPVerse: no definitions file (a launch config only, I1 s2) -> H1 fails as shipped, but its token figures anchor the size sweep.
- PolicyLayer corpus: no download, a vendor (**X**), moving snapshot -> usable only as a documented distribution, not as material.
- BFCL, tau2, ToolSandbox: catalogues of 12-34 tools cannot span n* upward (H2).
- ToolMATH (about 12k synthetic Python tools): real-looking but synthetic and math-specific; CC BY-SA 4.0; dominated by P5-2 because its tools are not the thing P5 needs to be real about [I].

### Uncertainty
The largest: all three candidates give definitions whose tokens depend on the route's tokenizer; the sweep must record the counts the API returns. Whether deferred definitions are billed (second P5 question) needs no benchmark at all.

## 3. P3. Do models search when the needed tool is deferred?

**Construct.** Search probability and what follows, across cells (deferred but present, absent, wrong tool visible, oracle) with and without a one-line index. Hard: H1 gold set of needed tools (with the correction X2), H2 catalogue in or above R-mid, H3 defer or withhold a tool without editing the tools array, H4 reproducible tool answers, H5 no live drift.

### Ranked candidates
**P3-1. AppWorld train/dev tasks with AppWorld definitions (all 457 or a 100+ subset), cells built by V5's harness.** T: train (105) and dev (60) tasks, whose reference solutions are public, so the needed APIs can be read from them; gold from the reference code, equivalents adjudicated on a pilot (X2). D: the 457 definitions as files (offered by V5's harness; the benchmark's own approach already uses a task-specific selected subset of up to 20 APIs fixed per task [F, I1 s6]). E: in-process, offline, reset per task. S: tool-call match against the gold APIs (own code) plus AppWorld's unit-test state check as a secondary score.
- Hard requirements: H1 met with amendment X2 (not met as written, nothing meets it); H2 met; H3 met by the harness (definitions are in a list I build); H4 met (offline); H5 met (no live service).
- Modifications: V5's request layout; cell construction (which API to defer/withhold); tasks are multi-step with many API calls (about 42-47 [F, 17 s5]) so "needed tool" occurs many times per task; I would count per needed API, with task as the cluster [I].
- Trade-offs: a multi-API task confuses "did not search" with "searched and failed later"; the oracle-registry ablation (`05`, V5-R11) addresses that. Floor: open-weight AppWorld scores are not in the stored cards beyond "open models in the paper" [U]. Contamination: public since 2024 [S].
- Would change my ranking: a pilot showing the route models score near zero on dev (floor) would move P3-2 to rank 1.

**P3-2. Constructed single-need tasks over real definitions.** T: constructed short tasks, each with exactly one needed tool and a unique, checkable gold (author or generated, then hand-checked), run over AppWorld or MCP schemas as D; E: stub that returns a fixed result for gold and a fixed error otherwise; S: deterministic call match.
- Meets H1-H5 most cleanly because the gold is by construction (equivalents controlled by writing tasks whose requirements exclude alternatives).
- Cost: R7 (17 s3): constructed variants may be easier than human-written ones (Gill, outside tool use); single-author selection bias (17 s1.4: "our own selection bias"); a synthetic-only result "is not reported as real-world evidence" (17 s4). Needs a documented construction method and an independent check of gold.
- I rank it second because the construct (a binary behaviour per task) does not need task realism, but the claim "models do not search unprompted" is only credible if the task prompts look like real ones; P3-1 carries that realism.

**P3-3. MCP-Atlas keyless subset (tasks whose called tools are keyless).** T: 500 public tasks; 18 of 100 sampled have all called tools keyless [F, I1 s1(e)], i.e. about 90 of 500 if the sample is representative [I]; gold: reference TRAJECTORY and 2-8 required tools [F, 17 s5]. D: running servers (`list-tools`). E: Docker sandbox with a built-in response cache for whitelisted servers; some keyless servers use live web content [F]. S: own call match (the benchmark's judge reads claims only, trajectory never read [F, I1 s1(f)]).
- H1: gold from trajectory, one path (X2 applies); H2: catalogue of 220/307 declared; H3 met (client-side filtering of ENABLED_TOOLS already exists [F, I1 s1(g)]); H4 partly (cache helps, live web content remains); H5 partly fails (live content).
- Trade-offs: the nearest to the thesis' MCP setting. Ground truth defects confirmed on the third-party issue list (#76, #8, 12 of 89 misaligned by the audit, 17 s6) and write tools on shared state (#71). The sampled pool of about 90 is workable for 20 tasks x 4 cells x 2 variants, but I1's count rests on 100 sampled rows [I].
- Would change my ranking: a frozen, replayable sandbox state for the live-web keyless servers would lift it to rank 2.

**P3-4. BFCL multi-turn missing-function, adapted.** The native design appends held-out functions to the next request's tools list and replaces the user message by a fixed default prompt [F, I2 s5, blog **A**]; the checker has no code for held-out functions, and Epoch found defects in 24 of 50 sampled items (48%) [F, 17 s6, **I**]. The native catalogue is small (fails H2 without padding), and appending a function is a tools-array edit (fails H3 as shipped).
- Everything of the "adaptation" is a rebuild: the only thing kept is the idea (a function held out). I rank it fourth: the register's and `05`'s preference for BFCL seems to be a prior choice (17 s1.4 says so).

**P3-5. ToolMATH "Distractors-only" / Fail-TaLMs "chosen tools made unavailable".** Both match two cells (distractors without the target; target removed), have large synthetic catalogues (about 12k; 906) and deterministic (ToolMATH exact match) or GPT-4o-graded scoring (Fail-TaLMs). Environment of Fail-TaLMs not established; ToolMATH is single-turn math with Python tools [F, 17 s5]. Weak on realism; useful as a method precedent. Rank 5.

### Rejected for P3
MCPVerse, MCP-Universe, MCP-Bench, LiveMCP-101, Toolathlon-web, MCPMark remote services: live drift (H5) or keys; MCP-Bench also uses a single model (o4-mini) as generator and judge [F, 17 s6]. tau2-bench, ToolSandbox: catalogue 12-34 (H2), user simulator problems with open-weight models [F, e05].

### Uncertainty
P3 outcomes depend on the wording of the prompt and the index line; whichever candidate is picked, two prompt variants (as `05` says) are the main source of spread. The Tool-DE finding (one gold under-credits) bears directly on how P3 counts a "wrong-tool call" and is stated only by extension (17 s6).

## 4. P1. Memory-informed offering for returning users

**Construct.** Effect of seeding tools needed before on the bill and accuracy for returning users, with seed hit rate h. Hard: H1 several sessions per user with later sessions needing earlier tools (recurrence measured); H2 catalogue above n*; H3 harness decides where memory goes; H4 no simulator or judge the route cannot serve; H5 history-needed check (corrected by X3).

**Finding to report first [F, I2 s7 and 17 s4].** No candidate was found with more than about 100 tools in which later sessions need tools used earlier. A construction is therefore unavoidable, as `17` s4 already says.

### Ranked candidates
**P1-1. Constructed returning users over AppWorld.** T/E/S: AppWorld tasks (train/dev for the loop, test for E2E), offline and deterministic, unit-test scorer, no simulator, no judge. A "user" is a constructed sequence of 2 or more tasks that share apps or APIs; **recurrence is measured from the reference solutions** (the share of session-2 required APIs that session 1 used), and a family of sequences is generated at several recurrence levels. D: the 457 definitions. Tool record: the memory rule's seed set comes from the tools actually called in prior sessions (V5-R13, `05`), under V5's harness.
- Hard requirements: H1 met by construction, with recurrence reported; H2 met (457); H3 met; H4 met (nothing to serve); H5 as corrected met (recurrence).
- Modifications: the user is constructed (not human); gaps are a V5 variable (the harness chooses time between sessions, e.g., longer than the cache lifetime of 4 h on gpt-oss-120b [F, `10` s11 via STATE]); no real-user history.
- Trade-offs: the recurrence level is what P1's answer depends on, and I choose it, so the result is a function of my construction, not a measure of how real users behave. That must be stated; the result can say "at recurrence r, the bill is X", not "returning users save". If the AppWorld scenario-variant structure exists [U: from memory, steward to check], the natural recurrence is high by design and over-favours seeding [S]. Mitigation: report results across a recurrence grid including values at which seeding should fail.
- Would change my ranking: a native multi-session benchmark with a larger catalogue and tool-level recurrence discovered later (I2 s7 says none found).

**P1-2. ATRBench, padded.** T: 20 personas, 568 learning sessions, 284 rule/test pairs; scorer deterministic tool-level match; Apache-2.0, personas CC BY 4.0; reports list and cache-discounted cost with hit rate per cell [F, 17 s5, I2 s3]. D: 74 tools in custom YAML (73 domain tools + confirmation); fixed array per session [F, I2]. 
- Hard requirements: H1 learning-then-test sessions exist; whether later sessions need **tools** used earlier is not shown, because memory carries preferences, not tool names [F, I2 s3] -> H1 unverified/probably partial; H2 74 tools natively (borderline, X4) -> padding needed; H3 memory is appended to the system prompt once per session by the benchmark, V5 would replace that [F]; H4 user simulator pinned to GPT, router to Gemini, Responses API, model map restricted to eight ids [F, I2 s3] -> a loop on this route needs code changes and a re-validation of the simulator; H5 n/a.
- Strengths: the only native multi-session candidate with deterministic scoring and explicit cache accounting; no independent criticism found, which is absence of scrutiny, not quality (17 s6 reading).
- Would change my ranking: a read of the 284 rule/test pairs showing that test-session gold tools recur from learning-session tool calls.

**P1-3. VitaBench 2.0.** 56 users, 771 subtasks, sequences over days to months, native gaps; MIT code, dataset licence not shown; LLM user simulator and rubric judge (gpt-4.1), agreement not reported; tool list rebuilt per subtask; about 12 tools per domain (66 per paper) [F, 17 s5, I2 s2]. H1 plausible; H2 fails (padding needed); H3 harness has memory modes null...custom; H4 fails unless simulator and judge are replaced and validated. Native time structure is a strength P1-1 lacks. Rank 3.

**P1-4. Momento.** 161 tasks, 1-5 past sessions each, one task per user in the sample, only the last task runs, 26 tools, DB state scorer, tools array fixed at construction [F, I2 s1]. H1 fails (the past sessions are text, not runnable earlier sessions needing earlier tools; one run per user), H2 fails. Rank 4 (reuse of its stored-session design only).

**P1-5. MPT.** 13 functions, argument matching only, CC BY-NC-SA 4.0 [F]. H2 fails; scorer is weak. Rank 5.

### Rejected for P1
ETAPP (no multi-session structure, no licence file), DolphinBench (details not stored; **X** Mem0; licence not stated; the with-and-without test is X3's different construct), Mem2ActBench, EvoMemBench, PEToolBench, PTBench, APOLLO, Evo-Memory (triage, 17 s5). A fully synthetic per-user generator without a task benchmark: dominated by P1-1, which at least starts from tasks and checks written by others.

### Uncertainty
H4 is the practical bottleneck for every native option: whichever user simulator is used must be served by the route (open-weight only) and re-validated; tau2's own issue #710 shows a gpt-oss-120b simulator merging turns in 5 of 12 runs [F, 17 s6]. P1-1 avoids it; the price is that real-user behaviour is not tested.

## 5. P2. Offering a subset at a fixed cached prefix

**Construct.** Accuracy with only a subset offered, all definitions in the cached prefix, against all offered; no prefix break. Hard: H1 gold set per task, H2 R-mid catalogue with all definitions declarable, H3 reproducible, H4 multi-step.

### Ranked candidates
**P2-1. AppWorld dev (and train) with all 457 definitions declared.** The benchmark's own agent already selects up to 20 APIs per task and fixes the array [F, I1 s6], so "subset offered" has a native counterpart, and the gold subset (oracle ablation) is read from reference solutions. Offline, unit-test scorer (no judge), reset per task, multi-step (42-47 calls). Requirements H1-H4 met (H1 as in X2). Modification: the "all in prefix, subset visible" arm requires a route mechanism found by P0; `allowed_tools` is rejected on this route [F, STATE], so the subset arm must be realised by another means (e.g., the subset named in a trailing message) -- the design question P2 itself is testing, not the benchmark's concern. Trade-offs: floor/ceiling on the route models [U]; AppWorld is not MCP; contamination [S]. Pool: dev 60 + train 105 for the loop, test_normal 168 / test_challenge 417 for a confirmatory run (the split is AppWorld's own: held-out sets are disjoint from pilots by construction [I]).

**P2-2. MCP-Atlas with all 220 (or 307) declared vs ENABLED_TOOLS.** ENABLED_TOOLS (13-30, mean about 15) is applied client-side already [F, I1 s1(d),(g)], so the benchmark has a native "subset" arm; gold = reference trajectory (2-8 required). Scorer: LLM judge on claims, judge-human agreement 78% on 100 tasks, 12 of 89 misaligned [F, 17 s5, s6]. H3 partly fails (live web content on several keyless servers, shared write state). Use only the keyless subset (about 18 of 100 by called tools [F]) -> small pool. Closest to MCP in practice; weak reproducibility and scorer. Rank 2.

**P2-3. Toolathlon, local-only 31 tasks** (inspector's classification [F, I1 s4]; 604 tools, 69.9 per task, deterministic state scripts). No licence file; open-weight scores 13-20% [F] -> floor makes an accuracy difference "nearly the same" by default (17 s1.4 floor and ceiling). Rank 3.

**P2-4. tau2-bench** (12-15 tools; fails H2 without padding; simulator and judge problems on the route). Rank 4 and only as a padded variant.

### Rejected for P2
BFCL multi-turn (small catalogue, 24 of 50 sampled items defective), MCPMark (floor 4.72% for gpt-oss-120b; 12 of 28 Postgres tasks passable without work), MCP-Universe / MCPVerse / LiveMCP-101 / MCP-Bench (live, keys, judge; MCP-Bench ceiling 0.668-0.692 compressed [F]).

### Uncertainty
The loop has about 20 tasks per arm (`05` s1), so only a large loss is visible. With AppWorld dev's 60 tasks and several repeats the loop could be larger at similar cost [I], a point for the human.

## 6. P4. Observation masking in long runs

**Construct.** Effect of masking old tool output on the bill and accuracy of long runs. Hard: H1 native large tool results (measured, not padded), H2 long runs, H3 deterministic final-state scorer, H4 reproducible environment.

### Ranked candidates
**P4-1. SWE-bench Verified subset (by stratified random sampling with a recorded seed, R6) -- if a floor pilot passes.** T/E/S: GitHub issues with repository containers and unit tests; large file reads and test logs are the tool results; tests are the scorer. D: bash and editor tools only (the catalogue is irrelevant to P4, see X1). Requirements H1-H4 plausible [I, SWE-bench structure not examined by the scouts] but not verified in the stored cards: no property card exists for it. The cache-read share above 97% (SWE-ContextBench, v5-ls-e03) is the one stored fact bearing on it. Flaws: Verified has broken tasks (16.4% floor from the OpenAI audit, **X**; Epoch e02) [F]; paired arms put scorer error on both arms. Contamination high [S] but irrelevant to billing mechanics. Floor on the route models [U]. Rank 1 conditional on X1 being accepted and a pilot being run; if the human holds that P4 must stay within tool-catalogue deployments (`05` s2: "if P0-P5 show deployments with large tool results"), then P4-2 is rank 1.

**P4-2. MCPMark Filesystem and Postgres (local) tasks.** T: 127 tasks over 5 servers; local: Filesystem, Postgres; remote: Notion, GitHub (accounts). D: per-server tools. E: local and reproducible for the two local servers. S: programmatic verifiers (deterministic); but 12 of 28 Postgres tasks passable without the work (issue #278, **I**), a median 22% of tasks flip between identical runs and 559 of 11,314 runs end without verdict, counted as failures (issue #272, **I**) [F, 17 s6]. Input 64K-1.4M tokens per task and about 16 turns (Table 9) -> H1 and H2 met by the paper's own figures [F, 17 s5]. Floor: 4.72% (gpt-oss-120b) to 24.80% [F] -> accuracy half of P4 invisible on that model; bill half unaffected. Apache-2.0 [per `03`]. Rank 2 (construct fit highest, floor and defects worst).
- The 05 text names MCPMark as the closest stored benchmark; I agree on construct, disagree on rank because of the floor and the reported flip rate.

**P4-3. Toolathlon local-only subset (31 tasks).** Deterministic scripts; about 20-27 turns; cost with caching on (no hit rate) [F]; no licence file; floor 13-20%. Tool-result sizes not in the cards [U] (H1 unverified). Rank 3.

**P4-4. AppWorld.** Long single-task runs (42-47 calls), offline, unit tests; API response sizes unmeasured [U]; the H1 "native large results" is the question. If measured sizes are small, it fails H1. Rank 4 pending a measurement.

**P4-5. Constructed large-output tasks on local servers** (filesystem with large files, Postgres with large result sets, deterministic final-state check). Meets H3 and H4 by design; H1 is arguable because results are large by task design, not padded, but their size distribution is my choice. Honest label: synthetic; not real-world evidence. Rank 5, useful as a control that isolates the mechanism if the others have floor or defect problems.

### Rejected for P4
MCP-Atlas / MCPVerse / LiveMCPBench (judge scorers, live, short traces), BFCL and tau2 (small results), Terminal-Bench (not examined; no property card -- listed for a steward to triage under X1).

### Uncertainty
The size of tool results is the property that drives the bill for P4 and is "rarely reported" (17 s1.4); I need measurements from data for every candidate. I rank them with that missing.

## 7. E2E. V5-R against simpler policies, regimes and session patterns, at least two models

**Construct.** Bill per turn and accuracy across regimes and session patterns. Hard: H1 realistic tasks with gold and a scorer of known or measurable reliability; H2 R-small to R-large natively or by declared extension; H3 a session axis by a declared extension; H4 repeats feasible on the route. I add H5 (X5).

No single stored benchmark meets H1-H5. I rank **combinations**.

### Ranked candidates
**E2E-1. AppWorld base with declared extensions (regimes by app subsets and padding; sessions by P1-1's construction).** T/E/S: AppWorld test_normal (168) and test_challenge (417) for confirmatory, train/dev only for loop items. D: 457 real definitions (R-small: one or two apps, about tens of definitions; R-mid: all 457; R-large: the 457 plus constructed filler, labelled; the filler's size distribution anchored as in X6). Sessions: constructed chains with measured recurrence and gaps shorter and longer than the cache lifetime. Scorer: unit tests, no judge. Cost: lowest per repeat among stored candidates [I] (no live services, no simulator); repeat feasibility H4 met.
- H1: realistic in the sense of AppWorld's task authors; scorer reliability is "unit tests" and has only small evaluator bugs on its issue list (titles only, `P`, 17 s6) -- the best-scrutinised deterministic scorer here but still not an independent audit [I]. H2 natively R-small to R-mid, R-large by declared extension. H3 declared extension. H5 met.
- Resolvable difference at n = 168 (paired, assumed 20% discordance) is about plus or minus 7 points at 95% [I]; the register's open question (estimation-only versus a margin) is not changed.
- Weaknesses to state in any report: AppWorld is Python-style APIs, not MCP; contamination possible [S]; open-weight performance not established in the cards [U]; all sessions and recurrence are constructed.
- Would change my ranking: a pilot floor/ceiling problem on the route's models; a human decision that the claim must concern MCP servers (then E2E-2).

**E2E-2. E2E-1 plus a second, real-MCP arm: MCP-Atlas keyless subset (or LiveMCPBench keyless set with results frozen).** The second arm checks whether the bill ratio (a common unit, R2) holds under real MCP schemas, with the heterogeneity shown, raw accuracy not pooled across scorers. MCP-Atlas: pool about 90 of 500 if I1's sample generalises, LLM-judge scorer with the judge pinned and validated on a pilot (R4); live content in several keyless servers remains a variation source (X5) -- a record-and-replay of tool results would be needed [S]. LiveMCPBench: 527 keyless tools (the largest keyless real-MCP set, spans R-mid to R-large), apache-2.0 data, a `route` tool of its own, "time-sensitive" tasks and a judge with a fixed bug (#9, **I**), open-weight range 30.5-48.4% [F] -> no floor problem. Rank 2 because it costs more, and its judge/live issues are known; it is the better test of the thesis' MCP framing.

**E2E-3. ATRBench padded to R-mid/R-large.** Native multi-session, deterministic scorer, cache accounting, Apache-2.0 (P1-2 above). H4 needs code changes for the route (eight-model map, Responses API, GPT-pinned simulator [F, I2 s3]). Preference-learning, not tool recurrence; so the session axis does not test V5's memory rule unless gold tool recurrence is confirmed. Rank 3.

**E2E-4. VitaBench 2.0 with a replaced simulator/judge** (native days-to-months gaps). H1 judge agreement not reported; tools about 12 per domain; padding needed. Rank 4.

**E2E-5. tau2-bench v2.0.0 padded.** Custom agent supported (`HalfDuplexAgent`), MIT, DB-state plus NL judge; open issues on empty replies dropping out of the denominator (#672) and open-weight simulator failure (#710) [F]. Catalogue 12-15. Rank 5.

**E2E-6. A fully synthetic study** (constructed catalogue, tasks, sessions). Cheap and fully controlled; but the register's own rule bars reporting a synthetic-only result as real-world evidence (17 s4); useful only as a mechanism control. Not ranked as a primary.

### Rejected for E2E
MCP-Bench (ceiling 0.668-0.692; generator and judge the same model), MCP-Universe (keys; reproducing 11 against a published 24.44, #45), MCPVerse (live, "no longer executable/reproducible"), LiveMCP-101 (no release found), TheMCPCompany (no licence, no open-weight results), Toolathlon (no licence; 52 of 108 tasks need accounts; floor), MCPMark (floor, flip rate), MPT / Momento / ETAPP / DolphinBench (see P1).

### Uncertainty
Whether to pool: by R2 only paired bill ratios can be pooled; accuracy is per scorer. With two or three models, agreement testing does not apply (R2). The number of benchmarks follows the claim (17 s1.3); I recommend two (one deterministic offline, one real MCP) for a headline claim about MCP deployments and one if the human restricts the claim to what AppWorld represents.

## 8. V5 assumptions the evidence challenges (reported, not changed)
1. `05` P3 "BFCL's withheld-function design adapted to deferral": the native design appends the held-out function to the tools array of the next request and replaces the user message by a default prompt [F, I2 s5]; it tests whether a model recognises that a function is missing, not whether it searches. The adaptation is a rebuild. Epoch's 48% defect rate on sampled items [F, 17 s6]. Challenges the idea that BFCL is "a" design to adapt.
2. `05` P1 "ATRBench's learning-then-test sessions are the closest stored design": memory in ATRBench carries preferences, not tool names, and the simulator/router are pinned to other vendors' models [F, I2 s3]. Closest in structure, unverified in construct.
3. `05` P4 "MCPMark's set was the closest stored benchmark": construct fit yes; floor 4.72% for the open-weight model named in the paper, 22% median flip between identical runs (deprecated logs), 12 of 28 Postgres tasks passable without work [F, 17 s5/s6]. Challenges the use of accuracy as the second P4 outcome on that model.
4. `05` s1: about 20 tasks per arm. For P3 and P1 the pools are larger (AppWorld dev 60, train 105; MCP-Atlas keyless about 90 [I]); the 20 reflects cost, not availability. Not a challenge to the decision rule.
5. D-01's d = 250 tokens per definition: MCPVerse's two figures give about 200 and 254-266 tokens per tool [I, arithmetic from 17 s5]; PolicyLayer gives a per-server median (1,864 tokens) with an unknown tools-per-server count (**X**). So 250 is in the range of one benchmark's figures [I]; it is one source family, and V5-R's regimes would be better stated as a range of d. D-04 already varies d [F, STATE: "D-04 varies only r, w, o"] -- note it does not vary d; `calc/regime_bill.py` section C does ("by definition length").
6. The phrase "R-large" lacks a numeric size in what I read. The largest real catalogues in the stored cards are MCPVerse full (552 tools, about 140-147k tokens), Toolathlon (604), AppWorld (457), LiveMCPBench (527 keyless) and TheMCPCompany (18,505, generated). Whether R-large means the first group (hundreds) or the last (thousands, beyond a 200k window) changes the candidate set; D-01 section D already asks about the window.
7. `17` s1.2 "older, more vetted ones tend to have small catalogues and a higher risk of being in training data" -- consistent with my reading for BFCL and tau2; AppWorld is an exception on catalogue size (457), not on age.
8. `17` s6 reading "every audited benchmark shows an error rate of one in ten to one in two": AppWorld's issue list is titles-only (`P`), so its place in that sentence is not established either way. This reading cuts against my top pick; I treat it as the main reason to require a scorer check on the actually used subset (R4).

## 9. Alternatives I considered and did not adopt
- Rank by leaderboard presence or independent evaluation: rejected (17 s1.2 [refine]); independent evaluation is thin in this niche and scored as a property.
- Use one benchmark for all experiments: attractive (one harness) but P3 and P5 benefit from constructed cells; P4 needs large outputs. Using AppWorld for P2, P3, P1, E2E and (maybe) P5 is a consequence of the cards, not a decision to concentrate; and it makes the thesis's evidence depend on one benchmark's properties (an overall risk I name in section 10).
- Use an MCP-native benchmark as base for E2E: only if the human's question requires MCP-only claims; otherwise reproducibility (X5) dominates.

## 10. Falsifiers, assumptions, limits
**Falsifiers (what would change my ranking).**
- A floor/ceiling pilot on the route's models: if success on AppWorld dev is near zero or near one for the models in use, P2/P3 move to P3-2/P2-2 (constructed or MCP-Atlas).
- A steward check that AppWorld's definitions have a mean token length far from 250 tokens, or that its response sizes are small (P4-4 falls, P5-1 moves relative to P5-3).
- A read of ATRBench's 284 rule/test pairs showing tool recurrence across learning and test sessions (P1-2 rises above P1-1 for realism).
- A human decision that results must be about MCP servers specifically (E2E-2 or MCP-Atlas-based options rise).
- A property card for SWE-bench Verified / Terminal-Bench showing small tool results or an unrunnable setup on the route (P4-1 falls).

**Assumptions.** (1) The register's property cards and the inspectors' counts are correct as stated (I did not re-read the stored pages). (2) AppWorld's package can be used locally with an Apache-2.0 licence and encrypted bundles without redistribution; I did not read the licence myself. (3) The route's models can call functions in a Chat Completions format with a 457-definition tools array within their window: 457 x about 250 = about 114k tokens [I, arithmetic], which is within a 200k window but near some route models' limits [U]; the window of each route model should be checked. (4) The recurrence parameter of constructed sessions is a free variable, and the result is reported as a function of it.

**What this proposal does not claim.** That AppWorld represents real deployments; that any candidate is valid for the thesis question (not supplied); that constructed sessions represent real returning users; that the ranking is independent of the lead's (I did not see it, so any agreement is not evidence of correctness either); anything about open-weight accuracy on AppWorld or SWE-bench (not in the stored cards).

**Unresolved limitations.** No property card exists for SWE-bench Verified or Terminal-Bench; AppWorld's token and response sizes, scenario/variant structure, and open-weight scores are unmeasured in the stored material; AppWorld's issue list is read by titles only; the numeric meaning of R-small/R-mid/R-large is not fixed in what I read; the threshold and margin question (estimation-only versus a margin) is the human's.
