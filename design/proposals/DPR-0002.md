# DPR-0002: Mechanism families, simpler comparators, multi-stage conditions, recovery

**Proposal.** Compare nine mechanism families against the decision problem of DPR-0001 (revision 2). For each viable family give a complete comparator policy that is simpler than a staged version of it. State the conditions under which a stage is justified and those under which a single stage or no restriction dominates. State the recovery case in full. Conclude, where the evidence supports it, that parts of a staged structure are **not presently justified**. Nothing here is a finding; every effectiveness claim is a hypothesis (see HYP records) unless an EXT id supports it at the stated level.

**Requirements it answers.** AUTH-004: "Challenge the assumption that a multi-stage architecture is automatically superior to a simpler policy"; "Examine whether recovery or later capability disclosure is necessary". REQ-S2 (EXT-0002 s1.2): "Required. Think of a policy, not only retrieval"; "Required. A stepwise structure in which each step saves tokens"; "Required. A fallback: 'you should give some way for the LM to query the tools that is in the passive registry and get the details'"; "Required as a lens. Consider graded/partial exposure". These classifications are the earlier researchers' reading of 2026-10-02; REGISTER G.3 Q2 and Q4 (is the staged form binding; does "each step saves tokens" bind a design with re-add) are open. REQ-O14-08: a fixed top-N cut-off "is not a policy". REQ-O14-12/15 are classed `unclear` / `supervisor-example` and are not used as evidence for any design element.

## A. Why exposure count is not the cost: the accounting facts the comparison rests on
- [vendor] Modifying tool definitions invalidates the whole cache (EXT-0008). Adding/removing definitions mid-conversation invalidates it and "the resulting miss can cost more tokens than the definitions you removed" (EXT-0014). OpenAI: changing the loaded tool set "will break the model's cache from that point forward" (EXT-0011, per map).
- [vendor] Discovery can preserve the cache: the discovered definition "is appended inline as a `tool_reference` block ... The prefix is untouched, so prompt caching is preserved" (EXT-0008). Per map, every deferred definition is still sent in the `tools` array each request (EXT-0009): what shrinks is model context, not necessarily payload; and OpenAI says deferral is "mostly deferring the parameter schema" (EXT-0010, per map).
- [F, one corpus] cache reads priced at 0.1x input; "the addressable saving from removing one delivered tool token is an order of magnitude smaller than nominal token counts suggest once that token has entered the cached prefix" (EXT-0016/0018, per map; the study concerns tool-output compression, tool definitions not separated from the system prompt; the "order of magnitude" is the authors' inference). I do not use the number.
- [vendor] Discovery "adds a step and depends on finding the relevant tool" (EXT-0012, read directly). Vendor rule: keep the 3-5 most-used tools non-deferred (EXT-0009, per map).
- [I] Therefore for a provider with prefix caching, the saving from restriction is regime-dependent: visible-token savings overstate billed savings when schemas sit in a cached prefix; they may be exact when caching is absent or the session is short; extra turns re-read context; a restriction that rewrites the prefix mid-session can cost more than it saves. No stored source measures billed cost of catalogue filtering together with task success (map, bounded negative: ledger C3-19, not re-read here). Correction after CH-0015: the S4I erratum Q-1 adds Toollery as a near-miss: selection hit rate .989 (full catalogue) vs .144 (top-10), input tokens -97.5%, billed-input-cost difference inconclusive, single step, authors' own, hit rate not task success (as cited by the challenger, not re-read by me). It is the nearest instance for HYP-0005 and Card A. The cache rule R-cache is a design constraint, not a fact: OpenAI says the break is "from that point forward" (EXT-0011, per challenger and map) and Anthropic "Entire cache" (EXT-0008), while the ledger C3-27 reportedly records a mid-conversation tool-changes beta that withdraws tools without editing the cached array (per CH-0015, not re-read): the withdraw-without-rewrite route is therefore a further candidate to test, not excluded.

## C. Complete simpler comparators (each fully specified; none a straw man)
Each comparator states D-points used, signals, actions, failure handling and what would make it win. Parameters stay symbols (`m`, `G`, `tau`).
- **P0, expose all.** D0: `E_1 = K`, full grade; never changed. Signals: none. Failure handling: none; if `K` does not fit, P0 is infeasible and the reference becomes `pi_ref` (DPR-0001 R2). Wins when `n L` fits, caching is on, the model is robust to distractors (EXT-0026) and tasks are short.
- **P1, static core.** D0 offline: `E_1 = A` (core chosen on data disjoint from evaluation tasks); never changed. Signals: S10, S2. Failure handling: none; tasks needing a tool outside `A` fail. Wins when the workload is narrow and omission cost is low.
- **Scorer rule for P2, P6, P7 (CH-0009 conceded).** "Wins when recall is high" was tautological. The scorer is a named, strong, symmetrically tuned baseline (tuned on data disjoint from evaluation tasks, with the same tuning effort given to any cascade stage; S4D addendum 2.3 per CH-0009, not re-read), and its type (lexical, embedding, LLM, learned) is the first factor of the comparison. Until chosen, P2/P6/P7 are templates.
- **P2, single-stage query-conditioned top-`m`.** D0: rank non-core tools by one scorer on S1 and S2 (scorer type unset), expose the top `m` plus core `A` at full grade for the whole run. No change after D0. Failure handling: none. This is not "a policy" in the sense of REQ-O14-08; it is a comparator. Wins when the scorer's recall at `m` is high and `n` large.
- **P3, deferred loading with a search tool.** D0: `E_1 = A` plus a search/describe tool. D2: the model calls search; matched definitions are **appended after the cache breakpoint** (EXT-0008) as discovered. The *model* decides whether to search, but a relevance decision is still taken by the provider's search component: the API runs a regex or BM25 variant over names, descriptions, argument names and argument descriptions (EXT-0009, read; the default result count and the limit set by the model are per the challenger's EXT-0007/0009 reading, not re-checked). My earlier "system takes no relevance decision" was wrong (CH-0009). Failure handling: if the model does not search, the task proceeds with `A` (the cost is the failure; initiation [U]). Wins at large `n` with a model that initiates, on a provider with append-style discovery.
- **P4, two-grade exposure.** D0: all tools at a cheap grade (name + short description), none at full schema except `A`. D2: the model requests full schema for a listed tool, appended. Failure handling: a tool never requested is never usable; the full list of names still informs the model. Wins when schemas dominate descriptions in token length and catalogue size is moderate. Costs the cheap-grade list for all `n` tools every turn (cached if stable).
- **P4 feasibility note (CH-0009).** The cheap-grade list of all `n` tools is itself `O(n)` tokens per turn; at `n` large enough that even names and descriptions overflow context P4 is infeasible, which is exactly where a cascade may win. P4 is therefore a comparator for moderate `n`; for large `n` the group-level variant P4g applies.
- **P2h, system-run two-level cascade (complete; added after CH-0018).** D0 only. Level 1: a scorer `s_1` (type unset) ranks **groups** (servers/namespaces, using group name and description, S2) against S1 and keeps `g_1` groups (unset). Level 2: a scorer `s_2` (type unset; may be an LLM) ranks the tools **inside surviving groups**, reading only those tools' name and description, and keeps `m` tools; level 2 sees nothing from groups cut at level 1. Exposure: `A` plus the `m` tools at full grade, fixed for the session. Costs: `D = (b_1 + a_1 * #groups) + (b_2 + a_2 * #tools in kept groups)`. Failure handling: none (a variant adds N3). This is the `hier` pattern of EXT-0053 and the retrieve-then-rank pattern cited from S4F-PA (unread), and it is the form REQ-O14-12 describes (class `unclear`). Section D's `b_j, a_j, r_j` model describes P2h; it does not describe P4g.
- **P4g, group-then-tool disclosure (the model-driven two-level comparator; the cascade written out, CH-0009). Feasible range:** the group header list costs `O(#groups)` tokens per turn (cached if stable), so P4g fails when the number of groups is itself too large for context. D0: expose `A` plus group headers (namespace or server name and description; groups of fewer than `g_max` tools, unset). D2: the model loads a group (its tool list at cheap grade), then upgrades individual tools to full schema; all loads appended after the cache breakpoint. No system relevance decision; the group descriptions are the selector, written by the catalogue owner (a signal-quality dependency: S2). Failure handling: a tool whose group is not opened is unreachable; model non-initiation is the dominant risk (HYP-0004). This is the shipped form recommended by OpenAI (EXT-0010). It is a two-stage disclosure by construction; HYP-0002 covers **both** cascades: P2h (system-run) and P4g (model-driven), each against the best single-stage comparator of the same driver type (system-run P2/P6/P7; model-driven P3/P4). A result for P4g says nothing about P2h and conversely. "Any multi-stage design" no longer satisfies the hypothesis.
- **P5, stable meta-tool.** D0: `E_1 = {search, call_tool}`; the tool array never changes; all calls routed through `call_tool` (EXT-0014). Failure handling: argument errors returned as S7. Wins where prefix stability matters and the model can write correct calls from described schemas retrieved on demand. Loses on error-prone argument shapes [U].
- **P6, learned one-shot selector.** As P2 with a scorer trained offline (S10; disjoint data); as P2 otherwise. Wins when training logs exist in the target setting.
- **P7, append-only per-turn re-ranking.** D0: as P2. D1 each turn: re-rank `K` with `h_s` (S1,S2,S5,S6); append newly top-ranked tools after the breakpoint; never remove during the session; allowed evict only at conversation boundary. Failure handling: none beyond the re-ranking. This is a FitText-like form made cache-conscious. FitText (EXT-0035, read), for GPT-5.4-mini: static query 57.6, single-pass 62.1, multi-turn 70.7; the single-pass to multi-turn differences across the three models are +1.7, +2.5, +8.6 points (Qwen3.6-35B 33.5->35.2, Gemma4-31B 57.7->60.2, GPT-5.4-mini 62.1->70.7), and the static-query contrast is confounded (raw-query baseline, per the challenger's S4F-PA L39 reading, not re-read). EXT-0036 reports top-5 correct-tool availability after a wrong first pick (about 7% to 44% on G2-category for multi-turn), which is availability, not task success or cost. **Who initiates in FitText: [U] (both appear; section 4.2 not read).** EXT-0050: "at any step t, the agent may emit a pseudo-tool description dt, causing the system to update the function schema"; EXT-0051: when a "thought node contain[s] pseudo-tool description blocks, the system triggers a dynamic retrieval call". So an agent-emitted request with system-executed retrieval appears. EXT-0052 (per the challenger, CH-0019b) shows a system-side condition, "Dynamic retrieval triggers when: max SequenceSim(o, m) < 0.82 and o not-subset-of m for all m in M" (symbols not defined in the window; appendix on backtracking); whether the two are one mechanism is unknown, and EXT-0050 defers the trigger to its section 4.2, which nobody has extracted. I therefore do not say that FitText supports a model-emitted path, or a system-side trigger, only; P7 as written (system re-ranking each turn) is a design of mine, not a FitText replication.
- **P8, working set.** As P3 but discovered tools persist across the session and across sessions until evicted by a rule (unset). Wins with repeated related requests.

## D. When a stage is justified; when a single stage or no restriction dominates
Model [T, assumptions listed]. Let a cascade have stages `j = 1..J`. Stage `j` reads `n_{j-1}` candidates, keeps `n_j` (`n_0 = n`), has fixed cost `b_j` (calling the component), per-candidate read cost `a_j`, and recall `r_j` (probability that a needed tool present at the input is kept). The single-stage comparator is stage `J` alone on `n_0` candidates with cost `b_J + a_J n_0` and recall `r_J^0`.
- Decide cost of the cascade: `D_cas = sum_j (b_j + a_j n_{j-1})`. Of the single stage: `D_1 = b_J + a_J n_0`.
- **Revision after CH-0007 (model structure conceded).** The model as first written let stage 1 only lose recall. The end-to-end effect is `r_1 * r_2(n_1) - r_2(n_0)`, where `r_2(x)` is stage 2's recall when it reads `x` candidates. The sign is not given by the model: `r_2(n_1)` can exceed `r_2(n_0)` (a smaller candidate set may raise the later stage's accuracy, for LLM readers and for context-size cliffs), so a first stage can *raise* end-to-end recall. Conversely `r_2(n_0)` is undefined if `n_0` exceeds the reader's context (S4G line 28), in which case the single-stage comparator is infeasible, not merely worse. Also `a_j` is not linear in tools in two respects the model omitted: (i) a stage may read **groups** (namespaces, servers) rather than tools: OpenAI recommends namespaces or MCP servers because "token savings are usually more material there" and the model first sees only the namespace or server name and description, with "fewer than 10 functions" per namespace as a best practice (EXT-0010, read); this is already a group-then-tool two-level disclosure, shipped; (ii) a stable catalogue prefix can be cached, so repeated reading of the same candidates is priced at the read rate (EXT-0008, vendor). With positively correlated stage errors, condition (iv) below (compounding) is nearly empty; what remains are cost conditions. The model therefore yields conditions, not a sign; the sign needs measurement (E).
- **Stage 1 earns its place against dropping it** (J=2 case) only if `b_1 + a_1 n_0 < a_2 (n_0 - n_1)` (it saves more expensive reading than it costs) **and** the recall loss it adds is worth that saving: `(1 - r_1) * V < saving`, where `V` is the price of a miss (task failure value plus recovery price, if any recovery exists).
- **End-to-end recall** of the cascade is `prod_j r_j` **only if stage errors are independent**; if errors are positively correlated (the same hard-to-match tools missed at every stage) the compounding is smaller; if later stages cannot see what earlier stages cut, nothing offsets earlier losses.
- **A single stage dominates** when: (i) `a_1` is not much below `a_2` (the first stage is not cheaper per candidate, so it cannot save reading); (ii) `n_0` is small enough that `a_2 n_0` is small relative to `b_2` and fixed turn costs; (iii) the downstream grade or cache effects make final exposure the same size anyway (then `c_vis` is not reduced by stage 1); (iv) per-stage recall loss compounds and `V` is large; (v) each stage that rewrites the tool set breaks the cache (EXT-0008, EXT-0014): extra stages that change the visible set mid-session add cost not in `D`.
- **No restriction dominates** when: the full catalogue fits, prefix caching holds `n L` at the cached price, the model tolerates distractors (EXT-0026), and tasks are short; or when the restriction mechanism's decide cost exceeds the net cost of reading the unneeded tools.
- **A stage is justified** when: `a_1 << a_2`, `n_0` is large, `r_1` is near the single-stage recall at the same `n_1` on the same tasks, and restriction pays in the regime. Whether these hold is not shown by the extracts read here (EXT-0007..0054): no controlled multi-stage vs single-stage comparison on tools with both success and cumulative cost was found there; EXT-0053 compares success only.
- **Evidence on the argument itself (rescoped after CH-0008):** EXT-0045/0046 (read) concern JIT schema loading: a compact tool list first, then agent-driven schema loading. That is the P4/P3 pattern, **not a filtering cascade**; its recall cost ("higher precision and lower recall"; "if the required tool is not selected in the first stage, its full schema is unavailable ... making subsequent recovery or pivoting more difficult") counts against P3/P4 equally. EXT-0046 continues that JIT is "particularly helpful with a large number of tools that could not be otherwise supported": the authors' stated regime for the staged step, and it points toward staging at large `n`. One small-model simulator. My statement "no extract shows a second stage pays" is limited to EXT-0007..0049. The governing records hold weak staged-evidence items I did not weigh and did not re-read (as cited by the challenger: ER-R 0.56 x 0.70 in S4F-PA L15, ITR re-ranker/hybrid ablation in S4F-PA L17/L60, MCP-Zero, DynamicMCPBench App. N rag vs hier); per the challenger none shows a stage paying net of cost. They are open evidence for HYP-0002's falsifier, not excluded. Weighed from the lead's extracts: DynamicMCPBench Appendix N Table 7 (EXT-0053, read): single-attempt pass rates on a 150-task subset, four models, hier (two-stage router: servers then tools) 28.0/32.7/32.7/36.0 vs rag:16 24.0/33.3/31.3/38.0 vs rag:32 28.7/34.7/36.7/40.0, each cell with a 95% interval of roughly +-8 points, so hier is **indistinguishable** from the single-stage retrievers at k=16/32; no token data in the passage; one retriever and one router; the authors state "Retrieval loss and distraction are separable" (curated to rag:8: -20.0 points from reachability; curated to flat: -8.0 points from distraction alone) and that on tasks the retriever never surfaced pass^3 is 0.0%, i.e. recall of the first selection is a hard gate; flat (1,168 schemas, one model) still costs 8 points. This neither supports nor refutes a cascade: a two-stage router matched single-stage retrieval in success; whether it paid in tokens is unmeasured there. EXT-0054 (ITR ablation, a weak source per the lead): a re-ranker is reported +3 pp success at +0 tokens per step; weak, not decisive. Enrich-Retrieve-Rank (0.56 x 0.70) and MCP-Zero remain "cited by the challenger from governing records, unread at the original". Skill Blocks gives an accounting model whose sign depends on load probability and reloads, not on stage count (EXT-0041, read; for skills; transfer to tools assumed [U]). "Decider cost scales with candidates read" is reasoning [T]; no extract measures `a_j` for tool selectors. So the cascade argument is **plausible, not supported** by measurement here.
- **Conclusion for staging [I]:** the stage count is unset. The extracts read (EXT-0007..0054) do not show that a second filtering stage pays net of cost, nor that it does not; EXT-0053 shows a two-stage router indistinguishable in success from single-stage retrieval, and EXT-0046 states the regime (many tools that could not otherwise be supported) in which a staged step is said to help. The record is consistent with P0, P1, P2+recovery, P3, P4g and P2h; it does not discriminate. A multi-stage cascade (P2h or P4g) is a hypothesis to test against the best single-stage comparator of the same driver type, not a presumption and not excluded. REQ-O14-12/13 (a graph of questions and stages) is carried as a requirement-of-unclear-binding (G.3 Q2): this proposal does not decide it.

## E. Recovery and later capability disclosure
Is it necessary? **Conditionally.** If a policy removes any tool irreversibly with recall `< 1`, a miss is a hard failure (DPR-0001 CH-0002 item 2). EXT-0045 [F]: when a tool is not selected "its full schema is unavailable ... JIT therefore provides an additional reduction in static tool context while introducing a stricter tool-selection bottleneck". EXT-0035/0036 [F]: re-retrieval over the evolving context raised pass rate and correct-tool availability after a wrong first pick (initiator mechanism [U], see P7). A policy that never removes a plausibly needed tool (P0, or P1 with a conservative core, or P4 where names remain visible) needs no recovery. The earlier-reading requirement REQ-S2 says a fallback is Required; this proposal treats it as an input and tests its price, not as proof it is worth it.
Questions:
1. **Trigger (signal class).** For a removed tool only S8 (the model asks) or system-side inference from R signals S16-S19 is legitimate (DPR-0001 R3). "This tool turned out relevant" (S13) is not available for an unexposed tool. REQ-O14-15 gives no observable.
2. **Initiator.** Model-initiated (P3, P4): depends on initiation [U in stored corpus: EXT-0037/0047 concern visible tools; EXT-0042: the agent "stops itself at ~5 successful calls out of 30 permitted" per map, showing self-stopping]. System-initiated (P7): needs a trigger with error; evidence is one corpus (FitText) and the re-retrieval is from evolving context. Hybrid possible.
3. **Cost when nothing was missed.** (a) The standing cost: the recovery interface (search tool schema, a stable meta-tool, or a retained removed-list) sits in the prefix every turn; cached after the first turn on supporting providers. (b) The trigger false-positive rate times (extra turn + retrieval cost + appended definitions + the cache/turn re-reading of those). (c) Any extra decision call. These can be zero only if recovery never fires and its interface is free; they are not zero by construction.
4. **Caching and turns.** Append-after-breakpoint preserves the prefix (EXT-0008, EXT-0014 [vendor]); rewriting the tool array does not. Each recovery step spends a turn; the closest vehicle has a 12-turn budget that handicaps discovery-heavy arms (magnitude unknown, S4G L27, read).
5. **Comparability.** Replay scoring can favour recovery that re-surfaces the reference tool and penalise a route the reference did not exercise; the direction is unknown, "for C2 it may inflate recovery's value" (S4G L21 and CAVEATS row 3, read). A recovery comparison on that vehicle needs the bias treated as a threat.
6. **When the trigger is wrong.** False positive: wasted turn/tokens, possible distraction from re-added tools. False negative: same outcome as no recovery plus the standing overhead. Both must be counted.
7. **Initiation as a measured variable.** Initiation of search or recovery is observed in sources but is not a measured variable in any candidate (CAVEATS row 16); the validation plan in DPR-0003 makes it one.
**Correction after CH-0012 and CH-0016 item 1.** (i) There is no evidence here for a purely *system-side* trigger: in FitText the model emits the pseudo-tool request and the system executes retrieval (EXT-0050/0051, see P7), which supports a model-emitted request path. (ii) On MCP-Atlas I wrote "cuts both ways"; that was wrong: EXT-0037/0047 support nothing about discovery initiation, they are silent. What does bear on initiation is vendor design statements: OpenAI "Our models have primarily been trained to search those surfaces" (namespaces/MCP servers, EXT-0010, read) and the vendor rule to keep 3-5 tools non-deferred "so Claude can call them without searching first" (EXT-0009, read), which indicates vendors do not rely on initiation for the most-used tools. These are vendor statements, not measurements. ## Falsifier and assumptions
