# A model-agnostic billing equation of turns and sessions

**Proposal.** Measure every configuration by the bill it causes, written as one sum of components for every provider and model. The token counts come from the provider's usage records per request; the prices come from the provider's dated price page as a **price table**: one price per component, per pricing tier (for example the long-context step) and per mode (standard, batch, fast or priority, regional uplift), plus the tier thresholds, the write classes and any free allowances. With the price table defined that way, a change of model or provider changes the table, not the structure of the sum. The objective is the human's: minimise the bill on average over turns and sessions while keeping accuracy nearly the same (REQ-U21-07).

## 1. Units
- A **request** is one API call. (A provider-side server-tool loop can run several model iterations inside one request, EXT-0158; they are billed within that request.) A **turn** is one user message and every request the agent makes until it answers. A **session** is everything between a start and an end, including requests that belong to no turn (a cache prewarm, a memory summary written at the end, a keep-alive call). A **return** is a session that resumes after a gap (REQ-U21-10).
- Token counts are taken from the provider's usage fields per request, never estimated locally. They depend on the model's tokenizer (a newer Anthropic tokenizer produces about 30% more tokens for the same text, A-price L54 via FND-0039), so counts are compared only within a model. The earlier evaluation vehicle reads only prompt and completion tokens and has no cache discount (FND-0020: EXT-0194, EXT-0198); cache write and read counts, reasoning tokens and tool charges are new measurements for this work.

## 2. Cost of one request
For request r, with the price table of its model, tier and mode:

  C_r = π_F·F_r + π_W5·W5_r + π_W1·W1_r + π_R·R_r + π_O·O_r + T_r

| Symbol | Meaning | What the stored documentation says (FND-0039 unless stated) |
|---|---|---|
| F_r | fresh (uncached) input tokens: system prompt, the provider's tool-use system prompt (documented for Anthropic only), visible tool definitions, messages, earlier tool calls and tool results re-sent | input on every request unless cached or deferred (EXT-0123) |
| W5_r, W1_r | input tokens written to the cache with a 5-minute and a 1-hour lifetime | Anthropic: π_W5 = 1.25·π_F, π_W1 = 2·π_F (EXT-0085, EXT-0152); one request can carry both classes, since server-tool results get an automatic 5-minute write even when the caller's markers use 1 hour (EXT-0158 L94-96). OpenAI: a 1.25x write on GPT-5.6 and later, no write fee on earlier models (O-price via FND-0039). Gemini: no write line in the stored price page |
| R_r | input tokens read from the cache | π_R is model-specific: Anthropic 0.1, 0.05 or 0.025 of π_F (EXT-0085, EXT-0086); OpenAI 0.1, 0.05 on GPT-6.1 Sol, 0.25 or 0.5 on older models (O-price L54, L57 via FND-0039) |
| O_r | billed output tokens, whatever the usage field includes | output price / input price is 5 for the stored Anthropic and OpenAI standard rows and 6 for Gemini 3.1 Pro; 3.75 and 4.5 on the long-context rows. Gemini states that its output price includes thinking tokens; for Anthropic and OpenAI the stored pages do not say [U]. Reasoning tokens are reported separately (H_r) where the usage record shows them, but they are priced inside O_r only, never twice |
| T_r | per-call server-tool charges: web search per 1,000, file-search calls | FND-0039 Table 2; tool search itself is not metered separately at Anthropic (EXT-0131) |

Each π is read from the price table for the request's tier and mode. The modifiers are not one scalar: on the stored pages a batch request halves input and output but leaves Gemini's cache price unchanged, and the long-context step multiplies input and cache prices by 2 but output by 1.5 on OpenAI and Gemini (price-gemini L1118-1129, price-openai L35 via RV-0020); Anthropic's long-context tier is decided by F + W + R together (A-price L222). The table must carry these per component.

## 3. Cost of a session
  B_s = Σ_{r ∈ s} C_r + S_s + X_s

- The first sum runs over **every request of the session**, in a turn or not (prewarm, memory writing, keep-alive), so nothing the policy causes is left out (REQ-O02-02).
- S_s, **storage over time**: where a provider bills cached tokens per hour (Gemini explicit caches, EXT-0089) and file storage per GB-day (OpenAI file search). No hourly prompt-cache storage line was found for Anthropic or OpenAI.
- X_s, **time-based charges**: code-execution container time (Anthropic per hour with a 5-minute minimum; OpenAI per container session) and managed-agent session hours. Container time is counted here only, not in T_r.
- **Free allowances** (Gemini 5,000 searches, Anthropic 1,550 container hours a month) are not applied when configurations are compared, because they are account-level and not marginal; the comparison uses list prices and reports the allowances separately.
- **Gap cost (a consequence inside the sum, not an extra term).** A cached prefix stays live only while requests arrive within its lifetime (5 minutes or 1 hour at Anthropic, 30 minutes on newer OpenAI models). After a longer gap the next request pays for the prefix of P tokens again: p·P·(c_cold − ρ) more than a warm read, with c_cold = the write multiplier where a write surcharge exists (Anthropic, OpenAI 5.6+) and c_cold = 1 where the prefix is billed as fresh input instead (older OpenAI models). For Gemini the stored pages state no implicit-cache lifetime and no explicit-cache lifetime or write fee; for its explicit caches the gap acts through storage S_s. A gap can fall between any two requests, inside a turn too; it is already counted in W and R, so it must not be added again. The experiment records the wall-clock time between requests. Where caches are shared across sessions (OpenAI within an organisation; Anthropic not stated in the passages read), sessions are not independent and the order of runs matters.

## 4. The objective and what is reported
- **The human's words:** minimise the bill "on average", accuracy "nearly the same", no margin, budget or threshold (REQ-U21-07); the supervisor speaks of the cost per turn (REQ-O21-07).
- **Lead's operationalisation [I], for the human to accept or change:** the primary figure is the mean bill per turn, computed as total bill over total turns across all sessions of a task set (a ratio of sums). Its known weakness: one long run weighs more than many short returning-user sessions. The alternative is the mean of per-session bills per turn, which weighs each session equally. Both are reported; which is primary is the human's choice.
- **Comparators:** each configuration is compared with the all-tools baseline the supervisor asked for (REQ-O02-01) and with the other baselines, including Executor (REQ-O02-06); "decrease" and "nearly the same" are read against them.
- **Reported beside the bill:** accuracy (task success); the components (F, W5, W1, R, O, H, T, S, X), so the cause of a difference is visible; requests per turn; response time (REQ-O21-07).
- **Uncertainty:** in the proof-of-concept loop a few runs per setting suffice (REQ-U21-06, "not rigirous tests"); repeated runs showing statistical variance are required for the final end-to-end study (the supervisor's condition for publishable numbers, REQ-O21-09).
- **Choosing among configurations whose bill and accuracy are close** is argued and reported rather than settled by a number set in advance [I, lead's reading of the no-threshold decision].

## 5. Where each part of the policy acts on the sum [I]
- Tool exposure changes F, and W and R through the cached prefix; changing the visible tool definitions can invalidate the cache unless the provider's documented deferral or append mechanism is used (EXT-0158, EXT-0009).
- Discovery adds requests per turn and output tokens, and appended results add later input.
- Memory replaces re-sent history with a short summary, lowering F on later turns and the cold-prefix cost on returns; writing and reading memory can add requests (counted in the session sum).
- Cache layout (what sits in the stable prefix, which lifetime) moves tokens among F, W5, W1 and R; at Anthropic a 1-hour lifetime costs more per write and avoids rewrites after gaps of 5 to 60 minutes; OpenAI GPT-5.6 and later offer 30 minutes only.
- Keeping tool results out of the context (files, programmatic calling) lowers F on later requests but can add container time (X) and fixed overhead; Anthropic's own page reports one benchmark where programmatic calling cost about 8% more (EXT-0183 L36, L43-45, L57-68), so the net effect depends on the workload.

## 6. Evidence and what it does not show
Uses the stored price and caching pages of Anthropic, OpenAI and Gemini (2026-10-11, rechecked 2026-10-19) as tabulated in FND-0039 (file `findings/SUM-0041-billing-components.md`). Does not show: whether reasoning tokens are billed as output at Anthropic and OpenAI; whether OpenAI's usage record separates cache writes, reads and fresh input; Gemini's explicit-cache lifetime and write fee and implicit-cache lifetime; Bedrock multipliers; whether Anthropic shares caches across sessions; any price level after its stated date.

**Alternatives considered.** (a) Tokens only, the bill recorded separately (the 19 October working objective, replaced by the human's decision); (b) the bill of one named model (rejected by the human); (c) one multiplier table for all providers (simpler, but wrong for batch and long-context pricing, RV-0020 D-3).

**Falsifier and assumptions.** The equation is wrong for a provider if its usage records hold a billed quantity with no term here, if a quantity is counted in two terms (for example reasoning tokens inside and beside output), or if the bill computed from usage and the price table differs from the provider's invoice for the same requests. Assumed: each provider's usage record exposes fresh input, cache write and cache read separately (stated for Anthropic, EXT-0123; not shown for OpenAI in the stored pages). A first billing probe (ledger C-X07) checks this once per provider used.

**Objections received.** RV-0020 (D-1 to D-15); every correction is applied in this revision.

**Not claimed.** No price level is fixed; no provider or model is chosen; no saving is claimed for any policy.
