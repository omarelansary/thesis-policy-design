How this analysis was checked

An independent analyser agent wrote it from the committed files only. Eight other agents then checked it against the files in four rounds. They found 28, 23, 10 and 12 problems. I checked each one against the files myself before applying it. Most were claims that went further than the evidence; a few were wrong numbers or wrong attributions.

The corrections of the last round were not checked a fifth time, because I capped the process at four rounds. Treat the wording of those fixes with a little more care than the rest.

Four committed files were corrected on the way: ops/STATE.md (a P2 sentence that overstated accuracy), P4-REPLAY-A.md (a suggestion labelled as observed), RESULTS-P1.md (a prompt-size comparison that was not matched) and RESULTS-P3-RUN3.md (a wrong statement about the cache). Section "Doubts and corrections" lists them.

Markers used below: O observed in a file, D derived by arithmetic from numbers in a file, I interpretation, U unknown or not shown.

Summary

P3

Do models search for a hidden tool, and what stops a search for a missing one?

Three open-weight models searched without being told to, in 20 of 20 sessions each, and called the target in 19 to 20.

For a missing tool, no rule stopped the searching without also losing the other, doable task. The best combination (the stop rule plus one sentence in the instructions, now V5-R17) kept the doable task at 40, 39 and 37 of 40, and cut requests by 32 to 48%.

Small samples (20 tasks); tasks written by the lead; tools return a stub "Done"; the rule was built on the same 20 tasks it was tested on.

P2 and P2b

Does offering only a subset of the declared tools keep accuracy?

With the server enforcing the subset (OpenAI), the cache was kept and no call went outside it (0 of 120 task-runs). No accuracy difference was detectable, but the two models moved in opposite directions (+11.7 and −5.0 points).

An instruction alone worked for two of three models. Declaring only the subset was 20% and 10% cheaper on one stream.

Oracle subsets, 128 tools, 30 tasks from one app family; intervals allow losses up to 17 points. The university route itself was not tested.

P1

Does seeding tools from memory help returning users?

A role memory (the 6 tools other users need most) saved about 1.1 searches per session. The bill effect is −16%, −5% or +16% depending on one or two sessions, and every interval includes zero.

Per-user memory was not run live; on the data it loses, except one rule that seeds almost nothing.

One model; 33 sessions of 16 users; the session set depends on cost caps; the role memory looks ahead in time.

P4

Does clearing old tool results lower the bill?

On short tasks, the vendor's documented setting roughly doubled the bill (×2.06; ×2.66 where clearing fired) and raised calls (×1.37). Accuracy difference not detected.

The hypothesis is about long runs, which were not tested, so it is neither confirmed nor refuted.

One model; 20 tasks in 7 scenarios; I ran it although its precondition was not met.

The overall picture

  • What the tests support is at the level of mechanism: the cache survives enforced offering, and models search without instruction.
  • None of the four demonstrates a bill saving from a V5 add-on against run-to-run variation. Some point estimates are lower (removing unoffered definitions ×0.80 and ×0.90; one instruction result ×0.87 against ×1.37 on another model; P2b's instruction ×0.80), but they are single results and several are smaller than the gap between two identical runs. Enforced offering (×1.02, ×1.15) and clearing (×2.06) point up. P1's sign is unresolved. Role memory saves searches.
  • The large saving in these data is another one: deferral against showing everything (P3 run 1 side observation: ×4.6 to ×30 per session; P5: deferral costs about 14 to 15% of showing everything at 100 tools).
  • Every test is one benchmark (AppWorld), mostly short tasks, and one to three models. P3, P1 and P4 ran only on OpenRouter, not on the university API.

How to read this

CacheA repeated, identical start of the prompt is billed at a lower "cached" price.
DeferralTool definitions are not shown; the model gets a search tool and finds definitions on demand.
SeedingAt session start, offer the tools that memory says were needed before.
Masking (clearing)Replace old tool results in the history with a placeholder.
Oracle subsetThe tools the correct solution needs plus complete_task. A best case, correct by construction.
Enforced or instructedEnforced: the server refuses calls outside the subset (allowed_tools). Instructed: one sentence names the subset.
Break-evenThe catalogue size above which deferral costs less than showing everything.
BackstopA request cap per session, only a safety net in P3 (6 in run 1, 12 later).
×0.80 and similarA ratio against the reference arm: ×0.80 is 20% cheaper, ×2.06 is more than double.

The bill is the cost computed from the provider's usage records and a price table (billing equation DPR-0006). The goal is to minimise it on average over turns and sessions with accuracy nearly the same (ops/STATE.md B; requirements/REGISTER.md H). There is no margin or threshold. Reporting is estimation only: paired differences with intervals, no pass or fail.

P3: search for a hidden tool, and the stop for a missing one

Idea. If most tools are deferred, the model must decide to search for the one it needs, without being told to. You added a second question (INT-T-031): when the tool does not exist, what makes the model stop? The stop had to be deterministic, not a count of turns. (HYP-0019, V5-R17.)

Setup O. Four situations: all 468 tools shown (E); the target deferred (D); the target absent (A); a similar wrong tool visible (W). Runs 1 to 3 used single-need tasks. Runs 4 to 6 used 20 two-need tasks: both tools present (P), or one missing and named first (AF) or second (AS). A "substitute" is a state-changing call of another tool in the missing tool's app; a "false claim" is saying the missing action was done. Total spend $9.953 D (the run 1 and run 4 figures include their smoke tests).

How strong is this?

  • Samples are small (20 tasks per cell, 40 sessions per two-need cell); only large effects show. Two identical no-rule runs disagree on up to 5 of 20 tasks. O
  • O Only the forced reply in run 4 reached significance (p at most 0.016). No cell of DRY did. The run file calls both DRY effects "very probably real" (fewer substitutes, a gain; fewer doable tasks done, a cost) because DRY lies below the whole no-rule range on both.
  • I The comparison is across runs, with no-rule runs made earlier the same day. DRY was designed from run 4's logs on the same 20 tasks that runs 5 and 6 then used, and the sentence was added after seeing run 5's failure. So these results are in-sample.
  • I "At or above the no-rule range" holds for MiniMax (40 equals the top of 37 to 40) and GLM (37, above 30 to 33). DeepSeek's 39 lies inside 36 to 40.
  • O Replies were classed by one reader (me), with a keyword pre-filter. The tools return a stub "Done"; the research note reads that as the high-dishonesty condition for false claims. The nine primary sources behind the research note were stored and every quoted phrase was found in them; the note itself remains a summary.
  • O Tasks give every value in the prompt, and the search put the target in the top 3 for 17 of 20 whole-prompt queries; the models' own queries found it every time. Search quality on a hard ranker was not tested.

What P3 does not show

  • U The effect of the sentence alone: there is no instruction-only arm (moved to the end-to-end study).
  • U Behaviour on real AppWorld tasks with real tool results; other models (MiniMax kept 7 substitutes and 3 false claims of 40 even with the rule).
  • U Whether DRY plus the sentence works if the search tool stays and answers "no match" instead of being withdrawn (V5-R17 open item b). A note alone was weak in run 3 and showed no measurable effect in run 4.
  • I Withdrawing the search tool changes the tools array. V5-R02 forbids changing it within a session; V5-R17 item (b) says that routes with an offering mechanism (Anthropic tool removal, OpenAI allowed_tools) need no array change, and routes without one do. The cache cost of that change is real on the university route: the P0 probe (10-p0-university-api-reading.md section 7) found that on GLM-5.3 one tool added at the end of the list left 1,728 of 5,116 tokens cached, so 65% was rewritten. P1's own traces agree: calls right after the array changed had a cached share of 0.17 to 0.20, against 0.77 to 0.86 otherwise. The run 3 file had said the cache "stays clean"; that was wrong and is corrected.

P2 and P2b: offering a subset while all definitions stay declared

HYP-0018 claims no bill saving from this, since the definitions are still read at the cache price; the point is that it costs no accuracy.

What P2 and P2b do not show

  • Realistic subsets that miss a needed tool; offering that changes within a session (the memory case, where the problem would appear).

P1: seeding tools from memory for returning users

Idea. For a returning user, offer at session start the tools that memory says were needed before. If enough seeded tools are used, they replace searches and save money; if too few, they only add tokens to carry. calc/memory_seed.py gives the break-even share h* of seeds that must be used. (HYP-0017.)

Desk check first O (no model run; reproduced by the analyser and by a verifier). AppWorld has 34 users with tasks in 2 to 5 scenarios; ordered by date that gives 64 "returning sessions" (an ordering I constructed, not a recorded history).

  • Seeding "everything used before": mean precision 0.14, zero in 36 of 64 sessions.
  • All per-user rules lose on the bill, except "used in 2 or more earlier sessions", which seeds only 0.3 tools on average (net +88 at 8 requests).
  • "pop6", a role memory (the 6 tools other users need most, outside the current scenario): precision 0.24 and net +956 token-equivalents at 8 requests, about 2% of a roughly 50,000-token session. At one match per search it is −256; at 30 requests it is negative.

Live run. No memory ("none") against pop6, GLM-5.3, client-side search returning the top 3, 2 repeats, $11.394 in total. I dropped the best-case "oracle" arm before any run because the projection exceeded my $12 limit. Three of the four runs stopped at their cost caps, so the common session set became 33 sessions of 16 users.

How strong is this?

  • O One model and provider; 33 sessions (half the planned 64); the user-level interval is rough.
  • I Sessions averaged about 11 to 12 requests. At that length, with 3 matches per search, h* is 0.19 to 0.21 at the project's cache ratios (0.22 at GLM-5.3's list ratio). The measured 0.27 counts seeds called, 7 per run of them not needed; called and needed is 0.23 to 0.24. Both are above h* but only 0.01 to 0.02 above the 0.22 case, so by the arithmetic role memory should pay a little (about +580 to +670 token-equivalents, about 1% of a session). At 30 requests h* is 0.30 at the base ratio, above the measured 0.27, so the sign depends on session length.
  • I An expected saving of about 1% is far smaller than the interval (about ±34% of a mean of $0.071 per session). P1 could not have detected a 2% effect either way.
  • O Selection effects. The session set depends on pop6's own spending: it shrank from 44 to 35 to 33 sessions when pop6's runs reached their caps (my rule, applied after pop6 r1's cost was seen), and sessions that cost pop6 more were cut. I That may bias the main set in pop6's favour; the sensitivity column is the attempt to show the other side.
  • O pop6 looks ahead. It counts other users' later-dated sessions, which a deployed system would not have. I It also does not depend on the user, so it is closer to a larger core chosen by usage (S1) than to personal memory. The memory is built from the correct answers, not from what the model did earlier.
  • O Route. Discovered tools were appended to the tools array, which V5-R02 allows. Cached share was 0.63 to 0.74 (0.64 to 0.69 without memory), against about 0.9 in P2 and 0.82 to 0.94 for the same model without discoveries. The prefix size also differs. I Appended discoveries ended the cached prefix on this route, so V5-R02's "appended discoveries" is not cache-safe here. The effect falls on both arms; its effect on the trade between seeds and searches is unknown.
  • O No stop rule was used in P1; the harness assumes every task is doable.

P4: clearing old tool results

Idea. Old tool results sit in the history and are re-read on every request. Replace them with a placeholder and the prompt is shorter. But a change in the middle of the history makes the cached part after it cost more to rewrite. HYP-0021's claim is for long single runs.

Setup O.

  • Condition check. In P2's logs, old tool results were 13.1% of billed input; removing them for free would save at most 6.3% and 6.9% of the input bill, or 2.4% and 4.3% of the total. 05 says P4 runs "only if P0-P5 show deployments with large tool results", so its condition is not met by our results. Your message asked for P4 "if possible"; I read that as covering a run despite the check, and you have not ruled on the condition.
  • Step A, a replay on the P2 and P2b logs (no model call, behaviour held fixed). The vendor's defaults (trigger at 100,000 tokens) never fire. The documented example (30,000 / keep 3 / at least 5,000) raised the bill by +1.2% (gpt-5-mini), +1.0% (gpt-5.4-mini) and +7.5% (GLM-5.3).
  • Step B, live. The client applied the vendor example on GLM-5.3: 20 tasks in 7 scenarios, 2 repeats, $5.385. The keep-everything arm is P2b's two all runs on the same tasks, made a day earlier with the harness version before masking was added.

  • O These are short tasks (the keep arm's median is about 7 calls), not the longest available. The 20 tasks are P2b's first 20 in fixed order, because repeat 1 hit its $2.50 cap; I fixed the rule for repeat 2 after seeing the first 7 tasks' costs and before any accuracy. I So the number of tasks was set by the mask arm's cap.
  • O The "never fired" check is weak: the groups are defined afterwards by the mask arm, and the nine are all short (at most 12 calls). It is consistent with no drift between days for those tasks.
  • I The extra calls where clearing fired suggest the model called tools again after its results were cleared. That is suggested, not shown: repeat 1's cached share equals the keep arm's, so cache rewrites are not shown as the cause there. Step A held behaviour fixed and predicted +1% to +7.5%; the live result is ×2.06. Changed behaviour is the suggested reason for the gap; it is not decomposed.

Correction already made. My first note said "HYP-0021 falsifier met on this setting" (it is in a commit subject). The record now says it is neither met nor refuted, because the falsifier's domain is long single runs.

What P4 does not show

  • Long tasks, where clearing is meant to pay; other models or rule settings; providers with a cache-write premium; accuracy unchanged (the interval spans −17.5 to +12.5 points).

Across the four

What fits together

  • I Enforced offering at a fixed prefix does not by itself lower the bill (×1.02 to ×1.15). Uninstructed search is what lets deferral lower it (P3 run 1 side observation; P5). Seeds: bill effect not resolved. Clearing: cost more.
  • I For a subset fixed per session on a single stream, declaring only it looks cheaper (the P2 file says so); sharing across users is not priced.
  • I P5 is where the largest bill effect was computed (token counts from the university-API run, priced by a price table, stub tools). Break-even lies between 10 and 30 tools, and deferral costs about 14 to 15% of showing everything at 100 tools on a cold start (20% warm). I rechecked these figures against the P5 file.

What conflicts or depends on the model
