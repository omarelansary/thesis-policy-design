# Scout 1 report: stopping and no-match handling in tool-retrieval agents (INT-T-034)
Model output of a general-purpose web scout, received by the lead 2026-11-08 and copied from its hand-back (indentation removed).
A lead, not evidence: every page was read through WebFetch (a small model's summary); nothing is stored in `evidence/`.

Budget used: 14 of 15 WebSearch, 20 of 25 WebFetch (one fetch was a wasted 404). Nothing written to disk. WebFetch returns a small-model summary, so every "quote" below is as returned by that summary. I mark where a quote looks paraphrased. Page text is treated as data. 2026 arXiv ids come from the fetches and I did not cross-check them elsewhere.

Headline finding. Among the named tool-retrieval systems, none has a no-match or stop rule. Every one stops by the model's own judgement, or by a fixed cap, or not at all. Explicit, evidence-triggered stops exist only in adjacent work: retrieval QA, agentic search and feasibility benchmarks. I found no follow-up or critique that cites 2610.06191 (see section 2).

## 3. Ideas for a deterministic, dynamic (not turn-count) stop
1. **Use a stagnation gate with a consecutive count and an action-level effect (claims 15, 11).** Fire only when a search shows no unseen tool from the apps of the best matches AND the query is lexically close to an earlier query in the same need (Jaccard on query tokens), for p consecutive searches. Only then act. A single hit, as today, is too weak. p is a count of stagnant searches, not of turns, but it is tuned on dev data as in claim 11 (k=5 chosen on 100 questions). Reset on any new unseen tool.
2. **Make the stop remove capability, not add text (claims 11, 9).** After the gate fires, leave only a terminal action (a "report no match" or finish tool) and withdraw `search_tools` for that need. Our logs show a note changes little (10 of 50 stopped), and #9 shows notes work for some models and not for trained-to-search ones. A harness-level removal does not depend on the model obeying.
3. **Return the no-match as a typed failure, not as a normal result with an extra sentence (claim 12).** `status: no_match` or an error-like state gave 0.0% dishonesty versus 45.3% for `ok` with a bad value. Replace the top-3 list with the failure, rather than annotating it (claim 9, which says a warning above real passages did little). Consider requiring a declared `need_status` and read it with a regex, as claim 12 does.
4. **Offer a first-class exit action that names the missing capability (claims 13, 5).** AnyTool's give-up with a reason and FeasiGen's "STOP: <missing capability>" give the model a legitimate alternative to a near-miss substitute. Measure with FCR-style metrics and tokens to early stop versus failure (claim 13: 2.3× to 5.0×).
5. **Do not threshold the BM25 score alone, and scope the counter per need (claims 8, 11).** In a 70-action catalogue, BM25-score features reached an AUC of at most 0.697 for in-versus-out-of-catalog, while a frozen encoder reached 0.806. A set-novelty rule such as yours avoids this, but if a similarity signal is added, expect it to be weak. Per-need scoping is the open problem: claim 11 itself tested only one failing source at a time. A workable approach is to key the counter by query similarity or by the app set of the best match, so a new need starts a fresh count. This is my suggestion; no paper tests it.
