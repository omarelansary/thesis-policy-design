## 3. Candidate stop rules for our setting
Our setting: BM25 `search_tools`, top 3, 463 tools, rewording yields unseen but irrelevant tools, 12-request backstop, several needs per task. No parameter below is calibrated. Each needs a value chosen and tested by the human.

**Rule A. Tool-side null result per need (enforcement).** When any stop trigger (rules B to D) fires for a need, `search_tools` returns an empty or NULL_RESULT observation for that need's queries, with no passages and no tool list. If a further search is still attempted, return the same null again. If the model keeps going, withdraw `search_tools` from the offered tools for the rest of that need. Ties to claims 12, 13, 21 and the known arXiv 2610.06191. Why: our note beside results was ignored, and the evidence says that is expected (the agent "anchors on visible passages", nudges "can be ignored"). Failure mode: it removes access even when a differently phrased query would find the tool (false stop). Search-R1 reportedly searched more after a refusal (claim 12, secondary source), so some models may retry with other tools, or answer anyway with a false success claim. A null result does not itself prevent a substitute action.

**Rule B. Relevance-aware stagnation gate (adapts claim 7).** For each search compute (1) J = Jaccard of stemmed, stopword-free query tokens against the closest previous query of the same need; (2) a new-and-relevant count: the number of tools shown that are not yet seen AND whose BM25 score is at least a fraction alpha of the best score seen so far for that need, or whose query-term coverage is at least that of the best tool seen so far. Stagnated if J >= tau_J AND the new-and-relevant count = 0. Stop the need after p consecutive stagnated searches. The reference setting in claim 7 had 0.6, 0.3 and 2 as the best label (inferred), but that was a different system. Why: raw "new tool shown" never reaches zero in our logs, so the novelty signal must be filtered by relevance. That is what claim 8 says about "new relevant recall". Failure mode: BM25 scores are not comparable across queries of different length; synonym rewordings with low token overlap pass the J test; alpha and the coverage rule need calibration on logged runs (human choice).

**Rule C. Frustration counter on unused results, with reset on consumption (claims 5, 16).** Define a search as "consumed" if the next action calls a tool shown in that search's results. Maintain, per need, the number of consecutive searches that were not consumed. Stop that need when the count reaches N. Reset to 0 whenever the model calls a shown tool or begins a new need. Why: it needs no relevance judgement, only the model's own behaviour as the relevance signal, and the reset gives a per-need structure (claim 16: "reset on progress marker"). Maxwell's finding supports a consecutive-non-relevant counter over a total count (claim 5, via abstract). Failure mode: a model may query two or three times before trying a tool, which makes N small enough to hurt legitimate searches; defining a "need" boundary is still open; a call to a wrong but shown tool resets the counter and gives an unproductive loop.

**Rule D. Giving-up time on the running best match (claims 6, 1).** For each need track best_t, the highest query-term coverage (fraction of the query's content tokens matched in the top tool's name and description) over all searches so far. A search is a "gain" if it raises best_t by at least epsilon; otherwise it is a miss. Stop after p consecutive misses (giving-up time, claim 6), or when the last gain is older than p searches. Why: every reword that surfaces an unrelated tool does not raise the best match, so the gain curve flattens exactly as in the knee method (claim 1) but needs no relevance labels. It is a rate-of-gain rule, not a count of turns. Failure mode: coverage rewards lexical overlap, not suitability; a plausible but wrong tool can set a high best_t early and mask later better tools; epsilon and p are free parameters; with only 12 searches the "average rate" of the MVT form is not estimable, so only the giving-up-time form is usable.

**Rule E. Near-duplicate and cycle fingerprint over search queries and result sets (claims 13, 14, 15, 16).** Normalise the query (lowercase, stem, drop stopwords, sort tokens); also fingerprint the set of top-3 tool ids. Fire when (a) a normalised query repeats for the third time, or (b) the same top-3 set returns twice in a row, or (c) two top-3 sets alternate (A-B-A-B). Optionally add an embedding similarity above a threshold to catch paraphrases (claim 15) with a local embedder. Failure mode: this is the weakest fit for our setting. Rewordings change both the query and the top-3 set, which is exactly what we observed, so exact-match detectors (claims 13, 14) will mostly not fire. The embedding variant needs a threshold chosen by the human and is a model dependency. Use it as a cheap complement to B to D, not as the main rule.

Notes on combination and what I do not recommend:
- Chao or capture-recapture (claims 3 and 4) is not recommended as a primary rule. Counts are too small and the independence assumption fails for rewordings of one need. It could be reported as a diagnostic.
- Learned or LLM-judged stops (claims 8, 10, 11, 21) break the deterministic requirement.
- A hard backstop of 12 requests stays as the last guard, as in the budget method of claim 2 (a bounded effort plus a slope test).
- The reset event and the "need" definition are shared across rules B to D. No source gave a deterministic definition, so that is the main unresolved design choice for the human.
