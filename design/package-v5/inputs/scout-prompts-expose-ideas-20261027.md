## TASK 1: tiered or compact tool definitions and lazy loading (V5-R10, EX-2)
The idea: tools found by search are appended to the context as short entries first (name plus one line, then typed arguments, then enums and defaults, then nesting), with the full schema only on request; fixed, comparable level definitions. Find: research on compressing, summarising or truncating tool descriptions and schemas and its effect on tool-call accuracy and tokens (for example work on tool-description quality, schema pruning, "progressive disclosure", skill libraries with resident summaries); vendor implementations (Anthropic's tool search tool and deferred loading, OpenAI's tool search and defer_loading, Google); open-source MCP gateways, proxies and dynamic-toolset projects (for example Executor, MCP-Zero, RAG-MCP, ScaleMCP, Speakeasy dynamic toolsets, mcp-gateway projects, LangGraph bigtool, litellm). For each: what tiers it uses, what it measured, whether the cache is mentioned, licence, and what a client-side wrapper over an OpenAI-compatible API (the university API serves open-weight models through LiteLLM and rejects `allowed_tools`) could reuse.

## TASK 2: maintaining the tool set within a session; metrics; oracle ablation (V5-R11, BR-1, BR-8, EX-9)
The ideas: (a) keep discovered tools for the session and optionally evict unused ones when the rewrite cost is worth it; (b) log the churn of the visible tool set (1 minus the overlap of this turn's and the last turn's set) and the recall of the offered set; (c) an oracle-registry ablation that guarantees the gold tool is present, to separate retrieval failures from downstream failures, and a decomposition of failures into selection, compression, routing and validation. Find: research on adding, retaining and evicting tools or tool descriptions during multi-turn agent sessions (for example MemTool arXiv 2507.21428, ToolMem, context-editing and tool-result clearing, "dynamic tool loading"); measured effects of changing the tool list on prefix-cache hits (vendor documentation and serving-system papers); papers that report oracle retrieval, gold-tool or oracle-retriever ablations in tool-use benchmarks (ToolBench and StableToolBench, ToolRet, BFCL, MCP-Bench, MCPVerse, LiveMCPBench and newer ones) and how they decompose failures; any standard metric names for tool-set churn, tool recall or tool-retrieval quality in agents. Report whether eviction is shown to help or hurt accuracy and cost, and what the metrics' published definitions are.

## TASK 3: validation gate, no-match rule and enriched searchable text (EX-5, BR-6)
The ideas: (a) validate a drafted tool call against the tool's schema offline and expand to the full schema only when validation fails; (b) abstain or answer "no suitable tool" when no candidate passes a relevance threshold; (c) enrich each tool's **searchable** text (positive and negative intents, related tools, input and output concepts, risk level) offline while showing the model only the compact text. Find: research and implementations of schema validation, constrained decoding and repair loops for function calling (accuracy and cost effects); benchmarks and methods for irrelevance or abstention in tool use (BFCL irrelevance and relevance detection, hallucinated tool names, closed-world gates); research on LLM-generated tool documentation or query-expanded tool indexes that improves tool retrieval (for example Toolshed, EasyTool, Re-Invoke, COLT, Tool2Vec, ToolRet, ToolGen, doc2query-style expansion) with the gains and the cost of generating them; open-source libraries that provide any of these (Instructor, Outlines, jsonschema validators, Pydantic AI, LlamaIndex or LangChain tool retrievers, semantic-router) with licence and whether usable client-side.

## TASK 4: retrieval and reranking, and the reuse side (EX-4, and reuse for D)
The ideas: (a) the discovery step D ranks tools with hybrid sparse and dense retrieval plus a reranker, indexing schema terms (tool and parameter names, argument types) while showing compact text; (b) D is built client-side because the university API (LiteLLM, OpenAI-style, open-weight models, serving an embedding model and a reranker) cannot restrict tools server-side. Find: papers and benchmarks on tool retrieval (ToolRet arXiv 2503.01763, COLT, ToolBench retrievers, RAG-MCP, MCP-Zero, ScaleMCP, Tool2Vec and newer 2026 work) with reported recall or nDCG for sparse, dense, hybrid and reranked systems and whether reranking helps for tools; open-source tool-registry, tool-router and MCP-search projects that already implement client-side discovery with an OpenAI-compatible endpoint (for example LangGraph bigtool, LlamaIndex ObjectIndex, MCP gateways, Executor, semantic-router, Toolhive-like projects), with licence, maintenance state if shown, language and what is reusable. Also look for any project or paper that reports the **billing or token cost** of client-side discovery (an extra request per search, appended definitions, cache effects), because that is what the thesis's bill equation needs.
