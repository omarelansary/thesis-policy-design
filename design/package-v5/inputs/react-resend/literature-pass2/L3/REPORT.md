# L3: Tool selection, retrieval and exposure at scale (2026-11-09)

Grades: [E] peer-reviewed/replicated with released code/data; [M] measured by authors; [V] vendor claim or vendor-internal measurement; [T] theory/proposal; [U] unverified. Read depth is in sources.tsv (S-ids). Token counts are never treated as bill unless cache pricing was accounted for; none of the sources below measured a cache-aware bill of tool-set reduction.

## Headline
No source found changes the direction of the existing work. Several sources change what should be claimed and how it should be evaluated: (a) independent evidence that fewer exposed tools helps is weaker and more conditional than vendor material implies; (b) top-k filtering can lower accuracy below the all-tools arm; (c) the one genuinely new structural fact is that two vendors now document ways to change the offered tool set without busting the cache, which weakens "append-only" as the only safe design. Nobody found measures the BILL of tool-set reduction with caching (see gaps).

## 1. Does fewer exposed tools improve accuracy? (independent evidence)
- Qualitative direction supported, magnitude and threshold not established. Vendor docs assert degradation "once you exceed 30-50 tools" (S2 [V]); Anthropic reports Opus 4 49->74% and Opus 4.5 79.5->88.1% with tool search on unnamed internal MCP evals (S1 [V], partly read). No independent replication was found.
- RAG-MCP: 43.1% vs 13.6% selection accuracy, retrieval vs all tools (S6 [M], abstract only). Own stress test; tokens only.
- Enrich-Retrieve-Rank (S17 [M], abstract): in-context routing Match@1 falls 0.85 -> 0.12 as the registry grows 10 -> 7,278; retrieve-then-rank 0.81 -> 0.39; crossover near N~500 in one model sweep. Registry-routing task, not ReAct execution; shows the crossover depends on catalogue size and model, so a "~10-30 tools" break-even from your measurements is plausible for cost but is not a general accuracy threshold.
- Small-model illustrations (46 tools fail, 19 succeed; S20 [M], snippet only) are single cases.
- AppWorld-relevant gap: no source tests a 400+-tool function-calling ReAct agent with an all-tools vs subset arm on a stateful benchmark and reports pass rate and cost together.

## 2. Contradictory or negative evidence
1. Top-k filtering can hurt. In ToolChoiceConfusion (S10 [M], partly read; synthetic, 100 mock tools, 4 models) all tools = 0.83 success / 24.6k tokens per task; keyword top-5 = 0.61 / 4.4k with more wrong-tool calls (2.36 vs 1.25); a state-aware minimal filter = 0.99 / 2.4k. Caveat: synthetic, mocked outputs, tokens not bill. Implication: the quality of the subset predictor, not the subset size, drives accuracy; a cheap prefilter can lose accuracy while winning on tokens.
2. Retrieval recall is the main failure mode. LiveMCPBench (S8 [M], tables read): retrieval errors are 50% of failures (Retrieve Error 50.0%, Query 13.3%, Tool 18.3%, Other 18.3%); retrieved k=1 gives 64.2% vs k=5 78.95% (p=0.02); k=10 adds nothing. ToolRet (S7 [E], abstract): strong IR models reach only nDCG@10 33.8 on a 43k-tool corpus and poor retrieval lowers pass rate. Implication for a <=20 predicted subset: the miss rate of the predictor sets the ceiling, and the fallback path (search / stop rule) is where accuracy is recovered or lost.
3. Fixed K can beat adaptive K at the aggregate level (S9 [M], partly read): on ToolBench fixed K=5 coverage 64.7% vs adaptive 61.9%; with a weak scorer the adaptive agent widened to K~80. Better downstream choice at small K (93.1% vs 87.1%) did not give better end-to-end accuracy (71.7 vs 73.3) because the gold tool was shown less often.
4. Better descriptions are not free: augmenting 856 MCP tool descriptions raised median success +5.85 pp but increased steps +67% and made 16.7% of cases worse (S18 [M], abstract). Descriptions are a lever on retrieval and on cost.
5. Caching can make dynamic discovery look worse on hit-rate yet cheaper in total: Vanta (S12 [M], production report, fetched fully) with 280+ tools / 75k tokens used core tools plus one domain-expansion tool, reported cache-hit rate down but cost per run -48%, completion +5% relative, P50/P90/P99 latency -8/-10/-15%. Not a controlled experiment, no CI, but it shows hit rate is the wrong objective; the bill is.
6. Anthropic's own guidance tempers deferral: tool search adds a search step, is not worthwhile under ~10 tools or when most tools are used every session, and recommends keeping 3-5 core tools loaded (S1, S2 [V]). OpenAI recommends comparing task completion, tokens and latency before making it the default (S5 [V]).
7. Harness bug reports show deferral can silently fail (tools not indexed, absent on first turn, regressions across versions) (S23 [U], snippets only). These are bugs in one harness, not accuracy evidence.
8. Contradiction noted inside the search results: some blogs reverse the direction of the RAG-MCP numbers. The arXiv abstract (S6) gives retrieval = 43.1%.

## 3. Cost and cache: what is and is not measured
- What the vendors state [V]: Anthropic: modifying tool definitions invalidates the entire cache; deferred tools are excluded from the prefix and discovered tools are appended as tool_reference blocks so the prefix is untouched; BUT the full definitions of deferred tools are still sent in the tools array on every request (S2, S3, full read). OpenAI: tool search "designed to preserve the model's cache", discovered tools injected at the end of context, "changing the loaded tool set will break the model's cache from that point forward"; supported only on gpt-5.4+ (S5, partly read). Neither gives bill numbers.
- New and decision-relevant: Anthropic now documents mid-conversation tool changes (tool_addition / tool_removal blocks in system-role messages, beta headers inline-tools-2026-09-15 and mid-conversation-tool-changes-2026-07-01) that change which tools are offered "while the tools array never changes, so the cached prefix stays intact" (S4 [V], read to ~88%). Not on Sonnet 5; Anthropic models only; not tested by anyone found. For open-weight models served by vLLM/OpenRouter (your setting) this mechanism does not exist, so append-only remains the only portable option, but it is evidence that "never edit the tools array" is a provider-specific constraint and that append/withdraw can be made cache-safe at the vendor layer.
- Measured cache effects of agent loops: Don't Break the Cache (S11 [M], partly read) reports 41-80% cost reductions from caching across 4 models on DeepResearch Bench and states that changing tool sets invalidates the prefix, but contains no experiment that changes the tool set (its tool-count ablation varies calls per session). It also notes that caching dynamic content may add write overhead without read benefit, though write cost is not measured. The cache-invalidation-on-tool-change claim is therefore documented by vendors and asserted in literature, but measured only in anecdotal issues (S22 [U]: hit ratio ~5000:1 -> ~1:1 when tool order is shuffled; ~70% of one user's input bill was schema replay outside cache breakpoints).
- A paper claiming cache hit 84% vs 22% for lazy schema loading (Tool Attention, S16 [T]) is a simulation whose success/cost are projections, not measured (stated in its abstract). Do not cite as evidence.
- Slite (S13 [M], full read): 17 tools upfront, 65+ on demand via tree entrypoints; cost/question -23%, latency -12% on 63 questions; no accuracy figure, no cache figure.
- TheMCPCompany (S14 [M], summaries only; PDF unreadable): with 18k Azure tools, retrieval agents were +5.4 points and $2.06/task cheaper than browser agents; ground-truth tools +13.8 and $2.29 cheaper; smaller models could not exploit retrieval. This is dollars, but the comparator is a browser agent, not an all-tools baseline, and cache treatment is not given in what I could read.
- Tokens vs bill: an ERL result, seen only via a search summary (S27 [U]), is consistent with your own finding: +85% input tokens gave only about +15% cost because 82% of input was cached. Treat as pointer.

## 4. Search/deferral recovery and over/under-searching
- No controlled study of how often models search, search too rarely or too often, or recover after a retrieval miss for tool catalogues was found. P3 (models search uninstructed) is therefore ahead of the published literature rather than contradicted by it.
- Indirect: SING (S19 [M], abstract) reports multi-step active discovery beating one-shot retrieval (up to +59.8% recall@5, +28.9% success; maxima, benchmarks unnamed); LiveMCPBench's route action in a ReAct loop recovers at k=5 but not at k=1 (S8); a Taiwanese-history agentic-retrieval study (snippet only) saw multiple retrieval calls on 68/120 questions where follow-ups recovered misses but the agent also controls when to stop (not graded; excluded as off-domain).
- Both vendors recommend namespace/server-level deferral and keeping a few tools always loaded (S2, S5), i.e., a core set plus a search path, matching your design; but those recommendations are unmeasured vendor claims.
- Retrieval method: lexical (regex/BM25) is what the built-in Anthropic search uses; competitor claims that it underperforms embeddings at ~3-4k tools (Stacklok 34% vs 94%, Arcade 56%/64%) are [V] snippets from companies selling alternatives (S24). Academic: ToolRet and ERR (S7, S17) indicate retrieval quality is a bottleneck. No neutral head-to-head found.

## 5. Personalisation / memory-informed seeding
PEToolLLM/PEToolBench, PTBench, ETAPP and PrefTool (S26) benchmark tool selection from user history, but I opened none beyond snippets; none reports ReAct exposure, cost or cache. Support for per-user seeding as a bill-reducer is therefore absent in the literature found; it is a design hypothesis, not a replicated effect. "ToolSpectrum" not found.

## 6. Code-execution / Code Mode
Cloudflare and Anthropic report 98-99.9% token cuts; Bifrost reports -92.8% input tokens at 508 tools with 65/65 passing (S25 [V]); a purportedly third-party AIMultiple figure (-78.5%) was seen only in a vendor article. All token-based. It changes the interaction (fewer ReAct requests per task), which bears directly on the supervisor's "pay twice" concern but is outside your fixed function-calling setup and I found no cache-aware measurement.

## What would change a tool-exposure policy or its evaluation
1. Evaluation: report pass rate and bill together for three arms: all tools, predicted subset, and subset + search fallback, because ToolChoiceConfusion and LiveMCPBench show a subset can lose accuracy and retrieval misses dominate failures. Report subset recall (gold tool in subset) per task so accuracy loss is attributable.
2. Hit rate is not the objective (Vanta); bill is. A policy that sacrifices some cache-hit rate for a smaller prefix can still win; a policy that keeps a large prefix and a high hit rate can still lose (your 66% cache-read share).
3. Provider-dependence of the append-only rule: Anthropic's mid-conversation tool changes and OpenAI's append-at-end design show cache-safe dynamics exist at the vendor layer; for self-hosted/OpenRouter models the stable-prefix argument rests on prefix-cache mechanics, not on a published benchmark. State this as an assumption with the provider's prefix-matching behaviour verified per route (the P2 test is the only measurement of this I found).
4. Break-even depends on model and on whether the search path is used: ERR's crossover (~500 capabilities, one small model) differs from your 10-30-tool measured break-even, which is a bill break-even, not an accuracy one. Do not equate them.
5. Quality of the descriptions the search sees matters (S18), a confound for any search-based arm.
6. Stop rule for a missing tool has no published counterpart; treat as novel and test, including the false-stop rate.
