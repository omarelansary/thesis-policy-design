# L5 report: context management, cache-aware compression, agent memory (2026-11-09)

Grades: [E] peer-reviewed/replicated with released code/data; [M] measured by authors; [V] vendor; [T] theory/proposal; [U] unverified. "Read" says how much I opened. Many of the strongest items are 2-4 week old preprints (Oct 2026); none is independently replicated. Pricing facts: Anthropic cache write 1.25x (5 min) / 2x (1 h), read 0.1x (0.05x on Opus 5.5 / Sonnet 5.5); OpenAI GPT-5.6+ read 0.1x, write 1.25x (30 min), earlier OpenAI models have no write charge [V, docs, S15/S16].

## 1. Findings by decision relevance

**F1. Editing already-sent history almost always loses money once cache pricing is applied; this is now directly measured, not just argued. [M, S01, high applicability]**
Vallecillos-Ruiz et al. (arXiv 2610.35496; 42 deletion configurations, 9,400 runs, SWE-bench Verified, two agents, one open-weight model) find that under flat pricing 26/42 configurations are cheaper, but under cache-aware pricing (read 0.1x) 0/42 are cheaper and 26 are significantly dearer. Tool-output-only deletion with a 2-turn delay: cost ratio 0.71 flat vs 1.20 cache-aware (mini-SWE-agent, 100% deleted), 1.01 vs 1.67 (Trae agent). Lowest cache-aware ratio of any delayed setting is about 1.03. Their model ignores cache-write premiums, so real Anthropic bills for rewriting would be worse. Read: abstract plus most of the HTML (first 100k characters). Limits: one run per configuration, random (not learned) deletion, one model, token-level and turn-level deletion only, and batching was not tested.

**F2. Sliding-window masking is the worst case; one rewrite is near neutral. [M, S02, high]**
Yu et al. (2610.34763, NeurIPS-26 workshop): Mask-5 (keep last 5 observations) cut prompt tokens 33% but raised uncached prefill 608%, time 37%, and solved 26 vs 29 of 100. A single anchored compaction ("Compact") was about neutral (prompt -6.5%, uncached prefill +22%). Their break-even: masking pays only when the cache hit rate is below about 0.55. Read: abstract plus a secondary summary (dev.to); not the paper body. Measured in tokens, GPU time and an energy proxy on a local GPU, not dollars.

**F3. Batched eviction is the only variant with positive evidence, and the evidence is thin. [M, S03, high]**
TokenPilot (2606.17016, EMNLP-26 Findings) evicts every B turns. B in {1,3,5,7,9,inf} was tested on one PinchBench category: B=3 best; B=1 (per turn) causes misses and premature truncation; no eviction maximises context and cost. Cost reductions of 56-87% against vanilla with GPT-5.4-mini hit/miss pricing (0.075/0.75 $/M), accuracy about equal (PinchBench +0.5/+2.1; Claw-Eval -1.4/-2.6). AgentDiet (2509.23586, FSE-26, S09) rewrites only step s-2 and only if the saving exceeds 500 tokens, thereby leaving every earlier step's cache intact; input tokens -40..-60%, cost -21..-36% (reads discounted, writes not priced), pass rate -1.0..+2.0 points, reflection overhead 5-10%. Read: TokenPilot HTML partial, AgentDiet HTML partial. Limits: neither is AppWorld; neither prices cache writes; TokenPilot's B=3 vs "tracking window 33" is ambiguous in the text; benchmarks are long (dozens of turns), unlike your 10-13 requests.

**F4. Anthropic's own docs concede the mechanism but publish no break-even. [V, S12, S13, S15]**
Context-editing docs: clearing "invalidates cached prefixes at the point of change, so you incur cache write costs each time"; `clear_at_least` exists "to justify cache invalidation"; default trigger 100k tokens, keep 3. The cookbook demo (n=1, synthetic) shows clearing at a 30k trigger freeing ~163k tokens per event and warns that `input_tokens` alone is misleading without cache fields. The blog numbers (+29% editing, +39% editing+memory, -84% tokens in a 100-turn search eval) come from an internal eval with no n, CI, defined baseline or cache-aware cost [V, S14, read in full]; do not use them as cost evidence.

**F5. A back-of-envelope break-even for your setting [I, derived by me from the documented multipliers; not from a source].**
Clearing F tokens from the oldest results when the prefix has P tokens means the (P-F) tokens after the first cleared item are rewritten once at the write price (1.25x) instead of read (0.1x), costing about 1.15(P-F) base-input units; each later request saves 0.1F. Break-even needs k > 11.5(P-F)/F further requests. With P about 6-10k, F about 2k and at most 5-8 requests left, this needs k of 25-45, so per-step clearing in a 10-13-request task cannot pay on Anthropic pricing; on OpenAI models without a write charge the factor is about 9 instead of 11.5, still too large. Batching helps only by amortising several freed items into one rewrite and by waiting until F is large relative to P; it cannot beat the "never rewrite" baseline unless F/P is large and many requests remain. Ingestion-time shrinking (truncating or offloading a result before it is first appended) has no rewrite penalty. That distinction is the actionable one.

**F6. Token counts mislead; trajectory effects can erase savings. [M, S05, high]**
Weinberger and Hozez (2607.12161): a compressor removing 38.4% of tool-output tokens raised the bill 6.8% (CI +2.8..+11.3); another proxy +48%; correlation between token reduction and cost change r=0.15; cache writes+reads about 80% of the bill, tool outputs about 3.3%. Mechanisms offered (extra retrieval/diagnosis turns, re-reads) are the authors' interpretation. Corroborated by S01 (re-fetch of deleted content up to 1.2-4.6x for tool-output deletion; no-delay deletion lowered solve rate significantly in 19/42 setups). Read: abstract + 100k chars of HTML. Limits: Claude Code only, about 38-45 effective tasks per arm, baseline success 96-98%.

**F7. Accuracy: masking/compaction can be accuracy-neutral, but evidence on interactive benchmarks is mixed. [E/M, S08, S10]**
Complexity Trap (2508.21433; code/data released; SWE-bench Verified, five model configurations): masking (M=10) about halves cost vs raw agent at equal solve rate (e.g. Qwen3-Coder 53.4 -> 54.8); LLM summarisation lengthens trajectories (+13-15%); results are mixed per model (Gemini 2.5 Flash thinking: raw 40.4, masking 36.4, summary 31.4). Its cost uses no cache read/write split (Qwen priced without hit distinction; Section 5.2 only notes hits can be 10x cheaper). On AppWorld, ACON (2510.00615, ICML-26; gpt-4.1; 168 tasks): no compression 56.0% / 9.93k peak / $0.331; learned history compression 56.5% / 7.33k / $0.285 (-14%) but latency +20%; naive compressors lost much accuracy (FIFO 45.8, LLMLingua 39.3, prompting 43.5). Its appendix states history compression "invalidates the existing KV-cache". ACON's peak is under 10k tokens, so AppWorld histories are short and the headroom small.

**F8. Does long history hurt accuracy by itself? Real but not shown for tool-loop agents. [M, S18, S19, abstract-only]**
Du et al. (2510.05381): 13.9-85% drops from input length alone, even with irrelevant tokens masked; recitation mitigates. Laban et al. (2505.06120): about 39% average drop in multi-turn vs single-turn; mostly unreliability. Both use synthetic or sharded tasks at long length, not 10-13-step ReAct histories of 5-10k tokens. I found no study showing history-length accuracy harm at your scale. Treat context management as an accuracy lever only for much longer tasks.

**F9. Memory-informed tool seeding: indirect, mostly unevidenced; failure modes documented. [M, S20-S24]**
No paper found that seeds or prunes the exposed tool set from per-user memory and measures bill and accuracy. Nearest: PRefine/MPT (2604.17886): existing memory systems (RAG, Mem0, LangMem) "often fail to beat full-history prompting" for multi-session personalised tool calling; abstracted preference hypotheses win (abstract-only; about argument preferences, not exposure). Xiong et al. (2505.16067, ACL-26): retrieved erroneous or misaligned memories are copied and propagate ("experience-following"); selective addition/deletion gave about +10% (abstract/snippet). ACE (2510.04618): evolving playbook lifts AppWorld ReAct 42.4 -> 59.4 and, because the playbook is stable, 91.8% of input tokens hit the prompt cache (GPT-5.1) cutting billed input 82.6%, but authors warn of context pollution with unreliable feedback. ReMe/MemSkill report AppWorld gains (numbers not read; no token-cost reporting). Mem0's own paper concedes full-context beat it on quality (72.9 vs 66.9 J) and excludes extraction cost [V; secondary]. ToolMem concerns choosing among generative tools, not exposure.

**F10. Stable-prefix design is the dominant lever, and tool-definition churn is a named risk. [M/V, S07, S15, S16, S17, S03]**
Don't Break the Cache (2601.06007; 3 providers; one benchmark): caching saves 41-80% of cost; most of the saving comes from the stable system part; changing tool definitions invalidates the whole prefix. Anthropic docs: any tool-definition change invalidates tools+system+messages; a new beta (`inline-tools-2026-09-15`) allows adding a tool mid-conversation without editing `tools`. OpenAI docs: keep the tool list fixed and use `allowed_tools`; "rewriting earlier turns or summarizing history" breaks the prefix. Manus (blog [V/T]): mask rather than remove tools; append-only; offload to files. TokenPilot notes tool-schema churn lowers prefix reuse. These bear on your policy directly: a per-step changing exposed subset can cost more than the tokens it saves.

## 2. Contradictory or negative evidence
- Token reduction vs billed cost: S05, S01, S02 are negative for in-place editing; S08/S10 report savings but price tokens without a cache split or at list price (ACON: -14% on AppWorld).
- Positive batched/delayed results (S03, S09) are on long coding/agent-ops tasks, price reads but not Anthropic-style writes, and are not compared against an unedited-but-cached baseline in the same cost units in a way I could verify.
- Summarisation: elongates trajectories (S08) and drops specifics (cookbook probe: 0/3 obscure values preserved, n=1).
- Memory: full-context or full-history often beats memory systems (S21, S22); stale/incorrect memory propagates (S20).
- Vendor accuracy gains (+29/+39%) are unreproduced and cost-blind (S14).

## 3. What would change a tool-exposure policy or its evaluation
1. Evaluation: report cost with explicit cache read / write / fresh split and price schedule (also OpenAI pre- and post-5.6 regimes), plus cost per success; token counts, peak tokens and "re-sent tokens" are not valid proxies (S05, S01). Report trajectory length and re-fetch/re-call rate as covariates.
2. Policy: tool-set changes mid-task should be treated like history edits (full-prefix invalidation, S15); stage exposure changes at session boundaries, at fixed prefixes, or via `allowed_tools`/mid-conversation addition where supported. This matches your P2 finding.
3. P4 design: do not test per-step clearing as a candidate to win; test (a) ingestion-time truncation or offload (no rewrite), (b) one or a few batched clears with a `clear_at_least`-style gate sized by F7-style break-even, (c) delayed clearing (a>=2). Expect negative or near-zero results on 10-13-request tasks; my break-even (F5) predicts this and the literature does not contradict it. A negative P4 result is consistent with S01.
4. Memory: seeding tools from per-user memory should be compared against a no-memory and a full-history baseline and measured for harm (wrong seed, stale seed) as well as gain; memory text itself is part of the (hopefully stable) prefix.
5. The supervisor's concern (each ReAct request re-sends the same input) is real, but the literature says its price is mostly the cache read (0.1x), and the lever is keeping the prefix byte-stable, not shrinking it after the fact.
