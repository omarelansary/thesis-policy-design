# L4 report: reducing model calls and re-reads (code-as-action, planning, batching)
Date 2026-11-09. Grades: E peer-reviewed/replicated with code; M measured by authors; V vendor; T theory; U unverified. Read depth is stated per source (see sources.tsv; S-ids below). About 45 tool calls; WebSearch returns summaries, so only fetched pages count as read.

## Bottom line
The broader literature does not overturn the thesis's framing, but it changes four things: (1) fewer requests helps the bill only where the workload is long, fan-out-heavy or has big tool results; on short sequential tasks code/programmatic modes are neutral or worse. (2) The one programmatic-calling mechanism I could check does NOT remove tool definitions from billing: the continuation request resends the tools array. (3) On AppWorld itself, independent evidence favours a code-writing agent on accuracy for strong models, but it collapses on some models, and published costs are not cache-accounted. (4) Evaluation hygiene (cache accounting, run concurrency, single-run noise) is a bigger risk than any of the proposed techniques. No source measured, on AppWorld, function-calling-with-subset vs code-agent with cache-priced billing. That is the gap.

## Findings by decision relevance

### 1. Does "you pay twice" (re-sent input each call) justify call-reduction techniques?
- Cache reads dominate dollar cost in long agent loops: SWE-bench Verified with OpenHands, Sonnet 4.5, cache reads dominate volume and dollars even though output is 80x per token [M, S17, read full html]. Same-task runs differ about 2x on average. This matches the thesis's own 66% figure and shows the concern is real but per-token cheap (cache read $0.30/M vs $3 input for Sonnet 4.5 [M, S16]).
- Direct AppWorld evidence that cutting calls cuts bill, but modestly: AWO meta-tools on an AppWorld coding agent cut LLM calls 7.6-11.9%, cost only 4-15% ($31.59->26.85 GPT 5.1; $29.63->28.39 Claude 4.5), success +3.6 / -3.6 pts (n=168, one run) [M, S13, full]. Calls fall faster than cost, and the authors say cache hits "contribute little to savings" since context stays similar. Applicability high; limit: extra meta-tool definitions not costed.
- Anthropic's own docs: removing round trips saves nothing when calls are sequential: on tau2-bench, PTC left scores unchanged and cost about 8% more; "sequential single-call workflows do not benefit" [V, S4, read from offset 30k]. 75-tool benchmark: about 38% fewer billed input tokens (vendor internal, method unnamed; caching interaction not stated).
- Pydantic (5,276 graded runs, 8 models): code mode cut cost 58%, wall time 51%, +16 pts success on long tasks, but cost 21-38% MORE on 3 of 5 small tasks; "models already batch parallel tool calls", so round-trip removal is not the main gain; the gain is fewer tokens written/read per request [V/M, S7, read full]. Break-even about 20-50 items. Code not public; cache treatment not stated. Applies to the thesis: with 23-57% of requests already parallel and about 10-13 requests/task, the fan-out regime where code mode wins (dozens of items) is probably not AppWorld's typical regime.

### 2. Are tool definitions re-billed in programmatic/code modes?
- Anthropic PTC: each resumption is a Messages call whose example says "Same tools array as the original request" [V, S4]. So tool definitions (including those with allowed_callers) are resent on resume; only tool RESULTS are excluded from token usage. PTC reduces result tokens and round trips; it does not substitute for tool-subset selection. Whether the resumed request hits cache is not stated in the part I read [U]. Grade V. PTC is Anthropic-only and cannot run on the thesis's MiniMax/GLM/gpt-5-mini; the client-side analogue is AppWorld's code agent.
- The Bitter Lesson paper: PTC puts typed stubs in the system prompt: about 1.5x input on chaining ablation, token crossover near 26 calls; same LLM-call count as JSON in its harness [M, S2, read full]. So even code-mode prompts carry an API-surface block; the code agent's apis.api_docs approach is progressive disclosure, which Anthropic's MCP post (S6, V, no accuracy, no caching) and Cloudflare (S8, V, not opened) also advocate. None of these quantified the split between definition re-reads and history re-reads in a cache-priced bill.

### 3. Code agent vs function-calling agent on AppWorld/comparable (most decision-relevant)
- AppWorld-UL (user-interactive AppWorld variant): code agent beats FC agent for every model pair run: Opus 4.7 48.6 vs 27.3 TGC, GPT-5.5 41.8 vs 24.2, Qwen 3.7 Max 40.3 vs 25.7, Kimi K2.6 30.6 vs 24.4, DeepSeek v4 28.5 vs 25.6 [M, S9, partial]. Single run, no variance; tokens/cost in a figure only (code agents on Pareto frontier). Caution: FC agent implementation (tool exposure, shortlisting) unknown, so the gap may partly be an exposure-policy effect.
- Exgentic (independent, 5 scaffolds x 5 models, 468 AppWorld actions): with Opus 4.5 smolagents-code 0.70 vs FC "OpenAI Solo" 0.68, ReAct 0.61, ReAct+shortlist 0.64; with Gemini 3 smolagents 0.13 vs FC 0.57; GPT 5.2 0.07 vs FC (no shortlist) 0.00 due to a 128-tool limit [M, S10, partial]. Architecture explains only 0.5% of success variance across all benchmarks, model 27.8%. Open-weight models (DeepSeek-V3.2, Kimi-K2.5) score at most 0.13 on AppWorld there. Implication: a code-agent advantage is model- and harness-specific; do not generalise from Claude.
- Shortlisting is independently supported: ReAct vs ReAct+shortlist cost for Opus 4.5 $5.75->$3.78, Gemini -$0.15, DeepSeek -$0.15, GPT 5.2 +$0.09; AppWorld success +22 (GPT 5.2), +5, +3, -5 (DeepSeek) [M, S10]. BenchmarkList (imported rows, U) shows Opus 4.5 LiteLLM tool calling 61% at $11.32 vs 64% at $3.43 with shortlisting and smolagents 70% at $5.59. The two sources disagree on OpenAI Solo cost ($8.54 vs $22.76), so absolute costs are unreliable and cache accounting is unstated in both.
- Original AppWorld paper (GPT-4o, 2024) [E, S15, partial]: ReAct (writes code) 48.8 TGC at about $0.7/example; function-calling IPFunCall (batched, up to 15 turns) 32.1 at about $0.33; Plan&Execute 44.6 at about $1.33. So batching function calls was cheaper but less accurate, and planning was costlier. 2024 models, no caching.
- Official AppWorld code agent on GPT-5.4 nano: 48.2% TGC at $16.6 for 417 tasks; a prompt-only variant 67.5% at $10.2; the official baseline lost about 15% from an instruction ambiguity [M, S12, partial]. Harness details swing results more than architecture.

### 4. Planning / plan-then-act / ReWOO / LLMCompiler
No 2026 independent re-evaluation of ReWOO or LLMCompiler on current models was found (searched; S23 and S24 not opened). The 2023-era claims (up to 6.7x cost, 3.7x latency) are unverified here [E-unverified]. Interactive-environment evidence is negative: Plan&Execute worse and costlier than ReAct on AppWorld (S15); ReAct above P&E on MobilityBench (snippet only, S24). Plan-first fits only when observations don't change the plan.

### 5. Speculation, fusion, skills (call-count reducers)
- Speculative actions/macro commit: AppWorld latency -45% with 1.2 pts lower TGC on Qwen3.5-27B, but no cost or call counts and 3 GPUs vs 1 [M, S14]. Speculation targets latency; it generally ADDS billed calls. Low relevance to the bill.
- Meta-tools (AWO, S13) above: modest. GPT-OSS issued MORE calls (+4.2%) with meta-tools: a backfire.
- Skill libraries (SkillX, AppWorld test-normal): +2 to +10 pts success, "planning skills reduce steps", steps/tokens only in charts, no cost [M, S20]. Skill-retrieval precision fell from 29.6% to 3.3% as the pool grew 5->100 [M, abstract only, S21]: the same scaling problem as tool selection.

### 6. Caching interacts with exposure policy
Changing the available tool definitions invalidates the cached prefix; dynamic tool results should be excluded from cache; caching saved 41-80% [M, S16, read full; one benchmark, 40 sessions/condition, Jan-2026 prices]. Any per-turn dynamic subset must be priced including re-writes. (The thesis's P2 fixed-prefix result already addresses this.)

### 7. Effort / thinking budget
Higher reasoning effort lengthens trajectories and can cost up to 42x on tasks all levels solve; start-low-and-escalate matches fixed top effort at lower cost for most proprietary models [M, S18, abstract only]. Ares router -52.7% reasoning cost on tau-bench (secondary, unread). After tool-exposure reductions, output/reasoning is a large remaining share, so effort control is a competing lever on the same bill.

## Contradictory or negative evidence
- Accuracy of PTC/code modes disagrees by setting: Pydantic +16 pts, Bitter Lesson parity or gain on 11/14 models (BFCL, echo stubs), Anthropic +3 to +5 pts (vendor), but Is-Bash-All-You-Need finds PTC 52.9/45.1 vs bash-only 69.4/67.1 TAC and the lowest tool-call success (65.2%) and highest final-message truncation [M, S1]. PTC reduced tokens 19-72%-class vs typed tools but is generally behind bash alone. Cost in S1 is Copilot list-rate estimates with cache reads inside input; rates unreported.
- Code agents fail on some models (smolagents 0.13 / 0.07 with Gemini 3 / GPT 5.2) and open-weight models in Exgentic. OpenAI models emit literal "\n" in multiline code causing syntax failure (S2). Small models write buggy code, retries repeat writes (S7).
- No source showed that fewer requests cut cost by the same ratio; AWO shows calls -12% gives cost -4 to -15%.
- Vendor token figures (98.7%, 99.9%, 37%) use undefined or hypothetical baselines (all definitions upfront); none reports cache-priced billed cost. Treat as upper bounds [V].
- Not found: independent PTC evaluation by a third party with cache accounting; negative-result papers specifically on Cloudflare Code Mode; ParallelTools-style benchmark of parallel-call adherence in modern models (only Bitter Lesson fan-out ablation and BFCL).

## What would change a tool-exposure policy or its evaluation
1. Add a code-agent arm (AppWorld's native agent with apis.api_docs) as a comparator on the same three models, priced by the same billing equation; published evidence suggests it may beat function calling on accuracy for strong models but is model-dependent, so run it per model.
2. Report calls per task and cost per task separately; calls -12% only gave cost -4 to -15%.
3. Treat tool-definition prefix as separable: any programmatic mode still resends it (Anthropic), so a subset policy and a code mode are complements, not substitutes.
4. Evaluation hygiene: single runs are noisy (Bai: about 2x same-task variance); cache hit rate fell more than 5% at 5 parallel runs (S12), so fix concurrency and cache keys; record cache write/read separately; do not accept token reductions as billed savings.
5. A fan-out regime (dozens of items) is where code mode pays; with 2-3 parallel calls per request, it likely does not. Verify with the thesis's own call-count distribution before building anything.
6. Monitor model-specific limits (GPT 5.2 128-tool cap in Exgentic) as hard constraints on "all tools" baselines.
