# L2 Report: cost measurement and evaluation methodology for agents (2026-11-09)

Grades: E peer-reviewed/replicated with released data; M measured by authors (preprint/blog); V vendor; T theory/proposal; U unverified. Source ids (S1...) refer to sources.tsv. About 34 tool calls; reading depth stated per source in sources.tsv.

## Bottom line
The methodology literature does not overturn the thesis's framing, but it changes how the existing result should be read in four ways: (a) the closest published analogue to the thesis finds that cutting tokens in a cache-dominated agent can RAISE the bill, so "fewer tool tokens" is not evidence of a smaller bill unless billed cost is measured per token class (S1, S9); (b) the cost share of each token class depends on the provider's cache pricing, so the "66% cache reads" figure is not transferable between providers; (c) the noise the team observed is normal and the literature gives explicit sample-size arithmetic showing that 57 tasks with 1-2 runs cannot resolve small differences in either accuracy or cost; (d) price-list computed cost and routing/backend are documented confounds. Nothing found says the supervisor's "you pay twice" concern is wrong as a description of re-sent input; what the literature adds is that the re-sent prefix is billed at a discount only if the cache actually hits, and that this is a per-provider, measurable quantity.

## Findings, ordered by decision relevance

**1. Token reduction is not cost reduction; evaluate on billed cost split by token class. [M] S1, S9**
- S1 (103 tasks, 2,848 provider-billed Claude Code runs): removing 38.4% of tool-output tokens was associated with +6.8% paired cost (95% CI +2.8 to +11.3, task-clustered bootstrap); per-task token change vs cost change r = 0.15. Bill shares: cache write 44.3%, cache read 35.4%, output 10.4%, uncached input 1.3%, unattributed 8.7%. The authors explicitly recommend labelling every cache read/write by source (system prompt, tool schemas, tool output) - exactly the prefix-vs-history decomposition the thesis wants, and note nobody had done it.
- S9 (Quesma, 1,740 attempts, 5 runs per task per arm): cache reads were 94-98% of input tokens yet only 26-30% of the bill; a tool's own "tokens saved" counter claimed 89% while cost rose 5-17% in one harness; the one harness with a saving owed it to a single task.
- Conditions: coding agents, Claude Code (Anthropic explicit caching, 1.25x write) and OpenCode/DeepSeek; neither manipulates tool definitions. Mechanism offered (not proven): reduction changes agent behaviour (more turns), and the saved slice is small relative to a cache-dominated bill.
- Implication [I]: our "66% cache reads under all tools" is a plausible, consistent observation, but the thesis conclusion must be stated as billed cost (and cost per success), with turn count and output tokens reported beside it, because the subset arm may move cost through turns and output rather than prefix.

**2. Input, not output, dominates agent cost, and cache reads of accumulated context dominate the input (for Claude); but output can dominate where cache read is cheap. [M] S2, S9**
- S2 (8 models, OpenHands, SWE-bench Verified, 4 runs/problem): input drives cost even with caching; for Sonnet-4.5 cache reads dominate tokens and dollars in every phase. S9: with DeepSeek's 1/30 cache-read price, output (incl. reasoning) was ~56% of cost. So the token-class mix is a function of the price ratios of the specific provider; compare per provider, not pooled. This matches our own observation that with the subset "history and output dominate".
- No study found that decomposes cost by tool-definition prefix vs history vs output for a tool-exposure manipulation (searched in S1-S3, S9-S11 and the tool-retrieval query). This looks like a genuine gap; our decomposition would be new measurement, not replication. Not found in the places searched is not the same as non-existent.

**3. Dynamic tool exposure and the cache. [V + T + small M] S18, S3, S11**
- Anthropic's documentation states the cache order tools -> system -> messages and that any change to tool definitions invalidates all three levels (S18, V, read partially). S3 says the same and recommends a fixed tool set (stated, not tested). S11 (CacheRouter, prototype, 55 queries) keeps a small fixed core and routes the rest through a sub-model, reporting 91-95% hit rate; it has only a no-cache baseline and no accuracy figures in the abstract (T).
- Conditions for our design [I]: a per-task predicted subset is fixed within an episode, so after request 1 the subset prefix is cached like any other; but each new task has a NEW prefix (cold write on first request), while the all-tools prefix is identical across tasks and can be warm from earlier tasks inside the TTL. That asymmetry is a measurement confound (see 5) and a real economic effect (cross-task reuse), and they must be separated. Our P2 result (offering server-enforced at a fixed prefix kept the cache) is consistent with S18.

**4. Statistical practice for small, clustered agent benchmarks. [E/M] S6, S7, S8, S1, S4**
- Cluster and pair: scenarios of 3 correlated tasks are clusters; Miller (S6, preprint) shows clustered SEs can exceed naive by >3x and recommends paired question-level differences. S1 does exactly this for cost (task-clustered bootstrap, ICC 0.37-0.55, effective n ~38-45 of 103 tasks). Our scenario bootstrap is the right unit.
- Repeats and power: S7 (E; 60,000 trajectories, 10 runs/config) finds single-run pass@1 swings 2.2-6.0 points, SD to ~1.8, even at temperature 0 (temperature 0 delays divergence but does not remove it; one model scored 31.4% at T=1 vs 20.4% at T=0); at SD 1.5 pts a 2-point difference needs ~9 runs and a 1-point difference ~36 for 80% power. Our setting (57 tasks, 1-2 runs, accuracy differences of a few points) is far below that; the observation that run-to-run variation equals arm differences is expected, not a defect. S4 used 5 runs and Student-t intervals and noted that agent evaluations are rarely reported with error bars.
- Small n: S8 (E, ICML 2025 spotlight; read abstract/snippets only) says CLT intervals understate uncertainty on small benchmarks and that bootstrap also performs poorly there, recommending Bayesian or exact intervals. With 19 scenario clusters, the bootstrap over scenarios may be too narrow for accuracy proportions; report an exact/Bayesian interval beside it. Caveat: S8 concerns accuracy, not cost.
- Equivalence framing: S1 itself lacked a non-inferiority margin and flags it as a limitation (baseline success 96-98%). "Nearly the same accuracy" needs a pre-stated margin; the project's rule of no margin is consistent with estimation-only reporting, and the literature supports that over claiming equivalence from non-significance.
- Reliability metrics: pass^k (S22, tau-bench, abstract only; S7) show a 20-point gap between pass@1 and pass^5 is common, so a policy that changes cost via retries can look good on pass@1 and bad on consistency.

**5. Cache warm/cold state and the order of runs is a documented confound that few papers control. [M] S1, S3, S18**
- S1 randomised arm order within paired blocks, but all consecutive runs fell inside the 5-minute TTL (100% of 2,136 pairs), so carryover "cannot be excluded"; it relied on null order tests. S3 separated cache conditions by >24 h to expire TTLs and ran warm-up calls. S18 notes concurrent requests do not see each other's cache and hits are not guaranteed. Our all-tools arm run back-to-back benefits from a warm shared prefix; the subset arm does not. Report cache-write and read tokens separately and, ideally, randomise or interleave arm order and record time gaps. No paper found that quantifies bias from warm/cold state on provider-side automatic caching (OpenAI/OpenRouter); gap.

**6. Cost accounting errors that are documented. [M/V] S1, S4, S5, S17, S19**
- Reconstructed vs billed: S1 found a median per-run residual near 0 but a dollar-weighted +8.7% unattributed share (thinking charges inconsistent across models); recommend keeping both and reporting the residual. S5 (HAL, E) computes cost from a price table fixed at 2025-09-24 and says prices change (o3 -80%); S4 says costs vary over time. Using one fixed price list for all arms is defensible but must be stated, and billed amounts (OpenRouter `cost`, OpenAI invoice) should be compared; note OpenRouter's doc does not state whether `cost` is computed or invoiced and `upstream_inference_cost` is BYOK-only (S17), so the computed-vs-invoiced question should be tested on a sample.
- HAL reports that token-based and dollar-based Pareto curves "provide very different pictures" (S5); a secondary summary lists incomplete caching accounting as a limitation of HAL (not confirmed in the text I read). Treat published leaderboard costs as not cache-aware unless stated.
- Hidden output: reasoning tokens can far exceed visible output and are billed (S19, U; snippet only). Reasoning effort is a hidden treatment: in HAL 21 of 36 model/agent/benchmark combinations had equal or lower accuracy at higher effort (S5, E). Anthropic's table also says thinking/effort changes invalidate message-level cache (S18). Fix and report effort per arm.

**7. Provider, routing and backend are uncontrolled treatments. [E/M/U/V] S5, S12, S13, S14, S15, S16**
- HAL warns aggregators like OpenRouter may serve different quantizations under one endpoint name (S5). S14 (M, abstract) shows the inference backend alone moves benchmark scores up to 16.6 pts at fixed weights and decoding, with prefix caching among the causes - relevant to the university vLLM server. S15 (V): temperature-0 outputs depend on server batch load (80 unique completions in 1,000 samples). S13 (U, secondhand) and S16 (V) report provider differences in tool-calling behaviour; S12 (E) shows substitution is hard to detect from outside. Practice: pin provider and quantization, disable fallbacks, log the serving provider per request, run arms close in time, report backend and version. I found no independent audit measuring OpenRouter provider variance on tool-calling agents.

**8. Pareto and price-normalised metrics. [M/E] S4, S5, S20**
- Dollar cost over proxies and Pareto frontiers (accuracy vs cost) are the established norm (S4, S5); cost-of-pass (expected cost per correct solution, S20, ICLR 2026, snippet only) and S1's cost per successful execution (failed runs kept in the numerator) are the price-normalised forms. These support the thesis's "bill at nearly the same accuracy" framing, and suggest also reporting cost per success so that a cheaper-but-failing arm cannot look good (S1 notes early failures look cheap).

## Contradictory or negative evidence
- S3 reports caching saves 41-80% (best mode per model; Table values as low as 27.8%) and recommends minimal dynamic changes; S1/S9 show that once caching exists, reducing tokens may not help. These are not contradictory: caching is the large lever, token trimming the small one. But note S3 has inconsistent ranges and no CIs.
- S2's variance statement is internally inconsistent (abstract "up to 30x tokens" vs body about 2x for the most expensive vs cheapest run on average); do not cite 30x.
- Mechanistic claims in S1/S9 (agents compensate with more turns) are offered as hypotheses; S1 states it avoids causal claims.
- OpenRouter says quantization is rarely the cause of tool-call variance, parsers are (S16, V); blog reports disagree (S13, U). Unresolved.
- No source supports a claim that exposing fewer tool definitions improves accuracy in ReAct from a methodology standpoint; that belongs to other lanes.

## What would change a tool-exposure policy or its evaluation
1. Report billed cost by class (fresh input, cache write, cache read, output/reasoning) and by source (tool-definition prefix, history, tool results, output) per arm, plus turns and tool calls (S1 recommendations). A subset arm that wins on prefix tokens but loses through turns or output must show up.
2. Evaluate per provider cache scheme; do not pool the 66%/34% split across providers with different write/read price ratios.
3. Pre-state the unit of inference (scenario cluster), pairing, and use intervals valid for ~19 clusters; pre-state the repeat count from a variance estimate (S7: ~9 runs for a 2-pt, ~36 for a 1-pt difference at SD 1.5), or accept and state that only large differences are detectable.
4. Control or randomise warm/cold state and arm order; record time gaps and provider per request.
5. Fix price list and reasoning effort; sanity-check computed vs billed cost.
6. If a policy changes the prefix per task (predicted subset), measure cross-task cache reuse loss explicitly, because the baseline benefits from it.
