## 2. Why C1 subset numbers differ
Subset arm request 0 of each task = predictor (no tools). Using it as the prefix gives prefix share 42.0/15.4% and the claimed split; using the first agent request (system+demos+14-ish tools+task) gives 28.8/9.2%. Predictor cost is a separate line: $0.052 (3.8% MM-sub), $0.250 (3.6% GLM-sub). Reconstructed total equals the recorded total only with the predictor as its own category. Qualitative effect: subset-arm prefix cache-read is even smaller than claimed (10%/5%).

## 3. C10 batching proxy
My detector variants on steps >=2 (strings/numbers newly first-appearing in the previous step's tool messages; + same-key=value id matches; + pagination continuation = same function seen before with page_index):
| arm | steps independent: A literal-only / B +id keys / C +pagination | bill share removable if whole request removed (A/B/C) | input-side only (A/B/C) |
| MM-all | 68/64/45% | 66/61/43% | 53/50/34% |
| MM-sub | 73/70/47 | 77/74/52 | 46/44/29 |
| GLM-all | 73/70/64 | 74/70/64 | 60/57/53 |
| GLM-sub | 84/77/62 | 93/75/59 | 60/47/36 |
Range 29-93% depending on arbitrary detector choices -> the "46-60%" is one point in an unconstrained range. Further defects: (i) 6-13% of steps are supervisor__complete_task with {} args, which are "independent" by literal test but are pure decision dependencies (model decides it is finished after checking) - false positives; (ii) no ground truth for what a model could have planned without seeing results (3-shot demos, temperature 0, one trajectory per task); (iii) removing a request does not remove its output tokens; (iv) merged calls need foresight which changes behaviour/accuracy; (v) the data cannot validate the detector. Defensible statement only: "a large fraction (roughly half or more) of steps carry no literal dependency on the previous step's results, so room exists in principle" - no bill saving. Models already parallelise 23-57% of tool-call requests, which is a lower-bound existence proof of the mechanism, not of the remainder. Do not quote 46-60%.

## 5. Errors, alternatives, confounds in the story
1. Subset-arm prefix mis-defined (predictor call) -> C1/C2 subset figures wrong (direction of conclusion unaffected, even strengthened).
2. "Gap explained >=100% by cache read" is an accounting near-identity, not a mechanism test; nothing was varied. P2 (a real intervention at 128 tools) supports the channel qualitatively (drop: cr -0.15/-0.33 USD pooled) but cache-hit losses (90%->74%) offset part.
3. All-vs-subset is not a clean tool-exposure contrast: predictor call and its recall (not measured here), different step counts and output length per request (GLM-sub output/req +68%), different accuracy (task goal completion MM 79.0 vs 80.7; GLM-all 40.4 vs sub 52.4 for control part and 36.1 for rest part). Failing runs (50-step, 52,611 s task) drive GLM-sub history cost. Single run per cell, temperature 0, 57 tasks in 19 scenarios (3 tasks per scenario correlated).
4. Cache warmth: tasks ran back-to-back, so the 469-tool prefix was cache-warm across tasks (96.8-99% cached). With realistic gaps beyond TTL the prefix is fresh (5x price) and the saving mechanism would be larger, not smaller, on first requests; the measured 66% is a best-case warm figure. GLM-bill is computed with GMICloud prices on a free server; its 99% hit rate is a vLLM prefix-cache property, not a priced observation.
5. GLM timeouts: 16 errored calls in glm-b2-control trace (and 2 in glm-all) are not in lm_calls and not in the bill; if billed upstream, bills are understated (unknown).
6. Cache-read price ratio is the lever: at 0.048 vs 0.24 (5x) MM, 0.13 vs 0.70 (5.4x) GLM; the "history re-read" shares move with that ratio; OpenAI ratio is 10x yet cached share of bill is only 25-33% because the prefix is 4x smaller.
7. "Once the tool block shrinks, history re-reads and output become the main costs": CONFIRMED in these data (sub arm hist-cr+hist-fresh 42/55%, output 35-38%), and this is true on the subset-arm bill of ~$1.4/$7.0.
8. Unexamined alternative: AppWorld's native code agents (no tool block, API docs read on demand) never appeared as baseline (C11a); call-reduction (parallelism already 23-57%) not tested.

## 6. What NOT to conclude
- Not that tool exposure saves X% in deployment: warm-cache back-to-back batch, one benchmark, 2 open-weight models, single runs.
- Not that history clearing/masking would save 2-36%: bound ignores rewrite penalty; my crude penalty makes per-step clearing net negative.
- Not the 46-60% batching saving, nor that steps are "mergeable".
- Not that scaling slopes are an elasticity/finding.
- Not that "prefix reads dominate" generalises: at 128 tools (OpenAI P2) cache-read is 25-33%, fresh 30-41%, output 34-38% of the bill.
- Not that the supervisor is wrong or right: Claude Code docs confirm full re-send per request, with caching making it ~5-10x cheaper; our bills measure exactly that term.
- Not that GLM numbers are a real bill (computed prices, free server).

## 7. Overall weight
Core of the story survives: re-sent prefix at cache-read price is 65-66% of all-tools bills and the all-vs-subset gap is >100% explained by cache-read tokens (replicated to the cent; robust to allocation). The subset-arm breakdown (C1/C2) must be corrected (prefix = first agent request; predictor separate). C3/C4 are valid arithmetic but low-information. C7, C8, C10 as presented cannot bear weight (C7 needs a rewrite penalty; C8 mechanical/confounded; C10 not quotable). The "unexamined alternatives" claim holds for code agents, partly for the request-count lever. Weight: moderate-high for "exposure saving works through the repeated-prefix read term in these runs"; low for any projected saving from history clearing or call batching.
