## 1. Anthropic PTC billing semantics
URLs: https://platform.claude.com/docs/en/agents-and-tools/tool-use/programmatic-tool-calling ; .../code-execution-tool ; .../tool-use-with-prompt-caching ; https://platform.claude.com/docs/en/about-claude/pricing (all fetched as .md, 2026-11-09)

- Flow [DOC-STATEMENT]: "3. When a tool function is called, code execution pauses and the API returns a `tool_use` block. 4. You provide the tool result, and code execution continues (intermediate results are not loaded into Claude's context window). 5. Once all code execution completes, Claude receives the final output and continues working on the task." Also: "Save tokens and latency by calling tools serially or in a loop without sampling Claude between tool calls."
- Resume request [DOC-STATEMENT]: "Send the full conversation history plus your tool result." ... "The user message that carries your result can contain only `tool_result` blocks." ... "Send the same `tools` array as the original request. The code execution tool must still be present for the paused code to resume, and the tools you send on this request are the definitions Claude and the running code can use for the rest of the turn." => Each resume is a separate /v1/messages HTTP request carrying the whole history and the full tools array. The docs never say in so many words whether a resume is a "new sampling"; the "without sampling Claude between tool calls" sentence implies the model is NOT re-sampled between programmatic calls, but the request still re-submits history+tools. How those re-submitted input tokens are billed (full / cache read) is NOT stated on the PTC page. [UNVERIFIED: whether the resume request is billed as input tokens at all; whether it bills a cache read]. No `usage` example for a resume request appears on either page (the only usage example on the code-exec page shows `input_tokens:105, output_tokens:239, server_tool_use.code_execution_requests:1` for an ordinary call).
- "do not count" note [DOC-STATEMENT, exact]: "Token counting for programmatic tool calls: Tool results from programmatic calls do not count toward your input/output token usage. Only the final code execution result and Claude's response count." Also "Tool results from programmatic calls are not added to Claude's context: Only the final code output is." Reading [INFERENCE]: the tool_result text that code consumes is not placed in the model's context, so it is not billed as tokens the model reads; it does NOT say the history/tools are not re-billed on the resume request.
- Pricing [DOC-STATEMENT]: PTC "uses the same pricing as code execution". Code execution: "free when used with web search or web fetch" (`web_search_20260209`/`web_fetch_20260209` or later in the request: "no additional charges ... beyond the standard input and output token costs"). Otherwise "billed by execution time, tracked separately from token usage: Execution time has a minimum of 5 minutes. Each organization receives 1,550 free hours of usage per month. Additional usage beyond 1,550 hours is billed at $0.05 USD per hour, per container. If files are included in the request, execution time is billed even if the tool is not called".
- Models [DOC-STATEMENT]: PTC front matter lists claude-haiku-5-5 (also sonnet-5-5, opus-5-5, opus-5, sonnet-5, fable/mythos, opus-4-5..4-8, sonnet-4-5/4-6). Haiku 4.5 is NOT supported for PTC ("accepts ... but doesn't support programmatic tool calling"). Requires `code_execution_20260120` or later.
- Timeouts [DOC-STATEMENT]: "the pending call times out after about 4 minutes and raises a `TimeoutError`" (example stderr: "no response after 270s"). Separate 90 s wall-clock per Python cell: `code_execution_20260521` description "tells Claude about the 90-second wall-clock limit on each Python cell in programmatic tool calling". Container: "expire 30 days after creation. After about 5 minutes of inactivity a container is checkpointed"; container ID required on resume.
- Cache interaction: the PTC and code-exec pages contain no mention of caching (grep: 0 hits). Tool-use-with-prompt-caching page [DOC-STATEMENT]: for code execution "Container state is independent of prompt cache"; and "When your request has prompt caching enabled and Claude uses a server tool such as web search, web fetch, or code execution, the API automatically places a cache breakpoint on the server tool result before running the next iteration of the agentic loop ... only applies when your request already has at least one `cache_control` marker." (That sentence concerns server-side iteration within one request; whether it covers client-resumed PTC pauses is not stated.) General caching rules [DOC-STATEMENT]: prefix order tools -> system -> messages; "Modifying tool definitions ... invalidates the entire cache"; so re-sending an identical tools array keeps the prefix valid.
- Related pricing [DOC-STATEMENT] (pricing page): cache read = 0.1x base, but 0.05x on Opus 5.5 / Sonnet 5.5 ($0.10/MTok on Sonnet 5.5) and 0.025x on Fable 5.1 / Mythos 5.1. Haiku 5.5: $0.10 in / $0.01 cache read / $0.50 out per MTok up to 100k prompt; $0.50/$0.05/$2.50 above 100k (prompt length counts cache reads/writes).
- Net for the supervisor's claim [INFERENCE]: PTC does remove model sampling between calls and keeps tool results out of context, but it is not "the LLM waits": the API call is split into several HTTP requests that each re-submit history + tools (cache-readable); the saving is fewer sampled turns/less context growth, not free waiting.

## 3. Cost structure
(a) Derivation [INFERENCE, arithmetic]. Prefix P (system+tools+task), each step adds delta tokens (tool result + model output). Request k carries P + k*delta. Without caching total input tokens = nP + delta*n(n-1)/2: linear in P, quadratic in n for the history term. With caching, each token is written once (1.25x) and read on every later request at r (0.1x, 0.05x on Sonnet/Opus 5.5): cost ~ 1.25*(P+n*delta) + r*(nP + delta*n^2/2) + output. So the quadratic term remains; only its coefficient drops ~10-20x. "Near-linear with caching" holds only while r*delta*n/2 << 1.25*delta, i.e. n << ~25 at r=0.1 (n << ~50 at r=0.05); and the repeated prefix P is re-read n times (linear in n, cheap but non-zero). So the chat's statement is right for short loops and wrong asymptotically. 
(b) Measurements:
 - arXiv 2604.22750 (Bai et al.; SWE-bench Verified, 8 LLMs, 4 runs each): agentic tasks "uses about 1000x more tokens" than code chat/reasoning; "input tokens rather than output tokens driving the overall cost"; runs on the same task differ up to 30x; Kimi-K2 and Sonnet-4.5 use >1.5M more tokens than GPT-5. Case study Sonnet-4.5, 5-minute write rate: "cache reads dominate both raw token volume and dollar cost ... Cache reads remain the dominant cost contributor in every phase", noting output priced ~80x per token higher than cache reads yet still outweighed. The paper gives this as figures (Fig. 8), not numeric percentages in text. [DEMONSTRATED, one model for the breakdown]. 
 - arXiv 2601.06007 "Don't Break the Cache": DeepResearchBench-style web-search agent, 40 sessions per cell (500 total), 10k-token system prompt, 4 models. Best-mode cost savings vs no-cache: GPT-5.2 79.6% (exclude tool results), Claude Sonnet 4.5 78.5% (system prompt only), Gemini 2.5 Pro 41.4%, GPT-4o 45.9%; TTFT 6-31%. At 50k-token prompt: GPT-5.2 89% ($0.253->$0.029), Sonnet 4.5 88% ($0.667->$0.080), GPT-4o 54%. The "tool count" ablation varies number of tool calls per session, NOT tool-definition size; savings stay ~flat (GPT-5.2 77-81%). Not a per-token-class breakdown. [DEMONSTRATED]
 - arXiv 2607.12161 "Token Reduction Is Not Cost Reduction" (Claude Code, paired provider-billed tasks; 1,212 child sessions, 11,773 requests): "cache creation plus cache reads account for approximately 87% of the reconstructed four-component cost - about 80% of the actual bill, with a further 8.7% ... left unattributed". Table 1: harness base (system prompt + tool definitions) = 71.6% of context, 92.0% of cache reads, 74.7% of cost; hidden thinking + residual 19.4%; tool outputs 3.3%; tool-call args 1.4%; retrieved files 0.8%. Most aggressive tool-output compression: -38.4% delivered tool-output tokens but +6.8% billed cost. [DEMONSTRATED; Claude Code, Anthropic models incl. Haiku 4.5/Opus 4.8].
 => In Claude Code the repeated prefix (system+tool defs) is ~3/4 of the bill; supports the supervisor's "you pay again for the same input" intuition, but at cache-read prices, and shows it is dominated by re-reads of a fixed prefix, not by re-reads of tool results.

## 4. Reducing calls / re-reads
- Parallel tool calls: no BFCL-based frequency found. Second-hand via search summaries [UNVERIFIED-second-hand]: finance-agent benchmark (arXiv 2608.11683): GPT 5.6 Sol 5.86 tools/turn vs Gemini 3.6 Flash 1 tool/turn needing ~3x more turns; Lean agent harness (arXiv 2605.27485): Claude Sonnet 4.6 two parallel searches in 82% of search turns, GPT-5.4 three in 77%, Gemini 3 Flash 8%; E-Bench (2607.23722): Grok-4.5 2.06, Seed-2.1-Pro 1.80 tool calls per turn. Parallelism varies a lot by model and harness.
- Observation masking vs summarization, arXiv 2508.21433 (Lindenbauer et al., JetBrains; SWE-agent, SWE-bench Verified): masking ~52% cheaper than raw agent with Qwen3-Coder 480B (solve rate 53.8 -> 54.8); observations ~84% of an average turn; hybrid -7%/-11% vs masking/summarization [via search summary; abstract-level; UNVERIFIED-second-hand]. 
- Anthropic context editing https://platform.claude.com/docs/en/build-with-claude/context-editing [DOC-STATEMENT]: "Tool result clearing: Invalidates cached prompt prefixes when content is cleared. ... clear enough tokens to make the cache invalidation worthwhile. Use the `clear_at_least` parameter ... You'll incur cache write costs each time content is cleared, but subsequent requests can reuse the newly cached prefix." Clearing thinking blocks also invalidates cache from that point. So context pruning trades re-read savings against cache re-writes (1.25x).
- OpenAI server-side state https://developers.openai.com/api/docs/guides/conversation-state [DOC-STATEMENT]: "Even when using `previous_response_id`, all previous input tokens for responses in the chain are billed as input tokens in the API." => no billing difference from chaining itself. ## 5. Tool-definition size
- Anthropic [VENDOR-CLAIM] (engineering post): five-server setup, "58 tools consuming approximately 55K tokens before the conversation even starts"; "tool definitions consume 134K tokens before optimization". Tool Search: "~77K tokens" up front -> "~8.7K tokens" ("85% reduction"); accuracy "Opus 4 improved from 49% to 74%, and Opus 4.5 improved from 79.5% to 88.1%" (internal MCP evals). Docs (tool-search-tool): "Tool search typically reduces this by over 85 percent"; "Claude's ability to pick the right tool degrades once you exceed 30-50 available tools." Caching: "Discovered tools load as `tool_reference` blocks, preserving prefix cache" [DOC-STATEMENT]. Independent replication of defer_loading numbers: not found (not searched beyond this).
- Independent: arXiv 2607.12161 above: system prompt + tool defs = 74.7% of cost in Claude Code. Cloudflare 1.17M vs 1k is definition-size only.
- On PTC resume: tools array must be re-sent ("Send the same `tools` array as the original request"); billing of it (cache read vs fresh) not documented for resume; with unchanged tools and a cache_control marker the generic caching rules apply [INFERENCE].

## 6. AppWorld (arXiv 2407.18901; ACL 2024; fetched arxiv.org/html/2407.18901)
- Baselines [DOC-STATEMENT]: (1) ReAct - "Reasoning ('Thought') step followed by an Act ('Code' in our case) step", model writes Python executed in a stateful shell calling `apis.*`; explores docs by calling the ApiDocs app instead of in prompt; max 100 LLM calls; (2) PlanExec (plan then ReAct each step); (3) FullCodeRefl (whole program in one go + Reflexion on errors; docs of predicted APIs inserted by an "API predictor" because full docs ~142K tokens); (4) IPFunCall ("Iterative Parallel Function Calling", OpenAI function-calling with parallel calls) - this is the function-calling baseline; (5) CodeAct (Mistral-7B fine-tune), (6) ToolLLaMA. Base LLMs: GPT-4o, GPT-4 Turbo, LLaMA3 70B, DeepSeek-coder.
- Results (Test-N / Test-C TGC) [DEMONSTRATED, paper]: GPT-4o ReAct 48.8 / 30.2; PlanExec 44.6 / 19.7; FullCodeRefl 33.9 / 19.2; IPFunCall 32.1 / 18.0. GPT-4 Turbo ReAct 26.8/17.5, PlanExec 32.7/11.0, FullCodeRefl 25.6/12.5, IPFunCall 30.4/14.6. LLaMA3 best FullCodeRefl 24.4 / 7.0.
- Cost [DEMONSTRATED]: with GPT-4o on Test-N about "$0.7 per example for ReAct, $1.33 for PlanExec, $0.33 for IPFunCall and $0.02 for FullCodeRefl"; GPT-4 Turbo ~2x, GPT-4 ~6x cost; total experiments ~$10K. Authors note long trajectories "substantially increase the cost of experiments". No token breakdown or cache accounting (2024, pre-caching). Newer leaderboard results/cost: not retrieved (appworld.dev not fetched).
