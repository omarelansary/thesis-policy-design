## 1. 2610.41905 Completeness and Cost of Retrieval Structures (Zhang, single author)
**Design.** 345 AppWorld queries (129 test-normal, 216 test-challenge) over 456 In-N-Out APIs; 103 MCP-Bench tasks. Nine arms (BM25, bge, e5, LLM decomposition+bge, AnyTool, MCP-Zero, Graph-of-Skills, COLT, simplified HYSET); one LLM, DeepSeek-V3.2 at temp 0. Retrieval is over API descriptions (AnyTool/MCP-Zero see only app names as server text).
**Required set** (l.271-286) [F]: "a query's required set [is] these APIs [the ones the query calls] together with their producers" (In-N-Out parameter-level edges), not just the gold solution's APIs. The six supervisor (credential) APIs are removed from rankings and required sets because the agent always receives them. Sizes 2-12, median 6.
**Metrics/statistics.** completeness@k, recall@k, LLM calls, tokens, latency; no dollars. Paired bootstrap (2,000 resamples); downstream 60 tasks, one run, exact McNemar.
**Headline.** Table 2: C@16 AppWorld: BM25 0, bge .020, e5 .064, decomposition .035, MCP-Zero 0, GoS .096, AnyTool .301, COLT .328, HYSET 0. Table 3: AnyTool median 31 LLM calls, ~99.7k tokens, ~307 s. COLT trained on 90 official training queries (57 dev for checkpoints).
**Downstream** (l.523-541, appendix l.866-872). Agent: port of the official simplified ReAct CODE agent (not function calling), DeepSeek-V3.2, temp 0, 50 steps, AppWorld 0.1.3. 60 test tasks "sampled at random within each split" (20 normal, 40 challenge). Exposure A = gold required APIs, C = COLT top 16. Hidden APIs are deleted from the environment, docs tools list only exposed APIs. A 46/60, C 23/60 (25 only A, 2 only C, McNemar p=5.6e-6). The 21 complete tasks: C 21/21, A 20/21. The 39 incomplete: C 2/39, A 26/39. C used median 32 steps vs 19, 30 unexposed-API errors vs 8, ~2x prompt tokens.
**Limitations.** Author: one LLM, base-size encoders, split is "observational". Mine: (i) no all-APIs arm, so nothing here says a subset is >= full exposure; (ii) complete tasks concentrate in test-normal (COLT C@16 .589 normal vs .171 challenge), so difficulty confounds; the gold arm itself passes 95% (20/21) of complete vs 67% (26/39) of incomplete tasks, so incomplete tasks are harder; (iii) 60 tasks, 1 run, Wilson 95% CI for 2/39 is about 1-17%, for 21/21 lower bound about 84%; (v) the supervisor/credential APIs are always exposed, which sidesteps the failure my thesis records show (GLM 0/22).
**Statement test.**
- "345 queries with expert dependency labels": ACCURATE (labels from In-N-Out).
- "no untrained retrieval structure with at most one LLM call completes more than 10% at k=16": ACCURATE as worded (abstract; max .096, GoS; decomposition+bge .035; MCP-Zero 0). OVERSTATED if read as "no cheap predictor works": the one-call arms see only the query (decomposition, MCP-Zero); an LLM that reads all API descriptions and lists the needed APIs (the AppWorld-paper API predictor, my thesis' predictor) was NOT tested. "Full exposure" and its cost were explicitly not run (l.343-348; catalog 64,874 tokens in function-calling format). Also fixed k=16, an encoder-size caveat, and the required-set definition including producers.
- ".33 trained (75-90 queries)", ".30 hierarchy, median 31-38 calls": ACCURATE (.328; .301; 31 AppWorld, 38 MCP-Bench).
- "21/21 vs 2/39": ACCURATE as numbers; the causal wording is not supported. Needed context: code agent, DeepSeek-V3.2, hard hiding, gold exposure 26/39 on the incomplete tasks, observational split. 60 tasks were randomly sampled within splits, not matched on required-set size.
**k=16 vs cap 20.** Required sets are median 6 (max 12) APIs, so size is not the limit; failure is ranking: 58% of COLT's misses sit at ranks 17-50, so a cap of 20 recovers few.
**Generalisation.** Same environment, different agent (code with doc tools; the thesis uses function calling with 469 definitions in context), different models, different completeness definition. 2/39 (5%) incomplete passes vs the thesis' 13/19 (68%) is a large discrepancy; candidate explanations are all [S]: completeness definition (gold+producers vs gold only), hard-hiding vs soft, model, task selection. It should be reconciled, not averaged. The 2x prompt-token result is the only cost evidence here and points AGAINST an imperfect subset (more steps, more tokens).

## 2. 2606.06284 ToolChoiceConfusion (two independent researchers)
**Design.** Synthetic: 102 template-generated tasks (34 per calendar/email/files domain), 100 mock tools, mocked outputs, max 6 steps; Nova 2 Lite, Nova 2 Pro Preview, Claude 3.5 Haiku, Sonnet 4; deterministic decoding, one run per cell (2,448 runs). The symbolic state is supplied at each step. Metrics: tokens only (input+output total, no dollars, no cache); no CIs or tests.
**Table 4 (l.~560).** Success / wrong tools / premature / tools per step / tokens: all 0.83/1.25/0.03/100/24,569; kw5 0.61/2.36/0.03/5/4,407; kw10 0.72/1.93/0.06/10/5,039; state-aware 0.65/1.98/0/5.73/4,354; full causal path 0.99/0.03/0.01/1.90/2,555; CMTF 0.99/0.01/0/1.00/2,405.
**Per model (text l.~640-650).** Lite: all 1.00 = CMTF 1.00. Pro: 0.83 -> 1.00. Haiku: 0.48 -> 0.94. Sonnet 4: 1.00 all-tools (24,858 tokens vs 1,819). The all-tools mean of 0.83 is carried by Haiku (0.48) and Pro (0.83).
**Limitations.** Author-stated: synthetic, mocked, contracts assumed available. Mine: CMTF's filter uses the gold precondition/effect contracts and the true state, i.e. it is an oracle-grade filter; it is not a predictor and cannot miss a tool by construction; the 90% saving is largely from 100 -> 1 tool schema per step.
**Statement test.** "100 mock tools, 4 models, Table 4 values": ACCURATE. "CMTF matches the strongest causal baseline": ACCURATE for success (0.99 = 0.99); CMTF's own number is 0.99 (0.01 wrong-tools). "Token use down about 90%": ACCURATE only relative to ALL-TOOLS (24,569 -> 2,405 = -90.2%); relative to the full-causal-path baseline the saving is -6% (2,555 -> 2,405). A reader can take the sentence as 90% below the causal baseline: ambiguous wording to fix.
**Cuts against reduction.** Every non-oracle subset lost success against all tools (kw5 -22 pts, kw10 -11, state-aware -18) while saving ~80% of tokens; for Lite and Sonnet 4 all-tools was already perfect.
**Generalisation.** Weak: mocked, 1-4 step chains.

## 3. 2508.01780 LiveMCPBench
**Design.** 95 daily tasks, 70 MCP servers, 527 tools, 12 models. The ReAct "MCP Copilot Agent" is NOT shown a pre-selected subset: it calls a Route action that retrieves k candidates from the full set (k=5, Qwen3-Embedding-0.6B), then Execute. LLM-as-judge success (DeepSeek-V3, 81.05% human agreement). Metrics: success, steps, tokens (millions); no dollars, cache not discussed.
**Statistics.** One run per model (not stated otherwise), n=95; exact McNemar for ablations (l.~915-966).
**Results.** Sonnet-4 78.95, Opus-4 70.53, GPT-5 52.63, ... Qwen3-32B 30.53 (Table 2). Table 3: k=5 78.95; k=1 64.21 (p=0.02); k=10 78.95 (p=1.00); BGE-M3 76.84 (p=0.84). The text does not name the model for the k ablation; 78.95 equals Sonnet-4's main result, so it is Sonnet-4 [I]. Error analysis (Appendix I): Query 13.33%, Retrieve 50.00%, Tool 18.33%, Other 18.33% - on failed trajectories of Claude-Opus-4 and Claude-Sonnet-4 only, human-labelled (about 60 failures, inferred from the percentages [I]).
**Statement test.** "ReAct agent over 527 tools": ACCURATE but mis-leading for this thesis (agent-initiated search, not an up-front subset). "Retrieval errors are 50% of failures": OVERSTATED - 50% of failed trajectories of two Claude models, human-classified; the abstract says "nearly half of all failures" for all models, but the analysis covers two. "k=1 64.2 vs 78.95 at k=5 (p=0.02)": ACCURATE; "k=10 adds nothing": ACCURATE (p=1.00; authors blame retriever limits). "Scores spread 57.9-76.8% over 23 reruns": NOT-FOUND-IN-TEXT of this paper; from the abstract of 2607.02577 (fetched): "23 repeated evaluations of the same setup produce scores ranging from 57.9% to 76.8%" (18.9 points). It says "repeated evaluations", so it is unclear whether agent reruns or judge reruns [U]. If it is the same setup it exceeds the k=1 vs k=5 gap (14.7 pts), which makes the single-run k result fragile.
**Generalisation.** Low: different mechanism (agent-driven search), judge-scored, one strong model.

## 4. 2505.10570 LongFuncEval (IBM)
**Design.** Challenge 1: BFCL simple, live-simple, multiple (858 samples); the one correct function (or functions) is inserted at fraction 0.1/0.3/0.5/0.7/0.9 into a list of RANDOM distractor functions from other BFCL entries, at 8,192/16,384/32,768/65,536/120,000 tokens = 49/102/207/417/741 tools on average (Table 3). Models: Mistral-large, Granite-8B, ToolACE-8B, Llama-70B/8B, BitAgent-8B, QwQ-32B, R1-Distill-32B, GPT-4o only on 3 lengths x 3 positions. Single-call AST accuracy, no agent loop, no tool subsets, no cost.
**Table 1** gives Max, Min and "% degradation" = (max-min)/max over ALL cells (context length x position), so position effects are included. Mistral-large 94%, BitAgent 79-82%, Llama-70B 70-72%, Granite 70-74%, ToolACE 62-64%, QwQ 41-42%, GPT-4o ~11-14% (Table 5 shows 6.4% for one condition).
**Statement test.** "Accuracy drops 7-85% as the catalogue grows (up to 741 tools)": roughly ACCURATE but OVERSTATED as a general claim: the text (l.100) says 7.59-85.58% "excluding Mistral-large" (94% with it); the numbers are relative max-to-min drops across context AND answer position; models are mostly 8B-class or distilled; the only closed model, GPT-4o, loses ~11-14% (7% quoted in the abstract applies to the tool-response experiment). "Tool response length 7-91%": ACCURATE (GPT-4o 7%, Mistral 91%; 10K to 80K tokens). "Multi-turn 13-40%": the abstract number is stated, but it concerns conversation length (10K to 80K), not the tool catalogue, and I could not reconcile it with Table 2, where models differ widely (Llama-70B stable at 0.96-0.99 in setting 1; several small models fall by half or more) [U].
**Generalisation.** Supports "long catalogue hurts weak models"; does not support a cost or subset claim, and gives no evidence on MiniMax/GLM/gpt-5-mini. Cuts the other way for strong models (GPT-4o "generalizes well").

## 5. 2503.01763 ToolRet
**Design.** 7.6k tasks, 43k tools; NDCG@10, recall, completeness@10. Downstream (Sec. 7, App. D.6): ToolBench G1/G2/G3, GPT-3.5 and ToolLLaMA; the pre-annotated toolset (~10-20 tools, "oracle") is replaced by the top tools retrieved from the 43k corpus; pass rate. One run, no CIs, no cost.
**Results.** Best w/o instruction: NV-Embed-v1 average NDCG@10 33.83 (Table 4, l.392); WITH instruction 42.71 (Table 5, l.476). Downstream (Table 15): GPT-3.5 G1 oracle 62.0 vs bge-large 50.6; G2 57.2 vs 49.0; G3 67.4 vs 56.9; ToolLLaMA G1 53.6 vs 37.6; retrievers fine-tuned on ToolRet-train reach 58-59.5 for GPT-3.5 (close to oracle).
**Statement test.** "best retrievers nDCG@10 33.8 on a 43k-tool corpus": ACCURATE for the without-instruction setting, UNDERSTATED/incomplete otherwise (42.7 with instruction). "Poor retrieval lowers downstream pass rate": ACCURATE (7-12 pts for GPT-3.5, up to 16 for ToolLLaMA). Caveat: retrieval-vs-pass-rate ordering is not monotone (e5-large G2 56.5 with NDCG 20.78 above bge-large 49.0 with 23.03); the baseline is the hand-picked 10-20-tool set, not the full catalogue; no AppWorld; no cost.
**Generalisation.** General support only.

## 6. 2510.19286 TheMCPCompany
**Design.** 175 tasks adapted from TheAgentCompany, 18,000+ MCP tools; OpenHands CodeAct agent. Three arms: Browser (default), MCPAgent (the agent calls a tool_finder over text-embedding-3-large and an invoke wrapper; top-k results), Oracle tool set (hand-curated, 6.5 tools on average, may contain extras). Six models (GPT-4.1, o3, GPT-5-mini, GPT-5, Sonnet 4, Opus 4.1). Cost: "calculated based on the token usage ... and prices published by LLM providers"; no cache split mentioned. Run count not stated: treat as single run; 1 task = 0.57 pts. No CIs. (The oracle arm has its own appended prompt, Tables 10-12.)
**Table 2** (success % / steps / $ for MCPAgent | Oracle): Sonnet 4 39.43/30.82/2.75 | 47.43/26.97/2.13; Opus 4.1 39.43/22.53/7.29 | 48.00/23.65/7.17; GPT-4.1 27.43/20.48/0.75 | 36.00/16.05/0.56; o3 37.14/23.41/0.83 | 40.57/22.53/0.65; GPT-5-mini 22.86/29.27/0.26 | 38.86/22.33/0.17; GPT-5 42.29/19.39/0.85 | 44.57/17.54/0.66. Browser success/cost: Sonnet 34.86/5.02, Opus 31.43/14.58, mini 24.57/0.41.
**Statement test.** All Table 1 numbers quoted (assessment calls it Table 1; it is Table 2 here): ACCURATE for GPT-5-mini, Sonnet 4, Opus 4.1. "Cost = tokens x published prices": ACCURATE. "Retrieval agents retrieve about 20 tools": ACCURATE (text l.795; Table 4: 13.5-25.8, cumulative over the run, not in context at once). "Oracle sets cost 2-35% less than retrieval, 44-70% less than browsing": ACCURATE [O]: oracle vs MCPAgent -1.6% (Opus), -22% (Sonnet, o3, GPT-5), -25% (GPT-4.1), -35% (mini); vs Browser -44% (o3) to -70% (GPT-5).
**Can the cost gap be step counts?** The data cannot separate it from definition size. Oracle runs are 4-24% shorter in steps for five of six models (mini 22.3 vs 29.3; GPT-4.1 16.1 vs 20.5; Sonnet 27.0 vs 30.8) and 2-16 pts more successful (fewer long failing runs); MCPAgent also pays for tool_finder calls and accumulates retrieved definitions; Opus has more oracle steps and almost the same cost (7.17 vs 7.29). The paper's own error analysis (GPT-4.1, 24 retrieval-only failures, Table 6): missed tools 12.5%, wrong tools 33.3%, correct tools but instruction drift 50.0%, other 4.2%, so most loss is not "tool was not shown".
**Model dependence [O]:** oracle minus MCPAgent success: GPT-5 -2.3, o3 -3.4, GPT-4.1 -8.6, Sonnet -8.0, Opus -8.6, GPT-5-mini -16.0; recall of oracle tools: mini 32.8%, GPT-4.1 44.9%, GPT-5 58.7%, Sonnet 60.0%, Opus 69.7% (Table 4). Mini with retrieval is worse than with browser (22.86 vs 24.57), authors' own caveat.
**Generalisation.** Closest to a "subset vs search" cost study with a gpt-5-mini row, but: agent-initiated search (not an up-front predictor), curated tiny oracle, different task domain, no full-catalogue arm (impossible at 18k tools). Supports "an incomplete/wrong subset costs the small model most".

## 7. 2601.22037 AWO (meta-tools)
**Design.** Not about shortening tool lists: it ADDS composite meta-tools mined from traces. AppWorld: 168 test-normal tasks, "the coding agent configuration" (ReAct code agent), five meta-tools = app auto-login routines. Also VisualWebArena (910 tasks). GPT 5.1 and Claude Sonnet 4.5, temperature 1, one run each; GPT-OSS-120B in the appendix. The meta-tools were mined from "execution traces generated across the full benchmark" (the same tasks it is evaluated on): in-sample.
**Metrics.** Cost from input/output tokens x price table, cache miss/hit/write split in Tables 10-11.
**Results (AppWorld).** GPT 5.1: calls 3,665 -> 3,229 (-11.9%), tokens 34.1M -> 29.0M, cost $31.59 -> $26.85 (-15.0%), success 69.6 -> 73.2 (+3.6). Claude 4.5: calls 2,801 -> 2,588 (-7.6%, Table 9; Fig. 5 shows 2,599, -7.2%: internal inconsistency), tokens -9.4%, cost $29.63 -> $28.39 (-4.2%), success 89.3 -> 85.7 (-3.6; about 6 tasks); the authors attribute the drop to "randomness". GPT-OSS: calls +4.2%, success 14.3 -> 16.1; "it often forgets what it had done".
**My cost decomposition from Table 11 [O].** GPT 5.1 base: miss $4.61 (15%), hit $3.51 (11%), output $23.50 (74%); the output tokens fell 0.34M, giving $3.4 of the $4.78 saving. Claude base: miss $6.63 (22%), hit $7.48 (25%), write $8.29 (28%), output $7.20 (24%); output tokens barely changed (0.48M -> 0.47M) and ~70% of its $1.24 saving came from fewer cache-hit reads. VisualWebArena Claude (Table 10): write $159 of $272 (58%).
**Statement test.** Numbers: ACCURATE (Claude calls use Table 9's -7.6%). "Paper says cache cost is not great and output tokens are the main cost driver": ACCURATE as a quote (App. D: "the cost from cache hits is not great ... most significant cost comes from output tokens"); the assessment's rebuttal is HALF RIGHT: for GPT 5.1 the paper is right (output 74%, miss only 15%); for Claude the four components are comparable on AppWorld and cache-write dominates on VisualWebArena, so the claim is model-specific and wrong as a general statement. Meta-tool definitions counted? Not discussed; costs come from measured total tokens so they are included implicitly [I].
**Generalisation.** Code agent, in-sample login bundling; evidence that removing early login turns saves 4-15%, not about tool exposure (it adds tools). Success differences are 6 tasks, 1 run.

## 8. 2607.20536 AppWorld-UL
**Design.** 516 user-in-the-loop tasks from 34 Test-C scenarios (306 individual + 210 compositional), LLM-simulated user via supervisor.message. Two scaffolds from the AppWorld paper: Code agent (ReAct) and Function-Calling agent (FunCall). Six models; temp 1 for Opus 4.7, GPT-5.5, Kimi K2.6 and 0 for the others; medium reasoning for Opus/GPT-5.5, default (high) otherwise; one run; no CIs. Cost only in Fig. 6 (USD per task axis), no table.
**Metric.** I-TGC = TGC AND the agent asked all necessary questions (not plain TGC); I-SGC scenario-level.
**Table 2 overall I-TGC (Code | FC).** Opus 4.7 48.6|27.3; GPT-5.5 41.8|24.2; Qwen 3.7 Max 40.3|25.7; GLM 5.1 38.9|FC pending (footnote 4, "API access issues"); Kimi K2.6 30.6|24.4; DeepSeek v4 Pro 28.5|25.6.
**FC implementation.** The main text says only "native function calling in a loop". The appendix Listing 3 (l.2195+) shows a first stage "determine which available APIs would be useful ... prioritize high recall" over App-wise API descriptions, followed by the function-calling loop, i.e. the FunCall agent uses a predicted API subset (the AppWorld paper's IPFunCall, which caps the predictor at 16 APIs) while the Code agent reads docs on demand over all APIs. The cap in this paper is not stated [U].
**Statement test.** "Code agent beats FC for every model pair": OVERSTATED - authors: "in most cases"; five pairs, not six (GLM has none); Kimi (+6.2) and DeepSeek (+2.9) gaps are small, single-run, unqualified (SE ~2 pts at n=516, scenario-correlated). Numbers: ACCURATE. The metric is I-TGC on a perturbed Test-C benchmark, not the TGC on original AppWorld. "Single run; cost in figure only": ACCURATE.
**Fair?** No: it confounds code-vs-function-call with docs-on-demand vs predicted-subset, prompt/demo differences and the user-interaction requirement; temperature and reasoning settings differ across models.

## 9. 2407.18901 AppWorld
**Design.** 9 apps, 457 APIs. Methods: ReAct (code, explores docs via ApiDocs app, no predictor), PlanExec (same docs-on-demand), FullCodeRefl, IPFunCall: these last use an API predictor, an LLM given ALL API descriptions and the instruction; the docs of predicted APIs go into the prompt. Predictor cap: "do NOT generate more than 16 APIs ... prioritize high recall" (Listing 4). Full docs are ~142K tokens. IPFunCall: parallel function calling, batch per turn, max 15 turns, 3-shot, signatures of predicted APIs. Greedy decoding, one run.
**Table 3 (TGC|SGC, Test-N).** GPT-4o: ReAct 48.8|32.1; PlanExec 44.6|23.2; FullCodeRefl 33.9|26.8; IPFunCall 32.1|16.1. GPT-4 Turbo: ReAct 26.8; PlanExec 32.7; FullCodeRefl 25.6; IPFunCall 30.4.
**Oracle-API test (Sec. 4.3, GPT-4o).** Test-N predicted -> oracle: ReAct 48.8 -> 54.8; PlanExec 44.6 -> 35.7 (worse); FullCodeRefl 33.9 -> 41.7; IPFunCall 32.1 -> 34.5. Test-C: 30.2 -> 35.2; 19.7 -> 19.9; 19.2 -> 29.0; 18.0 -> 18.9. Authors: "API retrieval is not the main bottleneck". Predictor (GPT-4o) per-API F1 87 Test-N / 71 Test-C (precision/recall in Table 4).
**Cost (App. E.8).** June-2024 rates at a flat "$5 per 1M tokens"; GPT-4o per Test-N example: ReAct ~$0.7, PlanExec $1.33, IPFunCall $0.33, FullCodeRefl $0.02; GPT-4 Turbo ~2x, GPT-4 ~6x; total ~$10K. No input/output split, no caching.
**Statement test.** TGC values: ACCURATE. Costs: ACCURATE as an estimate (flat blended price; "without caching" is not stated, it is merely absent). GPT-4 Turbo reversal (IPFunCall 30.4 > ReAct 26.8): ACCURATE on Test-N (PlanExec 32.7 is best; on Test-C IPFunCall 14.6 vs ReAct 17.5, so no reversal there). Turns: IPFunCall max 15 batch turns.
**Relevance.** The only paper with a predicted-vs-oracle design like ours (LLM predictor over all descriptions, <=16 APIs, function calling). For GPT-4o IPFunCall the oracle gain is 2.4 (Test-N) and 0.9 (Test-C) pts; the large gap to ReAct persists with oracle APIs (34.5 vs 54.8), so code-vs-FC is not an exposure effect. Old model, pre-reasoning-model era.

## Cross-questions
**(a) Is a predicted subset at least as good as all tools in AppWorld, per model?** No paper tests it for MiniMax-M3, GLM-5.3 or gpt-5-mini. 2610.41905 has no all-tools arm. The AppWorld paper compares subset-prompted methods with ReAct that browses all docs and finds oracle sets +0 to +10 points for GPT-4o (one -9) and predicted IPFunCall within 1-2.4 pts of oracle. AppWorld-UL cannot isolate it. Defensible statement: for GPT-4o with a <=16-API LLM predictor, the loss from imperfect prediction was small (<=2.4 pts for function calling); for DeepSeek-V3.2 with a trained retriever (C@16 .33) hard-hidden, gold exposure succeeded on 77% of tasks and the retrieved set on 38%, with 2x prompt tokens. Which regime applies to our predictor only our own records answer.
**(b) Model dependence.** TheMCPCompany is the only multi-model arm comparison: oracle-vs-search loss -2 (GPT-5) to -16 (gpt-5-mini) pts, oracle-tool recall 33-70%; ToolChoiceConfusion shows Haiku at 0.48 under all-tools (0.94 with CMTF) but Sonnet 4 at 1.00; LongFuncEval shows GPT-4o robust and 8B models not. Model dependence looks large but is not quantified for our models.
**(c) Code vs FC fair anywhere?** No. AppWorld's own and AppWorld-UL's comparisons differ in exposure (docs on demand vs predicted subset), prompting, and demos; the oracle test in the original paper shows the gap persists with identical APIs. The comparison measures whole scaffolds.

## Recommendations / changes
1. Reword the 2610 sentence: "no untrained structure that sees only the query (<=1 LLM call, base-size encoders) completes >10% at k=16 under a gold-plus-producers definition; a full-catalogue LLM predictor was not tested". Do not cite 21/21 vs 2/39 as causal.
2. Reconcile 13/19 (ours) vs 2/39 (there) by definition (gold vs gold+producers), hard hiding and model before claiming robustness to incompleteness.
3. Keep supervisor/credential APIs outside the 20-cap (2610 always exposes them; AWO login routines run in 98.2% of tasks; our GLM 0/22).
4. LiveMCPBench: "50% of Claude-Opus-4/Sonnet-4 failed trajectories"; k result is one model, single run, versus an 18.9-point rerun spread reported elsewhere.
5. AWO is a turn-reduction lever, not evidence for tool-list reduction; cost drivers are model-specific.
6. AppWorld-UL: say "most" and "I-TGC"; not a fair code-vs-FC comparison.
