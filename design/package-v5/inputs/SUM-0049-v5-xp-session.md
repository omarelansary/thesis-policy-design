## Per-idea section

### V5-R11 (log churn of the visible tool set and offered-set recall; oracle-registry ablation; failure decomposition)

- Published definition of churn: [F] not found. Grep of all `v5-xp-*` files for "churn", "offered-set", "offered set" returns nothing.
- Nearest published measures [F]: MemTool's Removal Ratio, "the proportion of tools successfully removed after being added", with a 3-turn window (2507.21428, 997-1005) and tool count per turn plotted (994-996). Tool Attention emits an `active_set` event per routing decision (2604.21816, 520-525), but defines no churn measure. Vanta reports cache-hit rate without a number (92-94).
- Offered-set recall equivalents [F]: Recall@K, "the proportion of target tools successfully retrieved within the top-K" and Completeness@K, 1 "if all target tools are included in the top-k" (ToolRet 527-535); Match@k, "any ground-truth capability appears in the top-k" (2608.22695, 268-273). [O] These are retrieval metrics on a single query, not per-turn recall of a persistent session set.
- Oracle ablation [F]: three stored pages replace an oracle tool set by a retrieved one: ToolRet 7.1 (GPT-3.5, ToolBench-G1, 50.60, down 11.40, 1531-1541); MCPVerse Table 4 (retrieve mode below oracle in the cells that can be trusted, 763-785, with the Claude row error above); ToolEx 4.4 (ToolEX-expanded above Oracle by 3.5-6.5 points, with the authors' caution, 813-817). [O] These three do not agree on direction: the oracle set is an upper bound in ToolRet and MCPVerse retrieve mode, but in MCPVerse Standard mode (all tools) Claude, Qwen3-235B-2507 and GLM-4.5 score above Oracle (565-567, 620-626 area), and ToolEX-expanded exceeds Oracle in ToolEx. 2608.22695 has no oracle ablation (grep).
- Failure decomposition [F]: LiveMCPBench Figure 7 (Retrieve Error 50.00%, Claude series trajectories, 1062-1067); Enrich-Retrieve-Rank 4.4 (retrieval vs reranking, 391-396); MemTool reports no failure decomposition of removal. [O] The categories differ (agent-run errors versus pipeline misses).
- [U] None of the stored pages decomposes failures into "tool never offered", "offered but not chosen", "chosen but misused" for a multi-turn session with a persistent set. LiveMCPBench's four categories are the closest.

### BR-1 (eviction of appended tools gated by the rewrite arithmetic)

- Does any stored page show eviction improving accuracy or cost? [F] No. Searched: all `v5-xp-*` files for "evict" (hits only: vLLM KV blocks, XPerf KV prefixes, an attention-eviction baseline in 2511.03728 line 1064, an Anthropic 5-minute cache-expiry comment at line 1053); MemTool read in full for its tables and discussion (no condition without removal, so removal's effect on accuracy or cost is not isolated). Vanta kept loaded tools and avoided disappearing tools (84). Tool Attention's LRU applies to cached schemas, in a simulation (453, 531). Anthropic context editing clears tool results, with a stated cache-write cost (118, 306), and the blog's 84% token reduction concerns that, with no stated baseline (context-management blog 39-40).
- Cost side [F]: removing or changing tool definitions invalidates cache. Anthropic: "Modifying tool definitions ... invalidates the entire cache" (prompt-caching 529). OpenAI: "changing the loaded tool set will break the model's cache from that point forward" (tool-search 2315); "Set tool_choice to none instead of removing the tool definitions" (prompt-caching 1576). Vanta: "Changing the toolset will invalidate cache for all messages that follow" (76). Write and read multipliers for GPT-5.6 and later are on lines 945-946 of the OpenAI page; the Anthropic multipliers are not in the pages I read for this batch.
- Anthropic's appended design [F]: the `tool_reference` block is appended and "The prefix is untouched" (tool-search-doc 258). [U] What removing a previously appended block does to the cache on Anthropic's side is not stated in the stored pages.
- Accuracy side [F]: MemTool Table 1 shows removal ratio and task completion by model and mode, but cannot separate eviction from other differences between modes. [O] In Autonomous mode GPT-o3's removal 0.941 comes with completion 0.90, GPT-4.1 Nano's 0.000 with 0.60, and Claude 3.5 Sonnet's 0.062 with 0.59 (731-734, 775-784); this is correlation across models with different abilities.
- Arithmetic gate: [U] no stored page defines or tests a break-even rule of the kind BR-1 describes. The nearest wording is Anthropic's `clear_at_least` "helps determine if context clearing is worth breaking your prompt cache" (context-editing 306), which applies to tool results.
- Not stored, not checked: the two GitHub issue reports (anecdotal) and the BFCL multi-turn categories. A conclusion on how real agents behave when tools are removed mid-session would have needed them.

### BR-8 (active-set metrics)

- [F] Published per-turn active-set measures in the stored pages: MemTool's tool count per turn, Avg Residual 3T ("average number of tools remaining after three turns", Table 1 caption 899-900) and removal ratio (2507.21428); Tool Attention's `active_set`, `phase1_tokens`, `phase2_tokens` events (2604.21816, 520-525) and effective context utilisation rho (a token ratio, measured, 573-575).
- [F] Active-set size and accuracy: Anthropic says "Claude's ability to pick the right tool degrades once you exceed 30-50 available tools" (tool-search-doc 65) as a vendor statement; MCPVerse reports that models with API tool-number limits drop sharply in Standard mode (631-634 area) while others improve; MemTool's authors set a 128-tool limit themselves (940-945). [O] These point in different directions on whether a larger visible set hurts; none of them tests it with set size varied alone.
- [U] No stored page reports offered-set recall per turn together with cost over a session.
