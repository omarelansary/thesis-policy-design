Which could serve P1, and what V5 would still build [I, my interpretation]:
- Serve the design: ATRBench (sessions, frozen memory, oracle arm, programmatic tool-level success, list and cache-discounted bill from measured hits); SWE-ContextBench (no-memory, free and oracle arms with cost per task); Letta Skills (none, given, must-find arms); ETAPP and MPT (tool calls conditioned on per-user history, with token counts).
- V5 would still build: a catalogue large enough that deferral matters; a returning-user generator whose tasks reuse earlier tools and a logged tool-use record; a gap model tied to cache lifetime; an offered-set recall and seed-hit-rate metric; and the bill from provider usage fields (cached, written, reasoning tokens). 5. ITEMS THAT CONTRADICT OR WARN AGAINST V5 CHOICES
- Memory often did not help or cost more: MemoryArena (E15), EvoMemBench at 128K (E16), MemoryBench (E17), SWE-ContextBench Free Summary below baseline (E23), VibeMemBench 11 of 12 pairings (E24), SWE-Bench-CL (E21, preliminary). These are against assuming M1-M3 pay; they support V5's position that P1 must test it.
- CTXbench (E22): a memory file raised cost about 20% and did not raise success significantly; tools named in it were used much more. Relevant for seeding: naming a tool makes it get used, so seed precision matters, and unneeded seeds may cost steps.
- A plain-file or full-context baseline matches memory systems on LoCoMo (E5, E7) and a verbatim log is close to hosted Mem0 on DreamBench-SWE (E25): supports a plain Markdown memory (V5-R05).
- LoCoMo as an accuracy gate is questionable (E4, E5).
- Memory write cost is large in at least three frameworks and excluded from per-query cost in the one paper that prices queries (E9): V5's W term should be counted explicitly.
