## 4. The landscape, slot by slot (checked claims; verdicts in brackets)

### 4.1 Prefix, tools array and where per-user content goes (S1, V5-R02, V5-R06, M3)
- **The vendors' own placement practice matches V5's rule within one user's prefix; sharing across users is a separate step (CH-0133).** Claude Code's documentation orders its cache layers with tool definitions in the system-prompt layer and CLAUDE.md, auto memory and rules in a later "project context" layer; "a change anywhere in the prefix recomputes everything after it" (A1 [C]); CLAUDE.md is "delivered as a user message after the system prompt" (A11 [C]); skills and commands "inject their instructions as user messages at the point of invocation" so nothing earlier changes (A5 [C]); because the system prompt embeds the auto-memory path, two directories build different prefixes and miss each other's cache, and the Agent SDK documents moving that path out of the system prompt to share caching across users (A8 [C]). Anthropic's engineering post: "static content first, dynamic content last", tools never added or removed mid-conversation, cache hit rate alerted on as an incident (F9 [C]). OpenAI: user-specific content at the end, keep tool definitions and their order consistent, restrict with `tool_choice`/`allowed_tools` instead of removing (F11 [C], not verbatim but every statement supported); **on the university route `allowed_tools` is rejected with HTTP 400** (`10` line 39), so that half of OpenAI's advice is not available there. Claude Code's own cache is scoped to one machine and directory (A8), so its practice shows placement within one user's sessions, not a prefix shared across users.
- **Order matters, not only content.** An open-source agent (Codex CLI) reported cache hit rates "below 1%" because MCP tools came out of a hash map in a different order each turn; the fix sorted them (B9 [C]; a later comment says the real cause was a map rebuilt on every call).
- **Self-hosted engines make the same rule mechanical.** vLLM hashes each KV block with the hash of everything before it and caches only full blocks (F16 [C]); so any per-user byte before the shared part changes every later block. This mechanism was already established in `13` (WD-050). [I] Block granularity can explain why cached counts come in block multiples in the human's probe (`10`), **not** why only 59-69% of a repeated prompt hit on some models (for example 3,296 of 5,574 tokens); that stays unexplained, and the university's serving engine is not known (CH-0133).
- **LiteLLM**, which fronts the university API, adds provider cache markers only when configured, for listed providers (F19 [P]); its own response cache is a separate exact-match layer (F20, lead).
- Memory placed **in the system prompt** (Letta memory blocks and MemFS, Oh My Pi's memory guidance, ReasoningBank) is fine for one user but, for a prefix shared across users, is what A8 warns against (C13, C14 leads; B11 [P]).

- **Deferral's own bill (CH-0134).** Anthropic's API still receives every deferred tool's full definition on every request, because it needs them server-side to run the search (F5, v5-ls-f02 line 244); whether those are billed is the open `05` P5 question, and this record does not settle it. Claude Code invalidates its cache when a denied tool is removed without tool search (A4, lead).

Reading: **STRENGTHENS** V5-R02, V5-R06 and M3's "append after the shared prefix". **CHANGE (small):** V5 says "never change the tools array" but not "serialize it identically every time"; B9 shows the second is a separate failure (proposal PL-1).

### 4.2 Memory read (M1, V5-R05)
- **Index in the prompt, entries on demand is the shipped shape.** Claude Code loads the first 200 lines or 25 KB of `MEMORY.md` (one line per memory) at session start and reads topic files on demand (A9 [C]); Kilo injects "a compact memory index" and recalls details with a tool (B1 [C]); Oh My Pi injects a summary within a 5,000-token budget (B11 [P]). Anthropic's API memory tool instead makes the model `view` its directory first (A14 [C]), i.e. a model-initiated read; V5's rule-based read at session start avoids that request [I].
- **A memory file costs tokens and changes behaviour.** In "Evaluating AGENTS.md", LLM-generated context files changed resolution by about -0.5% and -2% (not significant) while raising cost about 20% and 23%; developer-written files gave about +2.4% (not significant) at up to 19% more cost; tools named in the file were used about 1.6 times per instance against under 0.01 when not named (E22 [C]). [I] For seeding this cuts both ways: a seeded tool will be used, so a wrong seed is not harmless, and "the seeded tool was called" is not by itself evidence that the seed was right (CH-0127).
- **Memory can raise the bill a lot.** MemToolAgent's input tokens were 307,822 with memory against 72,345 without, on 50 queries over fewer than 40 tools, single run (D8 [C]).
- **A plain file is a reasonable baseline, but "plain" does not mean "no retrieval" (CH-0131).** Letta's filesystem agent "achieves" 74.0% on LoCoMo against 68.5% reported for Mem0's graph variant, and its files are embedded for semantic search (C12 [P], vendor; v5-ls-c09 line 22). In one independent testbed a graph memory scored lower and cost more than plain RAG or Mem0, and embedding-based Mem0 was the most accurate (C11 [P]: mem0 81.08%, RAG 78.31%, full context 77.16%, Graphiti 56.03%; TCO RAG $0.65, mem0 $5.43, Graphiti $6.95, full context $10.22). On the other side, as leads: with a 115k-token history Zep raised accuracy over full context (71.2% against 60.2%, C6); in a multi-session coding benchmark hosted Mem0 solved 97 of 180 against 82 for a verbatim log (E25); and MERIT finds "full replay is never economical" (F29; the lead read v5-ls-f20 lines 27-28).

Reading: **STRENGTHENS** V5-R05 and M1 (short summary plus index, full entries on request; plain Markdown first, per REQ-O21-09). It does **not** show that a retrieval-backed memory is worse; that comparison is left to the results V5's loop produces.

### 4.3 Memory write (W)
- **Products write in the background, after the session, gated.** Codex: memories off by default, generated in the background, skipping active or short-lived sessions, with a rate-limit gate (A22 [C]); Gemini CLI: sessions eligible only after three hours idle and at least 10 user messages, candidates held in an inbox for approval, experimental (A24 [C]); Oh My Pi: per-session extraction by the default model, then consolidation by a smaller model, skipping sessions active within 12 hours (B10 [C]).
- **Codex lets a deployment keep sessions that used MCP tools, web search or tool search out of memory generation** (A23 [C]; no reason or default stated). [I] Those are exactly the sessions V5's W learns from.
- **One vendor found model-driven rewriting destroyed information.** Mem0 replaced its ADD/UPDATE/DELETE reconciliation with a single ADD-only call because "Overwrites sometimes erased key information" and deletes "removed information that would be relevant later" (C3 [C], one vendor blog; the cost is that old and new facts both survive, so conflicts must be handled at read time). ACE keeps itemised entries with helpful/harmful counters merged by non-LLM logic (D22 [C]).
- **Writing everything hurts; a strict writer helps (CH-0128).** Adding every task to memory scored below a fixed memory bank on all four agents, and a strict (simulated-oracle) writer scored above it (D4 [P]); deletion shrank the bank with mixed effects (D5 [C]). Self-generated skills lowered pass rates by about 8 to 11 points while curated skills raised them about 16.6 (D27 [P], numbers from the stored v4).
- **A model-driven write pipeline can cost more than the memory saves** (these systems write every few turns; V5's W is at most one call per session, so the magnitudes do not transfer, only the warning that the write must be counted). "Total Recall at What Cost?": break-even against the full transcript ranges from the first tens of turns to never within 400 turns, no system wins on both cost and accuracy (F27 [P]; the main cost model counts input tokens without a cache split). MemoryTax: one memory system's build alone cost more than a full-context rollout (F28 [C], one conversation). MemoryAgentBench reports construction cost separately and excludes embedding indexing from per-query cost (E9 [P]).

Reading: **STRENGTHENS** "W at session end, rule or one cheap call". **CHANGE:** split W into a rule-based tool record written only from sessions that pass a gate, plus the short summary REQ-O21-03 asks for, and count its cost in the bill (proposals PL-2, PL-6).

### 4.4 Memory-informed offering (M2, M3): the gap, and the nearest work
- **Not found, in any of the seven searches:** a product, open-source agent, framework or paper that seeds tool definitions per user or role from a large catalogue at session start with the bill measured. This matches `03` section 5 and widens its search base; it is still "not found in the places searched".
- Nearest, each lacking a conjunct: Copilot's 13 core tools chosen "Based on tool usage statistics and performance data", population not stated, not per user as far as the page says (A21 [P]; its 94.5% coverage figure belongs to embedding routing, not to the core); Claude Code's MCP **discovery cache**, a per-user list of a server's tools saved from a previous session (a cache of the list, not of usage), on by default before v2.1.238 and now off by default without a stated reason (G17, lead; v5-ls-g11 lines 277-278, read by the lead); AutoTool, tool-to-tool transition statistics that skip model calls, not per user (D15, lead); Amp loads an MCP server's tools only when a skill is invoked, 17k to about 1.5k tokens, user-configured, no cache statement (A30 [C]); PEToolBench, per-user tool history choosing among 10 candidates, synthetic users, accuracy falling as history grows (D10 [C]); UserToolBench, 170 simulated tools, longer histories not better on most models (D11 [C]); PRefine on MPT, a 26-token per-user memory, 13 functions (D12 [C]); ETAPP, injects only the needed per-user preference categories, 35 APIs, with mixed effects on scores (E27 [P]); ToolSpectrum, "The more factors considered in personalization, the worse the performance" (D13, lead; v5-ls-d24 lines 767-768); ATRBench, 74 tools over sessions with cache-discounted costs (E13, already in `03`); Mem2ActBench, memory-dependent tool use where tool choice is near ceiling and parameters are the hard part (E12, lead). **Named by scout D but not read by anyone:** PrefTool (history-aware tool retrieval, EMNLP 2026 Findings, abstract only), DTDR (execution-history-conditioned retrieval, described second-hand), 2606.04703 and 2604.16968 (capability collapse and safety degradation from accumulated experience, snippets only). The gap statement is therefore bounded by these four unread items (CH-0130).
- **Memory size and cost:** a library-size threshold for selection accuracy, stable then dropping sharply as the library grows past about 30 (D28 [P], skills, synthetic libraries).
- **How much to inject.** Two or three skills were best in SkillsBench (D27 [P]); one retrieved experience was best in SWE-Exp (D24 [P]). "Inject once at the start" beat "always on" in one setting only, and on-demand retrieval beat both (D26 [P]). Remembered workflows wrapped as callable tools were used in 18.5% of tasks and did not raise task success (D17 [P]).

Reading: the gap **stands in the places searched**, bounded by the four unread items above. Contrary evidence for the idea itself: longer or richer personal context lowered tool-choice accuracy in three benchmarks (D10, D11, D13), and wrapped workflows were rarely used (D17). **New alternative to test:** usage-informed **retrieval** beside per-user **seeding** (PL-5).

### 4.5 Staleness and security of remembered tools (M2, S1, slot 8)
- **Validate at use, expire without reinforcement.** Copilot stores facts with citations and checks them against the current branch before use (G18 [C], vendor's own evaluation); memories expire after a period without reinforcement, **90 days by default, 7 to 180 configurable, reset when Copilot upvotes a memory, not on retrieval** (G20 **contradicted** as the scouts worded it: their "28 days, reset on use" is not on the stored page; v5-ls-g08 lines 149-155). Oh My Pi re-sends recalled memory unchanged on resume and adds a one-time note when a recalled memory was deleted, invalidated or changed (B12 [P]).
- **Changed tools hurt.** On MCP servers mutated by 11 operators, task-fulfilment scores fell from about 7.2 to about 6.2, early to late stage, for the two models the abstract names out of 12 (G24 [C]). A check by a whole-definition difference is "contract-free" in G25's sense, and such probes gave 40% false positives there, against none for checking only the assumptions a skill depends on (G25 [C]; CH-0135). The MCP specification has `listChanged` notifications but no versioning, hash or re-approval rule in the stored text (G16 [C], absence). Skill drift can be detected by checking the assumptions a skill depends on (G25 [C], skills, not MCP tools).
- **Memory as an attack path.** Untrusted content seen in a benign session can be stored and later act as instruction (G5 [C]); a write-time screen rejected 0 of 360 poisoned memories and a shipped provenance weight was indistinguishable from none (G10 [C]); binding authority to an entry's origin at write time is proposed with machine-checked theorems (G9 [C]; "up to 68%" is the success against existing defences). Biased preference text in memory shifted tool **parameters** (degradation 0.38-0.83 against 0.05-0.12), single-turn, selection not studied (D1, D2 [C]). Tool definitions themselves are attack surfaces (G14 [P], MCPTox). Against overweighting this, as leads: a replication found memory injection far less effective once legitimate memories exist (G4), and agents were hard to make overwrite their own memory files from untrusted content, the risk sitting in files others can edit (G7).

Reading: **STRENGTHENS** S1 as the bound on seeds. **CHANGE:** seeds are tool names from the S1 set only, checked against the current catalogue when seeded, and expire without reinforcement that is independent of the seed (PL-3); pooling across users, whether for per-role seeding or for retrieval, creates a cross-user write path that per-user seeding does not (PL-8, PL-5).

### 4.6 Cache economics for returning users (bill equation, D-02, `11`)
- Longer retention costs more to write: Anthropic 1-hour writes at 2x base input, 5-minute at 1.25x, reads 0.1x (0.05x and 0.025x on some models) (F2 [C]); OpenAI 30-minute writes at 1.25x, 12-hour at 2.5x, reads 0.1x or 0.05x; prewarming is billed (F11, F12 [C]). Gemini prices explicit-cache storage per million tokens per hour (F14 [C], Standard tier; some models allow implicit caching only). Anthropic checks at most 20 positions back from a breakpoint (F4 [C]; consecutive tool-use or tool-result runs count as one position).
- `11` and D-04 use a write ratio of 1.0 to 1.25 and no storage price.

Reading: **CHANGE (arithmetic only):** extend the D-04 grid with the long-retention write ratios (2.0, 2.5) and a storage-price variant, because a returning user's warm start is bought with exactly these (PL-6).

### 4.7 Evaluation (P1)
- No benchmark combines a large catalogue, sessions with a cache-relevant gap, a seed decision and cache fields (scout E's search; consistent with `03` section 9).
- Reusable designs: arms without memory, with agent-chosen memory and with oracle memory, with cost per task (SWE-ContextBench, E23 [P]: agent-chosen summaries scored below no memory in its Lite setting); none / given / must-find arms (Letta's skills benchmark, E19 [C], LLM-judged); construction cost reported beside query cost (E9 [P]); break-even counted in turns (F27 [P]). Memory systems often failed to beat simpler baselines (E24 [C], whose intervals all cross zero) and used more tokens (D25 [P]: from +16% for MemOS upward; the largest figure, +264%, is the BM25 retrieval baseline, not a memory method).

Reading: **STRENGTHENS** V5's position that memory-informed offering is not established and must be measured. **CHANGE:** add arms and measures to P1 (PL-7).

## 5. Corrections to the scouts (from the stewards)
- Copilot memory expiry: 90 days by default (7-180), reset on upvote, not on retrieval; not "28 days, reset on use" (G20, A20).

- Oh My Pi: the "does not alter the prompt-cache prefix" statement covers the `learn` call only (B11).
- Kilo's stored "memory bank" page is the AGENTS.md page carrying the deprecation notice (B4).

## 7. What stays unchanged, and limits
- **Examined here and not changed:** append-only discovery and the never-edit-the-tools-array rule (4.1), the deployment filter S1 (4.1, 4.5), plain Markdown memory first (4.2, per REQ-O21-09). **Not examined here, so neither confirmed nor changed (CH-0134):** the regimes and break-evens of D-01 (only the price grid is touched, PL-6), deferral's own bill (F5 is noted, P5 remains open), observation masking (the scouts' leads F8, F30, B23 and B25 were not checked), and the order of `05`.
- **Memory services (Mem0, Zep, Letta, Hindsight and similar):** not proposed as components.
