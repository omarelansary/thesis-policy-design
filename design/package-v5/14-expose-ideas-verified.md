## 3. Result per idea (checked unless marked)
### V5-R10 / EX-2: short entries first, full schema on request
- Vendors: Anthropic's search tool defers the whole definition and appends it on discovery without touching the prefix, so caching is preserved (X1, X2, X4 confirmed); OpenAI shows an individually deferred function's name and description with the schema deferred, appends discovered tools at the end, and warns that changing the loaded set breaks the cache from that point (X3 confirmed). Name-only, name-and-description and full-schema levels appear only as an unmeasured Anthropic suggestion (X5).
- Research: a two-stage name-and-description then schema flow raised precision and lowered recall in small models (X9); compressing schemas cuts about 44-57% of schema tokens and lifted accuracy only where the context budget binds (X10, X11, with one reported regression and the author's own benchmark); longer descriptions gave +5.85 points of success at +67.46% steps (X16), and what a description says mattered more than its length (X17). RAG-MCP and ScaleMCP report precision falling as registries grow (X13, X14).
- Against: the authors of 2511.03728 write that just-in-time schema loading "introduces a tool-selection bottleneck that can reduce the agent's" accuracy (line 746; a missed first-stage tool has no schema at argument time, line 533), and their own "Combined" variant trades recall for precision; their setting is small on-device models. Cost evidence: one vendor benchmark reports 2-3x more tool calls and about 50% more execution time for dynamic toolsets (X18). The 347-token name-and-description context against 2,120 minified tokens (X9) gives a fraction near 0.16 for a names-plus-description tier in that setting, which does not map onto D-03's 0.4 (CH-0124).
- **No checked source defines four fixed levels L0-L3 or measures them; the 0.4 compact fraction in D-03 still has no source.** The nearest measured cuts are the 44-57% above.
- Reuse (licence, language): Executor (MIT, TypeScript, search/describe/call) X19; langgraph-bigtool (MIT, Python, replaceable retrieval function) X20; TSCG (MIT, TypeScript) X11. Not usable as products on the university API: OpenRouter's tool search returns 400 for Chat Completions (X6); LiteLLM's tool-search page lists Anthropic-family providers only (X7, an absence in two stored pages); Pydantic AI's local fallback breaks the cache on Chat Completions (section 2). [I] The vendors' pattern (append discovered definitions at the end, never rewrite the prefix) agrees with V5's append-only choice, but **no stored page shows a client-side implementation of it on Chat Completions**. The human's probe (`10` section 7) shows that on GLM-5.3 one tool added at the end of the tools array rewrote 65% of the prompt, while gpt-oss and MiniMax-M3 kept almost all of theirs (unexplained). Whether a definition carried in a message becomes callable on the university route is untested (CH-0121).

### V5-R11 / BR-8 / EX-9: churn and recall logging, oracle ablation, failure split (SUM-0049)
- No stored page defines "churn" or "offered-set recall"; the nearest terms are Recall@K and Completeness@K (ToolRet), Match@k and MRR (Enrich-Retrieve-Rank) and MemTool's removal ratio. The thesis would define churn itself (1 minus overlap).
- Oracle conditions exist (ToolRet: retrieved tools lower pass rate, 50.60, down 11.40; MCPVerse Oracle/Standard/Retrieve, with the table error above) but the oracle is not always an upper bound (ToolEx: a retrieved set beat the annotated tools by 3.5-6.5 points). Failure splits exist in LiveMCPBench (Retrieve Error 50.00% of one small sample) and Enrich-Retrieve-Rank; none matches the exposé's four-way split.

### BR-1: evicting appended tools (SUM-0049)
- No stored page shows eviction improving accuracy or cost. MemTool measures whether models can remove tools (reasoning models 90-94%, some none) without a no-removal run. Vendors document that changing tool definitions breaks the cache from that point and offer `tool_choice: "none"` (OpenAI) and a minimum-saving gate for clearing tool results (Anthropic `clear_at_least`). A production blog reports cost down 48% while cache-hit rate fell with keep-and-append (its cache number is not given).

### EX-5: validation gate with expansion; no-match rule
- A reject-only gate exists (closed-world paper: the full stack executed 0 of 322 hallucinated calls, "by construction", and the paper calls its zero over-rejection a construction check, not a measured false-reject rate; the 15.25% of fabricated-argument trials that stay schema-valid, "irreducible", is a controlled ablation on a synthetic registry) Z6, CH-0117. Syntactically valid calls can still carry stale or wrong values (Z7, GPT-5 62.5% to 81.3% when prior values are restated). Validate-and-re-ask loops are in Instructor (MIT) and Pydantic AI and cost tokens and time per retry (Z11, Z12); `strict` enforcement is native on some hosted providers and ignored on others (Z12, Z13). A no-match threshold exists in semantic-router (MIT) only after calibration with labelled no-match examples (Z14). Models abstain poorly unprompted (best paired accuracy 59.5%, Z8); BFCL's irrelevance category is about 39% of its V2 Live entries, 10% of the V4 score, and an audit found defects in 48% of a 50-task sample (Z9, Z10).
- **Validation-triggered schema expansion was not found in the places searched.**

### BR-6: enriched searchable text
- The gains below come from bundled pipelines, not from enriched text alone (CH-0118): Toolshed's 46/56/47 points are its whole ensemble over BM25; Re-Invoke adds an online LLM intent extractor, so its gain is not purely offline; EasyTool's 15.0 to 52.8 is "Success", while its Pass rate moves from 62.3 to 69.8. Gains are real but mixed: Re-Invoke nDCG@5 0.6522 to 0.7821 on ToolE single (Z1, lead); Toolshed Recall@5 gains of 46%, 56%, 47% (Z3); EasyTool shortens documentation 70-97% and lifts success from 15.0 to 52.8 (Z4, partly); Tool2Vec (usage-query embeddings) beats description embeddings (Z5). Tool-DE: BM25s 36.41 to 39.35 but e5-mistral 40.02 to 38.85, documents 131.72 to 177.61 tokens, "semantic dilution" (Z2, lead; the Tool-DE authors call the dilution effect asymmetric and net-beneficial and give no reason for the e5-mistral drop, CH-0119).
- No checked paper reports the cost of generating the enriched text, so "one-time offline cost" in `09` remains an assumption.

### EX-4: hybrid retrieval plus reranking, client-side D
- ToolRet: generic rerankers give "limited and even negative improvements" (monoT5 33.83 to 28.92); BM25s with instructions is competitive (Z15, lead). ScaleMCP: hybrid sits below vector alone in the rows read; GPT-4o and Cohere reranking add 0.02-0.07 NDCG (Z16, with the row caveat). Dynamic ReAct prioritised vector-only methods over a BM25 hybrid (Z17). An industrial gateway (PayPal's SCOUT) fuses BM25 and dense by reciprocal rank fusion (Z18). MCP-Zero uses dense only (Z19). Hybrid weight and reranking are therefore things to measure, not settle.
- Reuse: ToolHive's optimizer accepts an OpenAI-compatible embedding service (Z22); LiteLLM's rerank follows the Cohere format, with the provider list in a separate table (Z23); ToolRet's benchmark repo and Tool-DE are Apache-2.0 (Z24).

### Cost of client-side discovery (the bill term)
- No checked source prices the extra request, the appended definitions and the cache effect together. Speakeasy reports tokens and dollars per task in one preliminary vendor run (Z21), but its token and dollar columns do not reconcile (1,300 tokens at $0.146 against 22,600 tokens at $0.065), so no conclusion about how savings vary with catalogue size is drawn from it (CH-0120); Tool Attention's dollar figures are projections (Z20).
