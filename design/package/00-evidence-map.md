## (a) Cost and caching: does fewer visible tools mean less cumulative or billed cost?
| Direction | Evidence | What it does not show |
|---|---|---|
| Visible-token savings can overstate billed savings | EXT-0016/0018 [F]: "cache reads are billed at 0.1x input price, the addressable saving from removing one delivered tool token is an order of magnitude smaller than nominal token counts suggest once that token has entered the cached prefix" (one Claude Code corpus). EXT-0015 [F]: harness base (system prompt + tool defs, not separable) = 71.6% of context, 92.0% of cache reads, 74.7% of cost in that corpus. EXT-0021 [F]: cache write 1.25x or 2x, read 0.1x (0.025x-0.05x on some models); EXT-0022 [F]: `tools` parameter and a tool-use system prompt are billed as input | The study is about tool-**output** compression (EXT-0016/0017), not schema filtering; tool defs are not separated from the system prompt; one harness/provider; the "order of magnitude" is the authors' inference |
| Changing the tool list can break the cache | EXT-0008 [F] (Anthropic): "Modifying tool definitions" invalidates the entire cache; EXT-0011 [F] (OpenAI): changing the loaded tool set "will break the model's cache from that point forward"; EXT-0014 [F] (MCP client guidance): adding or removing definitions mid-conversation invalidates the cache and "the resulting miss can cost more tokens than the definitions you removed" | Documentation statements, not measurements; sizes unknown |
| Discovery can be built to preserve the cache | EXT-0008/0009 [F] (Anthropic): discovered tools are appended inline as `tool_reference`; "The prefix is untouched, so prompt caching is preserved"; EXT-0010/0011 [F] (OpenAI): discovered tools "injected at the end of the context window". EXT-0014 [F]: append after the breakpoint, or route calls through a stable `call_tool` meta-tool | Vendor assertion; EXT-0009 [F] also says every deferred tool's full definition is still sent in the `tools` array on every request (what shrinks is model context, not the payload); OpenAI says the model still sees name and description of a deferred function, "in practice tool search is mostly deferring the parameter schema" (EXT-0010) |
| Discovery adds a step and may not pay at small catalogues | EXT-0012 [F] (OpenAI): "Discovery adds a step and depends on finding the relevant tool"; eager loading "unused definitions occupy context". EXT-0023 [F] (Speakeasy, vendor, "preliminary"): at 40 tools static initial tokens 43,300 vs 1,600 progressive, but the first-row simple-task cost is higher for progressive ($0.072 vs $0.045 as extracted; rows for larger toolsets were not reviewed by the lead) | Single vendor, small n, unreplicated (ledger C3-10) |
| Delivery method changes tokens a lot, confounded | EXT-0024 [F]: 7 vs 44 schemas per request, median 70,836 vs 216,986 tokens (x3.1); authors: "confounded ... a mechanism worth testing rather than one we have established" | One on-demand scaffolding, 4 vs 12 runs |
| A break-even form exists (skills, not tools) | EXT-0041 [F]: "net saving ~ (1 - p_i) s_i - (r - 1)(F + c + X) + r T"; "an accounting model, not a learned selector or a prospective performance guarantee"; reports cache reads at 0.1 | Skills, not tool catalogues; transfer to tools is an assumption (ledger C3-20) |
| Caching benefit itself | EXT-0019/0020 [F]: large reconstructed savings from caching a long system prompt in a deep-research workload, scaling with prompt size | Reconstructed from list prices, not billed; no tool-list changes studied |

[I] Reading: no stored source measures billed cost of catalogue filtering together with task success (ledger C3-19, bounded negative). The direction of "fewer exposed tools -> lower billed cost" is therefore **regime-dependent and unmeasured**: it depends on whether the exposed schemas are inside a cached prefix, how many turns re-read them, whether the restriction changes the prefix, and the extra turns discovery adds.

## (c) Discovery, recovery and initiation
- **Recovery can restore availability**: EXT-0035/0036 [F] (FitText, StableToolBench, GPT-5.4-mini): pass rate static query 57.6, single-pass 62.1, multi-turn re-retrieval 70.7, memetic 84.3; after a wrong first tool, correct-tool availability rises from ~7% (G2-category) to 44-83%. **Correction after the lead read the FitText method (EXT-0050/0051/0052):** my first label "system-initiated" was wrong or at best incomplete. EXT-0050 [F]: "at any step t, the agent may emit a pseudo-tool description dt, causing the system to update the function schema Ft+1 <- Ft U Retrieve(dt, T)"; EXT-0051 [F]: "thought node containing pseudo-tool description blocks, the system triggers a dynamic retrieval call"; i.e. the **model emits the retrieval request and the system executes it** (a model-initiated trigger with system-side retrieval, class S8-like, with the query written by the model from its context). EXT-0052 [F] also shows an observation-similarity trigger condition in an appendix about a search procedure with backtracking ("max SequenceSim(o, m) < 0.82 and ..."); the lead did not establish how that condition relates to the model-emitted mode, and it contains a numeric threshold that is FitText's own, not ours. **Resolved by EXT-0055 (FitText section 4.2, read by the lead after the challenger's CH-0019):** "retrieval fires whenever the agent's emitted thought contains a delimited pseudo-tool block that is not a near-duplicate of a previously explored intent (memory-based deduplication ...)"; the retrieval itself is embedding cosine top-k over the corpus, and the retrieved tools are injected into the function schema. EXT-0052 (condition "max SequenceSim(o, m) < 0.82 and o not subset of m for all m in M") is therefore, by section 4.2 and the notation of EXT-0056 (o = "LLM output", the emitted block; M = the tool memory of explored intents), a **near-duplicate filter on emitted blocks**, not a system-side relevance trigger. The prompts that make the model emit such blocks (Appendices B.1 and F) were not extracted: [U] how much of the "initiation" is produced by prompt design. So FitText is evidence for re-retrieval **given a model prompted to emit requests**, not for a purely system-side trigger. HYP-0006 and comparator P7 should not rest on it as "system-initiated". Limits (S4F, S4G; not re-read here): raw-query static baseline, LLM judge, simulated server, internal inconsistencies; token costs of the added retrievals are not in the extracted passage.
- **Models may not initiate**: EXT-0037 [F] (MCP-Atlas v3): "strong reasoning models refuse to invoke tools on a substantial fraction of failed tasks". EXT-0047/0048/0049 [F] (added after the challenger asked whether this means discovery tools or the task's own tools): `no_tool_use` is defined as "Answered from internal knowledge without calling any tool, even though tools were required"; Table 3 gives Claude Haiku 4.5 25.7% of diagnosed failures as No Tool Use (Opus 4.7 9.1%, Sonnet 4.5 6.4%, Gemini 3.1 Pro 1.6%); "40.1% of o3 Pro's failed trajectories contain no tool invocation". [I] It concerns the task's **own, already-visible** tools, not discovery or search tools; it shows that under-invocation exists when tools are exposed, and says nothing about whether models would call a search tool when a needed tool is absent. That second question is [U] in the stored corpus. EXT-0038 is the taxonomy only. EXT-0042 [F] (DynamicMCPBench e9.1, exploratory, n=50, one model): at budget 30 no task reached the budget; "the agent stops itself at ~5 successful calls out of 30 permitted"; this counts **against** the idea that the 12-call ceiling alone explains the long-bucket collapse, and shows self-stopping.
- **Removal without recovery loses recall**: EXT-0045/0046 [F] (on-device paper): JIT schema loading shifts "toward higher precision and lower recall"; "If the required tool is not selected in the first stage, its full schema is unavailable ... making subsequent recovery or pivoting more difficult."
- **Discovery costs a step**: EXT-0012 [F]; EXT-0009 [F] ("Keep your 3-5 most frequently used tools non-deferred so Claude can call them without searching first": a vendor design rule).

## (d) Staged / hierarchical / graded disclosure
- OpenAI exposes name+description and defers schema as its default graded form (EXT-0010 [F]); Speakeasy's progressive search is hierarchical list -> describe -> execute (EXT-0023 [F], vendor); Skill Blocks compares monolithic, tool, reference, hybrid-stub and block loading with "no universal winner" and a regime map (EXT-0039/0040 [F]; skills, same-provider, "paired tests detect no quality difference ... do not prove equivalence"). On-device ablation: Memory-Efficient vs Combined (JIT) are separable, with the precision/recall shift above (EXT-0045/0046).
- EXT-0053 [F] (DynamicMCPBench App. N, single attempts, 150 tasks, ~±8 pt Wilson intervals): curated (~8 tools) 37.3/42.7/44.0/54.0; rag:4 16.7-22.7; rag:16 24.0/33.3/31.3/38.0; rag:32 28.7/34.7/36.7/40.0; **hier (two-stage router: servers then tools)** 28.0/32.7/32.7/36.0; flat (1,168 schemas) 36.0 on one model. Read: hier is indistinguishable from rag:16-32 at that resolution, so this shows **no advantage of a two-stage router over a single retrieval stage** (nor a disadvantage); token costs are not in the extract. The authors also report that retrieval loss and distraction are separable, that on tasks whose tools the retriever never surfaced pass^3 is 0.0%, and that flat "still costs 8 points" despite no retrieval loss.
- EXT-0054 [F] (ITR ablation, weak source: model unnamed per S4F, authors' own numbers, abstract-vs-body mismatches noted in S4F): re-ranker off->on +3 pp API-success at +0 tokens/step; retrieval dense-only->hybrid +3. A retrieve-then-re-rank pipeline is two-step narrowing; the gain is small and the evidence is weak.
- [U] No extract here shows that **multiple filtering stages** beat a single stage on tools with task success and cumulative cost. Not extracted/not re-read in this thread: ITR, Tool Attention (ledger C3-28: its empirical statements conflict with its own text), TSCG, MemTool.

## (e) Signals and leakage
- ToolMenuBench's best method uses next-causal-frontier contracts and known state with fixed gold trajectories (EXT-0028/0029 [F]); keyword and state-aware variants did not beat all-tools (32.1 vs 22.1-24.0) in the same table. [I] A runtime policy cannot assume the contract/goal knowledge unless a legitimate source for it is shown.
- FitText's re-retrieval query is built from the agent's evolving context (EXT-0035/0036 [F]; hypotheses refined "against the corpus").
- Scoring side: DynamicMCPBench scorer is "deliberately conservative ... accuracies should be read as lower bounds" (EXT-0043 [F]); replay design limits in S4G section 2 (governing, not re-read in the original).
