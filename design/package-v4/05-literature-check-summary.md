### B. Do models use a search channel when a needed tool is absent? NOT ANSWERED for the exact question; evidence exists for the **instructed** channel
Three constructs of "absent" must be kept apart (CH-0061): (1) *hidden but discoverable* (in the catalogue, not visible; our setting); (2) *nonexistent* (no tool anywhere); (3) *visible but uncalled* (the model solves by hand or ignores a visible tool).
| Evidence | What it shows | What it does not show |
|---|---|---|
| TheMCPCompany (18,505 tools, 6 models, 175+17 tasks) | Retrieval is a tool the agent calls (embedding top-5); the system prompt **instructs** it ("you first have to find the tools that you need"). Retrieval attempts per Azure task 0.9-4.2 (primitive) and 1.1-8.7 (composite). GPT-5 reaches 42.29 with retrieval against 44.57 with an oracle tool set (close); GPT-5-mini 22.86 vs 38.86 (far); failure analysis of GPT-4.1 on 24 tasks: "missed tools" 12.5%, instruction drift 83.3% | no per-task distribution, no share of tasks with zero finder calls, no uninstructed condition |
| LiveMCPBench (70 servers, 527 tools, 12 models) | Two tools, route and execute; the prompt instructs use and the route description says to use it when "unable to solve them on your own"; average route calls per task 1.19 (Qwen3-32B) to 4.35 (Opus-4); retrieve errors 50.00% of failures for two models | instructed; no oracle condition; no distribution; text and table disagree in places (steward) |
| MCP-Zero | the request is instructed and every test item has a target tool; APIBank accuracy 97.60 -> 69.23 (schema injection) vs 95.19 (MCP-Zero) when the pool grows 40 times; prompt length cut 60-98% | no request rate |
| Vendor tool search | Anthropic internal tests report Opus 4 49% -> 74% with tool search (vendor-internal, no method; EXT-0074); "our models have primarily been trained to search those surfaces" (OpenAI, EXT-0010). The channel is provided; whether it is also instructed is not shown for vendors [U] | no rate, no method |
| SING (7,471 tools) | the agent's action set includes discover/invoke/respond, the first discovery request is formed by a prescribed decomposition | no initiation rate; prompt appendices not read |
| When2Call (arxiv-2504.18851) | with **no tool provided**, models choose "tool call" (hallucinated call) at 1.2%-67% depending on model: Llama 3.2 3B 52%, 3.1 8B 67%, 3.1 70B 57%, Qwen 2.5 21-23%, xLAM 8x22B 9.0%, GPT-4o 26% (18-item subset), tuned Mistral-NeMo-Minitron 1.2-1.9% | multiple-choice menu with "unable to answer"; **no search channel**; single turn; synthetic data |
| KAIST (arxiv-2406.12307) | with a wrong-but-similar tool visible, strong models often attempt it instead of abstaining; prompted yes/no recognition F1 ~87-89 (GPT-4), implicit variant 77.18 (3 models, one dataset) | no search channel; construct (2)/(3) |
| LOMEKWI section 6 (arxiv-2607.16961) | In a long-division task with up to 20 **visible** decoy tools and models under 35B, the **smallest** models probe tools freely (they cannot do the arithmetic), the **largest** mostly solve by hand: Qwen3.5 27B calls no tool in 154 of 180 episodes while 157 of 180 problems are solved by hand; the oracle tool is called in 2% of scored episodes (0.02 is oracle discovery, **not** success); told that exactly one tool solves the problem it rises to 0.60. | construct (3); a manual route exists, unlike our setting; the hint is an existence guarantee plus a candidate count, not a scope statement; Qwen only |

**Reading.** (i) For an **instructed** channel there is real evidence at catalogue scale that strong models use it and come close to oracle success (GPT-5 on 18,505 tools), at a measured cost premium, while weaker models fall far behind; that supports the *deployable* version of RA1 for strong models (**RA1a**: the model uses the channel when it is provided and instructed). (ii) **RA1b**, whether models use the channel *without* instruction, has no direct measurement. (iii) Models do call tools when none fits (When2Call) and when only a wrong one is visible (KAIST); that is a false-positive risk to be counted, not a prior against search. (iv) The residual question is narrow: with the catalogue fixed, how does the share of tasks with zero search calls change when the instruction is removed or the scope statement varies, per model, and what happens when the target tool is truly nonexistent.

### C. Cross-session tool memory: NOT ANSWERED for catalogue-scale discovery memory; related evidence exists
- Apple (arxiv 2607.09493): "tool configurations" are one of four bundled categories persisted across sessions; public study 0/12 (no memory), 12/12 (selective), 8/12 (full history), **single runs; the win is a formatting specification, not tool choice**; no component ablation.
- MemToolAgent (AWS, arxiv 2606.07909): stores past tool executions; WorkBench 57.56 -> 85.06; fewer than 40 tools; test queries share templates with the memory by design; single turn, not separate sessions.
- PREFINE (arxiv 2604.17886): multi-session, but stores argument preferences; memory-induced tool drift (arxiv 2605.24941): parameter values, tool selection explicitly excluded.
- Direction (weak): abstracting beats archiving full history in Apple and PREFINE. **This does not support "tool memory only" over conversation memory**: neither study compares those scopes (CH-0063).
- **Gap:** memory of which tools exist or were discovered in a catalogue too large to expose, measured by rediscovery steps, success or bill across sessions. Procedural or skill-memory work (surfaced by one search, not read) may bear on it [U].

## 2. What this changes
1. **The earlier claim "initiation is unmeasured" becomes two claims.** Instructed use is measured at scale for strong models; uninstructed use is not. This weakens the case that the whole discovery line rests on an unmeasured assumption, and sharpens what remains.
2. **Pilot 1 (cost and cache), reframed after CH-0066.** Not "read the cache fields". A defensible check is: the documented mechanism on one named provider and model, a stated TTL and breakpoint layout, full `usage` records of every call (including output tokens and discovery rounds) for a few matched trajectories with and without one appended block, cost per attempted and per successful task, whether deferred definitions are counted in `usage`, and the minimum-cacheable-length threshold (1,024-4,096 tokens by provider per the cache study; a small restricted prefix can fall under it). The claim is scoped to that provider, model, TTL and layout. Provider spread is large in the one multi-provider study (about 28-41% for Gemini versus 79-81% for GPT-5.2).
3. **Pilot 2 (initiation), reframed after CH-0062.** Keep the **tool-description-only** cell (search tool present, no scope statement, no hint) as the primary RA1b test; add a ladder (generic statement, catalogue-specific statement, explicit existence hint); pre-register a small set of statement wordings and a held-out task or catalogue split; charge the statement's tokens in the cost accounting; treat a catalogue-specific statement as partly exposing the catalogue; add an arm in which the target tool is **nonexistent** (When2Call-type false-positive calling) and one in which a wrong tool is visible. Report the per-task share with zero search calls, not only means. Two or more model families, including a strong and a weak one.
4. **Pilot 3 (memory)** stays a deferred hypothesis: no vehicle, no supporting design in the corpus.
5. **The thesis case.** Stronger: three specific, citable gaps (cache and bill behaviour of appended definitions; uninstructed initiation and its dependence on the scope statement, with false-positive calling as a counted cost; discovery memory in a large catalogue) and a measured cost premium of the retrieval route over an oracle that the design can aim to reduce. Weaker or unchanged: nothing here shows that any policy beats a vendor-style search-only arm; the "premium over oracle" is an upper bound; the instructed-channel evidence is for strong models.
6. **Corrections applied:** `01` section 4 last row (LOMEKWI rewritten), `04` sections 3, 4, 6, 7 (cache study, memory, stale sentences). The statement "no stored source evaluates cross-session tool memory" was replaced.

## 3. Round 3 (AUTH-013): what 16 more sources added
**Topic B, false-positive tool calling (steward 4a, `findings/SUM-0006`; challenger CH-0069/0070).** Still no source reports the exact rate (a model with a search or request channel it is not told to use, no visible tool fits). Every channel in the nine papers read is in the prompt, trained in, or absent. What exists instead are rates of **hallucinating, inventing or spuriously calling a tool when the right one is absent**, each with its own definition, **not interchangeable** (for one model the three constructs differ by up to 2x: Llama-3.1-8B 62.5 / 99.7 / 57.3, Qwen2.5-7B 34.8 / 54.7 / 34.8, DeepSeek-R1 17.6 / 42.6 / 26.5 for the Reasoning Trap's NTA, its DT, and Tool-Overuse's irrelevance-spurious share):
- The Reasoning Trap (arXiv 2510.22977), no-tool-available (NTA) task: the **queries name the missing tool** ("Please use the get_restaurant_address tool ...", file lines 1241-1248), the system prompt is "You are a helpful assistant." with no channel, and a response counts as hallucinated if it treats the missing tool as usable, **answers directly instead of via a tool result**, or invents a replacement (judge = DeepSeek-R1, which is also an evaluated model, lines 1519-1521). So it is a rate of *not honestly declining*, not of calling a tool when none fits. Values: Kimi-K2 Instruct 1.0%, Qwen3-8B (thinking off) 4.1%, DeepSeek-V3 10.8%, DeepSeek-R1 17.6%, Qwen2.5-7B Instruct 34.8%, Llama-3.1-8B Instruct 62.5%, Llama-3.1-8B R1-distill 96.3%; with one irrelevant tool provided 15.5% to 100%; Qwen3-4B goes from 3.4% (instruct) to 29.4% (thinking). [LLM-judged; a different setting from the next.]
- Tool-Overuse Illusion (arXiv 2604.19749): irrelevance detection over 10 models, authors' means 80.2% (frontier) and 62.5% (open-source), i.e. about 20% and 37.5% spurious calls when all given tools are irrelevant; the frontier mean reproduces only from five models including DeepSeek-R1, the open-source mean from five models of 3B to 32B; per-model spurious share 14.9% (Haiku) to 57.3% (Llama-3.1-8B); whether the setting is Python-interpreter-only is unclear in the text (limitation at line 1306 versus the BFCL-based setup at line 459).
- ToolBeHonest (14 models, 700 samples, 4-6 tools each) and ToolSandbox (34 tools) report scores for recognising unsolvable tasks, but the model is asked outright or given an exit tool, so the behaviour is prompted; ToolSandbox's category is a similarity score, not a rate.
- Prompted search-channel use by a small model: Llama-3.1-8B used a prompted `<search>` tool in 7.0% of GSM8K and 38.8% of MATH-500 problems (arXiv 2602.07213); the RL-trained Search-R1 7B searches on every query; Adapt-LLM's `<RET>` token is fine-tuned in.
- Direction for strong models is **not consistent across settings** (low in a no-tool setting for large instruct models, about 20% when irrelevant tools are visible); which applies to a hidden catalogue is not known. Several tables are ragged and one text-table mismatch exists (steward). No source gives a bill or cache effect.
- **Caveat on the earlier reading:** the "instructed channel at scale for strong models" evidence is TheMCPCompany and LiveMCPBench (pass 3), not the nine papers of this round, whose channel results are small models only.
**Topic A (steward 4b, `findings/SUM-0007`).** Nothing measures the billed or cache effect of definitions added or changed mid-session against a no-change alternative. CacheRouter (fixed core view plus a routing path, 11 tools) reports a token-level cache hit rate of 90.99% over 55 queries and 95.2% over a 30-turn dialogue, priced at about 12% and 8% of a no-cache baseline using one provider's stated hit:miss ratio (computed, not billed), and calls itself a feasibility check with no baseline arm. Code-mode token claims: a vendor blog reports 75.1M to 5.4M input tokens (-92.8%) and an estimated cost of $377 to $29 (-92.2%) at 508 tools, with a pass rate of 100% in both configurations (the number of queries, the models and the method are not stated in the stored text; smaller rounds in the same article: -58.2% at 96 tools and -84.5% at 251 tools; author at the vendor); the one independent test is narrow (63 tools, GPT-4.1, 2 tasks x 50 runs, 15,417 to 3,310 input tokens, -78.5%, output tokens 87 to 192, total tokens -77.4%, estimated cost reduction about 70%, caches cleared, the tested server's vendor subscribes to the benchmarker). ReCache is self-hosted KV reuse (no provider billing). **Gap unchanged.**

**Round 5 (steward 4d, `findings/SUM-0009` = FND-0007; not challenged).**
- *Topic B, the nearest "knowing versus doing" measurement:* "Model-Adaptive Tool Necessity Reveals the Knowing-Doing Gap in LLM Tool Use" (arXiv 2605.14038). Four small open-weight models (Qwen3-8B, Qwen3-4B, Llama-3.1-8B, Llama-3.2-3B), **one visible tool** (a calculator for 4,000 synthetic arithmetic items, a search API for 817 TruthfulQA items). "Tool-necessary" is defined per model as failing at least once in 10 tool-free runs at T=0.7, which inflates the necessary set. The headline 26.5%-54.0% is the mismatch column ("Mis." = necessary-but-not-called plus unnecessary-but-called) for arithmetic only; TruthfulQA 30.8%-41.8%; it mixes over- and under-calling (Qwen3-8B over-calls, the other three under-call). The steward's own arithmetic from the counts: the share of tool-necessary queries **not** called is 24%, 70%, 74%, 75% on arithmetic and 68%, 60%, 57%, 74% on TruthfulQA; a prompted yes/no self-assessment changes behaviour on 18-49% of samples. **Small models, one visible tool, no hidden catalogue, no search channel**; it still shows that recognising a need does not guarantee acting on it, which is a risk for RA1, not a rate for it.
- *Topic A, pool size and token cost:* AutoTailor (arXiv 2609.13548): 106 WebArena Postmill tasks, one model (Claude Opus 4.8); cutting the API pool from 1,283 to 33 reduces tooling request tokens per task from 2.78 million to 142.86 thousand without a ReAct fallback; with the fallback, correctness 90.6% versus 87.5% for ReAct alone and total request-token cost down 57.8%. Token counts only (no dollars, no cache pricing); reselection happens between tasks on a templated, stable task distribution; the authors caution against reading it as production behaviour.
- *MCP-Universe (arXiv 2508.14704):* 231 tasks, 11 servers, 133 tools, no tool-search ablation and no cost numbers; adding unrelated servers (7 servers, 94 tools) lowered success in the cells the authors report (for example 22.22 to 11.11 for Claude on Location Navigation, 40.00 to 35.00 for GPT-4.1 on Financial Analysis; per-domain samples of roughly 9-45 tasks, so differences are a few tasks; two bars in the flattened figure values appear to rise).
- *Cost convention:* Artificial Analysis's coding-agent benchmark states a cost model with standard input, discounted cached input, separate cache-write charges and output; StackOne (vendor explainer, nothing measured) states the same bill formula and relays OpenAI's guidance to keep tool definitions stable and use allowed-tools or tool_choice instead of deleting definitions. Neither measures the share of tool-definition tokens.

**Saturation.** Across 27 searches the same papers recur (LiveMCPBench, ScaleMCP, When2Call, MCP-Zero) and three differently worded queries found no third-party measurement of vendor tool search or of appended-definition cache behaviour, nor an uninstructed initiation rate. That **does not exclude** the three gaps by this sample, and the recurrence measures what a search engine ranks, not coverage: round 3 alone found nine papers on false-positive and overuse behaviour that rounds 1-2 had missed, and each gap is a conjunction of absent elements (instruction removed, hidden catalogue, rate reported, bill reported), which is weak evidence of absence. The sample is search-engine driven, recent preprints dominate, and vocabulary may differ ("agentic retrieval", "function hallucination", "tool abstention"). Say "not found in this sample", never "does not exist". CacheRouter's self-reported "tool evolution" A/B is a weak observation; the accurate phrase is "no independent, billed, baseline-controlled measurement".

## 4. What this changes in section 2
- Pilot 2 gains arms, but they must be defined for **our** setting, where a search call is the *correct* action when the target exists in the hidden catalogue (CH-0072). The counted events must be defined separately: (i) a search or request call, (ii) a call to a domain tool, (iii) a direct answer without a tool. Arms: *target hidden but present* (the correct event is (i) then (ii)); *target nonexistent, search channel present* (the correct event is a decline after searching); *no channel at all* (the Reasoning Trap's NTA, where any tool call or invented tool is the error); *a wrong tool visible* (KAIST, Tool-Overuse). The published rates (1-96%, 15-57%) are **reference points with different definitions**, not targets; scoring should be rule-based, not by an LLM judge that is also a candidate model. A rule that every arm needs a model with a published rate cannot be met for strong closed models and is dropped.
- A cost accounting for false-positive calls (wasted rounds, invented tool names) belongs in the bill; none of the papers prices it.
- The vendor and code-mode token claims are reductions in **input tokens**, with output tokens rising in the one independent test; the bill, not tokens alone, is the quantity the supervisor asked about, and none of these sources measures it.
