# Safeguards: what is enforced, what is only instructed, what was tested

Read this before trusting any "isolation" claim. **This workspace is not a sandbox.** Native Windows Claude Code has no OS-level sandboxing; every control below is a Claude Code permission rule, a deterministic hook, an instruction, or an after-the-fact check. A determined or careless session that runs arbitrary code can get around the hook layer (see "Known bypasses"). Findings from the independent review (`reviews/RV-0001.md`, thread T-20261016-91) that were confirmed by execution or by reading the cited file are marked "RV-0001 Dn".

Legend: **P** = permission rule in `.claude/settings.json` (evaluated before the model acts; deny rules also hold under `bypassPermissions`). **H** = PreToolUse hook `tools/guard.py` (deterministic, fires for the lead and for every subagent, fails closed). **I** = instruction only (CLAUDE.md, agent definitions, PROTOCOL; the model is asked to comply). **D** = detective (`tools/verify_workspace.py` reports it afterwards; nothing prevents it).

## Known bypasses and unverified items
- **The hook layer can be switched off by configuration (confirmed, C7, CLI 2.1.300).** A project-local `.claude/settings.local.json` containing `{"disableAllHooks": true}` made `echo ...research-cleanroom` execute that the guard had blocked in the control run. The same setting could be written at user level or in `settings.json` by anyone who can edit those files. What still holds without hooks: permission deny rules (C8: a Bash write to `settings.local.json` was denied with hooks disabled), the env model pin, agent definitions. What does not: path guard, ownership, immutability, SendMessage rules and the message cap. Consequences: (a) the deny rules are the second layer and must not be thinned; (b) `verify` (pin, `settings.local.json` check) is the detector; (c) **every session must run `python tools/verify_workspace.py --quick` first and stop on any FAIL**, which is instruction-level for the lead. User-level settings (`~/.claude/settings.json`) are outside the workspace and are not checked.
- **Interpreter-built paths** (confirmed, A1): `python -c` building the origin path from fragments read a harmless origin file. The origin boundary holds against honest or careless sessions, not against an adversarial one. Closing it needs an OS sandbox or a user account without access to the origin; neither was set up (not authorized, not available natively).
- **Bash writes bypass ownership and immutability** (by construction).
- **Edit tool** was tested only indirectly: an Edit no-op was rejected by the tool before the hook ran (C1); the hook's Edit branch is covered by Write tests and `guard_cases.py`, not by a live Edit.
- **All live tests ran in `-p` mode in a not-yet-trusted project folder.** Claude Code printed on every run: "Ignoring 7 permissions.allow entries from .claude/settings.json: this workspace has not been trusted." Observed in that state: deny rules, the hook, the env model pin and the agent definitions all took effect. Not observed: behavior after the interactive trust dialog (allow entries then apply), and whether hooks/settings behave the same interactively or in VS Code (**unverified**). Consequence: on first open, accept the trust dialog, check `/hooks` and `/permissions`, and run `python tools/verify_workspace.py --quick`. Before trust, the steward's Bash is not pre-approved (it was denied in R, RV-0001 D25).
- **VS Code runtime, observed 2026-10-16 (after the bootstrap; readiness assessment and thread T-20261016-92):** the guard blocked an out-of-workspace Read, a PowerShell command containing "settings.local" (a false positive on a read-only existence check; safe side) and a SendMessage with no active thread, so the hook layer is live there. The Agent tool returned ids of the form `a` + 16 hex characters, which the guard accepts; lead -> agent and agent -> agent sends and the reply leg worked; the evidence-steward's Bash ran `python tools/verify_workspace.py --quick` without a denial (permission mode not visible from inside the session). Agents' final reports reach the lead through a separate hand-back channel that the guard does not match and the cap does not count. **Not observed in VS Code:** the deny rules (exercising them means attempting a forbidden read), user-level settings, behaviour after the trust dialog, an idle agent resumed by a *peer* message, three-agent threads, agent teams.
- **Native agent teams** (shared task list, teammate mailbox): not enabled, **unverified interactively**. With `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1` under `-p`, no team-creation tool appeared; the Agent tool gained a `name` parameter and lead->agent and agent->agent sends by name were accepted; the reply leg was not confirmed (C5b). See WD-004. Names are refused by the SendMessage rule, so enabling teams needs a deliberate guard change.
- **Peer sessions**: `ListAgents` lists other Claude sessions on the machine (including the origin's). Item 10 blocks this workspace's agents from messaging them by name or session ref. Nothing stops another session from messaging this one; such a message is not an authorization.
- **Lead discipline**: the lead edited `ops/STATE.md` during test B against its own thread rules (caught by git, reverted); in R the lead declined a risky workaround correctly. Only git and review catch lead errors.
- **Not tested**: adversarial prompt injection through evidence text; two threads at once; `bypassPermissions` with the hook disabled; Windows 8.3 short-name aliases; whether the guard's `cwd` field is always present for subagents (the guard falls back to the workspace root).
