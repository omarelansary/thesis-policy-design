### 1. Mem2ActBench (M2A), topic C
1. Measured: [F] synthetic benchmark; "synthesizes 2,029 sessions with 12 user-assistant-tool turns on average", "400 tool-use tasks", "429 sessions used" (M2A:34-40, 637). Backbone for generation Qwen3-Next-80B-A3B-Instruct (M2A:554); evaluation backbones Qwen2.5-7B/32B/72B (M2A:651-653); seven memory systems (M2A:641-648). Memory content: persistent user preferences and task states within a conversation history; the thing to be picked is the tool call (tool plus parameters). Catalogue: not stated as a catalogue; candidate set tested at N in {1, 2, 5} tools (M2A:1034-1036). Main results "provide the ground-truth tool" (M2A:670-676), so tool choice is controlled away.
2. Numbers: [F] "TA stays tightly clustered (~87-97%)" (M2A:679-681); "mean F1 increases from 20.4 (7B) to 28.9 (72B)" (M2A:684-686). Retrieval ablation Table 4 (M2A:896-956, read by row order Strategy / Recall@k / F1 / BLEU / TSA): No Retrieval F1 10.0, TSA 73.8 (M2A:906-910); Hybrid k=5 F1 30.7, TSA 86.0 (M2A:938-946); Oracle F1 53.8, TSA 88.2 (M2A:951-956). [F] "oracle retrieval boosts performance to F1 ~53.8, creating a gap of over 23 F1 points" (M2A:713-716). Tool selection, Table 5: random negatives TSA 94.50 / 95.50 / 93.50 for N=1/2/5; hard negatives 94.50 / 78.00 / 69.75 (M2A:1045-1066; read by block order). [F] "agentic frameworks exhibit negligible tool selection errors, while a passive retrieval baseline shows a noticeable fraction of tool-selection failures" (M2A:1136-1140).
3. Limits: authors: "limited to offline tool-call generation, using a fixed backbone model family ... excludes interactive execution settings" (M2A:1176-1182); synthetic generation (M2A:1183-1185). Mine: [O] Table 3 (per-method, per-size) is a column-scrambled extraction (M2A:880-895); I did not read cell values from it. [O] Tool choice is mostly held fixed; the memory effect on tool choice is measured only via TSA in Tables 4-5 (1-5 candidates). [O] Memory here is about user parameter preferences, not about which tools exist or which tool worked.
4. Relevance: PARTIAL for Topic C. It is a measured effect of memory on tool-call correctness across sessions, but with 1-5 candidate tools, parameter grounding, not discovery of tools in a large catalogue, synthetic data, one model family. Indirectly: no retrieval TSA 73.8 vs oracle 88.2 is an effect of memory on tool choice in a small candidate set.

### 3. ToolRet (TR), topic A-adjacent (catalogue retrieval) and C-adjacent
1. Measured: [F] "7.6k diverse retrieval tasks, and a corpus of 43k tools" (TR:28-29), six types of retrieval models (TR:30). End-to-end part: ToolBench tasks, GPT-3.5 and ToolLlama, the "official Pass Rate" (TR:1527-1530, 1675-1677, 4039-4046); for each ToolBench task the pre-annotated toolset (oracle) is replaced by tools retrieved from the 43,000-tool corpus (TR:4043-4045). The retrieved set is pre-supplied; the agent does not itself search.
2. Numbers: [F] best model "achieves an nDCG@10 of only 33.83" (TR:139-142). [F] "all retrievers in our experiments achieve less than 35% in Completeness@10 and under 52% in recall@10" (TR:1001-1003). [F] "in ToolBench-G1, GPT-3.5 achieves a pass rate of 50.60 using tools retrieved by bge-large, decreasing by 11.40" (TR:1539-1541), i.e. from an oracle of 62.00 (Figure 6 label TR:1625). Intro pilot figure labels: "64.2" oracle, "decrease 10.1", "only 27.3 recall@10" (TR:69-77; figure text, not sentence). [F] "Poor retrieval leads to poor tool-use agents" (TR:1532); training the retrievers raises pass rate (TR:1677-1680). Table 15 pass rates are ragged in the extraction (TR:4700-4765); I did not read pass-rate cells by column.
3. Limits: authors: English text only; "insufficient investigation of prompt sensitivity" (TR:1809-1823); [F] one-to-many problem: a query's ground truth is one annotated tool though similar ones may also work (TR:1707-1713). Mine: [O] older models (GPT-3.5, ToolLlama); pass rate is a ToolBench measure; no cost or tokens; the effect is of retrieval quality at a fixed retrieved-set size, not of an agent-initiated search.
4. Relevance: PARTIAL. It is a measured link between retrieval quality over a very large (43k) catalogue and task pass rate, which touches "the agent must find tools it cannot see", but retrieval is system-side and pre-supplied, models are dated, there is no billing and no cache.

### 4. AIMultiple code execution with MCP (AIM), vendor-adjacent benchmark article
1. Measured: [F] two tasks, "We run each task 50 times for each approach" (AIM:179); both are the same page (aimultiple.com/open-source-embedding-models) lookups (AIM:181-183); Bright Data's MCP Server "Pro Mode", GPT-4.1 (AIM:156, 186); regular arm: LangGraph ReAct agent "has access to all 63 tool definitions" (AIM:190); code arm: "only tool names and truncated descriptions (60 characters) are included in the system prompt" (AIM:193). "We cleared any cached data and ensured a fresh MCP server connection per run" (AIM:187).
2. Numbers: [F] Avg input tokens 15,417 vs 3,310 (-78.5%); avg output 87 vs 192 (+120%); total all tokens 775,197 vs 175,081 (-77.4%); success rate 100% vs 100%; latency 9.66s vs 10.37s (+7%) (AIM:100-146; table cells read in row order). [F] "Estimated ~70% cost reduction with code execution" (AIM:172), an estimate, no price table shown in the lines I read. [F] "Higher output tokens: Code execution approach uses 2.2x more output tokens" (AIM:164).
3. Limits: authors: "Only 2 query types tested", "Only tested with GPT-4.1", code quality may reduce success on complex tasks (AIM:196-200). Mine: [O] 63-tool catalogue is one server; [O] the runs are single-task page lookups with ~4-5 steps (inferred from 87 output tokens/call, not stated); [O] caches were cleared, so no cache effect could appear; [F] disclosure: "Subscribers of AIMultiple's benchmarking services in Model Context Protocol include Bright Data" (AIM:378), and Bright Data is the server tested (AIM:156). [O] Whether the model discovered tools by listing is not what is measured: the code arm gets names in the prompt.
4. Relevance: PARTIAL. Same family of "keep definitions out of the prompt" design with token counts, but the code arm still lists all 63 tool names in the prompt, the tasks are trivial, one model, one server, no cache; token savings are from input tokens with caching switched off.

### 6. CacheRouter (EXT-0108, EXT-0110, EXT-0111, EXT-0112), topic A
1. Measured: [F] "A prototype implementation was exercised on 55 functional queries and a 30-turn dialogue" (EXT-0108 abstract). Both the main model and routing sub-model "call the DeepSeek API"; "11 tools distributed across five tool packages" loaded in Experiments 1-8 (EXT-0111); a fixed core set visible to the main model plus a router pseudo-tool that searches the full list and executes the tool in an independent channel (EXT-0108, EXT-0110). The 30-turn dialogue had "30 common-knowledge and arithmetic queries", "the first-round prompt grows monotonically from 958 tokens for Q1 to 2,483 tokens for Q30" (EXT-0112).
2. Numbers: [F] Table 9: "Input tokens (cache hit) 1,424,768", "(cache miss) 141,098", "Token-level cache hit rate 90.99%" (EXT-0112). Table 10: "Token-level cache hit rate 95.2% (227,200 / 238,701)", "Input cost after caching (1:30 pricing) about 8.0% of the no-cache baseline", "Router calls 1 (Q20)" (EXT-0112). Billing: "the billing ratio between cache-hit and cache-miss input tokens is about 1:30", cost after caching "(1 - h) + h/30 of the no-cache baseline" (EXT-0111). Also [F] "The Router was invoked 40 times" over the 55 queries and unanswerable queries "fell back honestly in 5/5 cases" (EXT-0112). [O] The 30-turn test queries are common-knowledge and arithmetic with one router call (EXT-0112), so in it the long-tail tool set is hardly exercised.
3. Limits: authors: "The evaluation is a feasibility check of the design, not a benchmark against other systems: the query set is modest ... the reported numbers are descriptive rather than significance tests" (EXT-0111). "This is an architectural guarantee about the request structure, not a promise about the actual hit rate" (EXT-0111). "no specific server-side hit rate is promised" (EXT-0112). Mine: [O] In the lines I read there is no arm in which tool definitions are added, changed or dynamically selected in the main request, so no hit rate for that alternative; the 90.99% and 95.2% are for the design itself; the cost figures are computed from a stated 1:30 ratio, not from billing statements. [O] The cost percentages are against a "no-cache baseline", not against a cached full-catalogue baseline. [O] Only 11 tools, so no catalogue-scale test. Experiment 3 (A/B cold-start comparison, "confirms the prefix stays stable across gateway restarts and tool evolution", EXT-0112) is described in a sentence only; I did not read it.
4. Relevance: PARTIAL for topic A. Same problem statement (a changing tool list invalidates the prefix, EXT-0108 abstract) and a measured cache hit rate and priced cost for a design that avoids changing the prefix; it does NOT measure the billed cost of definitions added or changed mid-session. Not independent of the authors' design (no baseline). Also: the main model must itself decide to call the router when "the current core tool set is insufficient" (EXT-0110); the 40 router calls in 55 queries are counted but I did not read whether any was spurious.

### 7. ReCache (EXT-0109, EXT-0113), topic A (KV cache in self-hosted inference)
1. Measured: [F] "benchmark assembled from seven public tool- and skill-use datasets, including resource-disjoint tests" (EXT-0109); Qwen3 backbones, end-to-end mainly Qwen3-4B (EXT-0113 Limitations). Metrics: Inv-F1, ID-F1, hallucination rate, TTFT, TPOT, attention latency, KV memory (EXT-0113 Tables 2-4, Figure 4). It is about open-weight inference with fine-tuning ("lightweight fine-tuning adapts the model", EXT-0109), not about provider-billed prefix caching.
2. Numbers: [F] "Resource-wise attention matches dense invocation performance (82.3% versus 82.4% Inv-F1) while providing a 3.655x time-to-first-token speedup. The complete framework reduces allocated KV-tensor memory by 92.43% and accelerates attention by 1.423x" (EXT-0109 abstract). [F] "Dense TTFT increases from tens of milliseconds to over 5,000 ms as resource contexts expand, whereas Omega_full maintains TTFT below 50 ms" (EXT-0113). Out-of-distribution: ReCache Inv-F1 60.8 (TOOD) vs Dense, "97.5% and 91.8% of performance of Dense" (EXT-0113). No dollar or provider-billed-token number.
3. Limits: authors: two Qwen3 backbones, mostly 4B; "full-parameter fine-tuning of larger models was beyond the computational budget" (EXT-0113). Mine: [O] reuse requires changing the model's attention and fine-tuning, so it is not something an agent calling a hosted API can apply; I did not read the remainder of the Limitations (cut off at the page end in my extract).
4. Relevance: NOT RELEVANT to billed cost with hosted providers; PARTIAL as context only: it confirms that standard prefix caching "requires reused content to form an identical prefix, which rarely holds for dynamically composed resource contexts" (EXT-0109 introduction), which is the authors' assertion, supported there by citations, not by a measurement of their own in the text I read.

## Topic A update (cost and cache behaviour of definitions added or changed mid-session)
- [F] No source in this batch measures the billed cost, or provider cache hit rate, of definitions added or changed mid-session against an alternative in which they are not. CacheRouter (EXT-0108/0111/0112) measures hit rates of 90.99% (55 queries) and 95.2% (30 turns) for a design that keeps the main request's tool list fixed, with a priced cost of about 12.0% and 8.0% of a no-cache baseline on DeepSeek's 1:30 ratio; its own text says the 30-turn run had one router call (EXT-0112) and that nothing is promised about the real hit rate (EXT-0111). The sentence stating the premise ("every change to the visible tool list invalidates the cached prefix", EXT-0108) is an assertion in the abstract; I read no measurement of it.
- [F] Bifrost (BIF:53-55) and AIMultiple (AIM:100-146) give input-token reductions (-92.8% at 508 tools; -78.5% at 63 tools) but neither models caching: AIM cleared caches (AIM:187); BIF does not mention caching. These are token counts, not billing under caching.
- [F] ReCache (EXT-0109/0113) concerns KV reuse in self-hosted inference: TTFT and memory, not provider billing.
- [O] So, for the lead's sentence "appended-definition cache behaviour has no independent measurement": nothing in this batch contradicts it. CacheRouter is a measurement by its own authors of a different design (fixed prefix), not of appended definitions.

## Topic C update (persisted memory and tool choice across sessions in a large catalogue)
- [F] M2A (M2A:896-956, 1045-1066) is the nearest measurement: retrieval from long-term memory changes tool selection accuracy (TSA 73.8 with no retrieval; 86.0 to 90.2 passive; 88.2 oracle) and parameter F1 (10.0 to 53.8 oracle), but with a candidate set of 1, 2 or 5 tools, synthetic sessions, Qwen2.5 and a fixed backbone family, offline generation.
- [F] MEMORA has no tool component (keyword search only; results section not read).
- [F] TR (TR:1539-1541, 4043-4045) measures a 43k-tool corpus and a pass-rate drop (62.00 to 50.60 for GPT-3.5 on ToolBench-G1) from retrieved vs oracle toolsets, but there is no memory and no repeated sessions.
- [O] Nothing here measures whether a memory of earlier discoveries (which tools were found or worked) changes tool choice in a large catalogue. The lead's sentence "discovery memory in a large catalogue is unmeasured" is not contradicted. M2A is a related effect at small scale and should be cited with its limits.
