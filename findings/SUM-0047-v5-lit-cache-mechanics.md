## 2. The five probe facts

Probe numbers are the human's measurements (doc 10, s2, s7, s9) [O]. The serving stack behind each university model is not stated in doc 10 [U]; so which source describes it is not known, and every link below from a source to a model is [I].

### Fact 1. Cached counts are multiples of a block (16 gpt-oss-120b, 64 GLM-5.3, 128 MiniMax-M3)
- Predicted by stored sources: block-granular caching with a fixed block size is stated by vLLM ("We only cache full blocks." L31; default block size 16, PagedAttention L1781), Mooncake (block size 512, L507), LMCache (256-token chunks, L591-593) and OpenAI (multiple of 128 for earlier models, L123). 16 equals the vLLM default and 128 equals the OpenAI rounding [I: coincidence of numbers, no source ties either to these models].
- Contradicted or not matching: SGLang default page size 1 (args L218; RadixAttention "one token" L262), which would give no block pattern unless configured. 512 (Mooncake) and 256 (LMCache) match none of the three. Qwen's multiple of 32 (doc 10 L32) is also unmatched.
- Hybrid note: vLLM raises attention block size for Mamba plus attention hybrids (hybrid L157-161) and lists "Minimax" among them (L21). [I] This is a possible reason a model's block size is not 16; the sources do not say it for MiniMax-M3, 64 or 128.
- Not predicted by any stored source: why 64 for GLM-5.3 and 128 for MiniMax-M3 and GLM-5.3-Flash; why different models on one route differ; that MiniMax-M3 "created" a 128-token block on every request.

### Fact 2. Plain prefix behaviour on GLM-5.3 and MiniMax-M3; tools first on GLM-5.3, system first on MiniMax-M3
- Predicted: a hit requires the whole preceding prefix to match, so a change invalidates everything after it: vLLM hash chain (L13, L21), SGLang radix tree over token sequences (L260), Mooncake chained hashes (L760-762), DeepSeek ("only matches the prefix part", L88), OpenAI "longest matching cached prefix" (L67). The probe is consistent with all of these [I].
- Not matching: CacheBlend (non-prefix reuse, L43, L201). No evidence in doc 10 that this route uses it [I].
- Position of tools versus system text: only Harmony is stored, which puts tools in the developer message after `# Instructions` (L1205-1209), with the system message first (L1198). That is the gpt-oss format; it does not describe GLM or MiniMax templates.
- Not predicted: the template order for GLM-5.3 (tools first) and MiniMax-M3 (system first). No stored source gives either template.

### Fact 3. gpt-oss-120b: cached length not monotonic in edit position (first tool edited 64, tool_10 3,248, tool_20 3,808, tool added at end 64, marker at start or end of system 64, base repeated 4,464)
- No stored source predicts this pattern. Under the plain prefix rule of Fact 2, an edit at the end (tool added at the end, marker at end of system) should leave most of the prefix cached; the probe shows 64.
- Candidate mechanisms stated in sources, none shown for this route:
  - (a) Only some prefixes are stored. DeepSeek's page describes cache prefix units persisted at request boundaries, on common-prefix detection and at fixed token intervals, with a hit only if a unit fully matches (L19-31). Under such a rule, a variant sharing a long prefix with the base but not ending on a persisted boundary could reuse only what a persisted unit covers. [I] This resembles the human's hypothesis "a cache that stores only some prefixes" (doc 10 L100); the DeepSeek page is about DeepSeek's service, not the university route.
  - (b) Different replicas: Year in LLM Serving L1742 (each instance has its own KV cache), OpenAI L268 ("Cached states live on individual machines"), CacheRoute abstract L10 ("returns to a server that still holds the prefix KV"). [I] Replicas would give non-repeatable hit lengths, but the base repeated at 4,464 (V7) and the 64 floor on four variants is a regular pattern, not noise.
  - (c) Sliding-window layers: gpt-oss alternates banded (128 tokens) and dense attention (model card L255-257). vLLM hybrid says a hit needs the intersection of groups and, for window layers, only the last window-1 tokens (L196, L208). [I] With a 128-token window this does not by itself explain a cap of 64 on early or late edits; the sources do not say it does.
- Not predicted by any stored source: the observed values 64 / 3,248 / 3,808, and that a late edit (tool added at end) behaves like an early one.

### Fact 4. Lifetime: present at about 75 minutes on three models; at about 5 hours gone on gpt-oss-120b and MiniMax-M3, present at about 5.5 hours on GLM-5.3
- Stored lifetimes: OpenAI in-memory 5-10 minutes up to one hour (L244), default 30 minutes with a 12-hour option on GPT-5.6+ (L83, L156-161); DeepSeek "usually within a few hours to a few days", best-effort (L94). Year in LLM Serving: 99% of reuse arrives within 15 minutes (L1433), a workload statistic, not a lifetime. LMCache: no TTL stated (searched).
- [I] 75 minutes exceeds the OpenAI in-memory range; "a few hours" (DeepSeek) is compatible with all four observations, but that page is another vendor's service.
- Not predicted: any lifetime for gpt-oss-120b, MiniMax-M3 or GLM-5.3 on the university route; why GLM-5.3 differs. Doc 10 L102 adds the caveat "if nobody touched the prefix in between".

### Fact 5. Could replicas, routing or eviction produce non-repeatable hit lengths?
- Sources that say it can happen in serving systems in general: OpenAI "Cached states live on individual machines ... overflow routing" (L268) and "do not pin requests to a machine or guarantee a cache hit" (L288); Year in LLM Serving "Each instance manages its own KV cache" (L1742) and "Stickiness preserves cache locality, but conflicts with load balancing" (L1699-1702); CacheRoute hit rate 64.1% under cache-blind balancing vs 93.2% (L15-16); DeepSeek "best-effort" (L92); eviction under memory pressure in vLLM (LRU, prefix-design L210) and SGLang (L252-254).
- [I] These show such effects exist elsewhere and are large; they do not show them on the university route.
- Not stored: anything about the university deployment (number of replicas, router, eviction, other tenants). Whether hit lengths are repeatable on the route is [U]; only a repeat run of the same variants would show it (that would be a new probe, outside this check).
