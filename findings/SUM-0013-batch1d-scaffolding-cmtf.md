## Row C-R03/CMTF

Question: what inputs does CMTF use in ToolMenuBench, and what does GIST-CMTF say CMTF assumes about the user request; which inputs are available to the agent at runtime and which are benchmark artifacts?

Verdict: **PARTLY**. The inputs are ANSWERED. Whether a deployed system would have them is stated only for the goal state (GIST-CMTF says the assumption is "often unrealistic"). The text does not say whether contracts or gold trajectories are available at runtime; the ToolMenuBench text separates them into benchmark artifacts only in part. A statement of "how the next frontier is computed in the experiments" beyond the definition (e.g. algorithm, code) was not found in lines 157-310; the other ranges were not read (see below).

Quotes:

1. CMTF definition, EXT-0148 (source lines 157-310; section IV.E at lines 297-301): "Causal Minimal Tool Filtering (CMTF) exposes only the next causally necessary frontier of tools. A tool is visible only when it is executable under the current state and its effects advance the remaining state toward the goal at the current step." (lines 299-301). Inputs of every method: "Each method receives the same task, current symbolic state, goal condition, and tool registry" (lines 264-265). Per instance: "Each benchmark instance consists of a user task, an initial symbolic state, a goal state, a tool registry, and a filtering method." (line 160) and "At each decision step, the filtering method maps the task, current state, goal, and registry to a visible subset of tools." (lines 161-162). Tool registry fields: "name, natural-language description, input schema, output schema, required state variables, produced state variables, risk label, optional cost label, domain label, and distractor category when applicable." (EXT-0148, lines about 187-190; the quoted list is the registry entry). Full causal path exposure "uses preconditions and effects to expose tools that may appear on some valid path from the current state to the goal." (section IV.D).
2. Gold trajectories, EXT-0148 (lines 200-210): "Each task includes a gold trajectory specifying the intended sequence of tools and the state variables produced after each step." "These trajectories support two forms of evaluation. First, they define the gold next tool at each step for filter-level evaluation. Second, they define the expected state transitions used to determine whether the downstream agent successfully completes the task." [F] The text names gold trajectories as evaluation material (to define the gold next tool and expected transitions); it does not state that CMTF reads the gold trajectory to build the menu. [U] whether the experiment code does.
3. Contracts, EXT-0136 (lines 118-135): "Causal filtering represents tools with lightweight preconditions and effects, then exposes tools according to their role in moving the current state toward the goal [8]. Causal minimal tool filtering (CMTF) exposes only the next causally necessary frontier, while Contract2Tool studies how such precondition-effect contracts can be learned from schemas, documentation, and execution traces [9]." In EXT-0148 (section IV.F): "Learned-contract CMTF applies causal filtering using inferred precondition-effect contracts rather than manually specified contracts." [F] In the reported experiments the contracts are, by implication, the manually specified/gold ones; the text calls learned-contract CMTF a "benchmark-supported extension", not a reported experiment.
4. Released artifacts, EXT-0134 (lines 84-90): "We provide benchmark artifacts including task definitions, tool registries, gold trajectories, tool contracts, distractor annotations, filtering baselines, evaluation scripts, and result-generation utilities."
5. Abstract numbers, EXT-0130 (lines 15-35): "In a controlled evaluation across seven model backends, three tool-menu sizes, six filtering methods, and seven evaluation settings, CMTF improves task success from 32.1% under all-tools exposure to 85.7%, while reducing average token usage by roughly 98%." Condition: synthetic registry, deterministic environment, ToolMenuBench tasks (EXT-0148: "synthetic but structured tool registry designed to isolate controlled tool-menu conditions"; "A deterministic environment executes the selected tool").
6. GIST-CMTF, EXT-0139 (lines 10-40; two-column extraction, ragged): "Causal Minimal Tool Filtering (CMTF) reduces tool-choice confusion by exposing only the next causally necessary tool frontier, but it assumes that the user request has already been mapped to a symbolic goal state." "Given a current symbolic task state and a target goal state, CMTF identifies a minimal causal path and exposes only the next causally necessary frontier." "even accurate contracts still require a target goal state [8]. This requirement exposes a critical upstream assumption: the user request has already been mapped to a well-defined symbolic goal. In practical agent workflows, this assumption is often unrealistic." GIST-CMTF figures with condition (abstract): "across seven model backends, six filtering methods, and 120 controlled tool-use tasks. GIST-CMTF achieves 97.0% task success, compared with 80.1% for top-goal CMTF and 82.9% for semantic-goal CMTF. It reduces wrong-goal execution from 19.4% under top-goal CMTF to 2.5%".

Classification (as the texts state it):
- Runtime-available per the texts: [F] task (user request) and "current state" are inputs to the filter; whether a deployed agent has a symbolic state or goal is not claimed. GIST-CMTF states the mapping from request to symbolic goal is not generally available ("often unrealistic") and adds a goal-inference layer.
- Benchmark artifacts per the texts: [F] gold trajectories, tool contracts, distractor annotations, risk labels and the symbolic initial state/goal state come from the benchmark ("benchmark artifacts including task definitions, tool registries, gold trajectories, tool contracts, distractor annotations"). [U] the text read does not say whether CMTF's contracts and goal state in the main experiments are taken from these gold artifacts, although the description of "manually specified contracts" and "a goal state" as instance fields is consistent with it. [I] this consistency is an interpretation, not a statement in the text.

What the passages do NOT show: the algorithm or code for computing the frontier; whether experiments' CMTF uses the gold trajectory; how many tools remain visible per step beyond the abstract's descriptor; what the 98% token reduction is measured against (average token usage across all runs, settings pooled); whether results hold on real, non-synthetic registries.

Limits: ToolMenuBench is a synthetic-registry benchmark with a deterministic environment; both papers appear to be preprints from the same line of work (GIST-CMTF arXiv 2606.16813v1, 15 Jun 2026); GIST-CMTF extraction is two interleaved columns (read left-to-right per column by the steward; wording joined across line breaks); the ToolMenuBench rest (results, experimental-setup sections after line 310, and any limitations) was not read; this row's 8th extraction (EXT-0148, lines 157-310) was chosen by adjacent reads using the view-only mode of the tool (lines 136-330 and 262-300 were viewed without writing an extract; these are not EXT and not cited).

[I] effect on ledger row: the stated concern ("may use information a deployed policy would not have") is consistent with the texts as far as the goal state and contracts are concerned (the goal-state requirement is explicitly called an upstream assumption by GIST-CMTF; the filter takes the goal as input). The texts do not say that CMTF reads the gold trajectory.
