## Topic A. Caching and dynamic or deferred tool definitions

### A1. AP (secondary web article, "Last reviewed: 2026-05-27", AP:190)
1. Measured: nothing of its own. It is an explanatory pattern page; no task, model, sample or run. [F] The numbers it uses are Anthropic's (see below). A catalogue is only discussed ("Stable tool set (30 tools)", "Dynamic RAG per step 5-15, varying", AP:32-45).
2. Topic A: no quantification of a cache effect. The table gives "Cache hit rate: Near zero / Effective cost: High" for dynamic per-step fetching (AP:37-40) with no data, provider run or citation for those cells. [F] Price premise: "Claude Sonnet 4's cache-read rate is $0.30/MTok against a $3/MTok base input" (AP:25). What changes: "Any change to tool definitions invalidates every level below it" (AP:17).
3. Decisive sentences: AP:17 "Any change to tool definitions invalidates every level below it." AP:25 "A single cache break per turn erases all savings from fewer tools." AP:63-69 "Token usage ~55K / ~8.7K; Accuracy (Opus) 49% / 74%" labelled "Anthropic's evaluations".
4. Limits: [F] the page itself lists when it does not apply (AP:97-117: small libraries, single-turn cold starts, local inference without shared KV cache). [O] "Established - multiple independent sources" (AP:188) is a self-label. [O] The pair "~55K -> ~8.7K" mixes two scenarios of the Anthropic page: EXT-0074 line 58 gives "58 tools consuming approximately 55K tokens", while the 8.7K endpoint belongs to the scenario "~72K tokens ... ~77K ... ~8.7K" (EXT-0074 lines 65-71). The page does not say so. [O] The sentence "A single cache break per turn erases all savings" is an assertion; no arithmetic is shown.
5. Relevance: PARTIAL. It states the mechanism clearly for our setting but contains no measurement.

### A2. SL (vendor case study, updated 2026-07-01 per SL:181-182)
1. Measured: Slite's own agent, "63 complex questions (an automated benchmark)", new unified agent vs "old v2 engine" (SL:155). "17 tools loaded upfront", "65+ tools available on demand" (SL:156-157). Models not stated in the text I read. Catalogue: tens of tools, "unbounded once you count MCPs".
2. Topic A: asserts the cache problem, does not measure it. SL:61-62 "'just load the tool when you need it' naively means: mutate the tool list mid-conversation -> blow away the entire prompt cache -> re-process every prior turn." The only number is the end result: "-23% cost per question, and -12% response time" (SL:159), for the whole redesign against a different engine. Provider and cache hit rates not given. [O] The article does not say where the on-demand definitions are placed (tools array or messages), nor how much of the 23% is cache.
3. Decisive: SL:159 "-23% cost per question, and -12% response time." SL:160-161 "The context budget and cache-invalidation problems both came from the same root cause: loading everything upfront." SL:165 "It's one piece of the puzzle that helped us solve the cache-invalidation problem, but you need real orchestration built around it".
4. Limits: [F] "This is our current approach - not an evergreen recommendation" (SL:166). [O] Vendor self-report, n=63, confounded (engine, prompts, tools changed together), no variance, no ablation of cache.
5. Relevance: PARTIAL. Same setting (MCP-scale catalogue, cost per question) but cost effect is not separated from other changes.

## Topic B. Do models initiate search or ask when a needed tool is absent?

### B1. K (KAIST, "Can Tool-Augmented LLMs Be Aware of Incomplete Conditions?")
1. Measured: binary classification "Yes/No: is tool use feasible" (K:296-307) on 1,610 instances built from APIBank and ToolBench: 900 by replacing the relevant API with a similar irrelevant one (tool absent), 710 by removing user information (K:286-290). 12 models (Llama3.1 8B/70B, Gemma3 4b/27b, Qwen2.5 7B-72B, GPT-3.5, GPT-4, GPT-4o-mini, GPT-4o), zero-shot and four-shot, temperature 0. Tool lists are short (average 2.13 / 5.13 APIs per instance, K:236-239); no large catalogue.
2. Topic B: it measures recognition that a tool is absent, as abstention, not search. API-replacement scores (F1, "No" positive class): APIBank 0-shot, GPT-4 87.56, GPT-4o-mini 88.41, GPT-4o 86.23, Llama3.1-8B 71.32; ToolBench 0-shot GPT-4o 75.06, GPT-4o-mini 72.97, Gemma3-4b 20.90 (K:364-376, 418-431; [O] columns read by position: 12 values per row in the order of the header, confirmed against the text "GPT-4o-mini and Qwen2.5-72B achieve strong accuracy (88.82% and 87.94%)" K:584-586). The main task is explicitly prompted. An "implicit" variant (no question about feasibility, just next action, K:770-781) was run on 3 models only (Llama3.1-8B/70B, GPT-4, APIBank): GPT-4 F1 drops 87.56 -> 77.18 (API replacement) and 89.27 -> 86.75 (utterance removal) (K:784-785); Llama3.1-8B API-replacement F1 39.66 (Table 5, K:724-727). The implicit prompt (Fig. 29, K:2307-2322) offers only "call an API or not"; no search or ask-a-question option.
3. Decisive: K:590-594 "LLMs consistently struggle to abstain from invoking tools under incomplete conditions, as indicated by low F1 scores (e.g., as low as 5.41% for Llama3.1-8B on ToolBench Utterance Removal)." K:786-790 "we hypothesize that the binary classification setup, which explicitly prompts the model to assess whether the current tool list or user information is sufficient for tool invocation, enables the model to better recognize when tool usage is appropriate."
4. Limits: [F] stated: model-based annotation with human verification; API-based tools only (K:1303-1312). [O] mine: prompted classification (the main numbers); implicit variant only 3 models and one dataset; absent tool is replaced by a similar one so the model sees a wrong-but-plausible tool; no mechanism to search; the 5.41% example is utterance removal, not tool absence.
5. Relevance: PARTIAL. It does measure recognition of a missing tool, but with a prompted yes/no format, short lists, and abstention instead of search.

### B2. SING (HKUST et al., "Synthetic Intention Graph for Active Tool Discovery")
1. Measured: retrieval accuracy (Recall@5, MRR) and executed task success on MCP-Universe, MCP-Atlas, MCP-Bench, with a corpus of 779 MCP servers / 7,471 tools (SING:597); runner model DeepSeek-V4-Pro, judge Kimi-K2.5 (SING:805-807). Settings: Default (ground-truth servers only), Restricted, Global (full pool). Baselines: embedding-only retrieval and MCP-Zero.
2. Topic B: no rate of spontaneous request or recognition of absence. Discovery is a prescribed pipeline step: "Given the user request x, the agent first decomposes it into a global discovery request ... and a set of subtasks" (SING:528-530). A failure analysis assigns failed MCP-Atlas runs to "Query Formulation" (agent "fails to express the correct tool need", SING:1029-1031), Retrieval, Tool Use, Reasoning; the text gives only retrieval counts (84 -> 64 Restricted, 156 -> 91 Global, SING:1046-1049); other category counts are in a figure not in the text.
3. Decisive: SING:948-952 "improving the overall success rate by 8.1 and 10.1 percentage points in the Restricted and Global settings, respectively" (vs MCP-Zero) and SING:953-956 "surpasses the DEFAULT setting, where only the ground-truth servers are provided, by 6.8 and 4.8 percentage points". SING:1010-1012 "SING reduces schema exposure from 693,574 to 1,298 tokens on average, a 99.8% reduction." [O] Table 1 (SING:637-686, ragged) read by position: overall SR Default 40.3%, MCP-Zero Restricted 39.0%, SING Restricted 47.1%, MCP-Zero Global 35.0%, SING Global 45.1%; these reproduce the stated differences (47.1-39.0=8.1; 45.1-35.0=10.1; 47.1-40.3=6.8; 45.1-40.3=4.8). On MCP-Atlas SING stays "below DEFAULT" (SING:984-986).
4. Limits: [F] evaluation cost, execution variability (SING:1096-1113). [O] one runner model, cost measured as schema tokens only (no billing, no cache, no latency of rounds), baseline MCP-Zero characterised as "detect capability gaps" by SING (SING:274-279) but the stored text does not show how MCP-Zero was configured.
5. Relevance: PARTIAL. Large MCP catalogue with executed tasks and a no-discovery reference, but discovery is scaffold-driven and cost is schema tokens only.

### B3. LOM (Lomekwi: "Resource-Bounded Tool Discovery in LLM Agents")
1. Measured: tool *discovery/creation* propensity. Environment 1 (Lomekwi): a combinatorial vault game where the agent can gather shards and build a machine (creation) or brute-force; Claude Haiku-4.5, Sonnet-4.6, Opus-4.8 and seven Qwen models, 20 episodes per configuration, 180 episodes per model (LOM:212-224, 261-262). Environment 2 (Recognition MCP): the agent is served T = 4..20 candidate tools plus a submission tool over a local MCP server; exactly one tool (the oracle) answers a long-division task, the others are identical decoys; Qwen2.5/3/3.5 only (all under 35B), 3-15 repetitions per cell (LOM:268-289).
2. Topic B: not "absent tool" and not catalogue search, but it reports the unprompted rate at which a model probes visible tools when it can solve the task by hand, and how an instruction changes that. Qwen3.5: recognition (oracle found) 0.29 at 2B, 0.10, 0.05, 0.02 at 27B (LOM:480-481); at 27B "the number of episodes in which the model never calls a single tool" is "154 of 180" and tool calls per episode 0.2 (LOM:622-625). With a "tool-prior" prompt stating one tool can solve the problem: Qwen3.5 27B 0.02 -> 0.60, 0.2 -> 5.6 calls per episode (LOM:783-785). Tools are visible in context.
3. Decisive: LOM:634-636 "because they are never told that a tool can solve the task, a capable model has no reason to spend budget probing." LOM:783-785 "Under the prior, the largest models return to exploring the tools and their recognition recovers ... Qwen3.5 27B rises from 0.02 to 0.60". LOM:823-827 "the decision of whether to reach for them is miscalibrated against the model's actual capability."
4. Limits: [F] "modest per-cell sample sizes"; two environments; obfuscated labels; explanation "supported by tool-call counts and representative rollouts rather than a controlled manipulation" (LOM:829-841). [O] mine: the Claude models appear only in Lomekwi (creation), the MCP experiment uses only small Qwen models; only a handful of tools; random single-letter names.
5. Relevance: PARTIAL (weak). The lead's suspicion is only half right: the Lomekwi game is about tool creation, but Section 6 is an MCP experiment about whether a model calls visible tools at all, and it shows the result depends strongly on whether the prompt says a tool exists. No hidden catalogue, no search tool.

## Topic C. Cross-session or persistent memory of tool use

### C1. PF (PREFINE, Hanyang University, "Latent Preference Modeling for Multi-Session Personalized Tool Calling")
1. Measured: benchmark MPT, 4,695 instances over 459 multi-session histories from three corpora (SGD, DuRecDial 2.0, HomeBench); five LLMs (GPT-5, Claude-4.5-Haiku, GPT-OSS-20B, Gemma-4-12B-IT, Qwen3-8B); six methods (full history, RAG, Mem0, LangMem, A-MEM, PREFINE) (PF:566-575, 18-20). Tool schemas are small fixed APIs.
2. Topic C: yes, memory that persists across sessions, but it stores a user's latent preference (e.g. cheap, economy) used to fill missing *argument values* of tool calls, not which tool to choose or tool configuration. Compared: PREFINE vs full-history prompting vs retrieval/memory systems. Abstract: "existing memory systems often fail to improve on full-history prompting; PREFINE outperforms all baselines and alone surpasses it on Preference Transfer" (PF:25-29).
3. Decisive: PF:136-139 "Retrieval- and organization-based memories (RAG, Mem0, LangMem) even fall below full-history prompting". PF:29-31 "memory for personalized agents must abstract behavior into preferences, rather than simply archive it."
4. Limits: [F] controlled setting, one preference per query, users composed from existing corpora (PF:1634-1653). [O] synthetic composed histories; F1 numbers per cell not extracted by me.
5. Relevance: NOT RELEVANT to tool discovery or catalogue cost (it stores argument preferences); [I] useful only as a data point that archived raw history was not better than an abstraction.

### C2. AP2 (Apple, "Shared Selective Persistent Memory for Agentic LLM Systems")
1. Measured: persisted context across sessions for code-generating agents; four categories kept: task specifications, data schemas, tool configurations, output constraints (AP2:20-26, 108-126). Compared: no memory vs full conversation history vs selective memory. Public replication: 4 datasets x 3 conditions, 12 trials per condition; enterprise: 24 tasks. Model: Claude Opus 4 (engine) and Claude Sonnet 4 (AP2:549-554). "Every cell is a single run" (AP2:555). "Tool configurations" are defined as "which external tools are available, their parameter schemas, invocation patterns, and authentication requirements" (AP2:120-122). Sources include MCP connectors but the tool set is small and fixed.
2. Topic C: this is the only text I read that persists tool configuration across sessions, but as one of four bundled categories, with no component-wise ablation. Numbers: "no memory completes 0/12 trials at 3.8K input tokens, selective memory completes 12/12 at 3.9K, and full conversation history completes 8/12 at 7.7K" (AP2:31-35); enterprise "23/24 against 19/24 and 17/24, though at that sample no pairwise difference reaches significance" (AP2:56-59); Table 1 means: input tokens 2.1K / 18.7K / 3.4K and completion 79% / 71% / 96% for No Mem. / Full Hist. / Selective (AP2:583-606, read by position).
3. Decisive: AP2:42-46 "Every no-memory failure is a specification failure and nothing else" (the missing item in the public study is a formatting specification, not a tool). AP2:1052-1073 "Every cell is a single run with no repeated seeds ... Three baselines are absent: ... a leave-one-component-out ablation".
4. Limits: [F] stated: single model family; single runs; tasks authored by the authors; no leave-one-out ablation; public sample underpowered (AP2:1052-1073). [F] Agent-level memory that "would retain effective tool sequences" is future work (AP2:1087-1090).
5. Relevance: PARTIAL. It evaluates persistence of tool configuration across sessions with token numbers, but the measured benefit comes from specifications, and tool memory is not isolated.

### C3. MD (Memory-Induced Tool-Drift, Virginia Tech)
1. Measured: how long-term memory of user personality biases tool-call *parameter values*. MEMDRIFT, 105 scenarios, five bias dimensions, seven professional domains, seven frontier models; three production memory frameworks (Mem0, MemPalace, SimpleMem); scan of 6,062 tools across 288 MCP servers, 608 flagged (MD:16-24, 330).
2. Topic C: persistent memory is present (stored biased memories) but the outcome is parameter deviation, "up to +3.6 points on a 1-5 scale" (MD:19-20). It does not evaluate memory of tool choices or configuration. [F] Explicitly: "we study parameter assignment within a fixed tool, not whether memories also bias tool selection" (MD:649-651).
3. Decisive: MD:19-20 "biased memories raise deflection scores ... by up to +3.6 points on a 1-5 scale". MD:649-651 as above.
4. Limits: [F] single tool per scenario, single-turn, parameter assignment only (MD:649-652). [O] adversarial synthetic scenarios; judge-scored metric.
5. Relevance: NOT RELEVANT to discovery or cost; [I] relevant only as a caution that persisted memory content can alter later tool calls.

### C4. MTA (MemToolAgent, AWS)
1. Measured: memory of past tool executions (query, tool call, environment or user feedback) retrieved at test time. WorkBench (27 tools; test 549 tasks = 108+99+72+81+189; memory seeded with one query per template from the same benchmark, MTA:390, 397-407), NESTFUL (first 500 tasks test, next 500 populate memory, MTA:413-415), PEToolBench (591 test queries, each with an 80-100 query history; comparison against A-MEM and Mem0 on the first 50 queries, MTA:490-503, 570-576). Claude 3.7 Sonnet (NESTFUL, WorkBench), Claude 3.5 Sonnet (PEToolBench) (MTA:519-521).
2. Topic C: yes, memory of tool use (including which tool was right for a user, "Tool Accuracy" in PEToolBench, MTA:506-507) that persists across queries; single-turn, not shown as separate sessions. Numbers: WorkBench overall 57% -> 85% vs no memory (MTA:561-564; table read by position: No Memory 57.56, ReAct 65.94, MemToolAgent 85.06); NESTFUL full sequence 15.6 -> 30.4, win rate 51 -> 70 (MTA:552-554); PEToolBench Tool Accuracy 0.82, "17% relative improvement over A-MEM and Mem0" (MTA:576-578; [O] table shows 0.700 and 0.820 in the final rows).
3. Decisive: MTA:403-405 "This ensures that there is at least one directly relevant memory entry for each test query. This setup is used to show the advantages of using the memory." MTA:824-829 "the benchmarks used contain fewer than 40 tools ... As the number of tools increases, it is more challenging to cover the usage of all tools with memory."
4. Limits: [F] cold start, fewer than 40 tools, single-turn only (MTA:822-844). [O] WorkBench test queries share templates with memory entries by construction; one model family; PEToolBench comparison on 50 queries; no bill or cost per task figure in the lines I read (a token analysis exists at MTA:794, not read).
5. Relevance: PARTIAL. Memory of tool use evaluated against no-memory and other memory systems, but small tool sets and in-template overlap.

## Statements by the lead checked against these texts
1. "No stored source measures whether a model spontaneously searches when a needed tool is absent." Consistent in the narrow form: nothing I read gives such a rate. [O] Nearby measurements exist and should not be omitted: K (prompted recognition of absent tool; unprompted variant on 3 models, F1 down from 87.56 to 77.18 for GPT-4 on APIBank), LOM (unprompted probing of visible tools, strongly prompt-dependent: 0.02 vs 0.60).
