## Verdicts

**A2 (no symbolic algorithm can beat the LLM across all cases): MIXED in the sources read; [I] the universal form is not testable from them and no source tries to prove or refute it.**
- Cases consistent with the direction: ToolMenuBench keyword top-5/top-10 (22.1, 22.4) are below all-tools (32.1) (EXT-0207); ToolRet re-ranking rows do not beat the embedder, but those rows are weak LLMs re-ranking a list (EXT-0210), which is the reverse direction (LLM rows lower than embeddings), so they do not support A2; ComplexMCP full-context LLM view beats embedding RAG (55.31 vs 13.47-36.88 for Gemini-3-flash); GIST-CMTF: the best non-oracle arm still uses an LLM to infer the goal (97.0%) and "the gains come from goal validation and clarification rather than from smaller tool menus alone" (EXT-0208).
- Cases in tension with it: ToolMenuBench CMTF 85.7% vs 32.1% for all tools, 1,125 vs 56,062 tokens, 0.99 vs 125 visible tools (EXT-0207); GIST-CMTF gold-goal CMTF 99.5% vs 53.5% all-tools (EXT-0208). In both, the symbolic filter relies on contracts/state that the benchmark supplies, and the competitor is the LLM given everything; no arm is an LLM given the same contracts, so "symbolic beats LLM" is not isolated from "annotated information beats unannotated".
- Not addressed: an LLM-based filter with the same inputs as CMTF (state and contracts); real-world (non-synthetic) tool sets with contracts; any theoretical argument ("first principle"). No stored source reports an impossibility or optimality result.
- Better-specified, testable version (for the supervisor to accept or drop): "In setting S (task set, tool count, models), a symbolic selector that uses annotated contracts/state reaches success X at token cost T_s, and an LLM-based selector given the same annotations reaches Y at cost T_l; the claim fails for S if X > Y with intervals not overlapping." Nearest stored numbers: symbolic 85.7% (1,125 tokens) vs LLM-with-all-tools 32.1% (56,062 tokens) in ToolMenuBench Table I (EXT-0207); 97.0% (hybrid) vs 53.5% (all tools) in GIST-CMTF (EXT-0208); an LLM-selector arm with the same contracts is missing.

**A10 (synonyms get the same embedding; keyword is "a layer before" semantic): NOT ADDRESSED for the "same embedding" part; MIXED for the layering.**
- [F] No stored text I read states that synonyms map to the same embedding. [O] The claim as worded ("same") is stronger than similarity; EXT-0004 row A10 already notes "embeddings of synonyms are similar, not identical". [U] I did not find a measurement of a synonym swap on tool descriptions in the stored files.
- Consistent with the vocabulary-mismatch motivation: ToolDreamer ("user requests are often poorly aligned with the language of TD", BM25 gains 19% vs Qwen3 8% when the LLM rewrites the query into description language); Tool2Vec, as described by two surveys; StackOne's embedding example "Make a task in my project tracker" matching jira_create_issue (`lit-stackone-bm25-hybrid.txt:355`).
- In tension with a strict "layer before": at Top-5 the StackOne arms are 87 / 90 / 85 (BM25 / hybrid / embeddings) and in ToolRet Table 4 BM25s (22.32) beats several dense models (all-MiniLM 16.30, contriever 17.81) but not the large ones (NV-Embed 33.83); ToolDreamer: "dense models are fundamentally necessary" for the best results. A cascade (keyword first, semantic second) is not measured in any of them except the StackOne BM25+TF-IDF hybrid, which is lexical only.
- Better-specified version: "On tool descriptions in domain D, a query that uses a synonym of a description term ranks the right tool at position p_k under BM25 and p_e under embedding model M" (a rank-change test); a cascade version: "keyword shortlist of size n, then embedding rerank, vs embedding over all tools: recall@5".

**A11 (semantic search does the same thing the LLM does): IN TENSION IN THE SOURCES READ for outcome equivalence; the analogy as a description of mechanism is NOT ADDRESSED.**
- ComplexMCP: embedding the question (k=30/60) gives 13.47 / 27.65 (Gemini-3-flash) and 11.34 / 24.82 (Claude-opus-4); an LLM-written search query over the same index gives 36.88 / 25.52; the LLM seeing all tools gives 55.31 / 41.84. MCP-Zero: LLM-authored request retrieval about 90-96% vs 65-72% for raw-query retrieval (one baseline number, author's method). ToolRet: LLM re-rank rows are below the embedding that produced the list (Table 4 avg N@10 28.80-29.60 vs 33.83), with weak LLMs and a single re-ranking framework (RankGPT).
- Consistent with the analogy: ToolDreamer's framing that the LLM "offload[s] a portion of the reasoning burden to the retriever" (`lit-tooldreamer-2510.19791.txt:34-36`) treats retrieval and LLM as sharing a task, and the generated hypothetical tools are then matched by lexical or dense models.
- Better-specified version: "For the same tool catalogue and queries, an embedding retriever and an LLM selector (given the same candidate descriptions) differ by less than d points in top-k recall and agent success." No stored source runs this arm pair with equal inputs.
