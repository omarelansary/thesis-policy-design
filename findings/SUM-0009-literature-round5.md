### 1. KD Model-Adaptive Tool Necessity Reveals the Knowing-Doing Gap, arxiv-2605.14038

1. Measured: [F] four open-weight models: Qwen3-8B, Qwen3-4B, Llama-3.1-8B-Instruct, Llama-3.2-3B-Instruct (KD:243-244). Two datasets: 4,000 synthetic arithmetic instances and TruthfulQA (817) (KD:246-254). Tools: "a calculator for arithmetic question answering and a search API for factual queries" (KD:271-272); one tool per domain, not a catalogue. Necessity per model: run N = 10 times at T = 0.7 without tools (KD:257); "samples where the model fails at least once as tool-necessary, and samples where the model consistently gives correct answers across all N = 10 runs as tool-unnecessary" (KD:258-260). Tool-call behaviour is then collected with tools available: "In this setting, models are provided access to external tools" and greedy decoding (KD:270-273), "model-specific handlers that expose these tools in the syntax expected by each model" (KD:274-276). Whether the user/system prompt tells the model to use tools, or only that they exist, is [U] in what I read (the prompt text was not seen); the paper calls it "direct task-oriented prompting" (KD:1098) and "task-oriented prompts" (KD:1116), i.e. not a self-assessment prompt. 
2. Decisive numbers: abstract KD:24-26 "find substantial mismatches of 26.5-54.0% and 30.8-41.8%, respectively" (arithmetic, factual QA). Table 1 (KD:301-361) defines "Mis." = N-NC + UN-C (KD:296-304). The range is exactly: arithmetic 26.5% (Qwen3-4B, KD:334) to 54.0% (Llama-3.2-3B, KD:356); TruthfulQA 30.8% (Llama-3.1-8B, KD:350) to 41.8% (Qwen3-4B, KD:339). Per model, Mis. is arithmetic / TruthfulQA: Qwen3-8B 41.7 / 31.1 (KD:323, 328); Qwen3-4B 26.5 / 41.8 (KD:334, 339); Llama-3.1-8B 38.5 / 30.8 (KD:345, 350); Llama-3.2-3B 54.0 / 32.8 (KD:356, 361). The mismatch is over ALL queries and mixes two opposite errors; the paper says "between roughly one quarter and one half of all queries result in a tool-use action that is inconsistent with the model's actual capability" (KD:365-368). The rate of NOT calling when needed is a different quantity. Cells from Table 1 (count and share of all queries) for N-NC ("Necessary-NotCalled"): arithmetic Qwen3-8B 140 (3.5%), Qwen3-4B 581 (14.5%), Llama-3.1-8B 1204 (30.1%), Llama-3.2-3B 1559 (39.0%) (KD:320, 331, 342, 353); TruthfulQA 146 (17.9%), 153 (18.7%), 130 (15.9%), 164 (20.1%) (KD:325, 336, 347, 358). UN-C ("Unnecessary-Called"): arithmetic 1526 (38.2%), 481 (12.0%), 335 (8.4%), 600 (15.0%); TruthfulQA 108 (13.2%), 189 (23.1%), 122 (14.9%), 104 (12.7%). My derived conditional rates [O, my arithmetic from the Table 1 counts, not stated by the authors]: share of tool-necessary queries not called = N-NC / (N-C + N-NC): arithmetic Qwen3-8B 140/578 = 24%, Qwen3-4B 581/834 = 70%, Llama-3.1-8B 1204/1623 = 74%, Llama-3.2-3B 1559/2085 = 75%; TruthfulQA 146/215 = 68%, 153/256 = 60%, 130/228 = 57%, 164/222 = 74%. Share of tool-unnecessary queries that were called = UN-C / (UN-C + UN-NC): arithmetic 1526/3422 = 45%, 481/3166 = 15%, 335/2377 = 14%, 600/1915 = 31%; TruthfulQA 108/602 = 18%, 189/561 = 34%, 122/589 = 21%, 104/595 = 17%. Check: Qwen3-8B arithmetic counts sum to 4000. Authors on failure modes: "On arithmetic, Qwen3-8B suffers from tool-overuse ... Qwen3-4B and both Llama models exhibit clear tool underuse" (KD:372-376); "no single, uniform bias can fully explain these mismatch errors" (KD:379-381). Knowing-doing: "the majority of the observed necessity-action mismatch cases originates from the transition from cognition to action" (KD:146-148); Figure 6 "the orange flow ... is by far the largest error category" (KD:691-693); the stage split is shown only as Sankey diagrams for two of the four models (Qwen3-8B, Llama-3.1-8B; KD:683-686), no numbers in text. Prompted self-assessment (appendix B, KD:1082-1122): asking the model "whether it is necessary to invoke an external tool" changes tool-calling on 18.20-49.27% of arithmetic and 20.93-34.64% of TruthfulQA samples (Table 3, KD:1138, 1152, 1159 etc.); Llama-3.1-8B "simply answers 'no' for every TruthfulQA sample" (KD:1101-1102).
3. Limits: [F] authors: only N = 10, T = 0.7 tried (KD:1165-1168); the probing method "makes our work inapplicable to close-source state-of-the-art LLMs like GPT or Gemini" (KD:1168-1169). [O] Four small open-weight models (3B-8B); no frontier model. [O] "Necessary" means failed at least once in 10 sampled runs at T = 0.7, so a query a model gets right 9 times out of 10 counts as tool-necessary; this inflates N-NC relative to a "cannot answer" definition. [O] The correctness of the final answer after calling is not part of Table 1; the mismatch is about call/no-call, not about task success. [O] One tool per domain, always visible; the model is never asked to find a tool; calculator on arithmetic is a case where no-call can be correct for easy items. [O] Synthetic arithmetic plus TruthfulQA (a benchmark of misconceptions, where a search API's usefulness is arguable). [O] The call decision is defined by the model's first generated token (P(call), KD:728-737 with greedy decoding), so multi-turn behaviour is outside the setting. [O] Table 1 layout is clean in the stored text (each model one row of 10 cells); I found no ragged cells.
4. Relevance: PARTIAL (topic B, indirect). It does give a rate, for small open-weight models with ONE visible tool, of tool calling that mismatches a model-specific need (26.5-54.0% arithmetic, 30.8-41.8% factual QA, of all queries), and per-model under-call shares (my derivation: 24-75% of tool-necessary arithmetic queries and 57-74% of tool-necessary TruthfulQA queries not called). It does not answer the question for our setting: no hidden catalogue, no search-for-tools channel, no frontier or API-served model, and the tool is directly visible.

### 2. AT AutoTailor, arxiv-2609.13548

1. Measured: [F] 106 WebArena Postmill tasks (AT:87-88); agents "instantiated with Copilot using Claude Opus 4.8" (AT:497-498); API pools from trajectories: 1,283 unrefined APIs (S_init), 87 after the quality and usage-likelihood filters (S_ULF), 33 after Dynamic Reselection (S_DR) (AT:92-94). Conditions with and without a ReAct fallback agent on Playwright MCP (AT:499-509). Metrics: correctness, latency, MCP API calls, LLM calls, tooling and total request/completion tokens (AT:519-523). "Capability gap detection" in the sense of this task: a task is uncovered when "the synthesized APIs fail a task or when the runtime web agent determines that no suitable API is available for the current user task" (AT:290-293); gaps are clustered over a rolling window of 100 tasks, cosine threshold 0.82 (AT:293-298); an LLM then picks up to five candidate APIs from inactive ones per gap (AT:306-307); candidates are added when "the MCP server reloads its registered tools" (AT:309-310). Unused APIs are pruned after 50 tasks (AT:318-319).
2. Decisive numbers: abstract AT:23-28 "With reasoning and acting (ReAct) fallback, this set achieves 90.6% correctness, compared with 87.5% for ReAct alone, while reducing average total request-token cost by 57.8% and latency by 29.4%. Without ReAct, it achieves 60.1% correctness, marginally matching the performance of unrefined set, while reducing request-token usage by 94.9%." Table 2 (no ReAct): tooling request tokens per task 2.78m (S_init), 452.58k (S_QF), 225.07k (S_ULF), 142.86k (S_DR) (AT:583-586); correctness 0.604, 0.599, 0.502, 0.601 (AT:548-554). With ReAct: S_init 2.39m tooling request tokens, 88.0% (AT:599-600); S_QF 403.30k, 83.5% (AT:601-603); S_ULF 205.13k, 87.3%, total request-token cost "increases slightly from 1.42m to 1.52m" because ReAct calls rise from 4.25 to 5.33 (AT:606-611); S_DR 98.46k tooling request tokens, 90.6%, total 1.32m, "more than a 24x reduction in tooling request tokens" (AT:614-617). [F] Authors' own caution: "reducing the exposed tool set can simplify tool selection while shifting unresolved tasks to the ReAct Fallback" (AT:611-613). Tokens are counted, not priced: [F] a grep for cache/billed/dollar found no match, so no cache pricing and no dollar costs appear in the stored text.
3. Limits: [F] authors: templated WebArena tasks simulate repeated interaction; "the observed benefit of dynamic reselection should be interpreted as evidence that the framework can adapt to a stable simulated task distribution, rather than as a complete characterization of production behavior" (AT:663-670). [O] One site (Postmill), one backbone, one run per condition as far as I read (no variance reported in the parts read). [O] The set S_DR (33 APIs) is "frozen" for the table (AT:639) and was derived with knowledge of the task distribution (same 106 tasks templated, rolling window), so the comparison is not held-out. [O] Reselection adds/removes tools between tasks (server reload), not inside a running conversation, so it says nothing about appended-definition cache behaviour. [O] The agent's declaring "no suitable API available" triggers the gap; the paper does not report how often the agent made that declaration, nor whether the agent was instructed to.
4. Relevance: PARTIAL (topic A, cost side only; topic B indirectly). Large pool (1,283 tools) cut to a small active set with measured request-token cost per task (not billed cost); a fallback general channel (ReAct) catches uncovered tasks. It is the tool-exposure-size versus cost trade, between tasks and with tokens rather than dollars. It does not measure discovery by the agent from a hidden catalogue, nor cache behaviour.

### 3. MU MCP-Universe, arxiv-2508.14704

1. Measured: [F] 231 tasks, 6 domains, 11 real MCP servers with "total 133 tools" (MU:172, 506); ReAct agents for many models; success rates GPT-5 43.72%, Grok-4 33.33%, Claude-4.0-Sonnet 29.44% (MU:33-35, 183-185). Three side experiments on selected domains with GPT-4.1 and Claude-4.0-Sonnet: a per-step summarization agent (long context; MU:956-962, Fig. 4), an "exploration phase" before the tasks (unknown tools; MU:1022-1027, Fig. 5), and connecting more unrelated servers (MU:1069-1076, Fig. 6).
2. Decisive sentences. Long context: "the number of tokens increases rapidly as the number of interaction steps grows" (MU:956-957), measured on Claude-4.0-Sonnet only (MU:963); the summarization experiment "yields mixed results" (MU:961). Unknown tools: "LLMs often struggle to correctly use tools provided by the MCP servers, indicating a lack of familiarity with their interfaces and constraints" (MU:1019-1020); exploration phase "the LLM is allowed to freely interact with the tools provided by the MCP servers" (MU:1023-1024); results "GPT-4.1 achieves a 30.77% success rate in the Browser Automation domain, an improvement of 7.69 percentage points. Similarly, Claude-4.0-Sonnet reaches a 62.50% success rate in the Financial Analysis domain, a 7.50 percentage point increase" while Claude in Browser Automation declines and GPT-4.1 does not improve on Financial Analysis (MU:1029-1033). More tools: "we connect a total of 7 MCP servers, comprising 94 tools ... results in a noticeable decline in performance" (MU:1073-1076); "Claude-4.0-Sonnet's success rate in the Location Navigation domain drops from 22.22% to 11.11%. GPT-4.1's ... Browser Automation domain decreases from 23.08% to 15.38%, and in the Financial Analysis domain, it drops from 40.00% to 35.00%" (MU:1078-1082). Ragged-figure flag [O]: the Fig. 6 values are flattened in the text (MU:1051-1061); read by position, GPT-4.1 Location Navigation appears to go 8.89 to 13.33 (a rise) and Claude Financial Analysis 55.00 to 62.50 (a rise), which the prose does not mention ("noticeable decline" is based on the three examples it names); I did not verify against the image, so treat the direction of those two as unchecked. Fig. 5 values likewise: GPT-4.1 Location Navigation 8.89 to 20.00 [flattened, unchecked]. There is no tool-search or retrieval ablation and no dollar cost; "token" numbers are context-length growth in a figure (image; no figures in text).
3. Limits: [F] the authors do not state a limitation section in what I read; they note thinking mode not used for Claude (MU:962) and that the context length experiment is Claude-4.0-Sonnet only (MU:963). [O] Few tasks per domain (the percentages are multiples of 1/45, 1/13, 1/20, i.e. denominators of about 9-45 tasks, e.g. 8.89 = 4/45, 23.08 = 3/13, 55.00 = 11/20), so the differences of 7.5-11 points are a few tasks; no variance reported in the part read. [O] "Unrelated servers" experiment adds 94 tools to what the task needs, all visible in context; the model is never asked to find tools.
4. Relevance: PARTIAL (topic A/B background). Direct numbers on success falling or not with 94 visible tools and on pre-task exploration improving some domains; no search/retrieval of tools, no cost, no cache. It gives the "unfamiliar tools" evidence in the form of a pre-task exploration phase; its effect is domain- and model-dependent in 2 models.

### 5. SO StackOne "Where your agent's tokens actually go", web-stackone-where-agent-tokens-go.txt

1. Measured: [F] nothing is measured by the authors. It is a 6-minute explainer by Guillaume Lebedel, September 25, 2026 (SO:222), from a vendor that sells a search-and-execute tool gateway (SO:21-22, 59-60, 265). It cites others' figures: Anthropic's Opus 5.5 announcement (40% running-cost saving at default settings; uncached input and output rates down 20%, cache reads down 60%; SO:253) and Artificial Analysis cost per task for GPT-6 Sol/Luna (SO:255, 305: $1.99 to $1.06, $0.18 to $0.07); OpenAI GPT-6 caching guidance (SO:282). Citations checked "on 25 September 2026" (SO:300) by the vendor; I did not check them against the sources.
2. Decisive sentences. Bill formula: "multiply the tokens in each disjoint billing category by that category's rate and add the charges. Include uncached input, cache reads, applicable cache-write tiers and output." (SO:234); "cost per completed task = model spend / completed tasks" (SO:237). Definitions: "A definition included in the request is part of the model's input, whether or not the tool is called ... Caching can reduce its price, but it does not make the definitions disappear from the context window." (SO:263-264). Search design: "The definitions for those two operations remain small as the catalogue grows across 560+ connectors. Search results and returned data still enter the conversation" (SO:265-266); "This is a design comparison, not a claimed percentage saving. Measure the extra search step and any additional model call against the definitions it removes. A handful of clear tools may be cheaper to expose directly." (SO:276). Cache: "Keep stable instructions and tool definitions early in the prompt" (SO:280); OpenAI guidance "requires stable tool definitions, schemas and ordering. Change which tools are callable with allowed_tools, or use tool_choice set to none, instead of deleting definitions." (SO:282); "These mechanisms do not make arbitrary schema changes cache-safe." (SO:284). Measured breakdown of where tokens go: none; the page says "The right intervention depends on which of those contributes most to your workload" (SO:228) and gives no share for tool definitions [F].
3. Limits: [F] the schematic table is "a design comparison, not a claimed percentage saving" (SO:276); the Sol/Luna numbers are "benchmark observations, not a forecast for your agent" (SO:259). [O] Commercial interest in search-based discovery; no experiment, no sample, no method for any number; the caching statements about OpenAI are relayed from guidance not stored here.
4. Relevance: PARTIAL (topic A, convention and mechanism claims). Stated by a vendor: the bill's four categories (same as AA), definitions occupy input even if unused, changing the callable set via allowed_tools or tool_choice rather than deleting definitions is the cited cache-preserving route, and arbitrary schema change is not cache-safe. These are claims, not measurements; no independent measurement of appended-definition cache behaviour is added.

## Topic updates

- Topic A (billed cost and cache behaviour of definitions added or changed mid-session): [F] AA and SO both state a four-category cost model (uncached input, cache read, cache write, output) (AA:120; SO:234); SO relays OpenAI guidance that stable definitions preserve cache, with allowed_tools or tool_choice instead of deletion, and that arbitrary schema changes are not cache-safe (SO:282-284), as a vendor claim with no measurement. AT measures request tokens (not dollars) for tool sets of 1,283/87/33 APIs and changes the active set between tasks (AT:309-310, 583-586). None measures billed cost or cache hits of definitions appended or changed inside a running session. [O] My finding is still "not found in these sources".
- Topic B (call/no-call decision, use of a request channel): KD gives a measured rate of call/no-call mismatch (26.5-54.0% arithmetic, 30.8-41.8% factual QA, of all queries; KD:24-26, Table 1) for four small open-weight models with one visible tool, plus my derived under-call shares among tool-necessary queries (24-75% arithmetic, 57-74% TruthfulQA). It answers "how often a model that has the option to call a tool fails to when needed" only for that setting: one calculator or one search tool, visible, 3B-8B models, necessity defined as at least one failure in 10 tool-free samples, no catalogue, no search-for-tools channel, no frontier model. It does not give the rate for a model with a request channel it was not told to use when no visible tool fits. MU's exploration phase (MU:1022-1033) is a pre-task step the experimenters impose, not a model-initiated one. AT's fallback invocation depends on the agent declaring that no API suits (AT:290-293) but no rate of that declaration is reported in what I read.
- Topic C (persisted memory/knowledge across sessions in a large catalogue): AT stores usage logs and uncovered-task clusters (AT:293-298) and changes the active set between tasks, with token (not billed) cost per task; the stable 33-API set generalises only to the same templated distribution (AT:663-670). MU's exploration phase gives the agent same-run knowledge of tool behaviour (MU:1023-1027), not persisted across sessions. KD, AA, SO: not relevant. Nothing here measures the effect of persisted memory on tool choice across sessions in a large catalogue.

Contradicting the lead's `05` statements: none found in these five sources. Note the claim "uninstructed initiation is unmeasured" is not contradicted: KD measures call/no-call with a visible tool, which is a different setting.
