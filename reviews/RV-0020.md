### Defects in section 1
- **D-1** (low). "no write fee on earlier models; Gemini implicit: no write line" cites EXT-0085, EXT-0152, which are Anthropic only. Correction: cite FND-0039 Table 1 for these two items and name its sources (O-cache; G-price L1090-1094), or drop the EXT ids from that cell.
- **D-2** (medium). EXT-0150 cited for rho; it is the minimum-length passage. Correction: cite EXT-0085 (Anthropic) and EXT-0086 (OpenAI) for rho; keep "older models 0.25 or 0.5" as FND-0039 / O-price L54, L57 without an EXT, or flag that no EXT exists. (EXT-0150 is relevant to a different point, that a prefix under the minimum is never cached, which DPR-0006 does not use anywhere; see D-9.)
- **D-3** (high). A single multiplier m_r on the whole bracket is wrong for the sources it cites:
  - Gemini 3.1 Pro batch: input $1.00 and output $6.00 are half of Standard, but "Context caching price ... Same as Standard" at $0.20 (G-price L1118-1129). Applying 0.5 to the cache term gives $0.10, which the page does not say. [F]
  - Long-context step is not uniform. OpenAI gpt-6.1-sol: input $2.00 to $4.00 (x2), cached $0.10 to $0.20 (x2), write $2.50 to $5.00 (x2), output $10.00 to $15.00 (x1.5) (O-price L35). Gemini 3.1 Pro: input x2, cache read x2 ($0.20 to $0.40), output x1.5 ($12 to $18), storage unchanged at $4.50/hour (G-price L1082-1094). [F, ratios computed]
  - At Anthropic the same modifiers are uniform (Haiku 5.5 over 100k: every column x5, A-price L34-35; fast Opus 5.5 $8/$40 vs $4/$20; residency x1.1 "on all token pricing categories", L160), which is probably why a scalar looked sufficient. Also Anthropic's long-context threshold is on the request's total prompt "including cache reads and cache writes" (L222), so the tier of request r depends on F+W+R, a coupling the equation does not show.
  - Correction: replace p, w, rho, kappa, m_r by a per-request, per-tier price vector (p_in, p_write, p_read, p_out, per tier and per mode), or state that m_r multiplies each price separately and may differ per component, and list the tier thresholds (100k, 200k, 272k) as part of the vector. The sentence "Changing model or provider changes the vector, never the equation" can stay only if the vector is allowed to be this rich (see D-12).
- **D-4** (medium). "Cache write" is billed at **two different multipliers inside one request** at Anthropic: EXT-0158 L94-96: the API automatically places a cache breakpoint on a server-tool result "always uses the default 5-minute TTL ... you may see 5-minute cache writes even when every `cache_control` you set uses a 1-hour TTL"; the usage fields split them as `cache_creation.ephemeral_5m_input_tokens` (and 1h). A single w W_r cannot represent a request that has both. Correction: W_r = W5_r + W1_r with w5 = 1.25 and w1 = 2 (Anthropic), or "w W_r" read as a sum over write classes.
- **D-5** (low). kappa "about 5-6" is true only for standard-tier rows (see table); give the range with the long-context rows (3.75 to 6) or say it is a per-tier price, not a constant.
- **D-6** (low). F_r's list (tool-use system prompt, tool definitions, tool_use/tool_result blocks) is documented for Anthropic; for OpenAI the hidden system tokens exist but are [U] in size and for Gemini tool-definition billing is [U] (FND-0039 Table 1, last rows). The DPR table cell reads as general. Correction: add "(documented for Anthropic; [U] for OpenAI and Gemini)".
- **D-7** (medium; misleading support). FND-0020 / EXT-0194 / EXT-0198 show the earlier vehicle logs two token fields and computes cost with input/output prices only, with "no cache-discount". It supports "tokens are taken from provider usage, not estimated", not "the vehicle already measures what this equation needs". Correction: "the earlier vehicle's code reads provider-reported prompt and completion tokens only (FND-0020; EXT-0194, EXT-0198); cache write/read, reasoning and tool-charge fields would be new measurements".
- **D-14** (low; record hygiene). Front matter `requirements` omits REQ-O21-03 and REQ-O21-09, which the body cites; `basis` omits EXT-0009 and every price-file line used (A-price, G-price, O-price are not EXT ids). Correction: add them or cite the price files by path as FND-0039 does.

### Defects in section 2
- **D-8** (medium). (a) Code-execution container time appears in T_r and in X_s: pick one owner (it is session- or time-based, so X_s). (b) Add storage per GB-day (OpenAI file search) to X_s or to S_s. (c) State the treatment of monthly free allowances and the 5-minute container minimum (A-price L292-299; O-price L487): both make the charge non-linear in requests.
- **D-9** (medium). B_s = sum over turns, sum over requests in turns, + S_s + X_s. Requests that belong to no turn have no home: a prewarm request (FND-0039 Table 3 Prewarm row), a memory-summarisation call at session end, a keep-alive, a one-time memory write. The DPR's own rule "every request the policy causes" (section 4) cannot be satisfied by the sum as written, and the per-turn denominator would not count them. Correction: add a term Z_s for out-of-turn requests, or define that such a request is charged to the turn that causes it, and say which.
- **D-10** (medium). Reasoning double-count risk: C_r adds kappa(O_r + H_r). If a provider's usage field that you take as "output" already includes thinking tokens, H_r is counted twice. FND-0039 cannot settle this for Anthropic or OpenAI (Table 1 [U]); Gemini says "including thinking tokens" in one price line. The stated falsifier (a billed quantity with no term) does not catch a term counted twice; only the second clause (computed bill vs invoice) can. Correction: define O_r as "the provider's billed output quantity, whatever its usage field includes" and H_r as "reasoning tokens not already in O_r"; add to the falsifier "a quantity counted in two terms".
- **Gap cost (the specific question).** Statement: after a gap longer than the lifetime the next request pays the write again, "so a return costs about p·P·(w - rho) more ... than a warm continuation".
  - Holds [I] for Anthropic and OpenAI GPT-5.6+, where a write fee exists, a lifetime is stated (A: EXT-0115 "5-minute lifetime", EXT-0152 1 h; O: 30 minutes, FND-0039 Table 3) and a read refreshes it (A-price L50; O-cache "reusing the prefix refreshes its lifetime without another cache-write charge"). Example: Sonnet 5.5, 5 minute: 1.25 - 0.05 = 1.2 p P.
  - **Does not hold as written for providers without a write fee.** Earlier OpenAI models: after expiry the prefix is billed as ordinary input, so the extra cost is p·P·(1 - rho), not p·P·(w - rho). If "no write fee" is read as w = 0 (the natural reading of the table cell), the formula gives a negative cost. The sentence "pays the write again (W instead of R)" is also wrong there: the tokens land in F, not W. Correction: write the gap cost as p·P·(c_cold - rho), with c_cold = w where a write surcharge exists and c_cold = 1 where tokens are just billed as fresh input; state W_r is only for surcharged writes.
  - **Does not follow from "lifetime rules" for Gemini.** Implicit caching states no lifetime (G-cache) and explicit-cache TTL and write fee are [U] (FND-0039 section 'Could not determine' 3). For explicit caches the gap is paid as storage (S_s, hours x $/MTok/hour) not as a rewrite, and a cache can be kept across the gap at a price. So "consequence, not an extra term" holds only where a lifetime rule and a rewrite exist; for Gemini the gap acts through S_s.
  - **Placement.** The lifetime applies between any two consecutive requests, including inside one turn (a slow tool, long reasoning, a user pause). The DPR files it under sessions and returns; FND-0039 also files lifetime under "session". A within-turn expiry would show up as W instead of R in C_r with no session-level cause. Not an error in the algebra (it is already in W and R, which is the right reason it is "not an extra term" and must not be added again) but the text should say it is a per-request event whose frequency depends on inter-request time, and that the experiment must therefore control or record wall-clock gaps. Related: Anthropic cross-session cache sharing and OpenAI per-organisation caches (FND-0039 "reuse across sessions") mean B_s of one session can depend on whether another session warmed the same prefix; sessions are not independent terms. DPR section 6 lists the Anthropic point as unknown but does not say what it does to the sum.
- **D-11** (low). Say that token counts are model-specific (tokenizer: A-price L54, "approximately 30% more tokens for the same text") and so cannot be compared across models without prices; add one sentence in section 1 or 4.
- **Double counting otherwise:** I found none among F, W, R. The F + W + R partition is consistent with the Anthropic identity in FND-0039 Table 1 (`total_input_tokens = cache_read + cache_creation + input_tokens`). For OpenAI, whether the usage record reports written tokens separately is not shown in the stored pages [U]; if only a total and a cached count are reported, W_r cannot be filled and falls into F_r. Add to the falsifier: "the provider's usage record must expose each of F, W, R", checked per provider.
- **Request definition.** "A request is one model call": with Anthropic server tools one API request contains several iterations ("later iterations within the same request", EXT-0158 L94); usage is per API request. Define request as "one API call and its usage record".

## 4. Misleading statements
- **D-12** (medium). Opening paragraph: "Changing model or provider changes the vector, never the equation." Tested against the sources, false in the strict sense: Gemini needs S_s and not W; earlier OpenAI models have no W; batch changes the cache price at Gemini but not as a multiple; the long-context step is per-component (D-3); Anthropic bills two write classes (D-4). It becomes true only if "vector" includes tiers, thresholds, per-component multipliers, write classes and free allowances, in which case say so. As written it invites the reading that a scalar price table is enough.
- **D-15** (medium). Section 5, last bullet: keeping tool results out of context "lowers F on later requests (EXT-0183 ...)". The same extract (L43-45) says programmatic calling "uses the same pricing as code execution" (container charges, X_s or T_r) and L36 reports a benchmark where it "cost roughly 8% more" with unchanged scores; L57-68 name the "small fixed overhead (container startup, script generation)". Section 5 shows only the F side. Correction: "lowers F on later requests and adds code-execution charges and a fixed overhead; the net is workload-dependent (EXT-0183 L36, L57-68, vendor claims)". The same one-sidedness, milder, applies to "Discovery adds requests per turn" (it is listed) and "Memory ... lowering F" (the extra request is listed; the memory write is not, D-9).
- Section 5 "a longer lifetime raises w but avoids rewrites after gaps": true for Anthropic (1h write 2x); OpenAI GPT-5.6+ offers only 30m (FND-0039 Table 3). Add "at Anthropic".
- Section 2 note "the split among the three is what the cache layout and the exposure policy change": acceptable [I], but it omits that a request below the minimum cacheable length (EXT-0150: 512 to 4,096 tokens by model) has W = R = 0, which is the natural place EXT-0150 would be used (D-9 note above).
- Section 3 summary of "Anthropic ... storage zero": FND-0039 says "no per-hour storage line found" (absence of a line, not a stated "free"); DPR-0006 writes "zero for Anthropic and OpenAI prompt caching". Soften to "no storage line found".

## Evidence that would favour the alternatives the proposal considered
- (c) Fixed multiplier table: would be favoured if the first billing probe (C-X07) shows that, for the providers actually used, the long-context and batch-cache cases above never arise in the study's request sizes and modes; then a scalar m_r and constant kappa would be adequate. Not shown either way here.
- (a) Tokens only with the bill recorded separately: favoured if the usage records of a chosen provider do not expose W, R or reasoning separately, so the bill cannot be reconstructed from usage (D-10, section 2); the invoice would then be the only bill.
