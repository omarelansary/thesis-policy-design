## Numbered objections (ranked)

1. **[blocking] The memory break-even h* (D-02) is biased in V5-R's favour, and it is the falsifier threshold of DPR-0007, HYP-0016 and HYP-0017 (CH-0075).** `memory_seed.py:8-12` says "the appended definition is paid in both cases". It is not: a tool seeded at session start is carried for T-1 reads, whereas a tool discovered mid-session (the lead's own `regime_bill.py` assumption, reads on "about half the remaining requests") is carried for about T/2. The extra carry of every needed seed, d*((T-1)-T/2)*r, is omitted. Second, `H*r + o*q` charges an avoided search as a separate request (see 2). Hand recomputation at r = 0.1 (the calc's table: 0.22 / 0.30 / 0.45 / 0.69 for T = 3 / 10 / 30 / 100): extra carry alone gives 0.23 / 0.32 / 0.53 / 0.99; in-response search alone gives 0.33 / 0.42 / 0.58 / 0.79; both give 0.33 / 0.45 / 0.72 / never pays at T = 100. The statement "about 0.22-0.30 for 3-10 requests, up to 0.69 for 100" (04 sections 1, 5; DPR-0007 falsifier) is therefore too low by about 0.1 to 0.3 and the long-session end is wrong in kind. Also no materiality: at h = 0.5, m = 5, T = 10 the net saving is about 1,800 fresh-token equivalents by the lead's formula (about 300 after my two corrections), less than one fresh send of the 5,000-token history.
2. **[should-fix] D-01 models each discovery as an extra request that re-reads prefix and 5,000-token history; the adopted vendor mechanism does not work that way (CH-0076).** `regime_bill.py:12-13`, `:26-30`. The stored Anthropic page shows search, search result and the model's `tool_use` in one assistant response, the search "runs on Anthropic's servers" (`L/v5-anthropic-tool-search-20261022.md:601-652`), and DPR-0006:19 itself says a server-tool loop is "billed within that request". Hand recomputation: break-even n* (d = 250, r = 0.1, T = 10) falls from 12 / 22 / 57 (D = 1 / 3 / 10) to 11 / about 19 / 45; at T = 3, D = 10 from 74 to 56. Direction: the headline "10 to 75 tools" is biased high (against deferral). Whether server-side iterations are billed with a prefix re-read is not shown in the pages read [U]; the calc picks one reading without saying so. For OpenAI and client-side search the extra-request model is right, so the model needs both branches.
3. **[should-fix] The minimum cacheable length is applied to the wrong thing, and not at all in the calc (CH-0077).** `04` section 2 defines R-small as "tool block below the model's minimum cacheable length". The vendor rule is about the whole cached prompt prefix: "minimum cacheable prompt length" (`L/v5-anthropic-prompt-caching-20261022.md:593-604`; OpenAI `:69`, prefix incl. instructions), so a system prompt carries a small tool block over it. The script has no uncached branch: the deferral prefix (5 tools plus search = 800-1,550 tokens at d = 100-250) always gets the write/read prices, although for models with a 1,024 / 2,048 / 4,096-token minimum (same page :596-599) that prefix may not cache at all. Hand: with an uncached deferral prefix, n* at d = 250, T = 10, D = 1 moves from 12 to about 37. Direction: the calc favours deferral at small catalogues.
4. **[should-fix] "Cold start" is built into every session of D-01, so the R-return regime is neither a separate regime nor consistent with V5-R06 (CH-0078).** `expose_all` and `deferral` charge `W` at the first request of every session. The table label "warm session" is wrong; both designs are priced cold. The "extra per return" block (`regime_bill.py:48-52`) is the cold-minus-warm difference, not an addition, and DPR-0006:44 warns "it must not be added again". More important, V5-R06 argues for one shared cached prefix across users; on a shared prefix, other users' traffic refreshes the cache and a returning user's gap does not matter (DPR-0006:44: "Where caches are shared across sessions ... sessions are not independent"). The 04 table row R-return and K0 ("pays the full prefix on every return") hold only for a low-traffic deployment; the traffic rate is the real variable and is absent.
5. **[should-fix] The headline ratios and regime boundaries are conditional on parameters the text does not name (CH-0080).** Varied: r, T, d (n* is printed only for d = 250). Fixed without a source: w = 1.25 (no 2x one-hour write), o = 5, H = 5,000, q = 150, K = 3, core = 5, search = 300, and D, which has no empirical basis anywhere in V5. The "factor of about 2-30 (D-01 table, T = 10)" (04 section 2, R-mid) is D = 1 to 3; at D = 10, n = 100, d = 250, T = 10 the ratio is about 0.57 (hand: 30,508 / 53,750), i.e. 1.8x. R-small is stated as "fewer than about 10-25 tools" but n* is 40-74 at D = 10 and depends on d: the boundary is in tokens and discoveries, not in tool count. The category index (HYP-0019 says it is charged) is not in the deferral prefix of the calc.
6. **[should-fix] Deferral's cache preservation is assumed, and a contradicting user report found by blind B is not weighed (CH-0079).** D-01 charges the deferred catalogue nothing after the core. `L/lit-ccissue-59650-deferred-cache-reads.txt:21-41` reports about 103k tokens of "deferred" schemas "loaded into the cache and re-read on every API call" in Claude Code; blind B flagged it (`inputs/blind-output-B-20261022.md:104`), V5's `03`/`04` do not mention it. It is one uncontrolled report, closed "not planned", and may be a display artefact [U]; but if true for the university route, deferral's ratio in the table goes to about 1 for the deferred share. The only check, P5, is last in `05` and absent from V5-R09.
7. **[should-fix] What V5-R adds over DPR-0008 is much smaller than "V4 substantially revised" and "New" suggest, and the recommendation rests on a requirement, not on evidence (CH-0081).** DPR-0008 (written without reading `04`) contains the same regime switch, deferral with native search, append, a static filter (D0(b)) and a Markdown summary. The regime switch is shipped by Claude Code (`03` section 3 row 43: upfront under 10% of the window, deferred beyond) and has an independent derivation by two blind instances, yet `06` section 1 marks it "New as a rule". The real differences are S1 as a mandatory stage, M2-M3 and H. For M2-M3 the evidence is: NONE FOUND in prior art, h unmeasured, h* biased (1). The table row "V5-R (recommended)" is stronger than 04's own header ("Nothing here is ... selected"). The honest reading is: V5-R = DPR-0008 plus one treatment (M2-M3) demanded by REQ-U21-04; that is a legitimate design but should be stated as such, with DPR-0008 as the default arm.
8. **[should-fix] Observation masking (H) is kept in the default on one coding-agent study, against the same table's other evidence (CH-0082).** `04` section 1 point 3 lists masking among "established parts adopted as they are". `03` section 6 gives the other side: tool outputs about 3.3% of cost and a 38.4% cut in tool-output tokens about 1.3% of total cost, paired cost up 6.8% (`L/pdf-tokennotcost-2607.12161v5.txt:240-243, :298`), and context editing "invalidates cached prompt prefixes" (:71). The masking study's cost is API-reported or priced post hoc without a cache-hit distinction (`03` row 75). Context editing is a beta feature (`L/v5-anthropic-context-editing-20261022.md:31`, header `context-management-2025-06-27`); 04 section 8 names only the offering mechanism as beta. DPR-0008 section 4 rejects H with these numbers; V5 does not answer them.
9. **[should-fix] The request-level selector and system trigger are dropped for "no evidence ... and each costs a request", an argument that is not applied evenly (CH-0083).** (a) M2-M3 has "NONE FOUND" in `03` slot 5 and is kept; P1/P3 have no support and are dropped; the difference is REQ-U21-04, but REQ-O14F-05/06 (staged narrowing; a filtered tool may be added again) are also requirements. (b) "Each costs a request" is true of an LLM selector only; Copilot's embedding-guided routing adds no model request, and its coverage figure (94.5% against 69.0% static, EXT-0228:51) is the only measured comparison in the packet of a pre-selection stage. It is a vendor figure and I do not rely on it, but V5 neither argues it away nor tests it. (c) V5-R07 cites EXT-0228's "cache miss" as the reason; `04` section 1 point 2 says slot-2 offering removes exactly that cost. Which is it?
10. **[should-fix] Requirements listed as met in `04` section 3 and DPR-0007 header are met only nominally in three places (CH-0084).** (a) REQ-O14F-06 "a filtered tool comes back through D": an S1-filtered tool is not declared, so D cannot return it (`04` section 5 says so: "D recovers only if the tool is declared"); the sentence in section 3 is true only for M2-held-back tools. S1 and S2 are per-deployment configuration, not run-time stages, though the Mermaid graph draws them as run-time boxes; "two session-level stages" (section 1 point 4) is M2 alone plus S1/S2 at deployment. (b) REQ-O02-06 is in the header list but the Executor row of the table is blank ("to be read from its own MCP surface"). (c) REQ-O21-03 "relevant part injected first, more when asked": M1 loads the file; no on-request path is specified. Q-J31 discloses (a) in part.
11. **[should-fix] V5 says vendor performance numbers are not relied on, but uses them (CH-0085).** `04` section 8 against section 4 K0 row ("2-5 points of resolution rate", EXT-0228, vendor's own), HYP-0018 "Why plausible", the 69.0% static-core coverage used for the core in DPR-0008, and "Copilot ... names remembering previous tool usage as its next step" (HYP-0017, `03` row 69, DPR-0008 D). EXT-0228:71-73 says a model "should ... remember previous tool usage, infer intent from history, and plan multi-step actions over long sessions" and that routing mechanisms "could ... help them reason across thousands of turns"; that is an aspiration about long-context reasoning, not cross-session memory-informed offering. Supporting a hypothesis with it overstates.
12. **[should-fix] Dependence on beta and provider-specific features is disclosed in one sentence but the design has no fallback, and P0 cannot observe half of its own falsifier (CH-0086).** M3 depends on `tool_addition` (beta; header `inline-tools-2026-09-15`; "listed models only", Sonnet 5 excluded from mid-conversation system messages, `L/v5-anthropic-midconv-sysmsg-20261022.md:18-20, :27`), on OpenAI `allowed_tools` (which only restricts among declared tools, so it needs the expose-all prefix, not the P0b prefix), on OpenAI tool search (gpt-5.4+ only), and on cache write/read prices that exist on specific vendor APIs. The user's route is "a free API from my university" with several models (REQ-U21-01). If that gateway does not pass beta headers, caching fields or tool search, D-01 and D-02 do not apply (without caching w = r = 1 and deferral wins at far smaller n), and V5 has no stated fallback beyond a client search. HYP-0020's falsifier includes "the API applies no cache discount", which cannot be seen in a usage record of a free API (tokens, not prices).
13. **[should-fix] P1 cannot end what it claims (CH-0087).** (a) The hit rate h is set by how the experimenter pairs tasks of one simulated user; real returning-user overlap is not produced by a benchmark, so P1 measures h of a construction and cannot support "pays for returning users". (b) The catalogue: tau2-bench is the named vehicle; `03` section 9 does not give its tool count; if it is a few dozen tools or less, S2 selects R-small (expose all) and M2 never runs; enlarging the catalogue with distractors again sets h. (c) About 20 pairs: a net saving of a few hundred to two thousand token-equivalents per session cannot be seen against run-to-run variance of a multi-request session bill. (d) A "hit" must exclude tools already in the core, otherwise h is inflated (the usage-derived core covers most needs; Copilot's static list covered 69.0%). (e) h* should be recomputed from the observed T, H and search mechanism, not read from the lead's table (1, 2).
14. **[should-fix] The accuracy side of every proof-of-concept item has no decision rule that can distinguish "nearly the same" from "lower" (CH-0088).** Falsifiers (HYP-0018, 0021, DPR-0007 (b)) are "lower beyond run-to-run variation". With about 20 tasks per arm a 2-5 point effect (the size EXT-0228 reports) is not detectable; failing to find a difference does not show equivalence, and REQ-U21-07 forbids a margin, DPR-0006:52 says close results are "argued". `05` section 1 then says an item "that fails its falsifier removes its stage", so a noisy loop can remove a stage, or keep one, without a stated error asymmetry. I do not challenge "no margin"; I challenge that `05` says what P2 "can end" while the stated design cannot end it either way for effects of that size.
15. **[should-fix] The loop is called "in dependency order" but P1 precedes what it depends on, and V5-R09 omits P5 (CH-0089).** P1's K1 arm needs models to search (P3, HYP-0019) and deferral to behave as D-01 assumes (P5, 6). V5-R09 lists the order as cache fields, hit rate, offering accuracy, uninstructed recovery; P5 is missing. P5 (reading list-price arithmetic from usage records at two or three sizes) and the P4 masking repeat sit near REQ-U21-03 (do not re-test the well-tested); P5 is cheap and defensible, P4 re-tests a published result on one provider.

For this review I checked V5-R02's `:27`, `:452` and `:440-441` and they say what is claimed; I did not check the others.

## What was tried and could not be broken
- **Arithmetic reproduces.** Hand checks of `regime_bill.stdout.txt`: T = 10, r = 0.1, n = 100, d = 250: expose-all 53,750, deferral D = 1 6,050 (1,550 x 2.25 + 2,562.5), ratio 0.11; R-return 115,000 and 1,782; `memory_seed.stdout.txt` h* 0.22 / 0.30 (T = 3 / 10, r = 0.1). The formulas implement their stated assumptions.
- **Direction of the large-catalogue result is robust.** Under every perturbation I tried (in-response discovery, uncached deferral prefix, D up to 10) deferral stays far cheaper at 400 tools and above (ratio below about 0.1 at D = 3 on the lead's table; my D = 10 check only at n = 100). What is not robust is the place of the boundary (10-75 tools) and the memory break-even.
- **Vendor quotations checked.** `L/v5-anthropic-midconv-sysmsg-20261022.md:27` and `:452` say the `tools` array stays unchanged and the cache still hits; `L/v5-openai-prompt-caching-20261022.md:440-441` says `allowed_tools` keeps the supplied list stable; EXT-0228 contains 94.5 / 87.5 / 69.0, "2-5 percentage point", "cache miss, an extra round trip". The V5-R02 and V5-R06 pointers are accurate.
- **Opposite conclusions.** Evidence favouring DPR-0008 over V5-R: no measured h, a biased h*, NONE FOUND in prior art, H contradicted by the 3.3% figure, the regime switch present in both. Evidence favouring V4 unchanged: none found in this packet (V4's per-request selector is unsupported and V5 does not claim otherwise); favouring "no improvement established": for M2-M3, yes, as of this packet. Evidence for DPR-0009 over DPR-0007: same as DPR-0008; DPR-0009's description of the blind outputs matches (A line 127 "likelier practical winner"), but DPR-0009 was built without the offering mechanisms, so it is not a clean rival to M2 either.
- **Tried to show that V5-R hides a requirement it should meet:** REQ-U21-04, REQ-U21-07 (bill criterion, no margin), REQ-O02-09 (a way to query held-back tools), REQ-O21-09 (plain Markdown first) are met in form by `04`; the doubts are in objections 10 and 14.

## Overall view and uncertainty
V5-R is a coherent, well-sourced packet whose weakest part is the quantitative layer it leans on to justify its own new parts. The two calculation scripts are first-order and honestly labelled, but both silently choose the assumption that favours V5-R's novel part (memory seeding) while penalising deferral's discovery; the corrections move h* up and n* down by amounts that matter for the stated falsifiers, not for the qualitative direction at large catalogues. The proof-of-concept items are well chosen but P1 and P2 cannot end the questions they are said to end with the stated size. My hand arithmetic is unchecked by a machine; items 1-3 should be rerun before anyone relies on the numbers above or in the packet. This review does not recommend adopting or rejecting V5-R; that decision belongs to the human.
