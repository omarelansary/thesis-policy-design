# A restricted surface that is stable across requests does not lose cache hit rate relative to the full library

**Hypothesis.** [hypothesis, not a finding] Toollery's natural replay (EXT-0062) shows a restricted per-query candidate list with hit rate 0.144 against 0.989 for the full library. If the loss is caused by the restricted list differing from request to request (a per-request varying prefix), then a restricted surface that is identical across requests (per deployment or per cohort) has a hit rate equal to the full library's within the cache lifetime, and the billed input cost ratio falls to about the token ratio (DPR-0005 section 3).

**Why it is plausible.** Cache matching is by identical prefix and the lifetime is 5 minutes, refreshed on use (EXT-0057, steward-verified V1); modifying the tools array invalidates the cache (EXT-0058). The cause of the low hit rate in the Toollery table is **not stated in the extracts** (V3); the per-request variation is my inference [I]. The forced-warm row (hit 0.970) is a boundary condition with exact duplicate prompts, so it overstates what a stable surface with varying queries would achieve.

**What would falsify it.** The falsifier in the front matter, plus a second reading: if hit rates are equal but the billed cost ratio is not close to the token ratio under the fitted price model, the cost model of DPR-0005 section 2 is wrong.

**Assumptions.** The provider caches the shorter prefix (minimum cacheable length not in the extracts [U]); request spacing within the lifetime or traffic from other sessions keeps the entry warm; the provider shares entries across sessions with an identical prefix [U, not in the extracts].

**Alternatives it competes with.** The reading that the low hit rate is caused by something else (prefix length below a cacheable minimum, provider/model specifics). 

**Not claimed.** That restriction reduces billed cost in agent loops; only that one named mechanism of loss is avoidable.
